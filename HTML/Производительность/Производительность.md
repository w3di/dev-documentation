## 1. Critical Rendering Path

### Определение

**Critical Rendering Path (CRP)** — последовательность шагов, которые браузер выполняет для преобразования HTML, CSS и JavaScript в пиксели на экране.

```
HTML → DOM → CSSOM → Render Tree → Layout → Paint → Composite
```

### Этапы CRP

#### 1. Parsing HTML → DOM

Браузер получает байты HTML, декодирует их в символы (используя charset), выполняет **tokenization** (разбивает на токены: start tag, end tag, character data), затем строит **DOM tree**:

```
Bytes → Characters → Tokens → Nodes → DOM
```

```html
<!DOCTYPE html>
<html>
<head>
  <title>Page</title>
  <link rel="stylesheet" href="style.css">
</head>
<body>
  <h1>Hello</h1>
  <p>World</p>
</body>
</html>
```

```
Document
├── html
│   ├── head
│   │   ├── title
│   │   │   └── "Page"
│   │   └── link[rel=stylesheet]
│   └── body
│       ├── h1
│       │   └── "Hello"
│       └── p
│           └── "World"
```

#### 2. Parsing CSS → CSSOM

Параллельно с DOM браузер строит **CSSOM** (CSS Object Model). CSS является **render-blocking** ресурсом — браузер не может построить Render Tree без полного CSSOM.

```
Bytes → Characters → Tokens → Nodes → CSSOM
```

> **Критически важно:** CSS блокирует рендеринг. Чем быстрее загружается и парсится CSS, тем раньше пользователь видит контент. Именно поэтому CSS помещается в `<head>`.

#### 3. Render Tree

Браузер объединяет DOM и CSSOM в **Render Tree**. В него входят только **видимые элементы**:

- `display: none` — элемент НЕ попадает в Render Tree
- `visibility: hidden` — элемент попадает (занимает место, но невидим)
- `opacity: 0` — элемент попадает
- `<head>`, `<script>`, `<meta>` — не попадают

#### 4. Layout (Reflow)

Вычисление **геометрии** каждого элемента: позиция, размеры, отступы. Layout — дорогая операция, зависящая от размера DOM.

#### 5. Paint

Растеризация элементов в пиксели. Происходит на нескольких **paint layers**. Свойства, вызывающие создание нового layer:

- `will-change: transform`
- `transform: translateZ(0)` (hack)
- `opacity` с анимацией
- `position: fixed`
- `<video>`, `<canvas>`

#### 6. Composite

GPU объединяет layers в финальное изображение на экране. Анимации `transform` и `opacity` происходят **только на этом этапе** — без Layout и Paint.

### Render-blocking vs Parser-blocking

| Тип | Описание | Примеры |
|-----|----------|---------|
| **Render-blocking** | Блокирует рендеринг, но НЕ парсинг HTML | `<link rel="stylesheet">` |
| **Parser-blocking** | Блокирует парсинг HTML | `<script>` (без async/defer) |
| **Оба** | Блокирует и парсинг, и рендеринг | `<script>` перед незагруженным CSS |

```html
<!-- Render-blocking: браузер парсит дальше, но не рендерит -->
<link rel="stylesheet" href="style.css">

<!-- Parser-blocking: браузер останавливает парсинг -->
<script src="app.js"></script>

<!-- НЕ blocking -->
<script src="app.js" async></script>
<script src="app.js" defer></script>
```

## 2. HTML парсинг и Preload Scanner

### Основной парсер

HTML парсер работает **последовательно** — сверху вниз. Когда он встречает `<script>` (без async/defer), он:

1. **Останавливает парсинг HTML**
2. Если перед script есть незагруженный CSS → ждёт загрузки CSS
3. Скачивает script (если external)
4. Выполняет script
5. Возобновляет парсинг

### Preload Scanner (Speculative Parser)

Пока основной парсер заблокирован скриптом, **preload scanner** продолжает сканировать HTML вперёд и инициирует загрузку ресурсов:

```html
<script src="heavy.js"></script>
<!-- Пока heavy.js загружается и выполняется, preload scanner уже нашёл: -->
<link rel="stylesheet" href="style.css">
<script src="analytics.js"></script>
<img src="hero.jpg">
```

> **Preload scanner** — одна из самых значимых оптимизаций браузера. Он может обнаружить ресурсы в HTML до того, как основной парсер до них дойдёт. Однако он НЕ может обнаружить ресурсы, загружаемые через JavaScript.

### Что preload scanner НЕ видит

```js
// Эти ресурсы невидимы для preload scanner:
const img = new Image();
img.src = 'dynamic.jpg'; // Загрузка начнётся только после выполнения JS

fetch('/api/data'); // Тоже невидимо

document.createElement('link').href = 'lazy.css'; // Невидимо
```

Решение — **resource hints**:

```html
<!-- Явно сообщаем браузеру о ресурсах -->
<link rel="preload" href="dynamic.jpg" as="image">
<link rel="preconnect" href="https://api.example.com">
```

### Speculative Parsing

Современные браузеры выполняют **speculative parsing** — они предположительно строят DOM даже для HTML после блокирующего скрипта. Если скрипт не модифицирует DOM через `document.write()`, спекулятивная работа сохраняется. Если `document.write()` меняет структуру — работа отбрасывается.

```html
<!-- document.write() убивает speculative parsing -->
<script>
  // АНТИПАТТЕРН: document.write() вызывает полный reparse
  document.write('<link rel="stylesheet" href="injected.css">');
</script>
```

> В Chrome `document.write()` для внешних скриптов может быть **полностью заблокирован** на медленных соединениях (2G). Это intervention, а не стандарт.

## 3. Загрузка скриптов: async, defer, module

### Сравнение стратегий загрузки

```
Обычный <script>:
HTML:  ────██████──────────██████──────────────────►
JS:         ↓ fetch ↓ exec
            ████████████████

<script async>:
HTML:  ────██████████████████████████──────────────►
JS:         ↓ fetch  ↓ exec
            █████████████████
                     ▲ парсинг HTML приостановлен на время exec

<script defer>:
HTML:  ████████████████████████████████████████────►
JS:         ↓ fetch          ↓               exec ↓
            █████████████████               ██████
                                            ▲ после DOMContentLoaded

<script type="module">:
HTML:  ████████████████████████████████████████────►
JS:         ↓ fetch + deps   ↓               exec ↓
            █████████████████               ██████
                                            ▲ deferred по умолчанию
```

### Подробное сравнение

| Атрибут | Загрузка | Выполнение | Порядок | DOMContentLoaded |
|---------|----------|------------|---------|------------------|
| `<script>` | Блокирует парсер | Сразу после загрузки | Гарантирован | Ждёт выполнения |
| `async` | Параллельно | Сразу после загрузки | НЕ гарантирован | НЕ ждёт |
| `defer` | Параллельно | После парсинга HTML | Гарантирован | Ждёт выполнения |
| `type="module"` | Параллельно (defer) | После парсинга HTML | Гарантирован | Ждёт выполнения |
| `type="module" async` | Параллельно | Сразу после загрузки | НЕ гарантирован | НЕ ждёт |

### Рекомендации

```html
<!-- Критический JS (редко нужно, но если да — в <head>) -->
<script src="critical.js"></script>

<!-- Основной бандл — defer в <head> (лучшая стратегия) -->
<script defer src="app.js"></script>

<!-- Аналитика, виджеты — async (порядок не важен) -->
<script async src="analytics.js"></script>

<!-- Современные модули с fallback -->
<script type="module" src="app.mjs"></script>
<script nomodule src="app-legacy.js"></script>
```

> **Best practice:** Помещайте `<script defer>` в `<head>`, а не в конец `<body>`. Defer начинает загрузку раньше (preload scanner находит его в head), а выполняется всё равно после парсинга.

### fetchpriority для скриптов

```html
<!-- Повышаем приоритет критического скрипта -->
<script src="critical-framework.js" fetchpriority="high"></script>

<!-- Понижаем приоритет некритического -->
<script src="widget.js" async fetchpriority="low"></script>
```

## 4. Resource Hints

### Типы Resource Hints

```html
<!-- 1. dns-prefetch: только DNS lookup -->
<link rel="dns-prefetch" href="https://cdn.example.com">

<!-- 2. preconnect: DNS + TCP + TLS -->
<link rel="preconnect" href="https://cdn.example.com">
<link rel="preconnect" href="https://fonts.googleapis.com" crossorigin>

<!-- 3. preload: загрузить конкретный ресурс с высоким приоритетом -->
<link rel="preload" href="font.woff2" as="font" type="font/woff2" crossorigin>
<link rel="preload" href="hero.jpg" as="image">
<link rel="preload" href="critical.css" as="style">

<!-- 4. prefetch: загрузить ресурс для будущей навигации (низкий приоритет) -->
<link rel="prefetch" href="/next-page.html">
<link rel="prefetch" href="next-page-bundle.js" as="script">

<!-- 5. modulepreload: preload для ES modules -->
<link rel="modulepreload" href="app.mjs">

<!-- 6. prerender (Speculation Rules API) -->
<script type="speculationrules">
{
  "prerender": [{
    "urls": ["/next-page"]
  }]
}
</script>
```

### Сравнение Resource Hints

| Hint | Что делает | Приоритет | Когда использовать |
|------|-----------|-----------|-------------------|
| `dns-prefetch` | DNS lookup | Низкий | Third-party домены, которые будут использованы |
| `preconnect` | DNS + TCP + TLS | Средний | Критические third-party (fonts, CDN) |
| `preload` | Полная загрузка | Высокий | Ресурсы текущей страницы, невидимые preload scanner |
| `prefetch` | Полная загрузка | Низкий | Ресурсы следующей страницы |
| `modulepreload` | Загрузка + parse модуля | Высокий | ES modules и их зависимости |

### Атрибут `as` для preload

```html
<!-- ОБЯЗАТЕЛЬНО указывать as — без него браузер загрузит с низким приоритетом -->
<link rel="preload" href="style.css" as="style">
<link rel="preload" href="app.js" as="script">
<link rel="preload" href="font.woff2" as="font" type="font/woff2" crossorigin>
<link rel="preload" href="hero.webp" as="image">
<link rel="preload" href="data.json" as="fetch" crossorigin>
```

> **Важно:** `preload` ресурс, который не используется в течение ~3 секунд, вызовет предупреждение в консоли. Не preload-ите то, что не нужно на текущей странице.

### Антипаттерны Resource Hints

```html
<!-- ПЛОХО: preload всего подряд -->
<link rel="preload" href="icon1.svg" as="image">
<link rel="preload" href="icon2.svg" as="image">
<link rel="preload" href="icon3.svg" as="image">
<!-- Если preload-ить слишком много — приоритеты размываются -->

<!-- ПЛОХО: preconnect к слишком многим доменам -->
<link rel="preconnect" href="https://a.com">
<link rel="preconnect" href="https://b.com">
<link rel="preconnect" href="https://c.com">
<link rel="preconnect" href="https://d.com">
<!-- Каждый preconnect — CPU и сетевые ресурсы. Максимум 2-4 -->

<!-- ПЛОХО: preload без as -->
<link rel="preload" href="font.woff2">
<!-- Без as — двойная загрузка! -->
```

## 5. Lazy Loading

### Нативный lazy loading

```html
<!-- Изображения -->
<img src="photo.jpg" loading="lazy" alt="Description" width="800" height="600">

<!-- Iframes -->
<iframe src="video-embed.html" loading="lazy"></iframe>
```

### Атрибут loading

| Значение | Поведение |
|----------|-----------|
| `lazy` | Откладывает загрузку до приближения к viewport |
| `eager` | Загружает немедленно (default) |

### Как работает lazy loading внутри

Браузер использует **Intersection Observer** внутренне. Порог загрузки зависит от:

- **Тип соединения**: на 4G ресурс начинает загружаться за ~1250px до viewport, на медленном 3G — за ~2500px
- **Это не точная наука**: браузеры имеют свои эвристики

### Важные правила

```html
<!-- ПЛОХО: lazy loading для LCP-изображения -->
<img src="hero-banner.jpg" loading="lazy" alt="Hero">
<!-- Hero image — это LCP! Lazy loading задержит его загрузку -->

<!-- ХОРОШО: eager + fetchpriority для hero -->
<img src="hero-banner.jpg" loading="eager" fetchpriority="high" alt="Hero">

<!-- ХОРОШО: lazy для below-the-fold -->
<img src="gallery-1.jpg" loading="lazy" alt="Gallery 1" width="400" height="300">
<img src="gallery-2.jpg" loading="lazy" alt="Gallery 2" width="400" height="300">
```

> **Всегда указывайте `width` и `height`** для lazy-loaded изображений. Без них браузер не знает размеры до загрузки → layout shift (CLS).

### JavaScript-based lazy loading

Для случаев, когда нативный lazy loading недостаточен (например, background images):

```html
<div class="lazy-bg" data-bg="large-bg.jpg"></div>

<script>
const observer = new IntersectionObserver((entries) => {
  entries.forEach(entry => {
    if (entry.isIntersecting) {
      const el = entry.target;
      el.style.backgroundImage = `url(${el.dataset.bg})`;
      observer.unobserve(el);
    }
  });
}, { rootMargin: '200px' });

document.querySelectorAll('.lazy-bg').forEach(el => observer.observe(el));
</script>
```

## 6. Оптимизация изображений

### Современные форматы

| Формат | Сжатие | Прозрачность | Анимация | Поддержка |
|--------|--------|-------------|----------|-----------|
| JPEG | Lossy | Нет | Нет | 100% |
| PNG | Lossless | Да | Нет | 100% |
| WebP | Lossy + Lossless | Да | Да | ~97% |
| AVIF | Lossy + Lossless | Да | Да | ~92% |
| JPEG XL | Lossy + Lossless | Да | Да | ~0% (удалён из Chrome) |

### Элемент picture для format fallback

```html
<picture>
  <!-- Браузер берёт первый поддерживаемый source -->
  <source srcset="photo.avif" type="image/avif">
  <source srcset="photo.webp" type="image/webp">
  <img src="photo.jpg" alt="Photo" width="800" height="600">
</picture>
```

### Responsive images с srcset

```html
<!-- Resolution switching: одно и то же изображение в разных размерах -->
<img
  srcset="photo-320w.jpg 320w,
          photo-640w.jpg 640w,
          photo-1280w.jpg 1280w,
          photo-1920w.jpg 1920w"
  sizes="(max-width: 600px) 100vw,
         (max-width: 1200px) 50vw,
         33vw"
  src="photo-640w.jpg"
  alt="Photo"
  width="1920"
  height="1080"
>
```

### Алгоритм выбора изображения браузером

1. Браузер смотрит `sizes` и определяет ширину слота (например, `50vw` на viewport 1200px = 600px)
2. Учитывает `devicePixelRatio` (DPR): на Retina 2x → нужно 1200px
3. Из `srcset` выбирает ближайший подходящий размер (1280w)
4. Браузер может выбрать меньший размер на медленном соединении

### fetchpriority

```html
<!-- LCP-изображение — высокий приоритет -->
<img src="hero.jpg" fetchpriority="high" alt="Hero">

<!-- Иконки в header — низкий приоритет -->
<img src="cart-icon.svg" fetchpriority="low" alt="Cart">
```

### Decoding

```html
<!-- async: декодирование изображения не блокирует main thread -->
<img src="large-photo.jpg" decoding="async" alt="Photo">

<!-- sync: гарантированное декодирование перед следующим frame -->
<img src="critical-ui.png" decoding="sync" alt="UI">
```

## 7. Font Loading

### Проблема: FOIT и FOUT

- **FOIT** (Flash of Invisible Text) — текст невидим, пока шрифт загружается (дефолт в Chrome)
- **FOUT** (Flash of Unstyled Text) — показывается fallback шрифт, затем переключение (дефолт в Firefox)

### font-display

```css
@font-face {
  font-family: 'CustomFont';
  src: url('font.woff2') format('woff2');
  font-display: swap; /* Рекомендовано для большинства случаев */
}
```

| Значение | Block period | Swap period | Поведение |
|----------|-------------|-------------|-----------|
| `auto` | Browser-dependent | Browser-dependent | Дефолт, непредсказуемо |
| `block` | ~3с | Бесконечный | FOIT 3с, потом swap |
| `swap` | ~0 | Бесконечный | Сразу fallback, swap когда готов |
| `fallback` | ~100мс | ~3с | Короткий FOIT, swap только если быстро |
| `optional` | ~100мс | 0 | Если не загрузился быстро — fallback навсегда |

### Preload шрифтов

```html
<!-- ОБЯЗАТЕЛЬНО crossorigin, даже для same-origin шрифтов -->
<link rel="preload" href="/fonts/custom.woff2" as="font" type="font/woff2" crossorigin>
```

> Без `crossorigin` атрибута шрифт будет загружен **дважды**: один раз через preload (anonymous), второй — через @font-face (cors).

### size-adjust для уменьшения CLS

```css
/* Fallback шрифт с подогнанными метриками */
@font-face {
  font-family: 'Adjusted Arial';
  src: local('Arial');
  size-adjust: 105%;
  ascent-override: 90%;
  descent-override: 20%;
  line-gap-override: 0%;
}

body {
  font-family: 'CustomFont', 'Adjusted Arial', sans-serif;
}
```

### unicode-range для частичной загрузки

```css
/* Загрузить только кириллический subset */
@font-face {
  font-family: 'CustomFont';
  src: url('font-cyrillic.woff2') format('woff2');
  unicode-range: U+0400-04FF; /* Кириллица */
}

@font-face {
  font-family: 'CustomFont';
  src: url('font-latin.woff2') format('woff2');
  unicode-range: U+0000-00FF; /* Латиница */
}
```

## 8. Core Web Vitals

### Три метрики

| Метрика | Что измеряет | Хорошо | Нужна работа | Плохо |
|---------|-------------|--------|-------------|-------|
| **LCP** | Largest Contentful Paint | ≤ 2.5с | ≤ 4с | > 4с |
| **INP** | Interaction to Next Paint | ≤ 200мс | ≤ 500мс | > 500мс |
| **CLS** | Cumulative Layout Shift | ≤ 0.1 | ≤ 0.25 | > 0.25 |

### LCP (Largest Contentful Paint)

Время до рендеринга крупнейшего видимого элемента. LCP-элементы:

- `<img>`
- `<video>` (poster image)
- Элемент с `background-image` (через CSS)
- Блочный элемент с текстом

**Оптимизация LCP:**

```html
<!-- 1. Preload LCP-изображения -->
<link rel="preload" href="hero.jpg" as="image" fetchpriority="high">

<!-- 2. Не lazy-load LCP -->
<img src="hero.jpg" alt="Hero" fetchpriority="high">

<!-- 3. Preconnect к CDN -->
<link rel="preconnect" href="https://cdn.example.com">

<!-- 4. Inline critical CSS -->
<style>
  .hero { /* critical styles */ }
</style>

<!-- 5. Defer non-critical CSS -->
<link rel="preload" href="non-critical.css" as="style"
      onload="this.onload=null;this.rel='stylesheet'">
```

### INP (Interaction to Next Paint)

Замеряет задержку от взаимодействия пользователя до следующего рендера. Заменил FID (First Input Delay) в марте 2024.

**Оптимизация INP:**

```html
<!-- Разбивайте длинные задачи через yield -->
<script>
// ПЛОХО: долгая синхронная задача
function processAll(items) {
  items.forEach(item => heavyProcess(item)); // Блокирует main thread
}

// ХОРОШО: yield to main thread
async function processAll(items) {
  for (const item of items) {
    heavyProcess(item);
    // Даём браузеру обработать пользовательский ввод
    await new Promise(resolve => setTimeout(resolve, 0));
    // Или scheduler.yield() (новый API):
    // await scheduler.yield();
  }
}
</script>
```

### CLS (Cumulative Layout Shift)

Суммарный сдвиг видимых элементов без действия пользователя.

**Причины CLS и решения:**

```html
<!-- 1. Изображения без размеров — ГЛАВНАЯ причина -->
<!-- ПЛОХО -->
<img src="photo.jpg" alt="Photo">

<!-- ХОРОШО -->
<img src="photo.jpg" alt="Photo" width="800" height="600">

<!-- 2. Динамический контент выше viewport -->
<!-- ПЛОХО: баннер появляется после загрузки JS -->
<div id="ad-banner"></div>
<main>Content shifts down!</main>

<!-- ХОРОШО: зарезервировать место -->
<div id="ad-banner" style="min-height: 250px;"></div>
<main>Content stays!</main>

<!-- 3. Web fonts без size-adjust (см. раздел Font Loading) -->

<!-- 4. Iframes без размеров -->
<!-- ХОРОШО -->
<iframe src="embed.html" width="560" height="315" loading="lazy"></iframe>
```

## 9. DOM Size и его влияние

### Рекомендации по размеру DOM

| Метрика | Рекомендация | Критично |
|---------|-------------|---------|
| Общее кол-во узлов | < 1,500 | > 3,000 |
| Максимальная глубина | < 32 | > 60 |
| Дочерних у родителя | < 60 | > 120 |

### Почему большой DOM — проблема

1. **Начальная загрузка**: больше HTML → дольше парсинг → позже First Paint
2. **Layout**: каждый reflow пересчитывает геометрию. O(n) от количества затронутых узлов
3. **Память**: каждый DOM-узел занимает ~0.5-1 KB
4. **querySelector**: поиск по большому DOM медленнее
5. **Event delegation**: всплытие событий проходит через больше узлов
6. **Сериализация**: `innerHTML`, `outerHTML` на большом поддереве — дорого

### Стратегии уменьшения DOM

```html
<!-- 1. Виртуализация списков (JS) -->
<!-- Вместо 10,000 элементов рендерить только видимые ~50 -->

<!-- 2. content-visibility: auto (CSS) -->
<style>
  .section {
    content-visibility: auto;
    contain-intrinsic-size: 0 500px;
  }
</style>

<!-- 3. Не рендерить скрытый контент -->
<!-- ПЛОХО: вкладки скрыты через display:none, но в DOM -->
<div class="tab" style="display:none">
  <!-- 500 элементов... -->
</div>

<!-- ЛУЧШЕ: рендерить содержимое только активной вкладки -->

<!-- 4. Использовать <template> для отложенного рендеринга -->
<template id="heavy-content">
  <!-- Контент не в DOM, пока не клонирован -->
</template>
```

## 10. Service Workers и кеширование

### Регистрация Service Worker

```html
<script>
if ('serviceWorker' in navigator) {
  window.addEventListener('load', () => {
    navigator.serviceWorker.register('/sw.js')
      .then(reg => console.log('SW registered:', reg.scope))
      .catch(err => console.error('SW failed:', err));
  });
}
</script>
```

### Стратегии кеширования

| Стратегия | Описание | Когда использовать |
|-----------|----------|-------------------|
| **Cache First** | Сначала кеш, при промахе — сеть | Статические ресурсы (CSS, JS, images) |
| **Network First** | Сначала сеть, при ошибке — кеш | Часто обновляемый контент (HTML, API) |
| **Stale While Revalidate** | Кеш сразу + обновление в фоне | Контент, где свежесть не критична |
| **Network Only** | Только сеть | Аналитика, non-GET запросы |
| **Cache Only** | Только кеш | Pre-cached assets |

### Precaching HTML shell

```js
// sw.js — App Shell pattern
const CACHE_NAME = 'v1';
const SHELL_URLS = [
  '/',
  '/shell.html',
  '/styles/critical.css',
  '/scripts/app.js',
];

self.addEventListener('install', event => {
  event.waitUntil(
    caches.open(CACHE_NAME)
      .then(cache => cache.addAll(SHELL_URLS))
  );
});
```

### Navigation Preload

```js
// Позволяет начать сетевой запрос параллельно с активацией SW
self.addEventListener('activate', event => {
  event.waitUntil(
    self.registration.navigationPreload.enable()
  );
});

self.addEventListener('fetch', event => {
  if (event.request.mode === 'navigate') {
    event.respondWith(
      (async () => {
        const preloadResponse = await event.preloadResponse;
        if (preloadResponse) return preloadResponse;
        return fetch(event.request);
      })()
    );
  }
});
```

## 11. HTTP/2, HTTP/3 и HTML

### HTTP/2 и влияние на HTML

| Особенность | HTTP/1.1 | HTTP/2 |
|------------|----------|--------|
| Соединения | 6 параллельных на домен | Одно мультиплексированное |
| Header compression | Нет | HPACK |
| Server Push | Нет | Да (deprecated в Chrome) |
| Приоритизация | Нет | Да (через weight/dependency) |

### Что изменилось для HTML-разработки

```html
<!-- HTTP/1.1: объединяли файлы для уменьшения запросов -->
<link rel="stylesheet" href="bundle.css"> <!-- all-in-one -->
<script src="bundle.js"></script>

<!-- HTTP/2: можно грузить модульно (мультиплексирование) -->
<link rel="stylesheet" href="base.css">
<link rel="stylesheet" href="components.css">
<link rel="stylesheet" href="utilities.css">
<script type="module" src="app.mjs"></script>
<!-- Модули загружаются параллельно через одно соединение -->
```

### 103 Early Hints

```
HTTP/1.1 103 Early Hints
Link: </style.css>; rel=preload; as=style
Link: </font.woff2>; rel=preload; as=font; crossorigin

HTTP/1.1 200 OK
Content-Type: text/html
...
```

Сервер отправляет 103 ответ **до** генерации HTML. Браузер начинает загружать ресурсы, пока сервер готовит страницу.

```html
<!-- В HTML это эквивалентно, но 103 быстрее: -->
<link rel="preload" href="style.css" as="style">
<link rel="preload" href="font.woff2" as="font" crossorigin>
```

## 12. Streaming HTML и progressive rendering

### Chunked Transfer Encoding

Сервер может отправлять HTML **по частям**. Браузер начинает парсинг сразу, не дожидаясь полного ответа:

```
Server: Отправляет <head>... (первый chunk)
Browser: Начинает парсинг, инициирует загрузку CSS/JS
Server: Отправляет <body> начало... (второй chunk)
Browser: Рендерит первый контент (First Paint!)
Server: Отправляет остаток... (третий chunk)
Browser: Продолжает рендеринг
```

### Паттерн: Early flush

```html
<!-- Сервер отправляет <head> сразу, пока формирует body -->
<!DOCTYPE html>
<html>
<head>
  <link rel="stylesheet" href="style.css">
  <link rel="preload" href="font.woff2" as="font" crossorigin>
  <script defer src="app.js"></script>
</head>
<!-- ← Flush здесь! Браузер начинает загрузку ресурсов -->
<body>
  <!-- Сервер генерирует body (запросы к БД и т.д.) -->
  <main>...</main>
</body>
</html>
```

### React Server Components и Streaming

```html
<!-- Streaming SSR: оболочка приходит первой -->
<div id="root">
  <header>Загружен мгновенно</header>
  <main>
    <template id="suspense-1">Loading...</template>
    <!-- Позже приходит chunk с данными: -->
    <script>
      // Заменяет template реальным контентом
      $RC("suspense-1", "<article>Real content</article>")
    </script>
  </main>
</div>
```

### Out-of-order streaming

Современные фреймворки (React 18+, Qwik, Solid) поддерживают **out-of-order streaming**: компоненты могут приходить в любом порядке, а JavaScript вставляет их в правильные места.

```html
<!-- Скелет приходит первым -->
<div id="slot-1">Loading...</div>
<div id="slot-2">Loading...</div>
<div id="slot-3">Loading...</div>

<!-- Данные приходят по мере готовности (slot-3 может прийти раньше slot-1) -->
<script>replaceSlot("slot-3", "<div>Content 3</div>")</script>
<script>replaceSlot("slot-1", "<div>Content 1</div>")</script>
<script>replaceSlot("slot-2", "<div>Content 2</div>")</script>
```

> **Streaming — одна из самых мощных оптимизаций** для серверного рендеринга. Она позволяет показать пользователю контент задолго до того, как вся страница сгенерирована.
