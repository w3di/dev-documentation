## 1. WCAG — стандарт доступности

### 1.1. Что такое WCAG

**WCAG** (Web Content Accessibility Guidelines) — набор рекомендаций, разработанных W3C WAI (Web Accessibility Initiative), определяющих, как сделать веб-контент доступным для людей с ограниченными возможностями. Актуальная версия — **WCAG 2.2** (октябрь 2023), в разработке находится WCAG 3.0 (Silver).

WCAG применяется не только к HTML — он охватывает любой веб-контент, включая PDF, SVG, мультимедиа и веб-приложения.

### 1.2. Принципы POUR

WCAG строится на четырёх фундаментальных принципах, объединённых акронимом **POUR**:

| Принцип | Оригинал | Описание |
|---------|----------|----------|
| **Воспринимаемость** | Perceivable | Информация и компоненты интерфейса должны быть представлены так, чтобы пользователь мог их воспринять |
| **Управляемость** | Operable | Компоненты интерфейса и навигация должны быть управляемыми (клавиатура, достаточное время, без мерцания) |
| **Понятность** | Understandable | Информация и интерфейс должны быть понятными (читаемость, предсказуемость, помощь при ошибках) |
| **Робастность** | Robust | Контент должен быть достаточно надёжным для интерпретации различными user agents, включая ассистивные технологии |

### 1.3. Уровни соответствия

WCAG определяет три уровня соответствия:

| Уровень | Описание | Примеры критериев |
|---------|----------|-------------------|
| **A** | Минимальный уровень. Базовые требования, без которых контент недоступен | Alt-текст для изображений, клавиатурная навигация, отсутствие контента, вызывающего эпилептические припадки |
| **AA** | Рекомендуемый уровень. Большинство законодательств требует именно его | Контрастность 4.5:1, resize текста до 200%, captions для видео, consistent navigation |
| **AAA** | Максимальный уровень. Не все сайты могут полностью соответствовать | Контрастность 7:1, язык жестов для аудио, альтернативы для time-based media |

> **Важно:** Уровень AA является стандартом де-факто для большинства организаций и правовых требований (ADA, Section 508, EN 301 549 в Европе). Полное соответствие AAA для всего сайта практически невозможно по спецификации WCAG.

### 1.4. Структура критериев WCAG

Каждый критерий имеет номер вида `X.Y.Z`:
- **X** — номер принципа (1-4)
- **Y** — номер руководства (guideline)
- **Z** — номер критерия успешности (success criterion)

Пример: **1.4.3 Contrast (Minimum)** — Принцип 1 (Perceivable), Guideline 4 (Distinguishable), Criterion 3.

### 1.5. Ключевые критерии WCAG 2.2

```
1.1.1 Non-text Content (A) — alt-текст
1.3.1 Info and Relationships (A) — семантическая разметка
1.4.3 Contrast (Minimum) (AA) — контрастность 4.5:1
2.1.1 Keyboard (A) — всё доступно с клавиатуры
2.4.7 Focus Visible (AA) — видимый фокус
2.5.8 Target Size (Minimum) (AA) — минимальный размер цели 24x24px (новое в 2.2)
3.3.7 Redundant Entry (A) — не требовать повторного ввода (новое в 2.2)
3.3.8 Accessible Authentication (Minimum) (AA) — доступная аутентификация (новое в 2.2)
```

## 2. ARIA — Accessible Rich Internet Applications

### 2.1. Что такое WAI-ARIA

**WAI-ARIA** (Web Accessibility Initiative — Accessible Rich Internet Applications) — спецификация W3C, расширяющая HTML семантикой для ассистивных технологий. ARIA добавляет к элементам три типа атрибутов:

1. **Roles** — определяют, чем является элемент (button, dialog, tab)
2. **States** — описывают текущее состояние (aria-expanded, aria-checked)
3. **Properties** — описывают характеристики (aria-label, aria-required)

### 2.2. Пять правил ARIA

> **Первое правило ARIA: не используйте ARIA, если можно использовать нативный HTML-элемент с нужной семантикой.**

| Правило | Описание |
|---------|----------|
| **1** | Используйте нативные HTML-элементы вместо ARIA, когда это возможно |
| **2** | Не изменяйте нативную семантику элемента без крайней необходимости |
| **3** | Все интерактивные ARIA-компоненты должны быть управляемы с клавиатуры |
| **4** | Не используйте `role="presentation"` или `aria-hidden="true"` для фокусируемых элементов |
| **5** | Все интерактивные элементы должны иметь доступное имя (accessible name) |

### 2.3. Нативная семантика vs ARIA

```html
<!-- ✅ Правильно: нативный элемент -->
<button type="button">Закрыть</button>

<!-- ❌ Плохо: ARIA-кнопка (нужно вручную реализовать клавиатуру и фокус) -->
<div role="button" tabindex="0" onclick="close()">Закрыть</div>

<!-- Если div с role="button", нужно обработать Enter и Space -->
<script>
  div.addEventListener('keydown', (e) => {
    if (e.key === 'Enter' || e.key === ' ') {
      e.preventDefault();
      close();
    }
  });
</script>
```

### 2.4. Категории ARIA-ролей

**Abstract roles** (не используются напрямую в разметке):
`command`, `composite`, `input`, `landmark`, `range`, `roletype`, `section`, `sectionhead`, `select`, `structure`, `widget`, `window`

**Widget roles:**
```
alert, alertdialog, button, checkbox, dialog, gridcell, link, log,
marquee, menuitem, menuitemcheckbox, menuitemradio, option, progressbar,
radio, scrollbar, searchbox, slider, spinbutton, status, switch, tab,
tabpanel, textbox, timer, tooltip, treeitem
```

**Document structure roles:**
```
article, cell, columnheader, definition, directory, document, feed,
figure, group, heading, img, list, listitem, math, none, note,
presentation, row, rowgroup, rowheader, separator, table, term, toolbar
```

**Landmark roles:**
```
banner, complementary, contentinfo, form, main, navigation, region, search
```

### 2.5. ARIA States и Properties

```html
<!-- Развёрнутое/свёрнутое состояние -->
<button aria-expanded="false" aria-controls="menu-1">
  Меню
</button>
<ul id="menu-1" hidden>
  <li><a href="/about">О нас</a></li>
</ul>

<!-- Состояние загрузки -->
<div role="status" aria-busy="true">
  Загрузка данных...
</div>

<!-- Выбранный элемент -->
<div role="option" aria-selected="true">Вариант 1</div>

<!-- Недоступный элемент -->
<button aria-disabled="true">Отправить</button>

<!-- Чекбокс с тремя состояниями -->
<div role="checkbox" aria-checked="mixed" tabindex="0">
  Выбрать все
</div>
```

> **Разница между `aria-disabled` и `disabled`:** Атрибут `disabled` удаляет элемент из tab-порядка и блокирует взаимодействие. `aria-disabled="true"` только сообщает ассистивным технологиям о недоступности, но элемент остаётся фокусируемым и кликабельным — блокировку нужно реализовать в JavaScript.

### 2.6. aria-hidden — подводные камни

```html
<!-- Скрывает элемент и всех потомков от accessibility tree -->
<div aria-hidden="true">
  <!-- ⚠️ Всё внутри невидимо для screen readers, включая фокусируемые элементы -->
  <button>Эта кнопка невидима для AT, но может получить фокус!</button>
</div>
```

> **Критическое правило:** Никогда не ставьте `aria-hidden="true"` на элемент, содержащий фокусируемых потомков. Если screen reader переместит фокус внутрь `aria-hidden`, пользователь окажется в «ловушке» — элемент невидим для AT, но фокус на нём.

Используйте `inert` атрибут (HTML Living Standard) для полного скрытия:

```html
<!-- ✅ inert скрывает от AT И убирает из tab-порядка -->
<div inert>
  <button>Недоступна ни для клавиатуры, ни для AT</button>
</div>
```

## 3. Landmark Roles — навигационные ориентиры

### 3.1. Что такое Landmarks

Landmarks — это регионы страницы, которые screen readers используют для быстрой навигации. Пользователь может перемещаться между landmarks с помощью горячих клавиш.

### 3.2. Соответствие HTML-элементов и ARIA-ролей

| HTML-элемент | ARIA role | Условия |
|-------------|-----------|---------|
| `<header>` | `banner` | Только если НЕ внутри `<article>`, `<aside>`, `<main>`, `<nav>`, `<section>` |
| `<nav>` | `navigation` | Всегда |
| `<main>` | `main` | Всегда. Допускается только один видимый `<main>` на странице |
| `<aside>` | `complementary` | Только если НЕ внутри `<article>`, `<aside>`, `<main>`, `<nav>`, `<section>` |
| `<footer>` | `contentinfo` | Только если НЕ внутри `<article>`, `<aside>`, `<main>`, `<nav>`, `<section>` |
| `<section>` | `region` | Только если имеет accessible name (aria-label или aria-labelledby) |
| `<form>` | `form` | Только если имеет accessible name |
| — | `search` | В HTML нет нативного элемента (до HTML 5.2). В HTML Living Standard есть `<search>` |

### 3.3. Правила использования Landmarks

```html
<!DOCTYPE html>
<html lang="ru">
<head>
  <title>Пример Landmark-структуры</title>
</head>
<body>
  <!-- banner -->
  <header>
    <a href="/" aria-label="На главную">Логотип</a>

    <!-- navigation — если несколько nav, дайте каждому уникальный label -->
    <nav aria-label="Основная навигация">
      <ul>
        <li><a href="/catalog">Каталог</a></li>
        <li><a href="/about">О нас</a></li>
      </ul>
    </nav>

    <!-- search landmark (HTML Living Standard) -->
    <search>
      <form role="search" aria-label="Поиск по сайту">
        <label for="site-search">Поиск</label>
        <input type="search" id="site-search" name="q">
        <button type="submit">Найти</button>
      </form>
    </search>
  </header>

  <!-- main — один на странице -->
  <main>
    <h1>Заголовок страницы</h1>

    <!-- region — section с label становится landmark -->
    <section aria-labelledby="featured-heading">
      <h2 id="featured-heading">Избранные товары</h2>
      <!-- контент -->
    </section>
  </main>

  <!-- complementary -->
  <aside aria-label="Боковая панель">
    <nav aria-label="Дополнительная навигация">
      <ul>
        <li><a href="/help">Помощь</a></li>
      </ul>
    </nav>
  </aside>

  <!-- contentinfo -->
  <footer>
    <p>&copy; 2026 Компания</p>
  </footer>
</body>
</html>
```

> **Подводный камень:** `<header>` внутри `<article>` НЕ создаёт `banner` landmark. Аналогично `<footer>` внутри `<section>` НЕ создаёт `contentinfo` landmark. Implicit role зависит от контекста.

### 3.4. Множественные landmarks одного типа

Если на странице несколько навигаций (`<nav>`), каждая **обязана** иметь уникальный accessible name:

```html
<nav aria-label="Основная навигация">...</nav>
<nav aria-label="Навигация по категориям">...</nav>
<nav aria-label="Подвальная навигация">...</nav>
```

Без уникальных меток screen reader объявит три одинаковых «navigation», и пользователь не сможет их различить.

## 4. Live Regions — динамические области

### 4.1. Концепция Live Regions

Live regions — механизм ARIA, позволяющий screen readers автоматически озвучивать изменения DOM без перемещения фокуса. Это критически важно для динамических интерфейсов (чаты, уведомления, обновление данных).

### 4.2. aria-live

```html
<!-- polite — озвучит, когда screen reader закончит текущее действие -->
<div aria-live="polite">
  Корзина: 3 товара
</div>

<!-- assertive — немедленно прерывает текущее озвучивание -->
<div aria-live="assertive">
  Ошибка: сессия истекла!
</div>

<!-- off — изменения не озвучиваются (значение по умолчанию) -->
<div aria-live="off">
  Тихое обновление
</div>
```

| Значение | Поведение | Когда использовать |
|----------|-----------|-------------------|
| `off` | Изменения не объявляются | Значение по умолчанию |
| `polite` | Объявляет, когда пользователь неактивен | Обновление корзины, статусные сообщения, результаты поиска |
| `assertive` | Немедленно прерывает | Критические ошибки, тайм-ауты сессии, срочные уведомления |

> **Правило:** Используйте `assertive` только для критически важной информации. Злоупотребление `assertive` сделает интерфейс невыносимым для пользователей screen readers.

### 4.3. Сопутствующие атрибуты

```html
<!-- aria-atomic — озвучивать весь регион или только изменения -->
<div aria-live="polite" aria-atomic="true">
  <!-- При любом изменении озвучится ВСЯ строка целиком -->
  Товаров в корзине: <span id="count">5</span>
</div>

<div aria-live="polite" aria-atomic="false">
  <!-- Озвучится только изменённый узел -->
  <span>Товар добавлен: </span><span id="item-name">Ноутбук</span>
</div>

<!-- aria-relevant — какие изменения отслеживать -->
<div aria-live="polite" aria-relevant="additions text">
  <!-- additions — добавление узлов -->
  <!-- removals — удаление узлов -->
  <!-- text — изменение текстового содержимого -->
  <!-- all — все изменения -->
</div>

<!-- aria-busy — регион обновляется, подождать завершения -->
<div aria-live="polite" aria-busy="true">
  <!-- Screen reader подождёт, пока aria-busy станет false -->
  Загрузка результатов...
</div>
```

### 4.4. Implicit Live Regions

Некоторые ARIA-роли имеют встроенное поведение live region:

| Role | Implicit aria-live | Описание |
|------|-------------------|----------|
| `alert` | `assertive` | Важное сообщение, требующее немедленного внимания |
| `status` | `polite` | Статусное сообщение, не требующее действий |
| `log` | `polite` | Журнал событий (чат, лог) |
| `marquee` | `off` | Бегущая строка |
| `timer` | `off` | Таймер |
| `progressbar` | — | Зависит от реализации |

```html
<!-- Эквивалентно aria-live="assertive" aria-atomic="true" -->
<div role="alert">
  Ошибка: неверный пароль!
</div>

<!-- Эквивалентно aria-live="polite" -->
<div role="status">
  Результаты поиска обновлены: 42 записи
</div>
```

### 4.5. Паттерн «инъекция в live region»

```html
<!-- ✅ Правильный паттерн: регион существует ДО контента -->
<div id="notifications" aria-live="polite" role="status"></div>

<script>
  // Контент инъецируется ПОСЛЕ инициализации
  function notify(message) {
    const region = document.getElementById('notifications');
    region.textContent = message;
  }
</script>

<!-- ❌ Неправильно: создание элемента с aria-live и контентом одновременно -->
<script>
  // Screen reader может не подхватить — регион не был в DOM до изменения
  document.body.innerHTML += '<div aria-live="polite">Новое уведомление</div>';
</script>
```

> **Критически важно:** Live region должен присутствовать в DOM **до** того, как в него будет помещён контент. Многие screen readers не отслеживают динамически добавленные live regions.

## 5. Keyboard Navigation — клавиатурная навигация

### 5.1. Принципы клавиатурной навигации

Критерий WCAG **2.1.1 Keyboard (A)** требует, чтобы всё функциональность была доступна с клавиатуры (за исключением действий, требующих аналоговый ввод, например рисование от руки).

Нативные интерактивные элементы (`<a href>`, `<button>`, `<input>`, `<select>`, `<textarea>`) уже получают фокус и реагируют на клавиатуру. Проблемы возникают при создании кастомных компонентов.

### 5.2. tabindex — управление порядком фокуса

| Значение | Поведение |
|----------|-----------|
| `tabindex="0"` | Элемент добавляется в естественный tab-порядок (определяется позицией в DOM) |
| `tabindex="-1"` | Элемент удаляется из tab-порядка, но может получить фокус программно через `element.focus()` |
| `tabindex="1+"` | Элемент получает приоритет в tab-порядке. **Крайне не рекомендуется** — нарушает естественный порядок |

```html
<!-- Элемент в tab-порядке -->
<div role="button" tabindex="0">Кнопка</div>

<!-- Элемент фокусируем только программно -->
<h2 tabindex="-1" id="results-heading">Результаты поиска</h2>
<script>
  // После загрузки результатов — фокус на заголовок
  document.getElementById('results-heading').focus();
</script>

<!-- ❌ Не используйте положительные tabindex -->
<input tabindex="3">  <!-- Получит фокус ПЕРВЫМ -->
<input tabindex="1">  <!-- Получит фокус ВТОРЫМ... или нет — зависит от реализации -->
<input tabindex="2">  <!-- Путаница гарантирована -->
```

> **Правило:** Положительные значения `tabindex` создают хаос в навигации. Порядок фокуса должен определяться порядком элементов в DOM, а не `tabindex`.

### 5.3. Focus Trap — ловушка фокуса

Focus trap удерживает фокус внутри определённого контейнера (модальное окно, диалог). Пользователь не может покинуть контейнер с помощью Tab, пока не закроет его.

```html
<div role="dialog" aria-modal="true" aria-labelledby="dialog-title">
  <h2 id="dialog-title">Подтверждение</h2>
  <p>Вы уверены, что хотите удалить?</p>
  <button id="confirm-btn">Да</button>
  <button id="cancel-btn">Нет</button>
</div>

<script>
  const dialog = document.querySelector('[role="dialog"]');
  const focusableElements = dialog.querySelectorAll(
    'button, [href], input, select, textarea, [tabindex]:not([tabindex="-1"])'
  );
  const firstFocusable = focusableElements[0];
  const lastFocusable = focusableElements[focusableElements.length - 1];

  dialog.addEventListener('keydown', (e) => {
    if (e.key === 'Tab') {
      if (e.shiftKey) {
        // Shift+Tab на первом элементе → перенести на последний
        if (document.activeElement === firstFocusable) {
          e.preventDefault();
          lastFocusable.focus();
        }
      } else {
        // Tab на последнем элементе → перенести на первый
        if (document.activeElement === lastFocusable) {
          e.preventDefault();
          firstFocusable.focus();
        }
      }
    }

    // Escape закрывает диалог
    if (e.key === 'Escape') {
      closeDialog();
    }
  });

  // При открытии — фокус на первый элемент
  firstFocusable.focus();
</script>
```

> **Совет:** Используйте нативный `<dialog>` с методом `showModal()` — он реализует focus trap автоматически, включая `inert` для остального содержимого.

### 5.4. Roving Tabindex — блуждающий tabindex

Паттерн для композитных виджетов (табы, меню, radio group), где только один элемент группы находится в tab-порядке, а навигация внутри группы — стрелками:

```html
<!-- Только активный таб имеет tabindex="0" -->
<div role="tablist">
  <button role="tab" tabindex="0" aria-selected="true" id="tab-1">Вкладка 1</button>
  <button role="tab" tabindex="-1" aria-selected="false" id="tab-2">Вкладка 2</button>
  <button role="tab" tabindex="-1" aria-selected="false" id="tab-3">Вкладка 3</button>
</div>

<script>
  const tabs = document.querySelectorAll('[role="tab"]');
  const tablist = document.querySelector('[role="tablist"]');

  tablist.addEventListener('keydown', (e) => {
    const currentIndex = Array.from(tabs).indexOf(document.activeElement);
    let newIndex;

    switch (e.key) {
      case 'ArrowRight':
        newIndex = (currentIndex + 1) % tabs.length;
        break;
      case 'ArrowLeft':
        newIndex = (currentIndex - 1 + tabs.length) % tabs.length;
        break;
      case 'Home':
        newIndex = 0;
        break;
      case 'End':
        newIndex = tabs.length - 1;
        break;
      default:
        return;
    }

    e.preventDefault();

    // Обновить tabindex
    tabs[currentIndex].setAttribute('tabindex', '-1');
    tabs[currentIndex].setAttribute('aria-selected', 'false');
    tabs[newIndex].setAttribute('tabindex', '0');
    tabs[newIndex].setAttribute('aria-selected', 'true');
    tabs[newIndex].focus();
  });
</script>
```

### 5.5. Focus Management при SPA-навигации

При переходе между «страницами» в SPA (Single Page Application) фокус должен перемещаться осмысленно:

```javascript
// После загрузки нового контента
function navigateToPage(pageId) {
  loadContent(pageId);

  // Вариант 1: фокус на заголовок
  const heading = document.querySelector('main h1');
  heading.setAttribute('tabindex', '-1');
  heading.focus();

  // Вариант 2: фокус на skip link target
  const main = document.querySelector('main');
  main.setAttribute('tabindex', '-1');
  main.focus({ preventScroll: false });

  // Обновить document.title
  document.title = `Новая страница — Название сайта`;

  // Объявить для screen reader
  announceToScreenReader(`Загружена страница: ${pageTitle}`);
}

function announceToScreenReader(message) {
  const announcer = document.getElementById('sr-announcer');
  announcer.textContent = '';
  // Небольшая задержка для надёжного срабатывания
  requestAnimationFrame(() => {
    announcer.textContent = message;
  });
}
```

## 6. Screen Readers — экранные дикторы

### 6.1. Как работают Screen Readers

Screen readers не читают DOM напрямую. Браузер строит **Accessibility Tree** — упрощённое представление DOM, содержащее только семантически значимую информацию:

```
DOM Node → Accessibility Object
  - Role (роль элемента)
  - Name (accessible name)
  - Description (описание)
  - State (состояние)
  - Value (значение)
  - Relations (связи с другими элементами)
```

**Цепочка построения:**

```
HTML → DOM Tree → Accessibility Tree → Platform Accessibility API → Screen Reader
                                       (AX API на macOS)
                                       (UIA/MSAA на Windows)
                                       (ATK/AT-SPI на Linux)
```

### 6.2. Accessibility Tree vs DOM

Не все DOM-элементы попадают в accessibility tree:

| Элемент / ситуация | В Accessibility Tree? |
|--------------------|-----------------------|
| `<div>`, `<span>` без роли | Нет (generic role, обычно удаляется) |
| `<div>` с текстовым содержимым | Да (как текстовый узел) |
| `display: none` | Нет |
| `visibility: hidden` | Нет |
| `aria-hidden="true"` | Нет |
| `opacity: 0` | Да (всё ещё доступен) |
| `position: absolute; clip-rect` | Да (sr-only паттерн) |
| `<button>` | Да (role: button) |
| `<input type="hidden">` | Нет |

### 6.3. Основные Screen Readers

| Screen Reader | ОС | Браузер | Стоимость |
|--------------|-----|---------|-----------|
| **VoiceOver** | macOS, iOS | Safari | Бесплатно (встроен) |
| **NVDA** | Windows | Firefox, Chrome | Бесплатно (open source) |
| **JAWS** | Windows | Chrome, Firefox, Edge | Коммерческий (~$1000/год) |
| **TalkBack** | Android | Chrome | Бесплатно (встроен) |
| **Narrator** | Windows | Edge | Бесплатно (встроен) |
| **Orca** | Linux | Firefox | Бесплатно (open source) |


## 7. Альтернативный текст и текстовые метки

### 7.1. alt для изображений

Атрибут `alt` обязателен для всех `<img>`. Значение зависит от функции изображения:

| Функция изображения | alt | Пример |
|--------------------|-----|--------|
| **Информативное** | Описание содержимого | `alt="График роста продаж за 2024 год"` |
| **Функциональное** (ссылка, кнопка) | Описание действия | `alt="Перейти на главную"` |
| **Декоративное** | Пустая строка | `alt=""` |
| **Сложное** (диаграмма, инфографика) | Краткое описание + ссылка на подробное | `alt="Диаграмма процесса" + aria-describedby` |
| **Текст в изображении** | Точный текст из изображения | `alt="SALE — скидка 50%"` |

```html
<!-- Информативное -->
<img src="team.jpg" alt="Команда разработчиков на конференции React Summit 2025">

<!-- Декоративное — ОБЯЗАТЕЛЬНО alt="" (не удаляйте атрибут!) -->
<img src="decorative-line.svg" alt="">

<!-- ❌ Без alt — screen reader прочитает имя файла -->
<img src="IMG_20250315_143022.jpg">
<!-- SR скажет: "Image, IMG underscore twenty twenty five..." -->

<!-- Функциональное (внутри ссылки) -->
<a href="/">
  <img src="logo.svg" alt="На главную страницу Компании">
</a>

<!-- Сложное изображение -->
<figure>
  <img src="chart.png" alt="Квартальные продажи" aria-describedby="chart-desc">
  <figcaption id="chart-desc">
    Q1: 120M, Q2: 145M, Q3: 180M, Q4: 210M. Рост составил 75% за год.
  </figcaption>
</figure>
```

> **Анти-паттерн:** Не начинайте alt с «Изображение...» или «Картинка...» — screen reader уже объявляет элемент как «image» или «graphic». Добавление «изображение» создаёт дублирование: *«image, Изображение логотипа»*.

### 7.2. aria-label, aria-labelledby, aria-describedby

```html
<!-- aria-label: текстовая метка прямо в атрибуте -->
<button aria-label="Закрыть диалог">
  <svg><!-- иконка крестика --></svg>
</button>

<!-- aria-labelledby: ссылка на элемент(ы) с текстом метки -->
<div role="dialog" aria-labelledby="dialog-title dialog-subtitle">
  <h2 id="dialog-title">Подтверждение</h2>
  <p id="dialog-subtitle">удаления аккаунта</p>
</div>
<!-- SR: "Подтверждение удаления аккаунта, dialog" -->

<!-- aria-describedby: дополнительное описание (после паузы) -->
<input
  type="password"
  aria-label="Пароль"
  aria-describedby="pwd-requirements"
>
<p id="pwd-requirements">
  Минимум 8 символов, одна заглавная буква и одна цифра.
</p>
<!-- SR: "Пароль, password edit" ... пауза ... "Минимум 8 символов..." -->
```

### 7.3. Приоритет вычисления Accessible Name

Браузер вычисляет accessible name по алгоритму **Accessible Name Computation** (AccName spec). Приоритет:

1. `aria-labelledby` (наивысший приоритет)
2. `aria-label`
3. Нативная метка (`<label>`, `alt`, `<caption>`, `<legend>`, `<figcaption>`)
4. `title` (наименьший приоритет, **не рекомендуется** как единственный источник)
5. `placeholder` (только для `<input>` и `<textarea>`, **не рекомендуется** как метка)

```html
<!-- aria-labelledby побеждает aria-label -->
<button aria-label="Закрыть" aria-labelledby="custom-label">
  Текст кнопки
</button>
<span id="custom-label">Отменить</span>
<!-- Accessible name: "Отменить" (aria-labelledby победил) -->
```

### 7.4. Паттерн sr-only (visually-hidden)

Текст видим только для screen readers:

```css
/* Стандартный паттерн sr-only */
.sr-only {
  position: absolute;
  width: 1px;
  height: 1px;
  padding: 0;
  margin: -1px;
  overflow: hidden;
  clip: rect(0, 0, 0, 0);
  white-space: nowrap;
  border: 0;
}

/* Вариант с возможностью показать при фокусе (для skip links) */
.sr-only-focusable:focus,
.sr-only-focusable:active {
  position: static;
  width: auto;
  height: auto;
  overflow: visible;
  clip: auto;
  white-space: normal;
}
```

```html
<button>
  <svg aria-hidden="true"><!-- иконка удаления --></svg>
  <span class="sr-only">Удалить товар «Ноутбук» из корзины</span>
</button>

<!-- Или для дополнительного контекста в таблице -->
<table>
  <tr>
    <td>Ноутбук</td>
    <td>45 000 ₽</td>
    <td>
      <a href="/delete/123">
        Удалить
        <span class="sr-only">ноутбук за 45 000 ₽</span>
      </a>
    </td>
  </tr>
</table>
```

## 8. Skip Links — ссылки для пропуска навигации

### 8.1. Зачем нужны Skip Links

Пользователи клавиатуры и screen readers вынуждены проходить через всю навигацию на каждой странице. Skip link позволяет перейти сразу к основному контенту. Это требование **WCAG 2.4.1 Bypass Blocks (A)**.

### 8.2. Реализация

```html
<body>
  <!-- Skip link — первый фокусируемый элемент на странице -->
  <a href="#main-content" class="skip-link">
    Перейти к основному содержимому
  </a>

  <header>
    <nav>
      <!-- Длинная навигация -->
    </nav>
  </header>

  <main id="main-content" tabindex="-1">
    <h1>Заголовок страницы</h1>
    <!-- Основной контент -->
  </main>
</body>
```

```css
.skip-link {
  /* Визуально скрыт по умолчанию */
  position: absolute;
  top: -100%;
  left: 50%;
  transform: translateX(-50%);
  padding: 12px 24px;
  background: #000;
  color: #fff;
  font-size: 16px;
  font-weight: 700;
  text-decoration: none;
  z-index: 10000;
  border-radius: 0 0 8px 8px;
  transition: top 0.2s ease;
}

.skip-link:focus {
  /* Появляется при фокусе */
  top: 0;
  outline: 3px solid #4A90D9;
  outline-offset: 2px;
}
```

> **Подводный камень в Chrome/Safari:** Если целевой элемент (`#main-content`) не является фокусируемым, переход по anchor может не переместить фокус клавиатуры. Добавьте `tabindex="-1"` к целевому элементу.

### 8.3. Множественные Skip Links

Для сложных страниц с несколькими блоками контента:

```html
<div class="skip-links">
  <a href="#main-content" class="skip-link">Перейти к основному содержимому</a>
  <a href="#sidebar" class="skip-link">Перейти к боковой панели</a>
  <a href="#footer-nav" class="skip-link">Перейти к навигации в подвале</a>
</div>
```

## 9. Accessible Forms — доступные формы

### 9.1. Связь label и input

```html
<!-- ✅ Explicit label (рекомендуемый способ) -->
<label for="email">Email</label>
<input type="email" id="email" name="email">

<!-- ✅ Implicit label (wrapping) -->
<label>
  Email
  <input type="email" name="email">
</label>

<!-- ❌ Без label — input не имеет accessible name -->
<input type="email" placeholder="Введите email">
<!-- placeholder — НЕ замена label. Исчезает при вводе, плохой контраст -->
```

### 9.2. Группировка с fieldset и legend

```html
<fieldset>
  <legend>Способ доставки</legend>

  <label>
    <input type="radio" name="delivery" value="pickup">
    Самовывоз
  </label>

  <label>
    <input type="radio" name="delivery" value="courier">
    Курьером
  </label>

  <label>
    <input type="radio" name="delivery" value="post">
    Почтой
  </label>
</fieldset>
<!-- SR: "Способ доставки, group. Самовывоз, radio button, 1 of 3" -->
```

> **Правило:** Группы radio buttons и checkboxes ДОЛЖНЫ быть обёрнуты в `<fieldset>` с `<legend>`. Без `<legend>` screen reader не сможет объяснить контекст группы.

### 9.3. Сообщения об ошибках

```html
<div>
  <label for="username">Имя пользователя</label>
  <input
    type="text"
    id="username"
    name="username"
    aria-required="true"
    aria-invalid="true"
    aria-describedby="username-error"
    aria-errormessage="username-error"

  <p id="username-error" role="alert" class="error">
    Имя пользователя должно содержать от 3 до 20 символов.
  </p>
</div>
```

### 9.4. Паттерн валидации формы

```html

  <div>
    <label for="reg-password">Пароль *</label>

      aria-required="true"

      minlength="8"
    >
    <p id="pwd-hint" class="hint">Минимум 8 символов</p>
```

## 10. Color and Contrast — цвет и контраст

### 10.1. Требования к контрастности (WCAG)

| Критерий | Уровень | Соотношение | Применение |
|----------|---------|-------------|------------|
| 1.4.3 Contrast (Minimum) | AA | 4.5:1 для текста, 3:1 для крупного текста | Основное требование |
| 1.4.6 Contrast (Enhanced) | AAA | 7:1 для текста, 4.5:1 для крупного текста | Повышенные требования |
| 1.4.11 Non-text Contrast | AA | 3:1 для UI-компонентов и графических объектов | Кнопки, иконки, границы полей |

**Крупный текст** определяется как 18pt (24px) обычный или 14pt (18.66px) полужирный.

### 10.2. Цвет как единственный индикатор

WCAG **1.4.1 Use of Color (A)** запрещает использование цвета как единственного средства передачи информации:

```html
<!-- ❌ Только цвет указывает на ошибку -->
<input style="border-color: red;" value="неверный email">

<!-- ✅ Цвет + иконка + текст -->
<div class="field-error">
  <input
    style="border-color: red;"
    value="неверный email"
    aria-invalid="true"
    aria-describedby="email-err"
  >
  <span class="error-icon" aria-hidden="true">⚠</span>
  <p id="email-err" class="error-text">Введите корректный email-адрес</p>
</div>
```

### 10.3. prefers-color-scheme — тёмная тема

```html
<meta name="color-scheme" content="light dark">

<style>
  :root {
    --bg-color: #ffffff;
    --text-color: #1a1a1a;
    --link-color: #0066cc;
  }

  @media (prefers-color-scheme: dark) {
    :root {
      --bg-color: #1a1a1a;
      --text-color: #e0e0e0;
      --link-color: #6bb5ff;
    }
  }

  body {
    background: var(--bg-color);
    color: var(--text-color);
  }

  a { color: var(--link-color); }
</style>

<!-- Для конкретного элемента -->
<meta name="color-scheme" content="only light">
```

> **Важно:** При переключении цветовой темы убедитесь, что контрастность сохраняется. Тёмная тема часто нарушает контрастность AA, если цвета подобраны без проверки.

### 10.4. prefers-contrast — повышенная контрастность

```css
/* Пользователь запросил повышенную контрастность */
@media (prefers-contrast: more) {
  :root {
    --border-color: #000000;
    --bg-color: #ffffff;
    --text-color: #000000;
  }

  button {
    border: 2px solid #000;
    outline: none;
  }

  button:focus {
    outline: 3px solid #000;
    outline-offset: 2px;
  }
}

/* Пользователь запросил пониженную контрастность */
@media (prefers-contrast: less) {
  :root {
    --text-color: #555555;
    --border-color: #cccccc;
  }
}

/* forced-colors — Windows High Contrast Mode */
@media (forced-colors: active) {
  /* Системные цвета заменяют все кастомные */
  button {
    border: 1px solid ButtonText;
    background: ButtonFace;
    color: ButtonText;
  }

  /* SVG-иконки могут исчезнуть — используйте forced-color-adjust */
  .icon {
    forced-color-adjust: auto; /* или none для сохранения оригинальных цветов */
  }
}
```

### 10.5. prefers-reduced-motion — уменьшение анимации

```css
/* Уважайте предпочтения пользователей с вестибулярными нарушениями */
@media (prefers-reduced-motion: reduce) {
  *,
  *::before,
  *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}

/* Лучше: включать анимацию только когда пользователь не возражает */
@media (prefers-reduced-motion: no-preference) {
  .card {
    transition: transform 0.3s ease;
  }

  .card:hover {
    transform: scale(1.05);
  }
}
```
