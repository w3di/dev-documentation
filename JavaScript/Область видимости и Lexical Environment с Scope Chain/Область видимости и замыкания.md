## 1. Lexical Environment по спецификации

`Lexical Environment` — это спецификационный тип (не реальный объект в памяти), определённый в ECMA-262, который связывает идентификаторы с конкретными переменными и функциями на основе **лексической структуры** (вложенности) исходного кода. Каждый раз, когда движок встречает блок кода, функцию или скрипт, создаётся новый `Lexical Environment`.

Структура:

```
LexicalEnvironment = {
  EnvironmentRecord: { ... },                        // хранилище привязок идентификаторов
  OuterEnvironmentReference: <LexicalEnvironment | null>  // ссылка на внешнее окружение
}
```

### 1.1 Environment Record и его типы

`Environment Record` — это абстрактный класс спецификации. Конкретные подтипы определяют, **как** хранятся привязки.

**1. Declarative Environment Record**

Используется для функций, блоков `{}`, `catch`-клаузов и модулей. Привязки хранятся **напрямую** в записи — нет привязки к реальному JS-объекту. Это позволяет движку максимально оптимизировать доступ (хранение в регистрах, стеке):

```js
function processData() {
  let buffer = new ArrayBuffer(1024);  // DeclarativeEnvironmentRecord
  const size = 1024;                    // DeclarativeEnvironmentRecord
  // Движок может разместить buffer и size в регистрах CPU
}
```

У `Declarative Environment Record` есть два подтипа:

- **Function Environment Record** — для функций. Дополнительно содержит `[[ThisValue]]`, `[[ThisBindingStatus]]` (для arrow functions — `lexical`), `[[FunctionObject]]`, `[[NewTarget]]`:

```js
function MyClass() {
  // Function Environment Record содержит:
  // [[ThisValue]]: объект, созданный new (или контекст вызова)
  // [[ThisBindingStatus]]: "initialized"
  // [[FunctionObject]]: ссылка на MyClass
  // [[NewTarget]]: MyClass (при вызове через new) или undefined
}
```

- **Module Environment Record** — для ES-модулей. Наследует `Declarative Environment Record`, но добавляет метод `GetBindingValue`, который для `import`-привязок делегирует запрос к **исходному** модулю (живые привязки):

```js
// counter.js
export let count = 0;
export function increment() { count++; }

// main.js
import { count, increment } from './counter.js';
console.log(count); // 0
increment();
console.log(count); // 1 — живая привязка, а не копия значения
```

**2. Object Environment Record**

Привязки хранятся как свойства реального JS-объекта (`binding object`). Используется в двух случаях:

- Глобальный контекст — `binding object` это `globalThis` / `window`
- `with` statement — `binding object` это переданный объект

```js
// Object Environment Record в with:
const config = { host: "localhost", port: 3000 };
with (config) {
  // Object Environment Record, binding object = config
  console.log(host); // "localhost" — ищет config.host
  console.log(port); // 3000 — ищет config.port
}
```

**3. Global Environment Record — составной тип**

Это **уникальный** тип, объединяющий два компонента:

```
GlobalEnvironmentRecord = {
  ObjectEnvironmentRecord: { bindingObject: globalThis },  // для var, function declarations
  DeclarativeEnvironmentRecord: { ... },                    // для let, const, class
  [[VarNames]]: List<String>,                               // список имён, объявленных через var
  [[GlobalThisValue]]: globalThis
}
```

```js
var x = 1;           // ObjectEnvironmentRecord → window.x = 1
let y = 2;           // DeclarativeEnvironmentRecord → window.y === undefined
function foo() {}    // ObjectEnvironmentRecord → window.foo = function
class Bar {}         // DeclarativeEnvironmentRecord → window.Bar === undefined

console.log('x' in window);   // true  — var
console.log('y' in window);   // false — let
console.log('foo' in window); // true  — function declaration
console.log('Bar' in window); // false — class
```

Именно поэтому `var` на верхнем уровне создаёт свойство `window`, а `let`/`const` — нет.

### 1.2 Outer Environment Reference

`Outer Environment Reference` (он же `[[OuterEnv]]`) — это ссылка на `Lexical Environment` **родительского** лексического контекста. Ключевой принцип: эта ссылка устанавливается в момент **создания** (определения) функции, а не в момент её **вызова**. Это и есть суть `lexical scoping`:

```js
const lang = "JavaScript";

function createGreeter() {
  // [[OuterEnv]] → Global Lexical Environment (где createGreeter объявлена)
  const greeting = "Hello";

  return function greet(name) {
    // [[OuterEnv]] → Lexical Environment функции createGreeter
    // (где greet объявлена), НЕ окружение места вызова
    console.log(`${greeting}, ${name}! (${lang})`);
  };
}

const greet = createGreeter();

function someOtherContext() {
  const greeting = "Goodbye";  // не имеет значения
  const lang = "Python";       // не имеет значения
  greet("Alice");              // "Hello, Alice! (JavaScript)"
  // greet ищет переменные по цепочке, определённой при создании
}

someOtherContext();
```

Для глобального `Lexical Environment` значение `[[OuterEnv]]` равно `null` — это конец цепочки.

### 1.3 VariableEnvironment vs LexicalEnvironment

Внутри одного `Execution Context` (EC) существуют **два** компонента окружения:

- **`VariableEnvironment`** — привязки для `var` и `function declarations` (hoisted). Указывает на `Environment` уровня функции (или глобальный). **Не меняется** при входе в блок.
- **`LexicalEnvironment`** — привязки для `let`, `const`, `class`. При входе в блок `{}` создаётся **новый** `Lexical Environment`, чей `[[OuterEnv]]` указывает на предыдущий.

```js
function demonstrate() {
  // В этой точке:
  // VariableEnvironment = FuncEnv
  // LexicalEnvironment = FuncEnv (совпадают)

  var a = 1;  // → VariableEnvironment (FuncEnv)

  {
    // Новый LexicalEnvironment для блока!
    // VariableEnvironment по-прежнему = FuncEnv (не меняется)
    // LexicalEnvironment = BlockEnv (OuterEnv → FuncEnv)

    var b = 2;     // → VariableEnvironment (FuncEnv) — var игнорирует блок
    let c = 3;     // → LexicalEnvironment (BlockEnv)
    const d = 4;   // → LexicalEnvironment (BlockEnv)
  }

  console.log(a); // 1 — FuncEnv
  console.log(b); // 2 — FuncEnv (var не блочная)
  // console.log(c); // ReferenceError — BlockEnv уже уничтожен
  // console.log(d); // ReferenceError
}
```

Это объясняет, почему `var` «пробивает» блоки: `var` привязывается к `VariableEnvironment`, которое не создаётся заново для блоков.

### 1.4 V8: реализация на уровне движка

В реальности V8 не создаёт `Lexical Environment` как спецификационный объект. Вместо этого используются оптимизированные внутренние структуры:

**Context objects**

Когда функция имеет переменные, которые захватываются замыканием, V8 создаёт объект `Context`. Переменные, которые НЕ замыкаются, хранятся на стеке или в регистрах:

```js
function outer() {
  let captured = "я буду в Context";  // → Context object (замыкается inner)
  let local = "я буду на стеке";      // → стек/регистр (не замыкается)

  function inner() {
    console.log(captured);  // доступ через Context
  }

  return inner;
}
```

**ScopeInfo**

`ScopeInfo` — это метаданные, описывающие структуру scope: какие переменные существуют, их позиции, тип scope. Создаётся при парсинге и используется для компиляции bytecode.

**IC (Inline Caches) для scope chain lookup**

При первом обращении к переменной из внешнего scope V8 проходит по цепочке `Context` объектов. После нахождения переменной создаётся `Inline Cache`, запоминающий глубину и позицию. Последующие обращения используют кеш, минуя обход цепочки:

```js
function outer() {
  const config = { debug: true };

  function middle() {
    function inner() {
      // Первый вызов: V8 обходит Context chain (inner → middle → outer)
      // Находит config на глубине 2, позиция 0
      // Создаёт IC: { depth: 2, slot: 0 }
      // Последующие вызовы: прямой доступ через IC
      console.log(config.debug);
    }
    inner();
  }
  middle();
}
```

## 2. Виды областей видимости

### 2.1 Global scope

Глобальная область видимости — это самый внешний контекст выполнения, охватывающий весь код вне функций и модулей.

**`var` создаёт свойство `window` (configurable: false)**

```js
var globalVar = 42;

console.log(window.globalVar);          // 42
console.log(Object.getOwnPropertyDescriptor(window, 'globalVar'));
// { value: 42, writable: true, enumerable: true, configurable: false }
//                                                  ^^^^^^^^^^^^^^^^
// configurable: false — нельзя удалить через delete

delete window.globalVar; // false — не удалится
console.log(window.globalVar); // 42

// Но если присвоить свойство напрямую (не через var):
window.dynamicProp = "dynamic";
console.log(Object.getOwnPropertyDescriptor(window, 'dynamicProp'));
// { value: "dynamic", writable: true, enumerable: true, configurable: true }
delete window.dynamicProp; // true — удалится
```

**`let`/`const` НЕ создают свойства на `window`**

```js
let globalLet = "hello";
const globalConst = "world";

console.log(window.globalLet);   // undefined — нет на window
console.log(window.globalConst); // undefined — нет на window

// Они хранятся в DeclarativeEnvironmentRecord глобального окружения
// Доступ к ним возможен только по имени, не через window
console.log(globalLet);   // "hello"
console.log(globalConst); // "world"
```

**`globalThis` (ES2020) — кроссплатформенный доступ к глобальному объекту**

```js
// Работает везде: браузер, Node.js, Deno, Web Workers
console.log(globalThis === window);      // true (в браузере)
console.log(globalThis === global);      // true (в Node.js)
console.log(globalThis === self);        // true (в Web Worker)

// До ES2020 приходилось делать так:
const getGlobal = () => {
  if (typeof window !== 'undefined') return window;
  if (typeof global !== 'undefined') return global;
  if (typeof self !== 'undefined') return self;
  throw new Error('Unable to locate global object');
};
```

**Загрязнение глобального scope**

```js
// Антипаттерн: случайное создание глобальных переменных
function leaky() {
  oops = "я глобальная"; // без var/let/const — создаётся свойство на window (sloppy mode)
}
leaky();
console.log(window.oops); // "я глобальная"

// Strict mode предотвращает это:
"use strict";
function safe() {
  oops = "ошибка"; // ReferenceError: oops is not defined
}
```

### 2.2 Function scope

Переменные, объявленные через `var` внутри функции, ограничены телом этой функции. `let`/`const` тоже ограничены функцией (но дополнительно — блоком).

**`var` hoisting внутри функции**

```js
function example() {
  console.log(x); // undefined — var hoisted, но не инициализирован
  if (false) {
    var x = 10; // var поднимается на уровень функции, несмотря на if (false)
  }
  console.log(x); // undefined — код внутри if не выполнился
}
```

**`arguments` object scope**

```js
function showArgs() {
  console.log(arguments); // [Arguments] { '0': 1, '1': 2, '2': 3 }
  // arguments доступен только внутри function (не arrow function)

  const arrowInside = () => {
    console.log(arguments); // [Arguments] { '0': 1, '1': 2, '2': 3 }
    // Arrow function наследует arguments из внешней function scope
  };
  arrowInside();
}
showArgs(1, 2, 3);

const arrowTop = () => {
  // console.log(arguments); // ReferenceError — нет arguments в arrow function
  // на верхнем уровне (если не внутри обычной функции)
};
```

**Strict mode: влияние на function scope**

```js
function strictExample() {
  "use strict";
  // 1. Нельзя использовать необъявленные переменные
  // x = 10; // ReferenceError

  // 2. arguments не синхронизируется с параметрами
  function demo(a) {
    a = 99;
    console.log(arguments[0]); // Остаётся исходное значение (не 99)
  }
  demo(1); // 1 (в sloppy mode было бы 99)

  // 3. Нельзя использовать arguments.callee
  // function factorial(n) { return n <= 1 ? 1 : n * arguments.callee(n - 1); }
  // TypeError: 'caller', 'callee', and 'arguments' properties may not be accessed
}
```

### 2.3 Block scope

Введён в ES6. `let` и `const` привязываются к ближайшему блоку `{}`.

**`let`/`const` в `for` — новый binding каждую итерацию**

Спецификация явно требует, чтобы каждая итерация `for (let ...)` создавала **новый** `Lexical Environment` с **копией** переменной цикла:

```js
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 0, 1, 2 — каждое замыкание захватило свою копию i

// Внутренний механизм:
// Итерация 0: LexicalEnv₀ { i: 0 } → setTimeout замыкает LexicalEnv₀
// Итерация 1: LexicalEnv₁ { i: 1 } → setTimeout замыкает LexicalEnv₁
// Итерация 2: LexicalEnv₂ { i: 2 } → setTimeout замыкает LexicalEnv₂
```

Аналогично для `for...in` и `for...of`:

```js
const obj = { a: 1, b: 2, c: 3 };
const fns = [];

for (const key in obj) {
  fns.push(() => key);
}

console.log(fns.map(f => f())); // ["a", "b", "c"] — каждый callback замкнул своё значение key
```

**`switch` как один блок**

Весь `switch` — это **один** блок `{}`. Переменная, объявленная в одном `case`, видна в другом:

```js
switch (action) {
  case 'create':
    let message = 'Created';  // объявлена в блоке switch
    break;
  case 'delete':
    // let message = 'Deleted'; // SyntaxError: Identifier 'message' has already been declared
    message = 'Deleted';        // OK — та же переменная из case 'create'
    break;
}

// Решение — обернуть case в свой блок:
switch (action) {
  case 'create': {
    let message = 'Created';  // свой блок — свой scope
    break;
  }
  case 'delete': {
    let message = 'Deleted';  // свой блок — нет конфликта
    break;
  }
}
```

**TDZ внутри блока**

```js
{
  // TDZ для x начинается здесь
  console.log(typeof x); // ReferenceError (не "undefined"!)
  let x = 10;            // TDZ для x заканчивается здесь
}
```

### 2.4 Module scope

ES-модули создают собственную область видимости. Каждый модуль — это **отдельный** `Module Environment Record`.

```js
// utils.js
const API_KEY = "secret-key";  // Module scope — не видна другим модулям
export const helper = () => API_KEY;

// main.js
import { helper } from './utils.js';
console.log(helper());   // "secret-key" — через замыкание
// console.log(API_KEY);  // ReferenceError — не экспортирована
```

**Strict mode по умолчанию**

```js
// module.mjs — strict mode автоматически
x = 10; // ReferenceError — без объявления нельзя
// this на верхнем уровне модуля === undefined (не window)
console.log(this); // undefined
```

**Статические imports — живые привязки (live bindings)**

```js
// counter.js
export let count = 0;
export function increment() { count++; }

// main.js
import { count, increment } from './counter.js';
console.log(count); // 0
increment();
console.log(count); // 1 — живая привязка: main.js видит обновлённое значение

// count = 5; // TypeError — import bindings read-only для импортирующего модуля
```

**`import.meta`**

```js
// Доступ к метаданным модуля
console.log(import.meta.url); // "file:///path/to/module.js"
// В Vite/Webpack: import.meta.env, import.meta.hot и т.д.
```

**CommonJS vs ESM scope**

```js
// CommonJS — каждый файл обёрнут в функцию:
// (function(exports, require, module, __filename, __dirname) { ... })
// Поэтому переменные module-scoped через function scope обёртки

// ESM — настоящий Module Environment Record:
// - Статический анализ, tree-shaking
// - Живые привязки (не копии)
// - Top-level await
// - this === undefined (не module.exports)
```

### 2.5 Lexical scope vs Dynamic scope

JavaScript использует **лексическую** (статическую) область видимости. Scope функции определяется тем, **где** она объявлена в исходном коде, а не **откуда** вызвана:

```js
const value = "global";

function printValue() {
  console.log(value);
}

function wrapper() {
  const value = "local";
  printValue(); // "global" — lexical scope, определённый при создании printValue
}

wrapper();
```

Если бы JS использовал `dynamic scope` (как Bash, Emacs Lisp, Perl `local`), `printValue()` вывело бы `"local"`, потому что поиск шёл бы по стеку вызовов.

**`this` как единственный «динамический» механизм**

```js
const obj1 = {
  name: "obj1",
  getName() { return this.name; }
};

const obj2 = { name: "obj2" };
obj2.getName = obj1.getName;

console.log(obj1.getName()); // "obj1" — this определяется вызовом
console.log(obj2.getName()); // "obj2" — this определяется вызовом

// this — это НЕ scope variable, это компонент Execution Context
// Он разрешается динамически (по месту вызова), в отличие от обычных переменных
```

### 2.6 with statement

`with` создаёт `Object Environment Record`, чей `binding object` — переданный объект. Идентификаторы сначала ищутся как свойства этого объекта:

```js
const data = { x: 10, y: 20 };

with (data) {
  console.log(x + y); // 30 — x и y найдены как свойства data
  z = 100;            // Нет z в data → ищет во внешнем scope → создаёт глобальную (sloppy)
}
```

**Почему `with` деоптимизирует код**

V8 при компиляции статически определяет, в каком scope находится каждая переменная. `with` делает это **невозможным** — движок не может знать, появится ли свойство на объекте в рантайме:

```js
function slowPath(obj, condition) {
  with (obj) {
    // V8 не знает, является ли x свойством obj или внешней переменной
    // Каждое обращение к идентификатору — динамический lookup
    // Все оптимизации (IC, register allocation для scope vars) отключены
    return x + 1;
  }
}

// Strict mode запрещает with:
"use strict";
with ({}) {} // SyntaxError: Strict mode code may not include a with statement
```

### 2.7 eval и scope

**Direct eval** — вызванный как `eval(...)` — расширяет `Lexical Environment` вызывающего контекста:

```js
function directEvalDemo() {
  const x = 10;
  eval('var y = 20; console.log(x)'); // 10 — видит x из directEvalDemo
  console.log(y); // 20 — var из eval попала в scope функции (sloppy mode)
}
directEvalDemo();
```

В `strict mode` direct eval создаёт **свой** `Lexical Environment`, `var` из eval не утекает:

```js
function strictEvalDemo() {
  "use strict";
  eval('var y = 20;');
  // console.log(y); // ReferenceError — y осталась внутри eval
}
```

**Indirect eval** — любой другой способ вызова `eval` — работает в **глобальном** scope:

```js
function indirectEvalDemo() {
  const x = 10;
  const myEval = eval;
  myEval('console.log(typeof x)'); // "undefined" — не видит x
  (0, eval)('console.log(typeof x)'); // "undefined" — indirect eval
  window.eval('console.log(typeof x)'); // "undefined" — indirect eval
}
indirectEvalDemo();
```

Direct eval деоптимизирует код по той же причине, что и `with` — движок не может статически определить, какие переменные будут созданы или прочитаны:

```js
function cantOptimize(str) {
  let x = 10;
  eval(str); // Может прочитать, изменить или создать любую переменную
  return x;  // V8 не может заоптимизировать x в регистр
}
```

## 3. Scope Chain

### 3.1 Алгоритм поиска переменных

Когда движок встречает идентификатор, он выполняет **ResolveBinding** — поиск по цепочке `Environment Record`:

```
1. Проверить текущий EnvironmentRecord
2. Если не найдено → перейти к OuterEnvironmentReference
3. Повторить шаг 1-2 до достижения Global Environment
4. Если не найдено и в Global → ReferenceError
```

```js
const a = "global-a";

function outer() {
  const b = "outer-b";

  function middle() {
    const c = "middle-c";

    function inner() {
      const d = "inner-d";

      console.log(d); // Шаг 1: найдено в inner.ER
      console.log(c); // Шаг 1: нет в inner → Шаг 2: найдено в middle.ER
      console.log(b); // inner → middle → найдено в outer.ER
      console.log(a); // inner → middle → outer → найдено в global.ER
      // console.log(z); // inner → middle → outer → global → ReferenceError
    }
    inner();
  }
  middle();
}
outer();
```

Scope chain для `inner()`:

```
inner.LexicalEnv     { d: "inner-d" }
       ↓ OuterEnv
middle.LexicalEnv    { c: "middle-c" }
       ↓ OuterEnv
outer.LexicalEnv     { b: "outer-b" }
       ↓ OuterEnv
global.LexicalEnv    { a: "global-a" }
       ↓ OuterEnv
null  (конец цепочки)
```

### 3.2 V8: Context chain и IC

V8 реализует scope chain через связанный список `Context` объектов. Каждый `Context` содержит массив слотов (по одному на замкнутую переменную) и указатель `previous`, который и формирует цепочку:

```
Context (inner) → Context (middle) → Context (outer) → NativeContext (global)
     [d]              [c]               [b]               [a]
```

При первом доступе к переменной из внешнего scope V8 обходит цепочку и создаёт **Inline Cache** (IC):

```
// Псевдокод IC для доступа к переменной b из inner:
// IC: { contextDepth: 2, slotIndex: 0 }
// Следующий доступ: context.previous.previous.slots[0]  — без поиска
```

`TurboFan` (оптимизирующий компилятор) может полностью развернуть (`inline`) обращения к внешним переменным на основе данных IC.

### 3.3 Performance и глубина scope chain

Теоретически глубокий scope chain замедляет lookup. Практически V8 кеширует через IC, и после первого обращения производительность не зависит от глубины. Однако:

```js
// Антипаттерн: глубокая вложенность ради вложенности
function level1() {
  const data = heavyComputation();
  function level2() {
    function level3() {
      function level4() {
        function level5() {
          // Доступ к data — 4 прыжка по Context chain (до IC)
          // IC кеширует, но Context objects всё равно аллоцированы в heap
          return data;
        }
        return level5();
      }
      return level4();
    }
    return level3();
  }
  return level2();
}

// Лучше: передать как параметр или уменьшить вложенность
function betterApproach() {
  const data = heavyComputation();
  return processData(data); // Прямой доступ, нет Context chain
}
```

Каждый `Context` объект — это heap allocation. Даже если lookup быстрый благодаря IC, количество `Context` объектов увеличивает давление на GC.

### 3.4 Shadowing

Переменная во внутреннем scope «затеняет» одноимённую переменную из внешнего scope:

```js
const x = "global";

function outer() {
  const x = "outer"; // shadowing global x

  function inner() {
    const x = "inner"; // shadowing outer x
    console.log(x);    // "inner" — движок находит x в текущем ER и прекращает поиск
  }

  inner();
  console.log(x); // "outer" — inner.x не влияет на outer.x
}

outer();
console.log(x); // "global"
```

**Shadowing `var` через `let` в блоке**

```js
function demo() {
  var x = 1;
  {
    let x = 2;      // Новый x в блочном scope — shadowing var x
    console.log(x); // 2
  }
  console.log(x);   // 1 — var x не изменился
}
```

**Нельзя shadowing `let` через `var` внутри того же scope:**

```js
function illegal() {
  let x = 1;
  // var x = 2; // SyntaxError: Identifier 'x' has already been declared
}
```

## 4. Hoisting

### 4.1 Creation Phase и hoisting

`Hoisting` — это следствие `Creation Phase` при создании `Execution Context`. На этой фазе движок сканирует код и **регистрирует** все объявления в соответствующем `Environment Record` **до** начала построчного исполнения.

Важно: hoisting **не перемещает** код. Движок не переставляет строки. Он лишь создаёт привязки (bindings) в `Environment Record` заранее.

```js
// Исходный код:
console.log(a);        // undefined
console.log(typeof b); // ReferenceError (TDZ)
greet();               // "Hello!" — работает

var a = 10;
let b = 20;
function greet() { console.log("Hello!"); }

// На уровне ER (Creation Phase):
// VariableEnvironment.ER = { a: undefined }
// LexicalEnvironment.ER  = { b: <uninitialized>, greet: <function object> }
```

### 4.2 Полная таблица hoisting

| Объявление | Hoisting | Инициализация на Creation Phase | TDZ | Scope |
|---|---|---|---|---|
| `var x = 1` | Да (declaration + init `undefined`) | `undefined` | Нет | Function / Global |
| `let x = 1` | Да (declaration only) | `<uninitialized>` | Да | Block |
| `const x = 1` | Да (declaration only) | `<uninitialized>` | Да | Block |
| `function f() {}` | Да (declaration + init body) | `<function object>` | Нет | Function / Global (Block — см. Annex B) |
| `var f = function() {}` | Как `var` (expression не hoisted) | `undefined` | Нет | Function / Global |
| `var f = () => {}` | Как `var` | `undefined` | Нет | Function / Global |
| `class C {}` | Да (declaration only) | `<uninitialized>` | Да | Block |
| `import x from '...'` | Да (полностью) | Живая привязка | Нет* | Module |

*`import` поднимается полностью — привязка доступна с самого начала модуля, потому что модули парсятся целиком до выполнения.

```js
// import hoisting:
console.log(add(2, 3)); // 5 — import уже доступен
import { add } from './math.js';

// function declaration hoisting:
console.log(square(4)); // 16
function square(n) { return n * n; }

// function expression — НЕ hoisted как функция:
console.log(typeof cube); // "undefined" — var hoisted, но значение undefined
// cube(3); // TypeError: cube is not a function
var cube = function(n) { return n ** 3; };

// class — TDZ:
// const obj = new Foo(); // ReferenceError
class Foo {}
const obj = new Foo(); // OK — после объявления
```

### 4.3 Function Declarations внутри блоков — Annex B

Поведение `Function Declaration` (FD) внутри блока `{}` — один из самых запутанных аспектов JS. Спецификация определяет это в **Annex B** (legacy web compatibility):

**Strict mode — предсказуемое поведение:**

```js
"use strict";

console.log(typeof foo); // "undefined" — foo ещё не определена

if (true) {
  // FD hoisted только внутри блока
  console.log(foo()); // "hello" — hoisted в пределах блока

  function foo() { return "hello"; }
}

console.log(typeof foo); // "undefined" — FD не вышла за блок
// foo(); // ReferenceError
```

**Sloppy mode — Annex B создаёт хаос:**

```js
// Sloppy mode (без "use strict")
console.log(typeof foo); // "undefined"

if (true) {
  function foo() { return "hello"; }
}

console.log(typeof foo); // "function" — FD «утекла» из блока!
console.log(foo());      // "hello"
```

Annex B в sloppy mode делает следующее:
1. Создаёт `var foo` в `VariableEnvironment` (function scope) с `undefined`
2. Внутри блока FD hoisted как обычно (в блочном scope)
3. При достижении FD в потоке выполнения — присваивает значение из блочного scope в `var`

```js
// Sloppy mode — демонстрация Annex B шаг за шагом:
console.log(bar); // undefined — var bar из Annex B

if (true) {
  console.log(bar); // [Function: bar] — FD hoisted внутри блока

  function bar() { return 1; }

  bar = 2; // Переприсваиваем внутри блока
  console.log(bar); // 2
}

// При выходе из блока: var bar = значение из блочного scope = 2
console.log(bar); // 2
```

### 4.4 Function Declaration vs var с одинаковым именем

Когда `Function Declaration` и `var` имеют одинаковое имя, FD имеет приоритет на этапе creation phase:

```js
console.log(typeof x); // "function" — FD имеет приоритет над var

var x = 10;
function x() { return 42; }

console.log(x); // 10 — на этапе execution: var x = 10 перезаписывает

// Порядок на Creation Phase:
// 1. var x → undefined (VariableEnvironment)
// 2. function x → <function object> — перезаписывает undefined
// Итого после creation: x = <function object>
//
// Execution Phase:
// 1. x = 10 — перезаписывает function object
```

При нескольких FD с одним именем побеждает **последнее** объявление:

```js
console.log(f()); // "second" — последнее FD в creation phase

function f() { return "first"; }
function f() { return "second"; }
```

### 4.5 V8: bytecode и preparser

**Preparser (lazy parsing)**

V8 не парсит все функции полностью при первом прохождении. `Preparser` выполняет быстрый проход, определяя:
- Границы функций (начало и конец)
- Наличие синтаксических ошибок
- Какие переменные из внешнего scope используются (для правильного hoisting)

Полный парсинг (`Parser`) происходит **при первом вызове** функции:

```js
function outer() {
  // Preparser проходит inner, определяет границы и scope info
  // Parser запустится для inner только при outer()
  function inner() {
    // Тяжёлый код — не парсится до вызова outer → inner
    const result = complexComputation();
    return result;
  }
  return inner;
}
// На этом этапе inner ещё НЕ полностью распарсена
```

**Bytecode generation для hoisting**

```js
function example() {
  console.log(x);
  var x = 10;
}

// Bytecode (упрощённо):
// LdaUndefined              — загрузить undefined
// Star r0                   — сохранить в регистр r0 (переменная x)
// LdaGlobal [console]       — загрузить console
// LdaNamedProperty [log]    — загрузить console.log
// CallProperty r0           — вызвать console.log(undefined)
// LdaSmi [10]               — загрузить число 10
// Star r0                   — записать в r0 (x = 10)
```

## 5. Temporal Dead Zone (TDZ)

TDZ — это участок кода от начала блока до строки инициализации переменной, объявленной через `let`, `const` или `class`. В этом участке переменная **существует** (привязка создана в `Environment Record`), но обращение к ней вызывает `ReferenceError`.

### 5.1 typeof в TDZ

Оператор `typeof` обычно безопасен для несуществующих переменных. Но в TDZ — нет:

```js
// Для необъявленных переменных typeof безопасен:
console.log(typeof undeclaredVar); // "undefined" — нет ошибки

// Но для переменных в TDZ — ReferenceError:
{
  console.log(typeof letVar); // ReferenceError: Cannot access 'letVar' before initialization
  let letVar = 42;
}
```

Это один из немногих случаев, когда `typeof` может бросить ошибку. Причина: привязка `letVar` **существует** в `Environment Record` (движок знает о ней), но не инициализирована. В отличие от `undeclaredVar`, которой нет вообще.

```js
// Практическое следствие для feature detection:
// Старый способ (работает):
if (typeof SomeGlobal !== 'undefined') { /* ... */ }

// С TDZ нужна осторожность:
{
  // if (typeof x !== 'undefined') {} // ReferenceError, если let x ниже
  let x = 10;
}
```

### 5.2 TDZ в параметрах функций

Параметры функций по умолчанию (`default parameters`) имеют **свой** scope и подчиняются TDZ **слева направо**:

```js
// Параметр b ещё в TDZ, когда a = b вычисляется:
function broken(a = b, b = 1) {
  return a + b;
}
// broken(); // ReferenceError: Cannot access 'b' before initialization

// Правильный порядок:
function working(a = 1, b = a) {
  return a + b;
}
console.log(working()); // 2 — a уже инициализирован, когда b = a вычисляется
```

Параметры образуют **промежуточный scope** между внешним и телом функции:

```js
const x = "outer";

function demo(a = x, b = () => a) {
  const x = "inner";
  console.log(a);   // "outer" — default parameter видит внешний x
  console.log(b()); // "outer" — замыкание b замкнуло параметр a
}
demo();
```

### 5.3 TDZ и destructuring

Самоссылка при destructuring с default values приводит к TDZ:

```js
// a используется как default для самого себя — TDZ
// let { a = a } = {};
// ReferenceError: Cannot access 'a' before initialization

// Причина: правая часть default (= a) вычисляется, когда a ещё в TDZ
// Потому что привязка a создана, но не инициализирована

// Корректные варианты:
const defaultA = 10;
let { a = defaultA } = {};
console.log(a); // 10

// Взаимная ссылка тоже опасна:
// let { x = y, y = 1 } = {};
// ReferenceError — y ещё в TDZ при вычислении x = y
```

### 5.4 TDZ для class

`class` declarations подчиняются TDZ точно как `let`/`const`:

```js
// const instance = new MyClass();
// ReferenceError: Cannot access 'MyClass' before initialization

class MyClass {
  constructor() {
    this.value = 42;
  }
}

const instance = new MyClass(); // OK
console.log(instance.value);    // 42
```

Особенно коварно при наследовании с ссылкой на класс до его объявления:

```js
// class Child extends Parent {} // OK — Parent объявлен ниже? Нет!
// class Parent {}
// На самом деле: ReferenceError при вычислении extends Parent

// Правильно:
class Parent {}
class Child extends Parent {}
```

Также TDZ для class влияет на `class expressions` присвоенные в `const`/`let`:

```js
// const factory = () => new Foo(); // Замыкание — не TDZ при создании
// factory(); // ReferenceError — Foo ещё в TDZ при вызове
// const Foo = class {};
// factory(); // OK — теперь Foo инициализирован

// Порядок вызова важен:
const Foo = class {};
const factory = () => new Foo();
factory(); // OK
```

### 5.5 TDZ в switch/case

Поскольку весь `switch` — один блок, переменная из одного `case` может быть в TDZ для другого:

```js
switch (value) {
  case 1:
    let result = 'one';
    break;
  case 2:
    // console.log(result);
    // ReferenceError — result в TDZ, если мы попали в case 2
    // (потому что let result объявлена в этом же блоке, но выполнение
    // не прошло через case 1, где инициализация)
    break;
  case 3:
    // result = 'three';
    // ReferenceError — всё ещё TDZ, если мы попали сюда напрямую
    break;
}
```

Решение — отдельные блоки для каждого case (как показано в разделе 2.3).

### 5.6 Почему TDZ существует

TDZ был введён в ES6 для решения конкретных проблем `var`:

**1. Предотвращение багов с `undefined`**

```js
// С var — тихий баг:
function buggyWithVar() {
  console.log(config); // undefined — не ошибка, но бессмысленно
  // 100 строк кода, разработчик думает, что config доступен...
  if (config) {
    // Этот блок НИКОГДА не выполнится, но ошибки нет
  }
  var config = loadConfig();
}

// С let — явная ошибка:
function safeWithLet() {
  // console.log(config); // ReferenceError — баг пойман!
  let config = loadConfig();
}
```

**2. Семантическая корректность `const`**

```js
// const должен быть инициализирован ровно один раз
// Если бы const hoisted с undefined, семантика нарушена:
// console.log(PI); // Было бы undefined — нарушение "константности"
const PI = 3.14159;
// TDZ гарантирует: до const PI = ... обращение запрещено
```

**3. Корректность для class**

```js
// Без TDZ можно было бы наследовать от ещё не определённого класса:
// class Child extends Parent {} // Без TDZ: Parent = undefined → ошибка в runtime
// class Parent {}
// С TDZ: ReferenceError сразу — предсказуемо
```

### 5.7 V8: ThrowReferenceErrorIfHole

V8 представляет неинициализированные (`<uninitialized>`) переменные через специальное sentinel-значение `the_hole`. При каждом доступе к `let`/`const` переменной генерируется bytecode-проверка:

```
// Bytecode для: console.log(x); (где x — let, возможно в TDZ)
LdaCurrentContextSlot [0]        // загрузить значение x из Context
ThrowReferenceErrorIfHole [x]    // если значение === the_hole → ReferenceError
// ... использовать значение
```

**TurboFan (оптимизирующий компилятор) может убрать избыточные проверки:**

```js
function optimizable() {
  let x = 10;
  // TurboFan знает, что x инициализирован в начале функции
  // Все обращения к x ниже — проверка ThrowReferenceErrorIfHole удаляется
  console.log(x);  // Нет проверки в оптимизированном коде
  console.log(x);  // Нет проверки — redundant check eliminated
  return x + 1;    // Нет проверки
}
```

Но если инициализация условная, TurboFan сохраняет проверку:

```js
function notOptimizable(flag) {
  let x;
  if (flag) {
    x = 10;
  }
  // TurboFan не может гарантировать, что x инициализирован
  // ThrowReferenceErrorIfHole остаётся
  return x; // Проверка сохранена
}
```

## 6. Замыкания (Closures)

Замыкание (`closure`) — это функция, которая «запоминает» и имеет доступ к переменным из своего лексического окружения, даже после того как внешняя функция завершила выполнение. Это фундаментальный механизм JavaScript, возникающий из `lexical scoping`.

### 6.1 Спецификационный механизм

Каждый `function object` имеет внутренний слот `[[Environment]]`, содержащий ссылку на `Lexical Environment`, существовавший в момент **создания** (определения) функции.

При вызове функции движок создаёт новый `Execution Context`, чей `LexicalEnvironment.[[OuterEnv]]` устанавливается равным `[[Environment]]` функции:

```js
function createCounter(initial) {
  // LexicalEnvironment_A: { initial: 10, count: 10 }
  let count = initial;

  // increment.[[Environment]] = LexicalEnvironment_A
  function increment() {
    // Новый LexicalEnvironment_B при каждом вызове increment
    // LexicalEnvironment_B.[[OuterEnv]] = LexicalEnvironment_A (из [[Environment]])
    count++;
    return count;
  }

  // decrement.[[Environment]] = LexicalEnvironment_A (тот же!)
  function decrement() {
    count--;
    return count;
  }

  return { increment, decrement };
}

const counter = createCounter(10);
// createCounter завершила выполнение, но LexicalEnvironment_A НЕ собран GC,
// потому что counter.increment.[[Environment]] и counter.decrement.[[Environment]]
// ссылаются на него

console.log(counter.increment()); // 11
console.log(counter.increment()); // 12
console.log(counter.decrement()); // 11
// increment и decrement разделяют ОДНО лексическое окружение (одну переменную count)
```

### 6.2 V8 Context object и escape analysis

**Context object — не все переменные замыкаются**

V8 не помещает все локальные переменные в `Context` (heap). Только те, которые **действительно замкнуты** (используются внутренней функцией), аллоцируются в `Context`. Остальные — на стеке:

```js
function outer() {
  let heapVar = "я в Context";    // Используется в inner → heap (Context)
  let stackVar = "я на стеке";    // НЕ используется в inner → stack
  const bigArray = new Array(1000000); // НЕ используется в inner → stack

  function inner() {
    return heapVar; // Только heapVar замыкается
  }

  return inner;
}

const fn = outer();
// stackVar и bigArray освобождены (были на стеке outer)
// heapVar жив в Context, доступном через fn.[[Environment]]
```

**Escape analysis**

V8 проводит `escape analysis` — определяет, «убегает» ли функция из текущего scope (возвращается, сохраняется в переменную, передаётся как callback). Если функция **не убегает**, V8 может не создавать `Context`:

```js
function noEscape() {
  let x = 10;

  function helper() {
    return x * 2;
  }

  // helper НЕ убегает — вызывается и результат используется здесь
  const result = helper();
  return result;
  // V8 может заинлайнить helper и не создавать Context
}

function escapes() {
  let x = 10;

  function helper() {
    return x * 2;
  }

  return helper; // helper убегает → Context обязателен
}
```

### 6.3 Классический баг var в цикле

Самая известная ловушка замыканий — `var` в цикле с асинхронным callback:

```js
// Баг:
for (var i = 0; i < 5; i++) {
  setTimeout(() => console.log(i), 100);
}
// Вывод: 5, 5, 5, 5, 5
// Все 5 callbacks замкнули ОДНУ переменную i (function scope)
// К моменту выполнения setTimeout цикл завершился, i === 5
```

**Решение 1: `let` (ES6)**

```js
for (let i = 0; i < 5; i++) {
  setTimeout(() => console.log(i), 100);
}
// Вывод: 0, 1, 2, 3, 4
// Каждая итерация — новый LexicalEnvironment с собственной копией i
```

**Решение 2: IIFE (pre-ES6)**

```js
for (var i = 0; i < 5; i++) {
  (function(captured) {
    // captured — параметр IIFE, своя копия для каждой итерации
    setTimeout(() => console.log(captured), 100);
  })(i);
}
// Вывод: 0, 1, 2, 3, 4
```

**Решение 3: `bind`**

```js
for (var i = 0; i < 5; i++) {
  setTimeout(console.log.bind(console, i), 100);
}
// Вывод: 0, 1, 2, 3, 4
// bind фиксирует значение i на момент вызова bind
```

**Почему `var` ведёт себя так — на уровне спецификации:**

```
for (var i = 0; ...) — var i привязана к VariableEnvironment (функция)
Все итерации разделяют одну привязку i

for (let i = 0; ...) — спецификация (13.7.4.9 ForBodyEvaluation):
На каждой итерации выполняется CopyDataProperties из старого LE в новый
Каждая итерация получает свежий LexicalEnvironment со своей копией i
```

### 6.4 Утечки памяти

Замыкания могут удерживать объекты в памяти дольше, чем нужно.

**Event listener, удерживающий большой объект:**

```js
function setupHandler() {
  const hugeData = new Array(1_000_000).fill('x'); // 1M элементов

  document.getElementById('btn').addEventListener('click', () => {
    // Замыкание захватило hugeData
    // Даже если мы используем только hugeData.length,
    // весь массив удерживается в памяти
    console.log(hugeData.length);
  });

  // hugeData НЕ будет собран GC, пока listener активен
}

// Решение: сохранить только нужное
function setupHandlerFixed() {
  const hugeData = new Array(1_000_000).fill('x');
  const length = hugeData.length; // Извлечь нужное

  document.getElementById('btn').addEventListener('click', () => {
    console.log(length); // Замыкает только number, не массив
  });
  // hugeData может быть собран GC после завершения setupHandlerFixed
}
```

**Таймер с замыканием:**

```js
function startPolling() {
  const cache = new Map();

  // setInterval возвращает ID, но если его не сохранить — утечка
  setInterval(() => {
    cache.set(Date.now(), fetchData()); // cache растёт бесконечно
  }, 1000);

  // Решение:
  const intervalId = setInterval(() => { /* ... */ }, 1000);
  // Где-то: clearInterval(intervalId);
}
```

**Closure удерживает весь scope (зависит от движка):**

```js
function potentialLeak() {
  const a = "small string";
  const b = new ArrayBuffer(100_000_000); // 100MB

  return function() {
    return a; // Использует только a
    // Вопрос: удерживается ли b?
  };
}

// Ответ зависит от движка:
// V8 (современные версии): b НЕ попадёт в Context (escape analysis)
//   V8 анализирует, какие переменные реально используются в замыкании
// Старые движки / eval: могли удерживать весь scope
//
// НО: если в замыкании есть eval или with — V8 помещает ВСЕ переменные в Context:
function definitelyLeaks() {
  const a = "small";
  const b = new ArrayBuffer(100_000_000);

  return function() {
    return eval('a'); // eval — V8 не знает, что будет запрошено
    // b тоже в Context, хотя не используется явно
  };
}
```

### 6.5 Closure и Garbage Collection

GC может собрать `Context` (и замкнутые переменные), когда **ни одна** функция, ссылающаяся на этот `Context` через `[[Environment]]`, не достижима:

```js
function createPair() {
  const shared = { data: "important" };

  const getter = () => shared;
  const logger = () => console.log(shared.data);

  return { getter, logger };
}

let pair = createPair();
// shared жив — getter и logger ссылаются на Context

pair.logger = null;
// shared всё ещё жив — getter ссылается на Context

pair.getter = null;
// shared МОЖЕТ быть собран — ни getter, ни logger не достижимы
// Context не достижим → GC собирает Context и shared

pair = null;
// Объект { getter: null, logger: null } тоже собирается
```

**WeakRef и FinalizationRegistry (ES2021) для мониторинга:**

```js
function monitorClosure() {
  let bigObject = { data: new Array(1_000_000) };
  const weak = new WeakRef(bigObject);

  const closure = () => {
    const obj = weak.deref();
    if (obj) {
      return obj.data.length;
    }
    return 'collected';
  };

  bigObject = null; // Позволяем GC собрать объект
  return closure;
}
```

### 6.6 Performance: Context allocation

Создание `Context` — это heap allocation. В hot paths это может стать bottleneck:

```js
// Медленный вариант — Context создаётся на каждый вызов:
function processItems(items) {
  return items.map(item => {
    const transform = (x) => x * 2; // Новая функция на каждую итерацию
    // Если transform замыкает что-то из processItems — Context allocation
    return transform(item);
  });
}

// Быстрый вариант — вынести функцию:
const transform = (x) => x * 2; // Одна функция, переиспользуется

function processItemsFast(items) {
  return items.map(transform); // Нет Context allocation в цикле
}
```

**V8: Context specialization в TurboFan**

TurboFan может специализировать код для конкретного `Context`, устраняя indirection:

```js
function makeAdder(n) {
  // Если makeAdder(5) вызывается очень часто (hot),
  // TurboFan может заинлайнить n = 5 прямо в скомпилированный код inner
  return function inner(x) {
    return x + n; // n = 5 может быть встроено как константа
  };
}

const add5 = makeAdder(5);
// После многих вызовов add5(x): TurboFan может скомпилировать как x + 5
for (let i = 0; i < 1_000_000; i++) {
  add5(i); // Hot loop → TurboFan оптимизирует
}
```

### 6.7 Паттерны

**Module Pattern — инкапсуляция через IIFE + closure:**

```js
const UserService = (function() {
  // Приватное состояние — недоступно извне
  let users = [];
  let nextId = 1;

  // Приватная функция
  function validate(user) {
    return user.name && user.email;
  }

  // Публичный API — замыкает приватное состояние
  return {
    add(user) {
      if (!validate(user)) throw new Error('Invalid user');
      users.push({ ...user, id: nextId++ });
    },
    getAll() {
      return [...users]; // Возвращаем копию
    },
    findById(id) {
      return users.find(u => u.id === id);
    },
    get count() {
      return users.length;
    }
  };
})();

UserService.add({ name: "Alice", email: "alice@example.com" });
console.log(UserService.count);   // 1
console.log(UserService.getAll()); // [{ name: "Alice", email: "alice@example.com", id: 1 }]
// console.log(UserService.users);  // undefined — приватное
```

**Фабрика с замыканием:**

```js
function createLogger(prefix, level = 'info') {
  // Приватные данные
  const logs = [];
  const startTime = Date.now();

  return {
    log(message) {
      const entry = {
        timestamp: Date.now() - startTime,
        level,
        message: `[${prefix}] ${message}`
      };
      logs.push(entry);
      console.log(entry.message);
    },
    getLogs() {
      return [...logs];
    },
    setLevel(newLevel) {
      level = newLevel; // Замыкание позволяет изменять замкнутую переменную
    }
  };
}

const dbLogger = createLogger('DB', 'debug');
const apiLogger = createLogger('API');
// Каждый logger имеет свой независимый Context (свои logs, prefix, level)
```

**Каррирование (Currying):**

```js
function curry(fn) {
  return function curried(...args) {
    if (args.length >= fn.length) {
      return fn.apply(this, args);
    }
    // Возвращает замыкание, запомнившее args
    return function(...moreArgs) {
      return curried.apply(this, [...args, ...moreArgs]);
    };
  };
}

const add = curry((a, b, c) => a + b + c);
console.log(add(1)(2)(3));    // 6
console.log(add(1, 2)(3));    // 6
console.log(add(1)(2, 3));    // 6
// Каждый промежуточный вызов создаёт замыкание, хранящее накопленные аргументы
```

**Мемоизация (Memoization):**

```js
function memoize(fn) {
  const cache = new Map(); // Замкнута — живёт пока жива мемоизированная функция

  return function(...args) {
    const key = JSON.stringify(args);
    if (cache.has(key)) {
      return cache.get(key);
    }
    const result = fn.apply(this, args);
    cache.set(key, result);
    return result;
  };
}

const fibonacci = memoize(function fib(n) {
  if (n <= 1) return n;
  return fibonacci(n - 1) + fibonacci(n - 2);
});

console.log(fibonacci(50)); // 12586269025 — мгновенно благодаря кешу
// Без мемоизации: ~2^50 вызовов (непрактично)
```

**Инкапсуляция с контролем доступа:**

```js
function createBankAccount(initialBalance) {
  let balance = initialBalance;
  const transactions = [];

  function recordTransaction(type, amount) {
    transactions.push({
      type,
      amount,
      balance,
      date: new Date()
    });
  }

  return Object.freeze({
    deposit(amount) {
      if (amount <= 0) throw new Error('Amount must be positive');
      balance += amount;
      recordTransaction('deposit', amount);
    },
    withdraw(amount) {
      if (amount <= 0) throw new Error('Amount must be positive');
      if (amount > balance) throw new Error('Insufficient funds');
      balance -= amount;
      recordTransaction('withdrawal', amount);
    },
    getBalance() {
      return balance;
    },
    getStatement() {
      return [...transactions];
    }
  });
}

const account = createBankAccount(1000);
account.deposit(500);
account.withdraw(200);
console.log(account.getBalance()); // 1300
// account.balance — undefined (нет прямого доступа)
// Object.freeze предотвращает добавление свойств
```

### 6.8 Closure vs Class

Оба подхода решают задачу инкапсуляции и управления состоянием. Trade-offs:

**Closure-based:**

```js
function createStack() {
  const items = []; // Истинно приватное — невозможно добраться извне

  return {
    push(item) { items.push(item); },
    pop() { return items.pop(); },
    peek() { return items[items.length - 1]; },
    get size() { return items.length; },
    [Symbol.iterator]() { return items[Symbol.iterator](); }
  };
}

const stack = createStack();
stack.push(1);
stack.push(2);
console.log(stack.size);    // 2
console.log([...stack]);    // [1, 2]
// stack.items — undefined (нет доступа)
```

**Class-based (с #private, ES2022):**

```js
class Stack {
  #items = []; // Приватное поле (синтаксис #)

  push(item) { this.#items.push(item); }
  pop() { return this.#items.pop(); }
  peek() { return this.#items[this.#items.length - 1]; }
  get size() { return this.#items.length; }
  [Symbol.iterator]() { return this.#items[Symbol.iterator](); }
}

const stack = new Stack();
stack.push(1);
// stack.#items — SyntaxError: Private field
```

**Сравнение:**

| Критерий | Closure | Class |
|---|---|---|
| Приватность | Полная (физически невозможно получить доступ) | `#private` fields (ES2022), до этого — конвенция `_` |
| Память | Каждый экземпляр имеет свои копии методов (в отдельных Context) | Методы на `prototype` — разделяются между экземплярами |
| Наследование | Нет встроенного механизма (композиция) | `extends`, `super` — нативная поддержка |
| `instanceof` | Не работает | Работает |
| Производительность (много экземпляров) | Больше аллокаций (Context + объект с методами на каждый экземпляр) | Меньше аллокаций (методы на прототипе) |
| Сериализация | Функции не сериализуемы (JSON.stringify игнорирует) | Состояние в свойствах — сериализуемо |
| Tree-shaking / Minification | Методы — свойства объекта, не minify-ятся | Методы прототипа — тоже не minify-ятся, но `#private` позволяет некоторые оптимизации |

**Когда что использовать:**

- **Closure** — для фабрик, утилит, middleware, когда не нужно наследование и экземпляров немного. Гарантированная инкапсуляция без поддержки `#private`.
- **Class** — для domain entities, компонентов с наследованием, когда создаётся много экземпляров (экономия памяти через `prototype`). Поддержка `instanceof`, `extends`, декораторов (Stage 3+).

```js
// Closure — middleware pipeline:
function createMiddleware(options) {
  const cache = new Map();
  return async function middleware(req, res, next) {
    const key = req.url;
    if (cache.has(key)) {
      return res.send(cache.get(key));
    }
    // Замыкание удобнее класса для stateful middleware
    const result = await next();
    cache.set(key, result);
    return result;
  };
}

// Class — domain entity:
class User {
  #password;
  constructor(name, password) {
    this.name = name;
    this.#password = password;
  }
  checkPassword(attempt) {
    return this.#password === attempt;
  }
}
// 1000 экземпляров User — checkPassword на прототипе, не дублируется
```
