## Механика throw / try / catch / finally

### Completion Records в спецификации

Каждый statement в ECMAScript возвращает **Completion Record** — внутреннюю запись вида `{ [[Type]], [[Value]], [[Target]] }`. Тип может быть `normal`, `break`, `continue`, `return` или `throw`. Когда выполняется `throw`, создаётся Completion Record с `[[Type]]: throw`, и движок начинает **раскрутку стека** (stack unwinding), пока не найдёт ближайший `catch` или программа не завершится.

### Базовый синтаксис

```js
try {
  // код, который может бросить исключение
  const data = JSON.parse(invalidJson);
} catch (error) {
  // обработка ошибки
  console.error('Parsing failed:', error.message);
} finally {
  // выполняется ВСЕГДА — и после return, и после throw, и после нормального выхода
  cleanup();
}
```

### `finally` всегда выполняется — даже после `return`

Блок `finally` выполняется **безусловно**, включая ситуации, когда в `try` или `catch` содержится `return`, `throw` или `break`:

```js
function example() {
  try {
    return 'from try';
  } finally {
    console.log('finally выполнился'); // всегда выполняется
  }
}
// Лог: "finally выполнился"
// Возвращает: "from try"
```

### `finally` может перезаписать возвращаемое значение

Если `finally` содержит собственный `return`, он **перезаписывает** return из `try` или `catch`. Это контринтуитивное поведение и антипаттерн:

```js
function dangerous() {
  try {
    return 1;
  } finally {
    return 2; // перезаписывает return из try
  }
}
dangerous(); // 2, а не 1!

function swallowsError() {
  try {
    throw new Error('critical');
  } finally {
    return 'ok'; // ошибка полностью проглочена!
  }
}
swallowsError(); // 'ok' — ошибка потеряна
```

Согласно спецификации, `finally` Completion Record **заменяет** Completion Record из `try`/`catch`, если `finally` сам возвращает abrupt completion (`return`, `throw`, `break`, `continue`).

### `try` без `catch` (только с `finally`)

Конструкция `try...finally` без `catch` валидна. Ошибка **пробросится дальше** после выполнения `finally`:

```js
function riskyOperation() {
  const resource = acquireResource();
  try {
    doSomethingDangerous(resource);
  } finally {
    resource.release(); // гарантированная очистка
    // ошибка не перехвачена — она уйдёт наверх по стеку
  }
}
```

### Optional catch binding (ES2019)

Начиная с ES2019, параметр `catch` можно опускать, если объект ошибки не нужен:

```js
// ES2019+
try {
  JSON.parse(input);
} catch {
  // параметр error не указан — мы знаем, что парсинг провалился,
  // и детали ошибки нас не интересуют
  return defaultValue;
}

// До ES2019 приходилось писать:
try {
  JSON.parse(input);
} catch (_unused) {
  return defaultValue;
}
```

### Что можно бросать через `throw`

Оператор `throw` принимает **любое значение**, не только объекты `Error`:

```js
throw new Error('сообщение');  // рекомендуемый способ
throw 'строка ошибки';         // антипаттерн — нет stack trace
throw 42;                      // технически валидно, но бессмысленно
throw { code: 'NOT_FOUND' };   // объект без прототипа Error
throw null;                    // валидно, но catch (e) получит null
```

Всегда бросайте экземпляры `Error` или его подклассов — только так вы получите `stack trace` и стандартный интерфейс.

## Типы ошибок

JavaScript имеет встроенную иерархию ошибок. Все наследуют от `Error.prototype`.

### `Error` — базовый класс

```js
const err = new Error('что-то пошло не так');
err.message; // 'что-то пошло не так'
err.name;    // 'Error'
err.stack;   // строка с трассировкой стека (нестандартное, но поддерживается всеми движками)
```

### `TypeError`

Выбрасывается, когда значение не того типа, который ожидается:

```js
null.property;             // TypeError: Cannot read properties of null
undefined();               // TypeError: undefined is not a function
const sym = Symbol();
sym + '';                   // TypeError: Cannot convert a Symbol value to a string

// Часто бросается вручную при валидации аргументов:
function greet(name) {
  if (typeof name !== 'string') {
    throw new TypeError(`Expected string, got ${typeof name}`);
  }
}
```

### `ReferenceError`

Обращение к несуществующей переменной или к переменной в **Temporal Dead Zone**:

```js
console.log(x);        // ReferenceError: x is not defined

console.log(y);        // ReferenceError: Cannot access 'y' before initialization
let y = 10;
```

### `SyntaxError`

Ошибка парсинга — код не соответствует грамматике языка. Возникает **до выполнения**:

```js
eval('function(');       // SyntaxError: Unexpected end of input
JSON.parse('{invalid}'); // SyntaxError: Unexpected token i in JSON at position 1
```

### `RangeError`

Значение вне допустимого диапазона:

```js
new Array(-1);                          // RangeError: Invalid array length
(1.5).toFixed(200);                     // RangeError: toFixed() digits argument must be between 0 and 100
function recursive() { recursive(); }
recursive();                             // RangeError: Maximum call stack size exceeded
```

### `URIError`

Некорректное использование глобальных URI-функций:

```js
decodeURIComponent('%');  // URIError: URI malformed
decodeURI('%E0%A4%A');    // URIError: URI malformed
```

### `EvalError`

Исторический тип — в современном JavaScript движками **не выбрасывается**. Существует для обратной совместимости. `eval()` при ошибках бросает `SyntaxError`.

### `AggregateError` (ES2021)

Контейнер для **нескольких ошибок одновременно**. Используется `Promise.any()`:

```js
const errors = [
  new Error('first'),
  new TypeError('second'),
  new RangeError('third'),
];

const aggErr = new AggregateError(errors, 'All promises rejected');
aggErr.message; // 'All promises rejected'
aggErr.errors;  // [Error, TypeError, RangeError]

// Promise.any бросает AggregateError, если все промисы отклонены:
try {
  await Promise.any([
    fetch('/api-1'),
    fetch('/api-2'),
    fetch('/api-3'),
  ]);
} catch (err) {
  if (err instanceof AggregateError) {
    for (const e of err.errors) {
      console.error(e.message);
    }
  }
}
```

### Свойство `.cause` (ES2022)

Позволяет **связывать ошибки в цепочку**, сохраняя оригинальную причину:

```js
async function fetchUser(id) {
  try {
    const response = await fetch(`/api/users/${id}`);
    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`);
    }
    return await response.json();
  } catch (err) {
    // Оборачиваем низкоуровневую ошибку в доменную, сохраняя cause
    throw new Error(`Failed to fetch user ${id}`, { cause: err });
  }
}

try {
  await fetchUser(42);
} catch (err) {
  console.error(err.message);       // 'Failed to fetch user 42'
  console.error(err.cause.message); // 'HTTP 500' или 'Failed to fetch'
}
```

## Кастомные ошибки

### Правильное наследование от `Error`

```js
class AppError extends Error {
  constructor(message, options) {
    super(message, options); // передаём options для поддержки cause
    this.name = 'AppError';

    // V8-специфичный метод: убирает конструктор AppError из stack trace
    if (Error.captureStackTrace) {
      Error.captureStackTrace(this, AppError);
    }
  }
}

class NotFoundError extends AppError {
  constructor(entity, id, options) {
    super(`${entity} with id ${id} not found`, options);
    this.name = 'NotFoundError';
    this.statusCode = 404;
    this.entity = entity;
    this.entityId = id;

    if (Error.captureStackTrace) {
      Error.captureStackTrace(this, NotFoundError);
    }
  }
}

class ValidationError extends AppError {
  constructor(fields, options) {
    super('Validation failed', options);
    this.name = 'ValidationError';
    this.statusCode = 400;
    this.fields = fields; // { email: 'Invalid format', age: 'Must be positive' }

    if (Error.captureStackTrace) {
      Error.captureStackTrace(this, ValidationError);
    }
  }
}
```

### Иерархия ошибок для приложения

```
Error
└── AppError (базовый для приложения)
    ├── NotFoundError     (404)
    ├── ValidationError   (400)
    ├── UnauthorizedError  (401)
    ├── ForbiddenError     (403)
    └── ConflictError      (409)
```

### `instanceof` проверка

```js
try {
  await getUser(id);
} catch (err) {
  if (err instanceof NotFoundError) {
    res.status(404).json({ error: err.message });
  } else if (err instanceof ValidationError) {
    res.status(400).json({ error: err.message, fields: err.fields });
  } else {
    // Неожиданная ошибка — логируем и возвращаем 500
    logger.error('Unexpected error', err);
    res.status(500).json({ error: 'Internal server error' });
  }
}
```

### Когда бросать, а когда возвращать `Result`

**Бросать (`throw`)** — для исключительных ситуаций, которые нарушают нормальный поток:
- Сетевая недоступность
- Невалидные аргументы (нарушение контракта функции)
- Отсутствие обязательного ресурса

**Возвращать `Result`** — для ожидаемых «неудач», которые являются частью бизнес-логики:
- Пользователь не найден при поиске
- Валидация формы
- Парсинг пользовательского ввода

```js
// Result type через дискриминированный union
function parseAge(input) {
  const num = Number(input);
  if (Number.isNaN(num) || num < 0 || num > 150) {
    return { ok: false, error: 'Invalid age' };
  }
  return { ok: true, value: num };
}

const result = parseAge(userInput);
if (!result.ok) {
  showFieldError(result.error);
} else {
  saveAge(result.value);
}
```

## Ошибки в асинхронном коде

### `try/catch` не ловит ошибки в `setTimeout` / `setInterval`

Колбэки макро-тасков выполняются в **другом стеке вызовов**:

```js
// НЕ РАБОТАЕТ — catch никогда не сработает
try {
  setTimeout(() => {
    throw new Error('async error');
  }, 100);
} catch (err) {
  // сюда мы не попадём
}

// Правильный подход — обрабатывать внутри колбэка:
setTimeout(() => {
  try {
    riskyOperation();
  } catch (err) {
    handleError(err);
  }
}, 100);
```

### `try/catch` с `async/await`

`await` «разворачивает» rejected Promise, превращая rejection в синхронный `throw`:

```js
async function loadData() {
  try {
    const resp = await fetch('/api/data');
    const data = await resp.json();
    return data;
  } catch (err) {
    // Ловит и сетевые ошибки (fetch rejected),
    // и ошибки парсинга JSON
    console.error('Failed to load data:', err);
    throw err; // пробрасываем дальше
  }
}
```

### Unhandled Promise Rejection

Если Promise отклоняется и нет обработчика `.catch()`, возникает **unhandled rejection**:

```js
// ОПАСНО — unhandled rejection
async function init() {
  const data = await fetchData(); // если упадёт — rejection утечёт
}
init(); // вызов без .catch()

// ПРАВИЛЬНО:
init().catch(err => {
  console.error('Init failed:', err);
  process.exit(1);
});
```

### Глобальные обработчики в браузере

```js
// Ловит синхронные ошибки и ошибки из тегов <script>
window.onerror = function (message, source, lineno, colno, error) {
  reportToSentry({ message, source, lineno, colno, stack: error?.stack });
  return true; // предотвращает вывод в консоль
};

// Ловит unhandled Promise rejections
window.addEventListener('unhandledrejection', (event) => {
  console.error('Unhandled rejection:', event.reason);
  event.preventDefault(); // предотвращает вывод в консоль
});

// Ловит Promise rejections, которые были обработаны с опозданием
window.addEventListener('rejectionhandled', (event) => {
  console.log('Rejection handled late:', event.reason);
});
```

### Глобальные обработчики в Node.js

```js
// Необработанное исключение — процесс в неопределённом состоянии
process.on('uncaughtException', (err, origin) => {
  logger.fatal('Uncaught exception', { error: err, origin });
  // Рекомендуется: логирование, flush, и ЗАВЕРШЕНИЕ процесса
  // Продолжение работы после uncaughtException опасно — состояние может быть повреждено
  process.exit(1);
});

// Необработанный rejection — с Node.js 15+ завершает процесс по умолчанию
process.on('unhandledRejection', (reason, promise) => {
  logger.error('Unhandled rejection', { reason });
  // В production — завершить процесс, пусть оркестратор перезапустит
  process.exit(1);
});
```

### Ошибки в `Promise.all` vs `Promise.allSettled`

```js
// Promise.all — fail-fast: первый rejection отклоняет весь результат
try {
  const [users, orders] = await Promise.all([
    fetchUsers(),
    fetchOrders(), // если упадёт — users тоже потеряны
  ]);
} catch (err) {
  // err — первый отклонённый промис
}

// Promise.allSettled — никогда не reject'ится, возвращает статус каждого
const results = await Promise.allSettled([fetchUsers(), fetchOrders()]);
for (const result of results) {
  if (result.status === 'fulfilled') {
    process(result.value);
  } else {
    logError(result.reason);
  }
}
```

## Stack trace

### Свойство `.stack`

Свойство `stack` не стандартизировано в ECMAScript, но поддерживается **всеми основными движками**. Формат зависит от движка:

```js
// V8 (Chrome, Node.js):
// Error: something went wrong
//     at functionName (file.js:10:15)
//     at otherFunction (file.js:20:3)

// SpiderMonkey (Firefox):
// functionName@file.js:10:15
// otherFunction@file.js:20:3

// JavaScriptCore (Safari):
// functionName@file.js:10:15
// otherFunction@file.js:20:3
```

### `Error.captureStackTrace()` (V8)

Статический метод V8, позволяющий контролировать, откуда начинается stack trace:

```js
class HttpError extends Error {
  constructor(statusCode, message) {
    super(message);
    this.name = 'HttpError';
    this.statusCode = statusCode;

    // Второй аргумент — функция-конструктор, которая будет ИСКЛЮЧЕНА
    // из stack trace (и все фреймы выше неё тоже).
    // Это убирает внутренности конструктора из трассировки.
    if (Error.captureStackTrace) {
      Error.captureStackTrace(this, HttpError);
    }
  }
}

// Без captureStackTrace: стек начинается внутри конструктора HttpError
// С captureStackTrace: стек начинается с места, где был вызван new HttpError(...)
```

### Очистка stack trace от шума

Для библиотек и фреймворков полезно убирать внутренние фреймы:

```js
function createError(message) {
  const err = new Error(message);
  // Убираем createError из стека — пользователь видит только свой код
  if (Error.captureStackTrace) {
    Error.captureStackTrace(err, createError);
  }
  return err;
}

// В Node.js можно настроить Error.prepareStackTrace для полной кастомизации:
Error.prepareStackTrace = (err, structuredStack) => {
  // structuredStack — массив CallSite объектов
  return structuredStack
    .filter(frame => !frame.getFileName()?.includes('node_modules'))
    .map(frame => `  at ${frame.getFunctionName() || '<anonymous>'} (${frame.getFileName()}:${frame.getLineNumber()})`)
    .join('\n');
};
```

### Async stack traces

По умолчанию, stack trace теряется при пересечении границ асинхронных операций. Современные движки поддерживают **async stack traces** (включены по умолчанию в V8 с Chrome 73+):

```js
async function inner() {
  throw new Error('deep error');
}

async function middle() {
  await inner();
}

async function outer() {
  await middle();
}

outer().catch(err => console.error(err.stack));
// С async stack traces вы увидите полную цепочку:
// Error: deep error
//     at inner (file.js:2:9)
//     at async middle (file.js:6:3)
//     at async outer (file.js:10:3)
```

### `Error.stackTraceLimit` (V8)

```js
// По умолчанию V8 сохраняет 10 фреймов
Error.stackTraceLimit = 50; // увеличиваем для отладки

Error.stackTraceLimit = 0;   // отключаем сбор stack trace (минимальный прирост производительности)

Error.stackTraceLimit = Infinity; // все фреймы (осторожно с памятью)
```

## Паттерны обработки ошибок

### Sentinel values

Возврат специального значения вместо бросания исключения. Примеры в стандартной библиотеке:

```js
const index = array.indexOf('x');   // -1 если не найден (sentinel)
const parsed = parseInt('abc');      // NaN если не распарсилось (sentinel)
const match = str.match(/regex/);    // null если нет совпадения (sentinel)
```

Проблема sentinel values — их легко забыть проверить, и они «протекают» через вычисления:

```js
// Баг: NaN протекает
const price = parseInt(userInput);  // NaN если ввод невалиден
const total = price * quantity;      // NaN — тихо распространяется
saveOrder(total);                    // сохраняем NaN в базу данных
```

### Result / Either монада

Функциональный подход — каждая операция явно возвращает успех или ошибку:

```js
// Простейшая реализация
class Result {
  #ok; #value; #error;

  constructor(ok, value, error) {
    this.#ok = ok;
    this.#value = value;
    this.#error = error;
    Object.freeze(this);
  }

  static ok(value) { return new Result(true, value, null); }
  static err(error) { return new Result(false, null, error); }

  isOk() { return this.#ok; }
  isErr() { return !this.#ok; }

  unwrap() {
    if (this.#ok) return this.#value;
    throw new Error(`Called unwrap on Err: ${this.#error}`);
  }

  unwrapOr(fallback) {
    return this.#ok ? this.#value : fallback;
  }

  map(fn) {
    return this.#ok ? Result.ok(fn(this.#value)) : this;
  }

  flatMap(fn) {
    return this.#ok ? fn(this.#value) : this;
  }
}

// Использование:
function divide(a, b) {
  if (b === 0) return Result.err('Division by zero');
  return Result.ok(a / b);
}

const result = divide(10, 0);
const display = result.map(v => `Result: ${v}`).unwrapOr('Error occurred');
```

### Error Boundaries (React-паттерн в общем контексте)

Изоляция ошибки в определённой области, чтобы она не «ронала» всё приложение:

```js
// Обёртка для безопасного вызова
function safeBoundary(fn, fallback) {
  try {
    const result = fn();
    // Если result — Promise, оборачиваем и его
    if (result && typeof result.then === 'function') {
      return result.catch(err => {
        logError(err);
        return fallback;
      });
    }
    return result;
  } catch (err) {
    logError(err);
    return fallback;
  }
}

// Express middleware как error boundary:
function asyncHandler(fn) {
  return (req, res, next) => {
    Promise.resolve(fn(req, res, next)).catch(next);
  };
}

app.get('/users/:id', asyncHandler(async (req, res) => {
  const user = await getUser(req.params.id);
  res.json(user);
}));

// Централизованный обработчик — единственное место, где ошибки превращаются в HTTP-ответы
app.use((err, req, res, next) => {
  if (err instanceof AppError) {
    res.status(err.statusCode).json({ error: err.message });
  } else {
    logger.error('Unhandled error in request', { err, url: req.url });
    res.status(500).json({ error: 'Internal server error' });
  }
});
```

### Fail Fast vs Defensive Programming

**Fail Fast** — обнаруживаем проблему как можно раньше и сразу бросаем:

```js
function processOrder(order) {
  // Проверки в начале функции — fail fast
  if (!order) throw new TypeError('order is required');
  if (!order.items?.length) throw new ValidationError({ items: 'at least one item required' });
  if (order.total < 0) throw new RangeError('total cannot be negative');

  // Основная логика — уверены, что данные валидны
  return submitOrder(order);
}
```

**Defensive Programming** — пытаемся продолжить работу при проблемах:

```js
function processOrder(order) {
  if (!order) return null;
  const items = order.items ?? [];
  const total = Math.max(0, order.total ?? 0);

  if (items.length === 0) return { status: 'empty' };

  return submitOrder({ ...order, items, total });
}
```

Правило: **fail fast для программистских ошибок** (нарушение контракта API), **defensive для пользовательских данных** (ввод формы, внешние данные).

### Стратегии восстановления после ошибок

```js
// 1. Retry с экспоненциальной задержкой
async function fetchWithRetry(url, maxRetries = 3) {
  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      return await fetch(url);
    } catch (err) {
      if (attempt === maxRetries) throw err;
      const delay = Math.min(1000 * 2 ** attempt, 30000);
      await new Promise(r => setTimeout(r, delay));
    }
  }
}

// 2. Fallback к альтернативному источнику
async function getData(key) {
  try {
    return await primaryCache.get(key);
  } catch {
    try {
      return await secondaryCache.get(key);
    } catch {
      return await database.get(key);
    }
  }
}

// 3. Circuit Breaker
class CircuitBreaker {
  #failureCount = 0;
  #lastFailureTime = 0;
  #state = 'CLOSED'; // CLOSED | OPEN | HALF_OPEN

  constructor(threshold = 5, resetTimeout = 30000) {
    this.threshold = threshold;
    this.resetTimeout = resetTimeout;
  }

  async call(fn) {
    if (this.#state === 'OPEN') {
      if (Date.now() - this.#lastFailureTime > this.resetTimeout) {
        this.#state = 'HALF_OPEN';
      } else {
        throw new Error('Circuit breaker is OPEN');
      }
    }

    try {
      const result = await fn();
      this.#onSuccess();
      return result;
    } catch (err) {
      this.#onFailure();
      throw err;
    }
  }

  #onSuccess() {
    this.#failureCount = 0;
    this.#state = 'CLOSED';
  }

  #onFailure() {
    this.#failureCount++;
    this.#lastFailureTime = Date.now();
    if (this.#failureCount >= this.threshold) {
      this.#state = 'OPEN';
    }
  }
}
```

## Performance

### Стоимость `throw` vs `return`

Операция `throw` **значительно дороже** `return` — движок должен:

1. Создать объект `Error` (включая сбор stack trace — самая дорогая часть)
2. Выполнить раскрутку стека (stack unwinding)
3. Найти подходящий `catch`

```js
// Бенчмарк (V8, приблизительные числа):
// return value:     ~1 наносекунда
// throw + catch:    ~5,000–10,000 наносекунд (из-за stack trace)
// new Error() без throw: ~3,000–7,000 наносекунд (почти вся стоимость — stack trace)

// Если нужен Error без stack trace (для performance-critical кода):
const errorNoStack = Object.assign(Object.create(Error.prototype), {
  message: 'fast error',
  name: 'FastError',
});
```

### Стоимость `try/catch` блока

В современных движках (V8 TurboFan) сам блок `try/catch` **не мешает оптимизации**, если `catch` не срабатывает:

```js
// V8 TurboFan оптимизирует try/catch на happy path
// Стоимость try/catch без исключений: практически нулевая
function optimized() {
  try {
    return heavyComputation(); // нормально JIT-компилируется
  } catch (e) {
    return fallback();
  }
}
```

Исторически (до TurboFan, в Crankshaft) `try/catch` **деоптимизировал** всю функцию. В современном V8 это давно не так.

### Почему `throw` для control flow — антипаттерн

```js
// АНТИПАТТЕРН: throw как goto
function findUser(users, id) {
  try {
    users.forEach(user => {
      if (user.id === id) {
        throw user; // «бросаем» найденного пользователя — это throw для control flow
      }
    });
    return null;
  } catch (user) {
    return user;
  }
}

// ПРАВИЛЬНО:
function findUser(users, id) {
  return users.find(user => user.id === id) ?? null;
}
```

Причины, почему это антипаттерн:

1. **Performance**: `throw` на 3-4 порядка медленнее `return`
2. **Читаемость**: `throw` сигнализирует об ошибке, а не о нормальном результате — вводит в заблуждение
3. **Отладка**: инструменты типа «Break on all exceptions» будут останавливаться на каждом «результате»
4. **Композиция**: невозможно отличить «нормальный» throw от реальной ошибки в catch

### Рекомендации по производительности

```js
// 1. Не создавайте Error заранее «на всякий случай»
// Плохо:
function validate(x) {
  const err = new Error('invalid'); // stack trace собирается ЗДЕСЬ, даже если не нужен
  if (x < 0) throw err;
  return x;
}

// Хорошо:
function validate(x) {
  if (x < 0) throw new Error('invalid'); // stack trace только при ошибке
  return x;
}

// 2. Для hot paths рассмотрите Result вместо throw
// 3. Error.stackTraceLimit = 0 в production для критичного к латентности кода
// 4. Переиспользуйте объекты ошибок только если не нужен актуальный stack trace
```
