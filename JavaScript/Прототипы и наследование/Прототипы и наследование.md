## 1. Внутренний слот `[[Prototype]]` и механика V8

Каждый объект в JavaScript имеет внутренний слот `[[Prototype]]` (определён спецификацией ECMAScript) -- это ссылка на другой объект или `null`. Этот слот **не является свойством** объекта, к нему нельзя обратиться напрямую из кода -- доступ предоставляется через `Object.getPrototypeOf()` и `Reflect.getPrototypeOf()`.

### Hidden Classes (Shapes / Maps) в V8

V8 не хранит объекты как простые hash maps. Вместо этого используется система **hidden classes** (в терминологии V8 -- `Map`, в SpiderMonkey -- `Shape`):

- При создании объекта V8 назначает ему `hidden class` -- описание структуры (какие свойства, в каком порядке, на каких смещениях в памяти)
- Объекты с одинаковой структурой разделяют один `hidden class`, что позволяет V8 генерировать оптимизированный машинный код
- `[[Prototype]]` является частью `hidden class` -- это критически важно для понимания производительности

```js
// Оба объекта разделяют один hidden class, т.к. у них идентичная структура
// и одинаковый [[Prototype]] (Object.prototype)
const a = { x: 1, y: 2 };
const b = { x: 3, y: 4 };

// Теперь V8 создаст НОВЫЙ hidden class для a,
// потому что изменился его [[Prototype]]
Object.setPrototypeOf(a, { z: 10 });
// a и b больше НЕ разделяют hidden class
```

### Inline Caches (IC) и прототипы

`Inline cache` -- механизм, которым V8 запоминает результат property lookup, чтобы не повторять поиск по цепочке прототипов при каждом обращении:

- **Monomorphic IC** -- кеш видел только один `hidden class`. Самый быстрый путь: прямой доступ по смещению в памяти
- **Polymorphic IC** -- кеш видел 2-4 разных `hidden class`. Линейный поиск по небольшому массиву
- **Megamorphic IC** -- кеш видел >4 `hidden class`. Фоллбэк на generic hash lookup, значительная деградация производительности

```js
function getX(obj) {
  return obj.x; // IC здесь запоминает hidden class объекта
}

// Monomorphic -- все объекты имеют одинаковый hidden class
const objects = Array.from({ length: 1000 }, () => ({ x: 1, y: 2 }));
objects.forEach(getX); // быстро: IC monomorphic

// Megamorphic -- объекты с разной структурой
const mixed = [
  { x: 1 },
  { x: 1, y: 2 },
  { x: 1, y: 2, z: 3 },
  { a: 0, x: 1 },
  { b: 0, x: 1 },
];
mixed.forEach(getX); // медленнее: IC переходит в megamorphic состояние
```

### Validity cells для прототипов

V8 хранит **validity cells** для каждого прототипа в цепочке. Когда свойство прототипа изменяется, validity cell инвалидируется, и все inline caches, зависящие от этого прототипа, сбрасываются. Это значит, что мутация `prototype` объекта может каскадно деоптимизировать код далеко за пределами точки мутации:

```js
function Foo() {}
Foo.prototype.bar = function() { return 42; };

const instances = Array.from({ length: 10000 }, () => new Foo());

// Все IC для .bar() оптимизированы, используют validity cell
instances.forEach(obj => obj.bar()); // быстро

// Мутация прототипа инвалидирует validity cell
Foo.prototype.baz = function() { return 99; };
// Даже .bar() IC теперь нужно перестраиваться!
```

## 2. `__proto__` vs `.prototype` vs `Object.getPrototypeOf()`

Это три принципиально разных механизма, которые часто путают:

| Механизм | Что делает | Где живёт |
|---|---|---|
| `obj.__proto__` | Аксессор (getter/setter) для `[[Prototype]]` объекта | `Object.prototype.__proto__` |
| `Func.prototype` | Обычное свойство функции-конструктора, становится `[[Prototype]]` для `new Func()` | На самой функции |
| `Object.getPrototypeOf(obj)` | Стандартный метод чтения `[[Prototype]]` | `Object` |

### Почему `__proto__` deprecated

`__proto__` -- это **аксессор** на `Object.prototype`, а не внутренний слот. Это создаёт проблемы:

```js
// __proto__ -- это getter/setter на Object.prototype
const descriptor = Object.getOwnPropertyDescriptor(Object.prototype, '__proto__');
console.log(typeof descriptor.get); // "function"
console.log(typeof descriptor.set); // "function"

// Проблема 1: объекты без Object.prototype в цепочке не имеют __proto__
const bare = Object.create(null);
bare.__proto__ = { x: 1 };
// bare.__proto__ -- это ОБЫЧНОЕ свойство, а не ссылка на прототип!
console.log(Object.getPrototypeOf(bare)); // null (не изменился)
console.log(bare.__proto__); // { x: 1 } (обычное свойство)

// Проблема 2: __proto__ как ключ в объекте-словаре
const dict = {};
dict.__proto__ = "malicious"; // НЕ создаёт свойство, а меняет прототип!
console.log(dict.__proto__); // {} (Object.prototype -- неожиданно)
console.log(Object.keys(dict)); // [] (свойства нет)
```

### Performance implications `Object.setPrototypeOf()`

Изменение `[[Prototype]]` после создания объекта -- одна из самых дорогих операций в V8:

1. **Инвалидация hidden class** -- объект получает новый hidden class, что разрывает его связь со всеми объектами той же "формы"
2. **Деоптимизация скомпилированного кода** -- TurboFan (оптимизирующий компилятор V8) может деоптимизировать функции, которые работали с объектами старого hidden class
3. **Сброс inline caches** -- все IC, видевшие старый hidden class, становятся невалидными
4. **Переход в slow mode** -- в некоторых случаях V8 может перевести объект в "dictionary mode" (медленный hash map вместо быстрого inline storage)

```js
// АНТИ-ПАТТЕРН: изменение прототипа после создания
function create(proto) {
  const obj = {};
  Object.setPrototypeOf(obj, proto); // деоптимизация!
  return obj;
}

// ПРАВИЛЬНО: Object.create задаёт прототип ДО инициализации hidden class
function create(proto) {
  return Object.create(proto);
}
```

Спецификация ECMAScript явно предупреждает: "Изменение `[[Prototype]]` объекта -- очень медленная операция по самой своей природе в любой реализации". Это не баг конкретного движка, а фундаментальное ограничение.

## 3. Прототипная цепочка и property lookup

### Алгоритм поиска свойств

Когда движок выполняет `obj.prop`, происходит следующее:

1. Проверить собственные свойства (`own properties`) объекта `obj`
2. Если не найдено -- перейти к `obj.[[Prototype]]` и проверить его собственные свойства
3. Повторять шаг 2 вверх по цепочке
4. Если достигнут `null` (конец цепочки) -- вернуть `undefined`

```js
const grandparent = { a: 1 };
const parent = Object.create(grandparent);
parent.b = 2;
const child = Object.create(parent);
child.c = 3;

// child -> parent -> grandparent -> Object.prototype -> null

child.c; // 3 (найдено на child, 1 шаг)
child.b; // 2 (найдено на parent, 2 шага)
child.a; // 1 (найдено на grandparent, 3 шага)
child.toString; // function (найдено на Object.prototype, 4 шага)
child.nonexistent; // undefined (прошли всю цепочку до null)
```

### Property shadowing

Когда свойство с одинаковым именем существует на разных уровнях цепочки, ближайшее к объекту свойство "затеняет" остальные:

```js
const proto = {
  value: 'proto',
  get computed() { return 'proto-computed'; }
};

const obj = Object.create(proto);

// Случай 1: shadowing data property -- работает интуитивно
obj.value = 'own';
console.log(obj.value); // 'own' (собственное свойство)
console.log(proto.value); // 'proto' (не изменилось)

// Случай 2: shadowing accessor property -- неочевидное поведение
obj.computed = 'overridden';
// Если прототип содержит SETTER -- вызовется setter, собственное свойство НЕ создастся
// Если setter НЕТ (только getter) -- в strict mode будет TypeError,
// в sloppy mode -- тихий провал (свойство не создастся)
console.log(obj.computed); // 'proto-computed' (getter прототипа!)
console.log(obj.hasOwnProperty('computed')); // false

// Чтобы создать собственное свойство, обходя accessor прототипа:
Object.defineProperty(obj, 'computed', {
  value: 'truly-own',
  writable: true,
  configurable: true,
  enumerable: true
});
console.log(obj.computed); // 'truly-own'
```

### Shadowing и `writable: false`

Ещё один неочевидный edge case -- если свойство в прототипе помечено как `writable: false`:

```js
const proto = {};
Object.defineProperty(proto, 'x', { value: 42, writable: false });

const obj = Object.create(proto);
obj.x = 100; // В strict mode -- TypeError. В sloppy mode -- тихий провал
console.log(obj.x); // 42
console.log(obj.hasOwnProperty('x')); // false (собственное свойство НЕ создано!)

// Обход через defineProperty:
Object.defineProperty(obj, 'x', { value: 100 });
console.log(obj.x); // 100
```

Это поведение часто становится источником багов: `writable: false` в прототипе блокирует создание собственного свойства через обычное присваивание.

### Monomorphic vs Megamorphic property access

С точки зрения V8, производительность `property lookup` напрямую зависит от состояния `inline cache`:

```js
// Monomorphic: все объекты одной "формы"
function process(items) {
  let sum = 0;
  for (const item of items) {
    sum += item.value; // IC: monomorphic -> 1 проверка hidden class
  }
  return sum;
}

// Создаём массив объектов с ОДИНАКОВОЙ структурой
const homogeneous = Array.from({ length: 10000 }, (_, i) => ({ value: i }));
process(homogeneous); // быстро

// Megamorphic: объекты с разной структурой проходят через одну точку доступа
const heterogeneous = [
  { value: 1 },
  { value: 1, extra: true },
  { x: 0, value: 1 },
  { a: 0, b: 0, value: 1 },
  { value: 1, toString: null },
  // ... разные формы
];
process(heterogeneous); // значительно медленнее
```

## 4. `Object.create()` и паттерны создания объектов

### Базовое использование

`Object.create(proto)` создаёт новый объект с `[[Prototype]]` равным `proto`. Это единственный способ задать прототип объекта ДО его создания (что критически важно для производительности):

```js
const animal = {
  speak() {
    return `${this.name} makes a sound`;
  }
};

const dog = Object.create(animal);
dog.name = 'Rex';
dog.speak(); // "Rex makes a sound"

// Эквивалент через конструктор:
// const dog = new Animal(); -- но для этого нужен конструктор
```

### Второй аргумент: property descriptors

`Object.create(proto, propertiesObject)` принимает вторым аргументом объект с `property descriptors` (аналогично `Object.defineProperties`):

```js
const base = {
  greet() { return `Hello, ${this.name}`; }
};

const user = Object.create(base, {
  name: {
    value: 'Alice',
    writable: true,
    enumerable: true,
    configurable: true
  },
  _age: {
    value: 30,
    writable: true,
    enumerable: false, // не появится в for...in и Object.keys
    configurable: false
  },
  age: {
    get() { return this._age; },
    set(val) {
      if (typeof val !== 'number' || val < 0) throw new TypeError('Invalid age');
      this._age = val;
    },
    enumerable: true,
    configurable: false
  }
});

console.log(user.greet()); // "Hello, Alice"
console.log(user.age); // 30
user.age = 25; // OK
user.age = -1; // TypeError: Invalid age
console.log(Object.keys(user)); // ['name', 'age'] -- _age не включён
```

### Паттерн dictionary objects: `Object.create(null)`

Объект без прототипа -- чистый словарь без методов `Object.prototype`:

```js
// Обычный объект наследует от Object.prototype
const regular = {};
console.log(regular.toString); // [Function: toString]
console.log(regular.constructor); // [Function: Object]
console.log('toString' in regular); // true

// Dictionary object -- чистый hash map
const dict = Object.create(null);
console.log(dict.toString); // undefined
console.log('toString' in dict); // false

// Безопасно использовать любые ключи, включая
// имена методов Object.prototype
dict['__proto__'] = 'safe'; // это обычное свойство, не ссылка на прототип
dict['constructor'] = 'also safe';
dict['hasOwnProperty'] = 'still safe';
console.log(Object.keys(dict)); // ['__proto__', 'constructor', 'hasOwnProperty']

// Практическое применение: безопасные lookup tables, кеши, конфигурации
function createCache() {
  const store = Object.create(null);
  return {
    get(key) { return store[key]; },
    set(key, value) { store[key] = value; },
    has(key) { return key in store; } // безопасно, т.к. нет прототипа
  };
}
```

V8 оптимизирует `Object.create(null)` объекты иначе -- они сразу получают словарный hidden class, что делает их эффективными для динамического добавления/удаления свойств.

## 5. Прототипное наследование без классов

### Функции-конструкторы

До ES6 `class` -- основной паттерн наследования:

```js
function Animal(name) {
  this.name = name;
}

Animal.prototype.speak = function() {
  return `${this.name} makes a sound`;
};

function Dog(name, breed) {
  Animal.call(this, name); // вызов "родительского" конструктора
  this.breed = breed;
}

// Настройка цепочки прототипов
Dog.prototype = Object.create(Animal.prototype);
Dog.prototype.constructor = Dog; // восстанавливаем ссылку на конструктор

Dog.prototype.bark = function() {
  return `${this.name} barks`;
};

const rex = new Dog('Rex', 'Shepherd');
rex.speak(); // "Rex makes a sound" (делегировано Animal.prototype)
rex.bark();  // "Rex barks" (собственный метод Dog.prototype)
rex instanceof Dog;    // true
rex instanceof Animal; // true

// ОШИБКА: Dog.prototype = Animal.prototype
// Это НЕ наследование -- это разделение одного объекта.
// Добавление метода в Dog.prototype добавит его и в Animal.prototype.
```

### Почему `Dog.prototype = new Animal()` -- анти-паттерн

```js
// НЕПРАВИЛЬНО:
Dog.prototype = new Animal();
// Проблемы:
// 1. Вызывается конструктор Animal без аргументов -- побочные эффекты
// 2. На Dog.prototype появляются instance-свойства (name = undefined)
// 3. Эти свойства будут shadowed при создании Dog, но всё равно занимают память

// ПРАВИЛЬНО:
Dog.prototype = Object.create(Animal.prototype);
// Создаёт чистый объект с правильным [[Prototype]], без побочных эффектов
```

### Parasitic inheritance

Паттерн, при котором новый объект создаётся путём "паразитирования" на существующем:

```js
function createAnimal(name) {
  return { name, speak() { return `${this.name} makes a sound`; } };
}

function createDog(name, breed) {
  const animal = createAnimal(name); // "паразитируем" на фабрике

  // Расширяем объект
  animal.breed = breed;
  animal.bark = function() { return `${this.name} barks`; };

  // Переопределяем метод (shadowing)
  const originalSpeak = animal.speak;
  animal.speak = function() {
    return `${originalSpeak.call(this)} (woof!)`;
  };

  return animal;
}

const rex = createDog('Rex', 'Shepherd');
rex.speak(); // "Rex makes a sound (woof!)"
```

Недостаток: методы создаются заново для каждого экземпляра (нет разделения через прототип), что увеличивает потребление памяти.

### Миксины через `Object.assign`

`Object.assign` копирует **собственные перечислимые** свойства из source в target. Это позволяет реализовать множественное наследование поведения (mixin):

```js
const Serializable = {
  serialize() {
    return JSON.stringify(this);
  },
  deserialize(json) {
    return Object.assign(Object.create(Object.getPrototypeOf(this)), JSON.parse(json));
  }
};

const EventEmitter = {
  _handlers: null,
  on(event, handler) {
    if (!this._handlers) this._handlers = Object.create(null);
    (this._handlers[event] ??= []).push(handler);
  },
  emit(event, ...args) {
    (this._handlers?.[event] ?? []).forEach(fn => fn.apply(this, args));
  }
};

const Validatable = {
  validate() {
    for (const [key, rule] of Object.entries(this._rules ?? {})) {
      if (!rule(this[key])) throw new Error(`Validation failed for ${key}`);
    }
    return true;
  }
};

// Комбинируем миксины
function User(name, email) {
  this.name = name;
  this.email = email;
  this._rules = {
    name: v => typeof v === 'string' && v.length > 0,
    email: v => /\S+@\S+\.\S+/.test(v)
  };
}

Object.assign(User.prototype, Serializable, EventEmitter, Validatable);

const user = new User('Alice', 'alice@example.com');
user.validate(); // true
user.on('save', () => console.log('saved!'));
user.serialize(); // '{"name":"Alice","email":"alice@example.com","_rules":{...}}'
```

**Важно**: `Object.assign` не копирует свойства из прототипной цепочки source, не копирует non-enumerable свойства и не сохраняет property descriptors (все свойства копируются как `writable: true, enumerable: true, configurable: true`).

### Composition vs Inheritance

Прототипное наследование создаёт жёсткую иерархию. Композиция -- более гибкая альтернатива:

```js
// Inheritance: жёсткая иерархия, проблема "гориллы с бананом"
// Dog -> Animal -> LivingThing -> ...
// Нужен только метод speak(), но приходится тянуть всю цепочку

// Composition: собираем поведение из независимых частей
const canSpeak = (state) => ({
  speak: () => `${state.name} says ${state.sound}`
});

const canMove = (state) => ({
  move: (distance) => {
    state.position += distance;
    return `${state.name} moved to ${state.position}`;
  }
});

const canFetch = (state) => ({
  fetch: (item) => `${state.name} fetches ${item}`
});

function createDog(name) {
  const state = { name, sound: 'Woof', position: 0 };
  return Object.assign(
    { get name() { return state.name; } },
    canSpeak(state),
    canMove(state),
    canFetch(state)
  );
}

function createRobot(name) {
  const state = { name, sound: 'Beep', position: 0 };
  return Object.assign(
    { get name() { return state.name; } },
    canSpeak(state),
    canMove(state)
    // робот не умеет fetch -- просто не добавляем
  );
}
```

## 6. Delegation pattern

### Прототипы -- делегирование, а не копирование

Фундаментальное отличие прототипного наследования от классического ООП: в JavaScript нет **копирования** поведения от "класса" к "экземпляру". Вместо этого объект **делегирует** поиск свойств вверх по цепочке прототипов:

```js
const shared = {
  counter: 0,
  increment() {
    this.counter++; // ВАЖНО: this указывает на вызывающий объект, не на shared
  }
};

const a = Object.create(shared);
const b = Object.create(shared);

a.increment();
console.log(a.counter); // 1 (собственное свойство a)
console.log(b.counter); // 0 (делегировано к shared.counter)
console.log(shared.counter); // 0 (не изменился!)

// Что произошло:
// 1. a.increment() -> найден на shared через делегирование
// 2. this === a (не shared!)
// 3. this.counter++ -> чтение a.counter -> делегировано к shared.counter (0)
// 4. a.counter = 0 + 1 -> СОЗДАЁТСЯ собственное свойство на a
```

Это поведение -- `implicit shadowing` -- ключевое следствие делегирования. Метод `increment` "живёт" на `shared`, но при записи `this.counter++` создаётся **новое собственное свойство** на `a`, потому что `this` привязан к `a`.

### OLOO (Objects Linked to Other Objects)

Паттерн, предложенный Кайлом Симпсоном, полностью отказывается от имитации классов:

```js
const Widget = {
  init(id, width, height) {
    this.id = id;
    this.width = width;
    this.height = height;
    return this;
  },
  render() {
    return `<div id="${this.id}" style="width:${this.width}px;height:${this.height}px"></div>`;
  }
};

const Button = Object.create(Widget);

Button.setup = function(id, width, height, label) {
  this.init(id, width, height); // делегирование к Widget.init
  this.label = label;
  return this;
};

Button.render = function() {
  // Можно вызвать "родительский" метод явно
  const html = Widget.render.call(this);
  return html.replace('></div>', `>${this.label}</div>`);
};

// Использование: без new, без class, чистое делегирование
const btn = Object.create(Button).setup('btn-1', 200, 50, 'Click me');
btn.render();
```

### Отличие от классического ООП

В классическом ООП (Java, C++):
- Класс -- это **чертёж**, экземпляр -- **копия** поведения
- Метод физически "принадлежит" каждому экземпляру (или его vtable привязан статически)

В JavaScript:
- Прототип -- это **живой объект**, экземпляр -- **ссылка** на него
- Метод не копируется, а находится через делегирование в runtime
- Изменение прототипа **после** создания экземпляров **влияет** на все экземпляры

```js
function Foo() {}
const a = new Foo();

// Добавляем метод ПОСЛЕ создания экземпляра
Foo.prototype.greet = function() { return 'hello'; };
a.greet(); // "hello" -- метод найден через делегирование

// В Java/C++ это невозможно: поведение класса зафиксировано при компиляции
```

## 7. Performance и оптимизации V8

### Длинные прототипные цепочки

Каждый шаг по цепочке -- это дополнительная проверка при property lookup. V8 оптимизирует это через inline caches, но первичный lookup всё равно линейный:

```js
// Глубокая цепочка -- 10 уровней
let current = { value: 'found' };
for (let i = 0; i < 10; i++) {
  current = Object.create(current);
}
current.value; // Поиск пройдёт 10 уровней вверх

// Практическая рекомендация: не более 3-4 уровней наследования
// Object.prototype -> YourBase -> YourChild -> instance
```

### Как V8 оптимизирует prototype lookup

1. **Validity cells**: V8 ассоциирует "validity cell" с каждым прототипом. IC кеширует не только hidden class, но и состояние validity cell. Пока cell валиден, V8 не проверяет цепочку -- сразу возвращает кешированное значение.

2. **Prototype chain checks в оптимизированном коде**: TurboFan (оптимизирующий компилятор) встраивает проверки прототипной цепочки прямо в машинный код:

```js
// TurboFan компилирует это примерно так:
// 1. Проверить hidden class obj === ожидаемый
// 2. Проверить validity cell прототипа
// 3. Если оба OK -> вернуть значение по фиксированному смещению
// 4. Иначе -> деоптимизация, переход в интерпретатор

function getMethod(obj) {
  return obj.method(); // если obj всегда одной формы, это компилируется в ~3 инструкции
}
```

### Что ломает оптимизации

```js
// 1. Object.setPrototypeOf -- полная деоптимизация hidden class
const obj = { x: 1 };
Object.setPrototypeOf(obj, { y: 2 }); // hidden class полностью пересоздаётся

// 2. Мутация свойств прототипа
function Base() {}
Base.prototype.config = { debug: false };

// Изменение свойства прототипа инвалидирует validity cells
Base.prototype.config = { debug: true }; // ВСЕ IC, зависящие от Base.prototype, сброшены

// 3. delete на прототипе -- переводит прототип в dictionary mode
delete Base.prototype.config; // прототип теряет fast mode

// 4. Добавление свойств к Object.prototype
Object.prototype.custom = true; // инвалидирует ВСЕ validity cells в ДВИЖКЕ
// Это затрагивает КАЖДЫЙ объект в программе. Никогда так не делайте.

// 5. Полиморфизм в точках доступа к прототипу
class A { method() { return 1; } }
class B { method() { return 2; } }
class C { method() { return 3; } }
class D { method() { return 4; } }
class E { method() { return 5; } }

function call(obj) { return obj.method(); }

// IC для call() станет megamorphic после 5 разных hidden classes
[new A(), new B(), new C(), new D(), new E()].forEach(call);
```

### Бенчмарк: prototype chain depth impact

```js
function benchPrototypeDepth() {
  const depths = [1, 3, 5, 10, 20];

  for (const depth of depths) {
    let proto = { value: 42 };
    for (let i = 1; i < depth; i++) {
      proto = Object.create(proto);
    }
    const obj = Object.create(proto);

    const start = performance.now();
    let sum = 0;
    for (let i = 0; i < 1_000_000; i++) {
      sum += obj.value; // первый вызов: IC учится. Последующие: IC hit (но с chain check)
    }
    const elapsed = performance.now() - start;
    console.log(`Depth ${depth}: ${elapsed.toFixed(2)}ms`);
  }
}
// Глубина 1-3: примерно одинаково (IC + validity cells оптимизируют)
// Глубина 10+: заметная деградация при первом вызове и при деоптимизациях
```

## 8. Edge cases и подводные камни

### Prototype pollution

Одна из наиболее опасных уязвимостей в JavaScript -- загрязнение прототипа через пользовательский ввод:

```js
// Уязвимый код: рекурсивный merge без валидации ключей
function deepMerge(target, source) {
  for (const key in source) {
    if (typeof source[key] === 'object' && source[key] !== null) {
      if (!target[key]) target[key] = {};
      deepMerge(target[key], source[key]);
    } else {
      target[key] = source[key];
    }
  }
  return target;
}

// Атака:
const malicious = JSON.parse('{"__proto__": {"isAdmin": true}}');
deepMerge({}, malicious);

// Теперь ВСЕ объекты в программе имеют isAdmin === true
const user = {};
console.log(user.isAdmin); // true -- prototype pollution!

// Защита:
// 1. Проверять ключ: if (key === '__proto__' || key === 'constructor' || key === 'prototype') continue;
// 2. Использовать Object.create(null) для target
// 3. Использовать Map вместо plain objects
// 4. Object.freeze(Object.prototype) -- радикально, но ломает некоторые библиотеки
```

### `hasOwnProperty` vs `Object.hasOwn()`

```js
const obj = Object.create(null);
obj.key = 'value';

// hasOwnProperty -- метод Object.prototype, недоступен для Object.create(null)
obj.hasOwnProperty('key'); // TypeError: obj.hasOwnProperty is not a function

// Классический workaround:
Object.prototype.hasOwnProperty.call(obj, 'key'); // true

// Ещё одна проблема: hasOwnProperty можно перезаписать
const tricky = { hasOwnProperty: () => false, x: 1 };
tricky.hasOwnProperty('x'); // false (вызвали перезаписанный метод!)
Object.prototype.hasOwnProperty.call(tricky, 'x'); // true

// Object.hasOwn() (ES2022) -- статический метод, решает обе проблемы
Object.hasOwn(obj, 'key'); // true
Object.hasOwn(tricky, 'x'); // true
// Не зависит от прототипной цепочки, нельзя перезаписать через shadowing
```

### Оператор `in` и прототипы

`in` проверяет всю прототипную цепочку, в отличие от `hasOwnProperty` / `Object.hasOwn`:

```js
const proto = { inherited: true };
const obj = Object.create(proto);
obj.own = true;

'own' in obj;       // true (собственное)
'inherited' in obj; // true (из прототипа)
'toString' in obj;  // true (из Object.prototype)

Object.hasOwn(obj, 'own');       // true
Object.hasOwn(obj, 'inherited'); // false
Object.hasOwn(obj, 'toString'); // false

// Практический совет: для проверки "есть ли свойство у объекта"
// почти всегда нужен Object.hasOwn(), а не `in`
```

### `for...in` и enumerable свойства в цепочке

`for...in` обходит **все перечислимые свойства** объекта, включая унаследованные через прототипную цепочку:

```js
const proto = { inherited: 'yes' };
Object.defineProperty(proto, 'nonEnum', {
  value: 'hidden',
  enumerable: false
});

const obj = Object.create(proto);
obj.own = 'mine';

for (const key in obj) {
  console.log(key);
}
// Выведет: 'own', 'inherited'
// НЕ выведет: 'nonEnum' (enumerable: false)
// НЕ выведет: методы Object.prototype (тоже non-enumerable)

// Фильтрация только собственных свойств (устаревший паттерн):
for (const key in obj) {
  if (Object.hasOwn(obj, key)) {
    console.log(key); // только 'own'
  }
}

// Современные альтернативы, которые НЕ затрагивают прототипную цепочку:
Object.keys(obj);    // ['own'] -- только собственные enumerable
Object.values(obj);  // ['mine']
Object.entries(obj); // [['own', 'mine']]
Object.getOwnPropertyNames(obj); // ['own'] -- собственные, включая non-enumerable
Object.getOwnPropertySymbols(obj); // [] -- собственные Symbol-ключи
Reflect.ownKeys(obj); // ['own'] -- все собственные ключи (strings + symbols)
```

### `instanceof` и подмена прототипа

`instanceof` проверяет, находится ли `Constructor.prototype` где-либо в цепочке `[[Prototype]]` объекта:

```js
function Foo() {}
const foo = new Foo();

foo instanceof Foo; // true
// Эквивалент: Foo.prototype находится в цепочке [[Prototype]] foo

// Подмена прототипа ломает instanceof:
Foo.prototype = {};
foo instanceof Foo; // false! Старый Foo.prototype больше не в цепочке

// Symbol.hasInstance позволяет кастомизировать поведение instanceof:
class EvenNumber {
  static [Symbol.hasInstance](value) {
    return typeof value === 'number' && value % 2 === 0;
  }
}

4 instanceof EvenNumber;  // true
3 instanceof EvenNumber;  // false
'4' instanceof EvenNumber; // false
```

### Замораживание прототипа и его последствия

```js
// Object.freeze(Object.prototype) -- защита от prototype pollution
Object.freeze(Object.prototype);

// Теперь нельзя добавить/изменить/удалить свойства Object.prototype
Object.prototype.polluted = true; // TypeError в strict mode, тихий провал в sloppy

// Побочные эффекты:
// - Некоторые полифилы перестанут работать (они добавляют методы в прототипы)
// - Object.prototype.toString нельзя переопределить (что ломает некоторые deep equal реализации)
// - Frozen объекты имеют свой hidden class, что может повлиять на IC

// Более мягкий вариант -- Object.seal:
// Object.seal(Object.prototype) запрещает добавление новых свойств,
// но позволяет изменять значения существующих writable свойств
```

### `Object.getPrototypeOf()` на примитивах

```js
// Примитивы автоматически оборачиваются (autoboxing) для получения прототипа
Object.getPrototypeOf(42);        // Number.prototype
Object.getPrototypeOf('hello');   // String.prototype
Object.getPrototypeOf(true);      // Boolean.prototype
Object.getPrototypeOf(Symbol());  // Symbol.prototype
Object.getPrototypeOf(42n);       // BigInt.prototype

// null и undefined -- TypeError
Object.getPrototypeOf(null);      // TypeError
Object.getPrototypeOf(undefined); // TypeError
```

### Прототип и JSON

```js
const proto = { type: 'default' };
const obj = Object.create(proto);
obj.name = 'test';

// JSON.stringify игнорирует прототипную цепочку -- сериализует только own enumerable
JSON.stringify(obj); // '{"name":"test"}' -- type из прототипа не включён

// JSON.parse всегда создаёт объекты с Object.prototype
const parsed = JSON.parse('{"x": 1}');
Object.getPrototypeOf(parsed) === Object.prototype; // true
```

## Итого: ключевые принципы для архитектурных решений

1. **Задавайте прототип при создании объекта** (`Object.create`, `new`, `class`), а не после (`Object.setPrototypeOf`) -- иначе V8 деоптимизирует hidden classes
2. **Держите прототипные цепочки короткими** (3-4 уровня максимум) и **неизменяемыми** после инициализации
3. **Не мутируйте встроенные прототипы** (`Object.prototype`, `Array.prototype`) -- это инвалидирует все validity cells в движке
4. **Используйте `Object.create(null)` для словарей** -- защита от prototype pollution и предсказуемое поведение `in` и `for...in`
5. **Предпочитайте `Object.hasOwn()` вместо `hasOwnProperty`** -- работает с `Object.create(null)` и не может быть переопределён shadowing
6. **Помните о делегировании**: прототипы -- это не копирование, а живая ссылка. Мутация прототипа отражается на всех "наследниках"
7. **Для множественного наследования** используйте миксины (`Object.assign`) или композицию, а не длинные цепочки
8. **Стремитесь к мономорфизму** в hot paths -- объекты одной "формы" проходящие через одну функцию дают V8 возможность максимально оптимизировать IC
