## `var`

### Функциональная область видимости

`var` привязывается к ближайшей **функции** (или к глобальному контексту, если объявлен вне функции).
Блоки `if`, `for`, `while`, `{}` **не создают** для `var` отдельную область видимости.

```js
function example() {
  if (true) {
    var x = 10;
  }
  console.log(x); // 10 — var игнорирует блок if
}

for (var i = 0; i < 3; i++) {}
console.log(i); // 3 — var утекает из блока for

// Сравните с let:
for (let j = 0; j < 3; j++) {}
console.log(j); // ReferenceError: j is not defined
```

В теле функции `var` виден **повсюду**, независимо от того, где объявлен:

```js
function demo() {
  console.log(a); // undefined (hoisted)
  if (false) {
    var a = 42;   // этот код НИКОГДА не выполняется
  }
  console.log(a); // undefined — но переменная существует!
}
```

### Hoisting `var`

При входе в execution context движок выполняет **два шага** для `var`:
1. **Declaration** — имя переменной регистрируется в `VariableEnvironment`
2. **Initialization** — переменная сразу инициализируется значением `undefined`

Assignment (присваивание) остаётся на месте в коде.

```js
console.log(a); // undefined (не ReferenceError!)
var a = 5;
console.log(a); // 5

// Движок интерпретирует это так:
var a;            // declaration + initialization = undefined
console.log(a);   // undefined
a = 5;            // assignment
console.log(a);   // 5
```

Для функций, объявленных через `Function Declaration`, hoisting поднимает и декларацию, и тело:

```js
greet(); // "Hello!" — работает
function greet() { console.log("Hello!"); }

// Но var + function expression — поднимается только var:
sayHi(); // TypeError: sayHi is not a function
var sayHi = function() { console.log("Hi!"); };
// sayHi = undefined в момент вызова → undefined() → TypeError
```

### Повторное объявление

`var` позволяет объявлять одну и ту же переменную многократно без ошибки:

```js
var x = 1;
var x = 2;
var x = 3;
console.log(x); // 3 — последнее присвоение побеждает

// В одном scope — никакой ошибки. Это design flaw языка.
// Именно из-за этого были введены let и const.
```

### Глобальный `var` и `window`

`var` в глобальном контексте создаёт **свойство объекта** `window` (в браузере) или `global` (в Node.js до ESM).
Но это свойство имеет `configurable: false`, поэтому `delete` не работает:

```js
var globalVar = "hello";

console.log(window.globalVar);    // "hello"
console.log(globalVar === window.globalVar); // true

// configurable: false
Object.getOwnPropertyDescriptor(window, "globalVar");
// { value: "hello", writable: true, enumerable: true, configurable: false }

delete window.globalVar; // false — не удаляется
console.log(window.globalVar); // "hello" — всё ещё здесь

// Сравните с прямым присвоением window property:
window.directProp = "world";
Object.getOwnPropertyDescriptor(window, "directProp");
// { value: "world", writable: true, enumerable: true, configurable: true }
delete window.directProp; // true — удаляется
```

> В `strict mode` попытка присвоить необъявленную переменную выбросит `ReferenceError`,
> а не создаст свойство `window`. Без strict mode — создаст `configurable: true` свойство.

### IIFE как изоляция

До ES6 единственным способом создать scope для `var` было **IIFE** (Immediately Invoked Function Expression):

```js
// Проблема: загрязнение глобальной области
var counter = 0;
var prefix = "item_";
// Эти переменные видны всему скрипту

// Решение: IIFE
(function() {
  var counter = 0;
  var prefix = "item_";
  // Изолированы внутри функции
})();

console.log(typeof counter); // "undefined" — не утекли

// Паттерн «модуль» (до ES6 modules):
var MyModule = (function() {
  var privateVar = 0;

  function privateMethod() {
    return ++privateVar;
  }

  return {
    increment: privateMethod,
    getCount: function() { return privateVar; }
  };
})();

MyModule.increment(); // 1
MyModule.increment(); // 2
MyModule.getCount();  // 2
// privateVar недоступен извне
```

### Классический баг: `for` + `var` + `setTimeout`

Одна из самых известных ловушек JavaScript:

```js
// Ожидание: 0, 1, 2, 3, 4
// Реальность: 5, 5, 5, 5, 5
for (var i = 0; i < 5; i++) {
  setTimeout(function() {
    console.log(i);
  }, 100);
}
// Все колбэки ссылаются на ОДНУ переменную i
// К моменту выполнения setTimeout цикл уже закончился, i === 5
```

**Почему так происходит:**

1. `var i` создаёт одну переменную на весь scope функции (или глобальный)
2. Каждая итерация **не создаёт** новую привязку — все замыкания ссылаются на одну и ту же `i`
3. `setTimeout` откладывает выполнение — к моменту, когда колбэки запустятся, цикл уже завершён
4. `i === 5` (условие `i < 5` ложно при `i === 5` — цикл остановился)

**Исправление через IIFE (ES5):**

```js
for (var i = 0; i < 5; i++) {
  (function(j) {
    setTimeout(function() {
      console.log(j);  // 0, 1, 2, 3, 4
    }, 100);
  })(i); // передаём текущее значение i как аргумент j
}
```

**Исправление через `let` (ES6):**

```js
for (let i = 0; i < 5; i++) {
  setTimeout(function() {
    console.log(i);  // 0, 1, 2, 3, 4
  }, 100);
}
// let создаёт НОВУЮ привязку на КАЖДОЙ итерации
```

## `let`

### Блочная область видимости

`let` привязывается к ближайшему **блоку** `{}` — будь то `if`, `for`, `while`, или просто пара фигурных скобок:

```js
{
  let x = 10;
  console.log(x); // 10
}
console.log(x); // ReferenceError: x is not defined

if (true) {
  let y = 20;
}
console.log(y); // ReferenceError

for (let i = 0; i < 3; i++) {
  // i доступна только здесь
}
console.log(i); // ReferenceError
```

`let` в `for` — особый случай. Спецификация (раздел 14.7.4.2) определяет, что для каждой итерации
создаётся **новое** `LexicalEnvironment` с **копией** текущего значения переменной цикла:

```js
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100);
}
// 0, 1, 2 — каждый колбэк замкнулся на свою копию i
```

### Temporal Dead Zone (TDZ)

`let` (и `const`) **поднимаются** (hoisted), но в отличие от `var`, не инициализируются.
Переменная существует в scope с момента входа в блок, но доступ к ней до строки объявления
вызывает `ReferenceError`. Эта зона между началом scope и строкой объявления — **TDZ**.

```js
{
  // --- TDZ для x начинается здесь ---
  console.log(x); // ReferenceError: Cannot access 'x' before initialization
  // --- TDZ для x ---
  let x = 10;
  // --- TDZ для x закончилась ---
  console.log(x); // 10
}
```

> Обратите внимание на текст ошибки: `"Cannot access 'x' before initialization"` —
> движок **знает** о существовании `x` (hoisting произошёл), но запрещает доступ.
> Это отличается от `ReferenceError: x is not defined` для несуществующих переменных.

#### TDZ в `switch` / `case`

Все `case` делят **один** блок scope:

```js
switch (action) {
  case "a":
    let x = 1; // x объявлена в scope всего switch
    break;
  case "b":
    let x = 2; // SyntaxError: Identifier 'x' has already been declared
    break;
}

// Решение — оборачивать case в блоки:
switch (action) {
  case "a": {
    let x = 1;
    break;
  }
  case "b": {
    let x = 2; // OK — другой блок
    break;
  }
}
```

#### TDZ при деструктуризации

```js
// Правая часть default-значения вычисляется в момент деструктуризации
// Переменные инициализируются слева направо

let { a = b, b = 1 } = {};
// a = b → b ещё в TDZ → ReferenceError!

// Корректный вариант:
let { b = 1, a = b } = {};
// b = 1, a = b = 1 → OK, b уже инициализирован
```

#### TDZ в параметрах функции с default values

```js
// Параметры вычисляются слева направо, каждый — в своём TDZ
function f(a = b, b = 1) {
  return a + b;
}
f(); // ReferenceError: Cannot access 'b' before initialization

// Корректно:
function g(b = 1, a = b) {
  return a + b; // 2
}
```

#### TDZ и `typeof`

`typeof` для необъявленных переменных безопасен, но для TDZ — нет:

```js
console.log(typeof undeclared);  // "undefined" — безопасно
console.log(typeof x);          // ReferenceError — x в TDZ
let x = 10;
```

### Запрет повторного объявления

`let` не позволяет объявить переменную дважды в одном scope — `SyntaxError` на этапе парсинга:

```js
let x = 1;
let x = 2; // SyntaxError: Identifier 'x' has already been declared

// Также нельзя смешивать с var в одном scope:
var y = 1;
let y = 2; // SyntaxError

// Но можно в разных scope:
let z = 1;
{
  let z = 2; // OK — shadowing, другой блок
  console.log(z); // 2
}
console.log(z); // 1
```

### `let` и `window`

`let` в глобальном scope **не создаёт** свойство `window`:

```js
let globalLet = "hello";

console.log(window.globalLet);    // undefined
console.log(globalLet);            // "hello"

// Переменная живёт в Script scope (глобальный LexicalEnvironment),
// а не в Global Object (window)
```

Это видно в DevTools: глобальные `let`/`const` отображаются в разделе **Script**,
а не в **Global**.

## `const`

### Обязательная инициализация

`const` требует значение при объявлении — без него `SyntaxError`:

```js
const x; // SyntaxError: Missing initializer in const declaration

const y = 42; // OK
```

### Запрет reassignment

Повторное присвоение `const`-переменной — `TypeError` в runtime:

```js
const x = 1;
x = 2; // TypeError: Assignment to constant variable

// Это также касается операторов +=, -=, ++, -- и т.д.:
const count = 0;
count++; // TypeError: Assignment to constant variable
```

### `const` и объекты

`const` запрещает **reassignment binding** (перепривязку), но **не immutability** содержимого:

```js
const obj = { a: 1, b: 2 };

// Мутация содержимого — OK
obj.a = 10;
obj.c = 30;
delete obj.b;
console.log(obj); // { a: 10, c: 30 }

// Перепривязка — TypeError
obj = { x: 1 }; // TypeError: Assignment to constant variable

// Аналогично для массивов:
const arr = [1, 2, 3];
arr.push(4);     // OK → [1, 2, 3, 4]
arr[0] = 99;     // OK → [99, 2, 3, 4]
arr = [5, 6, 7]; // TypeError

// Для истинной immutability используйте Object.freeze:
const frozen = Object.freeze({ a: 1, b: { c: 2 } });
frozen.a = 10;   // Тихо игнорируется (или TypeError в strict mode)
console.log(frozen.a); // 1

// Но Object.freeze — shallow:
frozen.b.c = 99;
console.log(frozen.b.c); // 99 — вложенный объект не заморожен
```

### `const` в циклах

#### `for...of` и `for...in` — новая привязка каждую итерацию

```js
const arr = [10, 20, 30];

for (const item of arr) {
  console.log(item); // 10, 20, 30
}
// Каждая итерация создаёт НОВУЮ const-привязку
// Нет reassignment — нет ошибки

for (const key in { a: 1, b: 2 }) {
  console.log(key); // "a", "b"
}
// Аналогично — новая привязка на каждой итерации
```

#### `for (const i = 0; ...)` — `TypeError` на второй итерации

```js
for (const i = 0; i < 3; i++) {
  console.log(i);
}
// Первая итерация: i = 0, console.log(0) ✓
// Операция i++ → TypeError: Assignment to constant variable

// Отличие от let: let создаёт новую привязку каждую итерацию
// и КОПИРУЕТ значение, затем увеличивает.
// const тоже создаёт новую привязку, но i++ — это reassignment текущей
// привязки, что для const запрещено.
```

## Спецификация: `LexicalEnvironment` vs `VariableEnvironment`

Каждый execution context содержит **два** environment record:

- **`VariableEnvironment`** — хранит привязки `var` и `function declarations`
- **`LexicalEnvironment`** — хранит привязки `let`, `const`, `class`

При входе в функцию оба environment изначально указывают на **один и тот же** environment record.
Но при входе в блок `{}` создаётся **новый** `LexicalEnvironment`, который оборачивает предыдущий
(через `[[OuterEnv]]`). `VariableEnvironment` при этом **не меняется**.

```
Execution Context (function scope)
├── VariableEnvironment: { var_a: undefined, var_b: undefined }
├── LexicalEnvironment → Block Scope (if)
│   ├── let_x: <uninitialized>  (TDZ)
│   ├── const_y: <uninitialized> (TDZ)
│   └── [[OuterEnv]] → VariableEnvironment
└── ...
```

Вот почему `var` "всплывает" на уровень функции — его привязка находится в `VariableEnvironment`,
который один на всю функцию. А `let`/`const` привязываются к `LexicalEnvironment` конкретного блока.

```js
function demo() {
  // VariableEnvironment: { a: undefined } (hoisted)
  // LexicalEnvironment: (пока совпадает с VariableEnvironment)

  console.log(a); // undefined (var hoisted + initialized)
  // console.log(b); // ReferenceError (let hoisted но в TDZ)

  var a = 1;

  if (true) {
    // Новый LexicalEnvironment для блока if
    // { b: <uninitialized>, c: <uninitialized> }
    let b = 2;
    const c = 3;
    var d = 4; // Попадает в VariableEnvironment функции, НЕ блока!
  }

  console.log(a); // 1
  console.log(d); // 4 — var утёк из блока if
  // console.log(b); // ReferenceError — b в scope блока if
  // console.log(c); // ReferenceError — c в scope блока if
}
```

### V8 и TDZ hole check

V8 (движок Chrome/Node.js) реализует TDZ через механизм **hole**:

1. При создании `LexicalEnvironment` слот `let`/`const` переменной заполняется специальным
   значением `the_hole` (внутренний маркер V8, не доступен из JS)
2. **Перед каждым доступом** к переменной V8 вставляет проверку: `if (value === the_hole) throw ReferenceError`
3. При инициализации (`let x = ...`) значение `the_hole` заменяется реальным значением
4. После этого hole check формально не нужен, но продолжает выполняться в интерпретаторе

**JIT-оптимизация:**

Turbofan (оптимизирующий компилятор V8) способен **устранить** hole checks для переменных,
которые гарантированно инициализированы:

```js
function optimized() {
  let x = 0;
  // V8 знает: x инициализирован в первой строке,
  // все последующие доступы гарантированно после инициализации
  for (let i = 0; i < 1000000; i++) {
    x += i; // hole check оптимизирован — удалён Turbofan
  }
  return x;
}

function notOptimized() {
  let x;
  // x остаётся hole до следующей строки
  if (someCondition()) {
    x = 42;
  }
  // V8 не может гарантировать, что x инициализирован
  return x; // hole check остаётся в скомпилированном коде
}
```

> В SpiderMonkey (Firefox) используется аналогичный механизм с `MagicValue(JS_UNINITIALIZED_LEXICAL)`.

## Performance мифы

### Миф: `const` быстрее `let`

Распространённое заблуждение: "используй `const`, и V8 будет оптимизировать лучше, потому что знает,
что значение не изменится".

**Реальность:** для примитивов V8 **одинаково** оптимизирует `let` и `const`. Turbofan проводит
**SSA-анализ** (Static Single Assignment) и самостоятельно определяет, изменяется ли переменная.
Ключевое слово `const` не даёт компилятору дополнительной информации.

```js
// С точки зрения V8 Turbofan — идентичная оптимизация:
function withConst() {
  const x = 42;
  return x + 1;
}

function withLet() {
  let x = 42;
  // x не переприсваивается → Turbofan это видит
  return x + 1;
}
// Обе функции компилируются в идентичный машинный код
```

`const` полезен для **читаемости кода** и **защиты от случайного reassignment**,
но не для performance.

### `eval()` деоптимизирует `var`

Если функция содержит вызов `eval()`, V8 **не может** оптимизировать доступ к переменным `var`,
так как `eval` может объявить новые переменные или изменить существующие:

```js
function withEval(code) {
  var x = 10;
  eval(code); // может сделать "var x = 999" или объявить новые переменные
  return x;   // V8 не знает, какое значение будет у x
}

// V8 вынужден:
// 1. Хранить все var-переменные в heap (а не в регистрах)
// 2. Каждый доступ к переменной — через lookup в environment record
// 3. Отключить inline caching для этого scope
```

`let` и `const` внутри `eval` в strict mode создаются в **отдельном** scope,
что частично смягчает проблему:

```js
"use strict";
let x = 10;
eval("let x = 20; console.log(x);"); // 20 — своя переменная
console.log(x); // 10 — не затронута
```

|-------------------------|---------------------------|-----------------------------|------------------------------|

| **Повторное объявление**| Разрешено                 | `SyntaxError`               | `SyntaxError`                |

| **`for...of` / `for...in`** | OK                   | OK                          | OK (новая привязка)          |

## Best practices

### 1. `const` by default

Объявляйте переменную через `const` по умолчанию. Это сигнализирует: "эта привязка не будет
переприсвоена". Когда читаешь код, `const` сразу говорит: значение привязки стабильно.

```js
const API_URL = "https://api.example.com";
const user = await fetchUser(id);
const items = data.filter(item => item.active);
```

### 2. `let` когда нужен reassignment

Используйте `let` только когда переменная действительно будет переприсвоена — аккумуляторы,
счётчики, флаги, значения, которые меняются в цикле:

```js
let total = 0;
for (const item of items) {
  total += item.price;
}

let retries = 3;
while (retries > 0) {
  try {
    await fetchData();
    break;
  } catch {
    retries--;
  }
}

let current = head;
while (current !== null) {
  process(current);
  current = current.next;
}
```

### 3. `var` — никогда (кроме legacy)

В современном коде нет ни одной причины использовать `var`:
- Если нужен function scope — оберните в `{}`  с `let`
- Если нужен hoisting — используйте `function declaration`
- Если нужен global — используйте `globalThis.prop = value` явно

```js
// Плохо:
var config = loadConfig();

// Хорошо:
const config = loadConfig();

// Если нужно присвоить позже:
let config;
if (env === "prod") {
  config = loadProdConfig();
} else {
  config = loadDevConfig();
}

// Или ещё лучше:
const config = env === "prod" ? loadProdConfig() : loadDevConfig();
```

### 4. Деструктуризация с `const`

```js
// Вместо нескольких let:
const { name, age, email } = user;
const [first, ...rest] = items;

// Swap без let (через деструктуризацию):
let a = 1, b = 2;
[a, b] = [b, a]; // a = 2, b = 1
```

### 5. Линтер правила

Настройте ESLint для принудительного использования `const`/`let`:

```json
{
  "rules": {
    "no-var": "error",
    "prefer-const": "warn"
  }
}
```

`prefer-const` автоматически подскажет заменить `let` на `const`, если переменная
ни разу не переприсваивается после объявления.
