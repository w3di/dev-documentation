# Lexical scope подробно

## Разрешение переменных на compile time

- При вложении функции (например, `ask` внутри `otherClass`) ссылка на переменную безоговорочно связывается с её объявлением на этапе компиляции.
- «Цвет marble» (принадлежность переменной scope) определён на compile time, а не через look-up в run time.
- Метафора «look-up в run time» — упрощённая концептуальная модель; в реальности связь известна заранее.
- Даже в худшем случае, когда связь неизвестна при компиляции, она вычисляется при первом обращении и больше не меняется.

## Почему lexical scope популярен

- Высокая оптимизируемость: компилятор заранее знает, откуда берётся каждая переменная, и не нужно вычислять это в run time.

## Визуализация scope как «пузырей»

- Каждый scope можно представить как «пузырь» (bubble) вокруг функции.
- Пузыри строго вложены друг в друга, не пересекаются и не делятся между двумя родительскими scope.
- Запись функциональных выражений в полной вложенной форме (а не в одну строку) помогает видеть границы scope.

## Инструмент ES levels

- Плагин **ES levels** (для редактора, например Sublime) раскрашивает переменные по принадлежности scope — визуализирует «цвета bucket и marble».
- Известный баг плагина: имя named function expression раскрашивается как принадлежащее внешнему scope, хотя имя должно принадлежать собственному промежуточному scope функции (разработчики не стали исправлять).
- Несмотря на неточности, инструмент помогает понимать происхождение переменных.

## Главное

- Принадлежность переменной scope фиксируется на compile time, а не разрешается заново в run time.
- Lexical scope оптимизируем именно потому, что связи известны заранее.
- Scope удобно мыслить как строго вложенные непересекающиеся «пузыри».
