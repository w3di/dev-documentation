# Compilation: разбор scope (compiler ↔ scope manager)

## Модель «разговора» двух участников

- На этапе компиляции «общаются» два участника:
  - **compiler** (компилятор) — обрабатывает программу, находит объявления.
  - **scope manager** (менеджер scope) — создаёт вёдра (buckets) и шарики (marbles), раскладывает шарики.
- Первый проход = компиляция: создаются планы вёдер и шариков. Второй проход = выполнение.
- Цвета scope для иллюстрации: глобальный scope — **красный (red)**, вложенные — **синий (blue)** и **зелёный (green)**.

## Обработка формальных объявлений

- Компилятор ищет **formal declarations** (формальные объявления): `var`/`let`/`const` и объявления функций. Тип объявления (`var`/`let`/`const`) сейчас не важен.
- Для каждого объявления компилятор спрашивает scope manager: «есть ли уже такой идентификатор в этом scope?»
  - Если есть — это no-op (никакого **redeclaration** нет, повторного создания не происходит).
  - Если нет — создаётся новый шарик нужного цвета и кладётся в соответствующее ведро.
- Шарики реально создаются только при выполнении; на компиляции строится лишь план.

## Пример пошагово

```js
var teacher = "Kyle";              // 1

function otherClass() {            // 3
    var teacher = "Suzy";          // 4
    console.log("Welcome!");       // 5
}

function ask() {                   // 8
    var question = "Why?";         // 9
    console.log(question);         // 10
}
```

1. Строка 1: `var teacher` — глобальный (красный) scope, идентификатора нет → красный шарик `teacher`.
2. Строка 3: функция `otherClass` → красный шарик `otherClass` в глобальном scope. Функция создаёт scope → нужен новый **blue bucket** (синее ведро) внутри красного.
3. Заходим в синий scope. Строка 4: `var teacher` — спрашиваем синее ведро (не красное!). Идентификатора нет → синий шарик `teacher`.
4. Строка 8: функция `ask` → красный шарик `ask` в глобальном scope + новое **green bucket** (зелёное ведро).
5. Строка 9: `var question` → зелёный шарик `question`.

## Shadowing

- **shadowing** (затенение) — наличие двух переменных с одинаковым именем в разных scope (например, `teacher` красный и `teacher` синий).
- Shadowing допустим и не является ошибкой.
- Следствие: при затенении нельзя лексически обратиться к внешней (красной) переменной из внутреннего scope — имя совпадёт с ближайшим (синим) шариком.

## Объявления vs ссылки

- На строке 5 `console.log` компилятор обрабатывает, но он не создаёт и не обращается к нашим переменным — для разбора scope этот шаг пропускается.
- Строка 10 (`console.log(question)`) — это ссылка, она не создаёт шарик; но важно знать цвет этого шарика для этапа выполнения.

## Ключевые выводы

- В lexically scoped языке все scope и идентификаторы определяются на этапе компиляции, а используются на этапе выполнения.
- После компиляции остаётся план всех вёдер и шариков — он передаётся движку как исполняемый код.
- Поскольку всё известно и зафиксировано, движок эффективно оптимизирует код: цвет шарика не может измениться в runtime.

## Главное

- Компиляция = «разговор» компилятора и scope manager: для каждого formal declaration создаётся шарик нужного цвета в нужном ведре.
- Функции и blocks создают вёдра; объявления переменных и функций создают шарики в текущем scope.
- Shadowing (совпадение имён в разных scope) допустим, но закрывает доступ к внешней переменной с тем же именем.
- Решения о scope — это author-time решения: где написана переменная, такого «цвета» она и будет всегда.
