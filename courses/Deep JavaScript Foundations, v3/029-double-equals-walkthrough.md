# Разбор `==`: число vs массив с числом

## Пример (плохой код)

```js
var workshop1Count = 42;
var workshop2Count = [42];

workshop1Count == workshop2Count   // true
```

- Сравнивать примитив с массивом так **не следует**. Но если бы пришлось — сработает ли coercively? В данном случае да. Важнее вопрос «**почему**», а не «работает ли».

## Пошаговый разбор по алгоритму

1. `==` сравнивает `42` (number) и `[42]` (array). `42` — уже примитив, `[42]` — нет.
2. К массиву применяется **ToPrimitive** → массив **stringify**'ится. У массива из одного элемента строковое представление — без скобок:

```
42 == "42"      // [42] → "42"
```

3. Теперь number vs string. `==` предпочитает **numeric comparison**, поэтому строка → число.
4. Типы стали одинаковыми → выполняется `===`:

```
42 === 42       // true
```

## Почему это «работает» только случайно

- Срабатывает лишь из-за специфичной stringification массива (без скобок) и **только** при **единственном** элементе. С несколькими числами не сработало бы.
- То есть это работает почти **по случайности**.

## Главный вывод

- Даже если код работает — это не значит, что так нужно писать. Это явный пример вредного coercion.
- **Чинить это через `===` — неправильно.** `===` лишь **скрывает** настоящую проблему — бессмысленное сравнение «число vs массив чисел».
- Правильное решение — устранить нелепое сравнение, сузить «поверхность» (surface area), не сравнивать число с массивом чисел.
- Виноват **не** `==`: виновата бессмысленная comparison. `===` её только прячет, а не чинит. Большинство corner cases возникают именно из-за полиморфной типизации, которой не должно быть.

## Q&A: «у автора такого кода проблемы серьёзнее?»

- Именно так — здесь проблемы больше, чем выбор оператора. Это то, на что жалуются как на «проблему `==`», хотя реальная проблема — нелепое сравнение.
- Осмысленное сравнение (строковое представление числа vs само число) — нормально, и coercion там уместен.

## Историческая причина ToPrimitive в сравнении

- По мнению Kyle: при дизайне coercion он бы оставил все приведения, **кроме** ToPrimitive для не-примитивов; единственное допустимое сравнение не-примитивов — identity.
- Но историческая причина: раньше делали `new String(...)` и получали объект, мысля его как примитив. Поэтому языку разрешили down-coerce такой не-примитив к его примитивному эквиваленту — отсюда этот шаг в алгоритме.

## Главное

- `42 == [42]` → `true`: массив через ToPrimitive стал `"42"`, затем строка → число, и `===` дал `true` — почти случайность (работает только с одним элементом).
- «Работает» ≠ «нужно использовать»; это пример вредного coercion.
- Решение — не `===` (он лишь маскирует проблему), а отказ от бессмысленного сравнения число↔массив.
- Виноват не `==`, а полиморфная нелепая comparison; осмысленные сравнения (строка-число) с coercion нормальны.
