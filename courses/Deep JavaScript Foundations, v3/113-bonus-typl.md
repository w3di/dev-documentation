# Бонус: TypL

## Мотивация

- Цель — типизация, не требующая менять стиль кода ради type-aware linting (линтинга с учётом типов).
- Проблема TypeScript / Flow: чтобы получить гарантии о поведении кода, приходится менять привычный код так, чтобы очевидное стало очевидным **компилятору**.
- «Очевидно читателю кода» и «очевидно компьютеру» — разные вещи, которые часто смешивают.
- TypeScript даёт пользу только на этапе компиляции; на выходе — чистый JavaScript без runtime-поведения типов. Чтобы получить всю пользу, код приходится делать «менее похожим на JavaScript».
- **TypL** — экспериментальный type-aware linter Kyle, идущий «по волокну» JavaScript: больше инструментов и уверенности без превращения JS во что-то иное. На момент урока — alpha, без документации, в репозитории код и тесты, движение к релизу 1.0.

## Принципы дизайна TypL

1. Только **стандартный синтаксис JavaScript** (и не просто комментарии) — чтобы избежать ecosystem lock-in.
2. И **compiler-компонент, и runtime-компонент**:
   - runtime-component — runtime-ассерты в поставляемом коде, сообщающие о проблемах.
   - Обязателен **выбор**: можно использовать только компилятор, только runtime, или оба. Существующие системы такого выбора не дают.
3. Всё **конфигурируемо** (в стиле ESLint): TypL «жалуется на всё», а пользователь отключает ненужные жалобы.
   - Тонкая настройка: например, разрешить `==` только между string и number и нигде больше.
4. Фокус смещён со **static typing** на инференс/аннотирование **значений** — это **value types** вместо **variable types**. Static-typing ошибки можно опционально включить.
5. Идти «по волокну» JavaScript, улучшать существующий язык, а не создавать другой.

## Аннотирование значений через template tags

- Базовый случай: при включённой опции TypL поймает смену типа значения (string → object) — как TypeScript, через inference.
- Явная аннотация значения делается **template tag** (тегом шаблона) — это стандартный JavaScript:

```js
teacher = string`Kyle`;
```

- Имя тега (`string`, `number`, …) задаёт интерпретацию значения; в бэктиках — само значение (`number` 42`).
- Отличие от Flow/TypeScript: аннотируется **значение в свойстве объекта**, не нужно создавать отдельный тип для объекта:

```js
student = {
  name: string`Kyle`,
  age: int`42`
};
```

- Можно тегировать и сам объект (`object`{...}``) — тогда нарушение даст «tagged type violation» вместо «inferred type violation».
- Идея: аннотировать **все места, где встречаются значения и выражения**, а не типы переменных, — потому что основные проблемы возникают там, где значения и выражения перемешиваются, а не при переприсваивании переменных.

## Числовые типы и inline-ассерты

- В TypL четыре числовых типа: **number**, **integer**, **finite**, **bigInt**.
- Inline-ассерт значения, например требование, чтобы `student.age` было числом:

```js
number`${student.age}`
```

- Если значение не подходит — ошибка компилятора (если он может это вычислить) или runtime-ошибка (если не может).

## Сигнатуры функций

- Тип-сигнатуру задают, переиспользуя default value expression:

```js
function getName(studentRec = { name: string`` }) {
  return studentRec.name;  // выведется как string
}
var studentName = getName(...); // тоже выведется string
```

- Всё это валидный стандартный JavaScript: код запустится в браузере (хотя на этапе компиляции может делать не всё то же самое).
- Преимущество перед TypeScript: не нужно создавать отдельный custom type — типы лежат на самих значениях.
- Сигнатуры **persistent** (устойчивы) и могут быть inline. Пример: аннотация callback-сигнатуры — параметр-объект с `name: string`, возврат `void`/undefined; функция, присвоенная переменной, сохраняет сигнатуру и сопоставляется с требуемой при передаче как callback.

## Multi-pass inferencing

- Случай, который TypeScript/Flow сейчас не обрабатывают (выводят `any` и не сообщают об ошибке):

```js
var x = gimme(3) + "foo"; // вызов раньше определения (function hoisting)
function gimme(num) { return num; }
```

- TypL делает **multi-pass inferencing** (многопроходный инференс):
  1. Вызов раньше определения → нужен второй проход.
  2. У параметра нет аннотации → при первом проходе запоминается, что в `gimme` передан `int 3`.
  3. На втором проходе: `num` — integer → возвращаемое значение — integer → результат `gimme(3)` — integer.
  4. Сложение integer + string → ошибка.
- Реализация заняла несколько недель; TypL «сияет» здесь благодаря фокусу на value types.

## Compiler vs runtime

- Компилятор вычисляет всё, что может, и **удаляет** это из кода, чтобы не нагружать runtime.
- То, что вычислить нельзя, остаётся как runtime-ассерт.
- Пример: параметры `name: string`, `topic: string = ""`, `count: int = 0`.
  - Случаи, известные на этапе компиляции (например, заведомо строковые литералы), валидируются компилятором и удаляются.
  - В production уходит сокращённый набор: дефолтные значения параметров + inline type-ассерты в виде tag-функций, которые компилятор включает в runtime и которые проверяют переданные значения при каждом вызове.
- Ассерт оставляют там, где есть выражение и нужно проверить во время выполнения (например, что значение действительно integer, а не NaN/Infinity).

## Главное

- **TypL** — type-aware linter, использующий только стандартный JavaScript (template tags) и не требующий менять стиль кода; alpha-проект Kyle.
- Ключевая идея: типизировать **значения и выражения** (value types), а не переменные; аннотации лежат на самих значениях — отдельные типы создавать не нужно.
- Гибкость: и compiler-, и runtime-компоненты с выбором «один/другой/оба», полная конфигурируемость в стиле ESLint, четыре числовых типа.
- Multi-pass inferencing ловит случаи (вызов до объявления), которые TypeScript/Flow помечают `any`; компилятор удаляет проверяемое статически и оставляет runtime-ассерты для остального.
