# Coercive equality: `==` с null/undefined

## Выбор `==`/`===` — индикатор понимания кода

- Как и для любой операции: зная типы, спросите — coercion здесь помогает или нет? Это критический анализ, а не догма.
- Дискуссия смещается с «`==` плохой и непредсказуемый» на «хочу ли я разрешить coercive-сравнение в этом месте — это безопаснее или нет?».
- Выбор `===` — **trailing indicator** (запаздывающий индикатор): он указывает, что вы чего-то **не знаете** о типах в сравнении и вынуждены защищаться.
- Лучше устранить корневую проблему — непредсказуемость/полиморфность типов. Это даёт меньше багов независимо от того, `==` или `===`.

## `==` при разных типах: null и undefined

- Если хотя бы один операнд — `null` или `undefined` (clauses 2 и 3 алгоритма):
  - `null == undefined` → `true` (и наоборот).
- **null** и **undefined** coercively равны **только** друг другу и ничему больше в языке (clause 10 → `false` для остального).
- Они не совпадут ни с одним другим clause, кроме 2 и 3.

## Почему это полезно

- Иметь два «пустых» значения путано; удобнее работать с одним.
- `null` короче печатать, чем `undefined` — можно «делать вид», что `undefined` не существует, или что они взаимозаменяемы.
- JS делает между ними некоторые различия (например, алгоритм default value), но в большинстве случаев их можно трактовать как неразличимые через coercive equality.

## Пример: проверка «задано или нет»

```js
// Многословно — явная проверка обоих пустых значений:
if (
    (workshop1.topic === null || workshop1.topic === undefined) &&
    (workshop2.topic === null || workshop2.topic === undefined)
) { ... }

// Чисто — coercive equality:
if (workshop1.topic == null && workshop2.topic == null) { ... }
```

- Различать «свойства не было», «сброшено в null», «сброшено в undefined» в подавляющем большинстве случаев бесполезно — это одно и то же состояние.
- `== null` яснее: «является ли это одним из двух пустых значений». Выбран `null`, т.к. короче.
- Даже жёсткие критики coercion используют `== null`-проверки — это наименее спорное применение `==`.

## Про линтеры

- **Linter** даёт мнение о коде (склонность к багам), а не проверяет корректность программы.
- Мнения у всех разные → лучшие инструменты — максимально **конфигурируемые**, в т.ч. под команды.
- Если линтер нельзя настроить и он мешает делать работу (ломает build), заставляя менять код под себя, — он вредит, а не помогает.
- Пример (ESLint): правило о var-объявлениях наивно путает осмысленный `a = 2; var a;` и допустимый случай присваивания внутри функции до объявления `var` выше по коду. Такое правило мешает — его можно отключить. В ESLint можно писать свои правила.

## Главное

- Выбор `===` — запаздывающий индикатор того, что вы не знаете типы; лучше чинить корень (предсказуемость типов).
- `null == undefined` → `true`; null и undefined coercively равны только друг другу — это удобно для проверки «задано или нет».
- `x == null` — чистый и общепринятый способ проверить «пусто ли» (null или undefined).
- Линтер — это настраиваемое мнение, а не проверка корректности; ценны конфигурируемые инструменты.
