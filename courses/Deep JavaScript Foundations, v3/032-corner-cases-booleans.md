# Corner Cases `==` с Boolean

## Главное предупреждение

- **Никогда** не делайте `== true` или `== false` (а по возможности и `=== true` / `=== false`).
- Это привычка из других языков, в JavaScript она приводит к багам.
- Нет ни одного сценария, где `== true`/`== false` лучше неявной коэрсии **ToBoolean** — а случаев, где хуже, много.

## Правильный способ: неявный ToBoolean

- Если нужно проверить «truthy ли значение», достаточно `if`:

```js
if (workshopStudents) {
    // ToBoolean(массив) → true (массива нет в "таблице falsy")
}
```

- Это корректная неявная **implicit ToBoolean coercion**.

## Почему `== true` ломается, а `== false` «срабатывает» наоборот

Для truthy-массива `workshopStudents`:

- `workshopStudents == true`:
  1. Массив → примитив → `""`.
  2. `"" == true`: разные типы → к number: `""` → `0`, `true` → `1`.
  3. `0 == 1` → `false`. Ветка кода **не выполняется**, хотя значение truthy.
- `workshopStudents == false`:
  1. Массив → `""`.
  2. `"" == false` → `0 == 0` → `true`.

- Итог: truthy-значение оказывается `!= true`, но `== false` — контринтуитивный результат на бессмысленной конструкции.
- С `===` тоже не сработало бы как ожидается: сравнение Boolean с массивом проходит через corner cases.

## Вывод про implicit vs explicit

- Здесь **implicit лучше explicit**: неявный ToBoolean не имеет gotcha, а явное `== true`/`== false` — имеет.
- Если действительно нужна проверка строго на `true`/`false` — используйте `===`.

## Нюанс: когда проверки недостаточно одного ToBoolean

- Сценарий выше предполагает: значение либо **unset**, либо массив, и ничего больше. Тогда хватает `if`.
- Если значение может быть set в разные типы (массив, объект, строка) — нужны более глубокие проверки:
  1. Сначала проверить, что значение вообще set.
  2. Затем проверить его «identity»: `typeof`, **duck typing** (наличие метода/`.length`), `Array.isArray()` и т. п.
- Рекомендация: **проектировать код с меньшей surface area** — пусть значение будет либо unset, либо массив (меньше полиморфизма, меньше проверок). Дополнительные проверки (duck typing и т. п.) добавлять в `if` лишь когда тип нельзя ограничить.

## Главное

- Никогда не пишите `== true` / `== false`; всегда полагайтесь на неявный **ToBoolean** в `if`.
- Сравнение Boolean с non-primitive проходит через corner cases и даёт контринтуитивные результаты (truthy-массив `!= true`, но `== false`).
- Уменьшайте число возможных типов значения — это сокращает количество необходимых проверок.
