# Introduction (Введение)

## О чём курс

- Тема — **React performance** (производительность React-приложений).
- Основной фокус — **client-side** (то, что выполняется в браузере). Server-side rendering затрагивается, но не в центре, т.к. серверная часть обычно framework-specific.
- Курс — преемник старого воркшопа по advanced state management. Раньше единственным способом ускорить React была правильная работа со state management; сейчас в React много встроенных инструментов, решающих задачи, которые прежде были либо нерешаемыми, либо требовали огромных усилий.

## Ключевая идея

- Архитектура и структура приложения влияют сразу на две вещи: **performance** и **maintainability** (поддерживаемость, способность держать в голове модель приложения).
- Обычно «удобно для разработчика» и «эффективно на уровне рендеринга» не совпадают. Цель курса — приёмы, которые дают оба эффекта одновременно.

## Структура курса

1. Концептуальная часть — как React работает «под капотом» (важно: внутренности сильно менялись за годы, хотя ергономика осталась похожей).
2. Базовый state management.
3. **Memoization** (мемоизация — кэширование результатов) и caching.
4. Грядущие изменения в React, упрощающие часть этих задач.
5. Новейшие возможности современных версий React.

## Для кого

- Для тех, кто хочет понять реальные внутренние механизмы React (модель «как я учил в 2017» устарела по внутренностям).
- Для тех, кто хочет научиться **диагностировать** проблемы производительности.

## Два подхода к performance

- **Reactive**: найти конкретный bottleneck (узкое место) и устранить его. Best practices стандартны, но способы, которыми всё ломается, в каждом приложении уникальны — поэтому навык диагностики важен сам по себе.
- **Proactive**: не доводить до проблемы изначально. Здесь нужен баланс между premature optimization / overengineering и риском «загнать себя в угол», из которого потом выбираться неделями. Важны эвристики: когда оптимизировать стоит, а когда — нет.

## Применимость

- Next.js / Remix: материал ориентирован на framework-agnostic, client-side части — применим независимо от фреймворка.
- **React compiler**: на момент записи — release candidate. Важно: он *не* отменяет необходимость мемоизации полностью. Работает в больших приложениях не «по щелчку» — миграции занимают время.
- Большинство концепций React 19 применимы и к React 18; React compiler поддерживается примерно с React 17. Фундаментальные механизмы развивались внутри React 3–4 года, просто стали заметны недавно.

## Формат лабораторных

- Маленькие, гиперсфокусированные лабы — каждая про один конкретный аспект.
- Причина: создать одно приложение со *всеми* возможными performance-багами специально — сложнее, чем кажется; плюс не нужно разбирать огромную кодовую базу.
- Примеры основаны на реальных случаях («scar tissue» — набитые шишки из практики).

## Главное

- Курс про client-side React performance; приёмы по большей части framework-agnostic.
- Архитектура влияет одновременно на скорость и на поддерживаемость — цель найти решения, выигрышные по обоим параметрам.
- Два режима работы: reactive (искать и чинить bottleneck) и proactive (не допускать проблем, не впадая в premature optimization).
- React compiler — не серебряная пуля; мемоизация и понимание внутренностей React остаются нужными.
