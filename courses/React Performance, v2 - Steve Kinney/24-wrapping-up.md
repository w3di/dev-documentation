# Wrapping Up (Заключение)

## Дополнительные материалы

- В репозитории есть расширенные заметки по темам, не разобранным полностью; pull requests приветствуются (начиналось как личные заметки лектора).

## Сводная карта приёмов (та самая итоговая схема)

В порядке применения:

1. **Структура / component hierarchy** — push state down («как высоко нужно, как низко возможно»). Всегда было верно, остаётся фундаментом.
2. **Memoization** — `useMemo`/`useCallback`/`React.memo`; либо **React compiler**, который применяет эвристики за тебя на постоянной основе. Даёт реальный прирост — не рендерим, когда не нужно.
3. **Suspense** — вместо ожидания данных через `useEffect`. Не «держать» промисы вручную.
4. **Transition API** — для **truly problematic** bottleneck'ов: алгоритм можно оптимизировать, но он всё равно может превышать 16 мс на широком спектре устройств («работает на моей машине» ≠ работает у всех).

## Почему упор на концепции

- Когда видишь `useTransition`, это **не магия**: понятно, что есть **priority lanes** в React Fiber, и хук кладёт работу в другую полосу, давая срочному выполниться раньше.
- **Optimistic updates** можно было делать задолго до React (на jQuery: вставить в DOM, при reject промиса убрать). Новые API дают удобный boilerplate для давно известных паттернов.

## Suspense vs waterfall of useEffect

- Старый путь: всё отрендерить → сработают `useEffect` → каждый запускает новый render phase → каскад эффектов → **waterfall of effects**.
- С Fiber + Suspense: блок показывает loading-компонент, **ждёт резолва промиса**, затем подхватывает работу (даже если будет второй commit). Тяжёлая переархитектура «под капотом» вылилась в набор **более простых API** для нас.
- Бонус Suspense — не только performance, но и **TypeScript-эргономика**: после suspense-точки ресурс гарантированно есть (либо ушёл в error boundary), и не нужно по всему дереву проверять «значение или null».

## Стратегия внедрения

- React 18 и 19 по большей части **обратно совместимы** — апгрейд не ломает приложение (в отличие от «расчисти календарь на месяц» у других фреймворков). Поэтому многое из performance — это **opt-in** в уже проделанную командой React работу.
- **Не делать всё сразу.** Transition нужен только там, где есть гигантский bottleneck (он есть в каждом приложении). Находить такие места:
  - React DevTools (мигает то, что не должно) и/или Chrome DevTools (CPU 100% несколько секунд → начинать отсюда).
- **Не быть худшим человеком на code review**: «1.1 мс → 1.05 мс после memo» — не делать. Большинство из нас выпускают софт для пользователей, а не красуются.
- Прогрессивная миграция: ручная пляска с `loading`/`error` state — «не задача на завтра», но повод постепенно переходить. **Не** делать find-and-replace всех `useCallback` + включить React compiler везом — рискуешь устроить outage.

## Что унести с собой

- Не обязательно помнить наизусть `useTransition`. Важно **понимать, что существует приоритизация работы** (lanes), memoization, Suspense — остальное гуглится / находится в заметках.
- Именно концептуальные части (lanes, назначение работы в полосы, фазы рендера) — то, чего обычно не хватает большинству. Плюс — **ставить под сомнение** допущение «должно ли это работать именно так».

## Главное

- Порядок: архитектура (push state down) → memoization / React compiler → Suspense → Transition API для отдельных bottleneck'ов.
- Новые API — удобные абстракции над давно известными паттернами (optimistic updates, ожидание промисов); Suspense убирает waterfall эффектов и улучшает TypeScript-эргономику.
- React 18/19 обратно совместимы — performance во многом это **opt-in**; внедрять прогрессивно, только в реальных pain points, найденных инструментами.
- Главное — концептуальная модель (lanes, фазы, referential equality), а не заучивание API.
