# React Performance Q&A (итоговая сессия вопросов)

## Q: С чего начать улучшение производительности незнакомого React-приложения?

- Часто проблема **не техническая, а организационная**: большое приложение делают несколько команд, у каждой дедлайны, а самые болезненные участки **никто не «владеет»**. Задача №1 — получить buy-in команд (вне технического вопроса).
- Технически — найти **самый большой pain point**:
  - Пример: первая отрисовка занимает 90 секунд (часто из-за того, что каждая команда грузит **свою версию React**) → начинать отсюда (монорепо, единая версия React).
  - Диагностировать: не грузится / тормозят API (нужно 10 вызовов ради одного экрана → стратегия **Backend for Frontend**) / медленный рендеринг.
- Метрика приоритизации **«agony»** (из Skylight для Rails): `agony = slowness × traffic`. Медленная страница ToS — потом; медленная login-страница — высший приоритет.
- Иногда боль вообще в другом: CI/CD постоянно падает, и все его пропускают.
- Для тем этого курса — открыть **React DevTools + Chrome DevTools** и смотреть, где «мигает то, что не должно», или рендер занимает аномально долго (мигание 1 мс — игнор; 1.3 с — отсюда начинать).
- Самые коварные баги: страница грузится нормально, но **деградирует со временем** использования (через 5 минут хуже). Если бы было очевидно — уже починили бы.
- Иногда правильный ответ — **не трогать** (старый код на Perl, который никто не понимает, но он не ломался десятилетие). Подход — научный: есть инструменты и способы оценки, применяй их. Конкретика уникальна для каждого большого приложения.

## Q: Почему React не применяет memo (пропуск ре-рендера при тех же props) везде сам?

- Потому что «не измениться» иногда **плохо**: компонент сам не изменился, но это **prop drilling**, и нужное значение шло через него к внуку. Если родитель «решит не обновляться» и не вызовет потомков — компонент тремя уровнями ниже, которому значение было нужно, останется без обновления.
- Исторически React работал **в runtime** и **не имел доступа к коду** — не мог знать, что вызывается ниже, поэтому вынужден был перестраховываться.
- **React compiler** анализирует код статически (видит импорты, вызовы) и может делать это безопасно — как Svelte/Solid, где этот подход уже работает.

### Дополнение: компонент должен быть pure

- Если в компоненте есть hook (`useState`/`useContext`), memo не спасёт: при изменении хука он всё равно ре-рендерится (но **не** от входящих props). Получаешь сразу обе проблемы — и баг (как с prop drilling), и отсутствие выигрыша.
- Поэтому «memo везде по эвристике» опасно: будет **быстрее, но сломано**. «Медленное работающее приложение лучше быстрого неработающего».

## Философское отступление: trade-offs

- Аналогия: «perfect app, который не выходит» vs работающий. Цитата Reid Hoffman: «если тебе не стыдно за первый релиз — ты выпустил слишком поздно».
- Идеализированный совет vs реальность: иногда нужно выпустить «плохую версию», чтобы узнать, нужен ли продукт вообще. Мир заставляет идти на компромиссы.
- Про React compiler: если можно вывести эвристику — её можно автоматизировать; людям остаётся «squishy weird stuff» (за это и платят).

## Q: Разделять ли UI от state/handlers по разным файлам (pure UI + логические обёртки, в контексте Redux)?

- Да, нравится — но **не всегда** так делает. «Любая жёсткая категоричная позиция неверна».
- Контрпример: если «всё в Redux» — кладёшь ли туда состояние «открыт/закрыт аккордеон»? Скорее нет → значит **не всё**, и вопрос в том, где граница.
- Нравится сам **паттерн Redux-редьюсера**: `(текущее состояние, новая информация) → новое состояние`. Легко тестировать (подал объекты — проверил результат), элегантно. Компоненты тоже тестируемы (Testing Library), но редьюсер проще.
- Полезное разграничение (аналогия с distributed systems): **data plane** (данные, как Dynamo) vs **control plane** (UI-виджеты/переключатели, как AWS-дашборд). Стоит ли применять разные подходы к «данным» и к «UI-состоянию» (что открыто/закрыто) — интересный вопрос; единого ответа на 100% у лектора нет.

## Главное

- Старт оптимизации — найти самый большой pain point (`agony = slowness × traffic`); часто проблема организационная, а не техническая.
- React не делает memo везде, потому что пропуск рендера может «обрезать» обновление нужному потомку (prop drilling) и бессмысленен для не-pure компонентов; безопасно это делает только статический анализ (React compiler).
- «Медленное работающее лучше быстрого сломанного»; категоричные правила (всё в Redux, memo везде) — ошибочны, всё решается измерением и компромиссами.
- Паттерн «pure UI + логические обёртки» хорош (тестируемый redux-редьюсер, разделение data/control plane), но применять его на 100% не обязательно.
