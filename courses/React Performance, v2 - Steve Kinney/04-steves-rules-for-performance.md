# Steve's Rules for Performance (Правила производительности)

## Правило 1: Не делать что-то быстрее, чем делать

- **Golden rule**: «not doing stuff is faster than doing stuff» — код, который не выполняется, быстрее кода, который выполняется.
- Идеал: React-приложение, которое никогда не ре-рендерится, — самое быстрое (доведённый до абсурда тезис: тогда это просто HTML-страница). Каждый шаг ближе к «не ре-рендерить» — это прирост производительности.
- Нюанс про **memoization** и **caching**: они сами по себе — «делание чего-то». Работают, только если стоимость кэширования меньше, чем работа, которую они экономят. Если кэширование добавляет больше работы, чем экономит, — оно вредит.
- Делать меньше — всегда быстрее.

## Правило 2: Казаться быстрым ≈ быть быстрым

- «Feeling fast is pretty much as good as actually being fast» — если интерфейс отзывчив (печатаешь без лагов), приложению необязательно быть быстрее по факту.
- Примеры приёмов, которые не ускоряют реально, но улучшают восприятие:
  - **Preloading** (предзагрузка) — технически не быстрее, но ощущается быстрее.
  - **Optimistic updates** — UI обновляется до ответа сервера; сервер не ускоряется, но лучше, чем смотреть на пустоту.
- Связанные performance primitives: **useTransition**, **useDeferredValue** и др. Их суть — сделать важное (urgent) раньше, а неважное может подождать, даже если общее время то же.

## Что значит «производительность» для вашего приложения

- Метрики вроде **time to first meaningful paint** критичны для **content site** (контентного сайта): от них зависит bounce rate. Там важны critical CSS, порядок загрузки (сначала контент/текст).
- Для **application** (приложение, в котором пользователь долго работает) логика иная: допустимо заплатить небольшую цену загрузки на старте, чтобы каждое последующее взаимодействие было snappy.
- Вывод: нужно определить, что именно значит performance для конкретного приложения, и делать критичное в первую очередь.

## Карта курса (куда движемся)

1. **Форма приложения / архитектура** — наибольший эффект. Правильно размещённый state + корректные cache/memoization → нет лишних ре-рендеров. «Хорошо в любом случае» = производительно.
2. **Memoization — палка о двух концах.** Может и навредить.
   - Отсылка к шутке: «два сложнейших вопроса в CS — naming things, **cache invalidation** и off-by-one errors». Ключевое здесь — cache invalidation.
   - Типичные баги: что-то не обновляется, т.к. система считает закэшированное значение актуальным, хотя оно изменилось. Часто вызвано избыточным навешиванием `React.memo` на всё подряд — проверка «нужно ли обновляться» сама по себе работа; для компонентов, которым memo не нужен, это медленнее, чем без него.
3. **Progressive loading** через **Suspense** — грузить нужное сейчас, остальное позже. Ощущается быстрее, потому что реально быстрее.
4. **Transition APIs** (`useTransition` и др.) — дают возможность разметить, что urgent, а что может подождать. В ранних версиях React такой возможности не было. Решают конкретный класс задач, часто в ~5 строках кода.

## Важно про новые API

- React усложнился «под капотом», но многие новые API **просто использовать** — сложность внутри, простота снаружи.
- Раньше был «один молоток» в наборе инструментов; теперь их 4–5. Задача — знать, какой инструмент под какой «гвоздь».

## Главное

- Правило 1: делать меньше — быстрее; идеал — не ре-рендерить лишнего. Memoization/caching оправданы, только если экономят больше работы, чем добавляют.
- Правило 2: воспринимаемая скорость почти равна реальной — preloading, optimistic updates, приоритизация urgent-работы.
- Performance определяется типом приложения: content site (метрики загрузки, bounce) vs application (цена на старте ради snappy-взаимодействий).
- Осторожно с `React.memo` на всё подряд — cache invalidation и лишние проверки создают тяжёлые баги; баланс достигается через архитектуру, Suspense и transition APIs.
