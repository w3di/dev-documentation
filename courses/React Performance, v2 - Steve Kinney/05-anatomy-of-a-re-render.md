# Anatomy of a Re-render (Анатомия ре-рендера)

## Три причины ре-рендера

Без какой-либо memoization компонент ре-рендерится по одной из трёх причин (это практически исчерпывающий список):

1. **Изменился собственный state** компонента — `useState` (или `setState` у class-компонентов).
2. **Изменился context** — Context API «из коробки» вызывает ре-рендеры по всему приложению часто неожиданным образом.
3. **Ре-рендерился родитель** — самая частая причина в простом приложении, где хуки и state живут в корневом компоненте `App`.

- Важно: по умолчанию React **проходит всё дерево вниз**, проверяя каждого потомка, даже если кажется, что должно работать иначе. Остановить это можно вручную (memoization) либо через **React compiler**.
- Логика остановки: если у компонента ничего не изменилось, можно считать, что у его детей тоже ничего не изменилось — и не идти глубже. Но если ниже по дереву есть Context API, обход возобновляется.

## Render phase и Commit phase

При изменении state React реагирует серией шагов:

1. **Render phase** — React вызывает функции компонентов (компонент = функция). Всё происходит в памяти через **virtual DOM** (виртуальный DOM — копия дерева в памяти). Работа в памяти быстрее, чем мутации реального DOM с repaint/relayout/reflow.
   - Рендер компонента = вызов его функции; рендер его детей = вызов их функций. React спускается по структуре в памяти и собирает все изменения.
2. **Commit phase** — собранные изменения применяются к реальному DOM.
   - У React есть **heuristics**: для одних изменений эффективнее хирургически переставить пару DOM-узлов, для других — контринтуитивно — быстрее снести целую секцию DOM и пересоздать с нуля. Это «good enough» алгоритм, продуманный командой React.
   - Нюанс: команда сеньоров может написать vanilla JS быстрее React, тонко настроив всё вручную. Но для больших команд с разным уровнем и дедлайнами эвристик React достаточно.
3. После commit — cleanup-шаги: вызов `useEffect` и др. Затем приложение в settled state до следующего изменения.

## Способы «делать меньше»

- **Остановить обход на середине дерева** через memoization (`React.memo`): если компонент — **pure function** (получает props, без внутреннего `useState`) и props те же, что и раньше → тот же вход даёт тот же выход. Можно сказать React: проверь только входные props, не рендери ради проверки результата. Если props не изменились — обход дерева ниже останавливается.
- **Начать изменение ниже по дереву** — игнорировать всё, что выше. Тоже «делать меньше».
- **Приоритизация (React 18/19)** — новый слой: решать, что urgent (нужно сейчас), а что может подождать.

## React Fiber

- До **React Fiber** обход дерева и вызов функций был **blocking, single-threaded**: если во время рендера случалось что-то более важное — оно ждало.
- После Fiber появились primitives, позволяющие декларативно указывать, что и когда нужно делать. Добавился слой: помимо «начать ниже / остановить выше» — «идёт это в fast lane или нет».
- При введении memoization третья причина ре-рендера («родитель изменился») заменяется на более нюансированную (проверку props).

## Context API: за и против

- **Context API** даёт условно «глобальный» state вне дерева, доступный низко в дереве без передачи через промежуточные компоненты.
- Альтернатива без него — **prop drilling** (проброс props): state живёт в ближайшем общем предке и пробрасывается через все промежуточные компоненты, которым он не нужен, до нужных потомков. Минусы:
  - Проблема **maintainability/sanity** (не производительности): чтобы перенести что-то из sidebar в footer, нужно «распутать» и заново протянуть props через всё приложение.
  - До официального Context API существовал внутренний неофициальный context, который использовали Redux и др.
- Минус Context для производительности: **если context изменился, все подписанные на него компоненты ре-рендерятся, и теоретически все их дети.**
  - Типичная плохая привычка: один большой context provider, в который свалено всё. Тогда любое изменение → ре-рендер почти всего.
  - Решение (спойлер): **разбить на несколько context'ов**. Цена — «pyramid of doom» из провайдеров в `index.ts`.

## Re-renders сами по себе не плохи

- Если state изменился — компонент **должен** ре-рендериться (иначе это была бы HTML-страница). Плохи только ре-рендеры, которые не должны были произойти (вышел тот же результат — работа впустую).
- Важная ловушка: в context часто кладут и state, и функции (например, обработчик кнопки delete). Сам обработчик не должен вызывать ре-рендер, но если он завязан в один объект с изменившимся state → React видит **новый объект** и ре-рендерит.
- Принцип React (и React compiler): при сомнении он **всегда ре-рендерит**, а не рискует показать неверное. Если compiler не может доказать корректность оптимизации — он просто не оптимизирует. Плохая memoization хуже отсутствия: «сэкономил рендер, но показал неверное» — невалидный state.
- Прагматика: если весь app ре-рендерится за миллисекунду — не оптимизируй вообще, не жертвуй ергономикой ради незаметного выигрыша. Context API можно сделать производительным с помощью разбираемых далее primitives, но это всегда зависит от конкретного приложения.

## Классификация state changes

- Два типа: **necessary** (необходимые) и **unnecessary** (лишние).
- Necessary делятся ещё на: **urgent** (срочные) и **non-urgent** (несрочные).
- Приоритет: сначала urgent, затем necessary, и по возможности не делать unnecessary — **если** стоимость сложности по их предотвращению не превышает выгоду.
- Пример urgent vs non-urgent: ввод в search-поле при сортировке 10 000 записей. Сортировка может тормозить, но критично, чтобы **keystrokes отображались сразу** (urgent), а пересчёт результатов с loading-индикатором может подождать (non-urgent).
  - Принцип восприятия: «лучше no Wi-Fi, чем bad Wi-Fi». Если клик/скролл/ввод замораживаются — пользователь злится; если интерфейс отзывчив, секундное ожидание данных терпимо.

## Темы курса через призму правил

- **Не делать = быстрее**: класть state в правильное место, чтобы не триггерить части дерева, которым он не нужен (вопрос структуры компонентов и state management).
- **Пропустить работу дешевле, чем сделать**: но если проверка дороже самой работы — не проверять.
- **Отложить работу**: вместо ручного жонглирования тремя state (`loading` boolean, `error` boolean, данные) — **Suspense**: сообщает reconciler «мы приостановлены, ждём промис, вернись позже». Проще, надёжнее и производительнее ручного подхода.
- **Загружать столько, сколько нужно, и так мало, как получится** — финальная цель, сильно зависит от конкретного приложения.

## Главное

- Без memoization React всегда обходит всё дерево вниз; три причины ре-рендера — собственный state, context, ре-рендер родителя.
- Цикл: render phase (вызов функций в virtual DOM) → commit phase (применение к DOM по эвристикам) → cleanup (`useEffect`).
- Context API хорош для maintainability (убирает prop drilling), но при одном «большом» провайдере вызывает массовые ре-рендеры — решение в разбиении на несколько context'ов.
- Re-renders не зло; цель — убрать unnecessary и приоритизировать urgent над non-urgent (Fiber, Suspense, transition APIs), не доводя оптимизацию до вредной сложности («it depends»).
