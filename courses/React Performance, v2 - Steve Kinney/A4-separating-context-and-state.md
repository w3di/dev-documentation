# Separating Context & State — раздел Context (архивный курс v1)

> Дополнение из старого курса (archive). Темы нет в v2.

## Идея урока

- Помимо **component hierarchy** есть **state hierarchy** — и никакие memo/context не спасут от плохой структуры данных. Многое из этого — концептуальное понимание; собственно работа — муторное перекладывание данных.

## Сюрприз №1: `children` + меняющийся массив

- Паттерн «pull content up with children» обычно спасает от ре-рендеров: проблемный компонент **физически живёт в родителе**, React видит «тот же компонент в памяти, он не на пути изменения» — и не трогает его (как в примере с игрой, где дорогой компонент был слотом между частями).
- **Но**: если `children` генерируются через `map` по **массиву users**, то при удалении пользователя массив **пересоздаётся** → пересоздаётся **массив children** → React его выбрасывает и ре-рендерит. Профайлер показывает «props changed: children».
- Вывод: `children` помогают, только если сам набор children стабилен. Это игра про то, как **JavaScript хранит объекты в памяти** и immutable state: спред-операторы создают новые ссылки, ломая memo.
- Лектор не закладывал этот баг специально — наткнулся сам. Мораль: вырабатывать привычку периодически проверять «unhappy path» (как «а что если эмодзи в инпут?») — does this perform? Лишние mount/unmount могут давать неожиданные side effects (например, у компонента `useEffect` с web socket).

## Сюрприз №2: вложенные immutable-структуры

- Удаление **одного комментария** ре-рендерит **весь post** — никакие memo не помогут.
- Причина: данные — **дерево** (post → comments[] → user внутри). Чтобы immutably изменить что-то в глубине, нужно спред-оператором пересобрать всё снизу вверх: comment → comments → post.
- Каждая пересборка = **новый объект в памяти** → ломает все memo, завязанные на ссылочное равенство. Сам акт изменения immutable-дерева триггерит каскад ре-рендеров, независимо от React.
- Дублирование (user «вшит» в comment, хотя есть отдельный список users) — две точки правки для одного имени.

## Два главных тезиса

1. **Component hierarchy** иногда важнее инструментов оптимизации.
2. **State hierarchy** не менее важна: в начале проекта продумать структуру state (независимо от того, что отдаёт API), потому что потом вес рефактора становится неподъёмным.
- Реальность: API часто не те, что хочется («fight with the APIs you have»). Полезен **слой трансформации** между API и view (даже если есть Backend for Frontend).

## Главное

- Структура state важна не меньше структуры компонентов; плохую структуру не вылечить memo/context.
- `children` спасают от ре-рендеров только при стабильном наборе children; `map` по меняющемуся массиву пересоздаёт children и ломает оптимизацию.
- Глубоко вложенные immutable-данные при любом изменении пересобираются снизу вверх (новые ссылки) → каскад ре-рендеров; продумывать форму state в начале проекта.
- Вырабатывать привычку проверять «а это перформит?» по ходу написания кода.
