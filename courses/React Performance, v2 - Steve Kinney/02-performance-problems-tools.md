# Performance Problems & Tools (Типы проблем и инструменты)

## Два типа проблем производительности

### 1. Большое узкое место (bottleneck)

- Один заметный, ощутимый тормоз: открываешь Chrome DevTools — и сразу его видишь.
- Свойства: **clear and present danger** — очевиден, локализован; «убрал занозу — и проблемы нет».
- Хорошая новость: часто решается малым числом строк кода.
- Раньше (React 15/16) такие задачи были **terra incognita**: приходилось бить в «escape hatch» — брать **ref** и временно уходить в vanilla JavaScript.
- Сейчас новые возможности React 18/19 (**transitions**, **React Fiber**) превращают вчерашние «месячные» проблемы в фикс на 5 строк. Важно: эти API могли «появиться незаметно» — опытные разработчики о них слышали, но не используют по привычке.
- Пример продвинутого приёма — **optimistic updates** (оптимистичные обновления — показ результата до ответа сервера). Старый способ (ручные boolean-флаги `loading`/`error`, переключаемые в `.then`/`.catch`) заменяется более простыми API.

### 2. Накопление мелочей (death by a thousand cuts)

- Множество мелких неоптимальностей, каждая по отдельности незначительна, но в сумме всё тормозит.
- Каждый отдельный случай не уникален — типовые ошибки.
- Нюанс про совет «оптимизируй только когда есть проблема»: он верен (over-optimization и premature optimization — плохо), но **prevention is the best medicine**. Когда таких мелочей тысяча, рефакторинг может занять месяц — а такой объём тяжело согласовать с руководством/продактами.
- Вывод: ловить проблемы **early and often** — и при написании кода, и на **code review**, чтобы не допустить накопления.

### Сравнение

- Большая проблема: всё не загружается, надо чинить немедленно (пример: страница грузилась 2 минуты).
- Мелкие: накапливаются незаметно, разматывать потом почти невозможно.
- Важно: бывают проблемы, которые не починить силами фронтенда (пример: 10 API-вызовов ради полной модели пользователя; «лучший API» все согласны сделать, но он не готов уже 4 года). Часть проблем возникает «несмотря на все добрые намерения» — задача в том, чтобы научиться с ними жить и навигировать.

## Инструменты

- **React Developer Tools** — Chrome-расширение, встраивается в Chrome DevTools.
  - Ключевая фича: **подсветка ре-рендеров** (компонент мигает при перерисовке). Видно, что мигает то, что мигать не должно — то есть лишние ре-рендеры.
  - Лечение часто простое: рефакторинг управления state, небольшие изменения архитектуры, правильное использование **Context API**. Это полезно и для performance, и для maintainability.
  - Позволяет видеть, что выполняется долго — и на уровне Chrome DevTools / чистого JavaScript, и на уровне конкретных компонентов.
- Нужно ли строго обязательно? Нет. Стоит ли поставить? Да. (Предполагается работа в Chrome; поведение в Edge/Firefox/Safari не гарантировано.)

## Главное

- Различай два класса проблем: один большой **bottleneck** (заметен, часто чинится быстро современными API) и накопление мелочей (**death by a thousand cuts**, дешевле предотвращать, чем чинить).
- Современный React (18/19: transitions, Fiber, optimistic updates) решает «гнарли»-задачи прошлого малым кодом — стоит освоить новые API вместо старых привычек.
- Профилактика мелких проблем — на этапе написания кода и code review.
- Главный инструмент диагностики — **React Developer Tools** с подсветкой ре-рендеров; лекарство часто лежит в архитектуре state и Context API.
