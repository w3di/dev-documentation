# React.memo & Referential Equality — раздел Memoization

## Три инструмента memoization

- Два **хука**: `useCallback`, `useMemo`.
- Один **higher order component (HOC)** — `React.memo`: «обёртка вокруг компонента» (термин был популярнее несколько лет назад). Проверяет: «те же ли props, что в прошлый раз?». Если да и компонент **pure** — тот же вход даёт тот же выход, рендер можно пропустить.

## Pure component

- **Pure component** — то, что выходит, напрямую зависит только от того, что входит.
- Проще описать, что **не** pure: всё, что содержит `useState` или `useContext` — они могут измениться сами по себе. Оборачивать такое в `React.memo` бессмысленно: компонент всё равно может ре-рендериться по своим причинам.

## Почему React не делает memo для всего автоматически

1. **Проверка — это работа** (сама по себе стоит времени).
2. Выгодно только для pure-компонентов.
3. Исторически React работал **только в runtime** — мог лишь выполнять код, но не анализировать его. С появлением **React compiler** это меняется: код можно статически анализировать до запуска.

## Что делает React.memo: referential equality

- Сравнивает props через **referential equality** (ссылочное равенство):
  - примитивы равны по значению: `true === true`, `1 === 1`, `"foo" === "foo"`;
  - два объекта/массива с одинаковым содержимым — **разные** в памяти, не равны;
  - две функции (без `useCallback`) — разные объекты в памяти.
- Парадокс: приёмы immutable state (создавать новый объект, чтобы вызвать рендер) — ровно то, что **ломает** `React.memo`.
- Что **не ломает** memo (примитивы): boolean, string, number, `null`, `undefined`, symbol.
- Что **ломает**: spread всех свойств, передача не-примитивов (новые объекты/массивы/функции). Без `useMemo`/`useCallback` можно обернуть в `React.memo`, и он не даст эффекта.

## Эвристики React.memo

- Сначала **дешёвая проверка**: одинаковое ли число ключей? Если разное — объекты точно разные, дальше не сравниваем (принцип «делать меньше = быстрее»).
- Затем — **поверхностная (shallow)** проверка: тот же ли объект в памяти. **Не** глубокая (deeply nested).
- Антипаттерн: «буду deep-equal всё подряд» — одна из самых дорогих операций; «memo любой ценой» становится вредным.

## Запутанность → React compiler

- Ручная схема сложна: оборачивать функции в `useCallback`, дорогие вычисления в `useMemo`, компоненты — в `React.memo` (это **не** то же, что `useMemo`).
- **React compiler** статически анализирует код на build time и применяет большинство этих паттернов за разработчика.
- Это не уникально для React: **Svelte** и **Solid** делали так с самого начала — анализ на build time, применение оптимизаций, удаление части runtime-зависимостей. Меньше работы в runtime = быстрее.

## Главное

- Три инструмента: `useCallback` и `useMemo` (хуки) + `React.memo` (HOC, проверяющий props на referential equality).
- `React.memo` помогает только pure-компонентам (без `useState`/`useContext`) и только при стабильных props.
- Referential equality: примитивы сравниваются по значению; объекты/массивы/функции — по ссылке, поэтому новые объекты ломают memo. `React.memo` делает shallow-проверку (число ключей → ссылка), не deep.
- Ручная связка хуков сложна и хрупка — её и автоматизирует React compiler через статический анализ на build time (как Svelte/Solid).
