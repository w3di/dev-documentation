# Using Multiple Contexts — раздел Context (архивный курс v1)

> Дополнение из старого курса (archive). Темы нет в v2.

## Диагноз проблемы

- `value={{ items, dispatch }}` собирает два значения в **новый объект** на каждом рендере. `items` и `dispatch` по отдельности могут быть теми же, но **сам объект новый** → инвалидирует все `React.memo`-проверки.
- ES6-деструктуризация прячет, что `dispatch` достаётся из нового объекта. Правила React не нарушены — мы сами отписались от оптимизаций, оставив бесполезные `React.memo`.

## Решение: два контекста

- Один контекст создал проблему → **два контекста** её решают.
- Принцип: re-renders сами по себе не плохи — плохи лишь нежелательные. Разделить:
  - **ItemsContext** — для того, что **меняется** (список items);
  - **ActionsContext** — для того, что **не меняется** (dispatch).

```js
const ItemsContext = createContext();
const ActionsContext = createContext();

export function ItemsProvider({ children }) {
  const [items, dispatch] = useReducer(reducer, initialItems);
  return (
    <ActionsContext.Provider value={dispatch}>
      <ItemsContext.Provider value={items}>
        {children}
      </ItemsContext.Provider>
    </ActionsContext.Provider>
  );
}
```

- `value={dispatch}` — статичное значение, никогда не меняется. `value={items}` — меняется, но это нормально.

## Tasting note: порядок провайдеров

- **Порядок важен** (по крайней мере, так считалось): все родители триггерят ре-рендер детей, поэтому **неизменяемый контекст — снаружи**, изменяемый — внутри (как push state down).
- Оговорка лектора: после обсуждения «children pulled up» он засомневался — возможно, порядок значит меньше, чем казалось (делал по привычке с 2018 г.). Стоит поэкспериментировать.
- Memoize значения можно, но не нужно — «делать = медленнее, чем не делать».

## Прячем сложность в кастомные хуки

- «Сделал плохое — прикрой» (абстракции — это «ложь», вся техника на электронах в проводах). Инкапсулировать оба `useContext` в хуки:

```js
export function useItems() {
  return useContext(ItemsContext);
}
export function useDispatch() {
  return useContext(ActionsContext);
}
```

- Потребители вызывают `useItems()` / `useDispatch()` вместо прямого `useContext`.
- Бонус: единая точка для будущей миграции (например, на Redux с его `useDispatch`) — меняешь один файл.
- `dispatch` оборачивать в `useCallback` не нужно — он и так стабилен.

## Итог по профайлеру

- Performance-гейны вернулись: ядро ре-рендерится <0.1 мс. Цена возврата — **сложность**, которую просто спрятали в одном месте (как сложность в исходниках React).
- Можно убрать `React.memo` с `ItemList`, т.к. он теперь получает только меняющиеся items, без лишнего проброса.

## Q&A нюанс

- Если `children` вычисляются до провайдера, они в первый раз могут получить дефолтное значение контекста, но при state changes сразу «подцепляются» к актуальному (context = prop, идущий сбоку от обычной иерархии и триггерящий ре-рендеры).

## Главное

- Разделить контекст на два: **меняющееся** (items) и **стабильное** (actions/dispatch) — это возвращает memoization.
- Неизменяемый провайдер — снаружи изменяемого (как push state down); но порядок стоит проверить экспериментом.
- Прятать `useContext` в кастомные хуки (`useItems`, `useDispatch`) — удобство + единая точка миграции; сложность не исчезает, а инкапсулируется.
