# Memoization with useMemo — раздел Memoization

## Пример Memomania

- Приложение `Memomania` с намеренно дорогими операциями (Fibonacci, факториалы и пр.). Классическая проблема: изменение чего угодно ре-рендерит почти всё.
- Для каждого примера в репозитории есть пошаговый guide. Цель урока — не довести оптимизацию до конца, а показать **как триажить**: понять, стоит ли memoization усилий.

## Триаж через Profiler

- Записать действия (record) → посмотреть, **почему** компонент ре-рендерился.
- Если причина не «parent changed» и не «изменились нужные props» — есть возможность для оптимизации.
- Замер показывает время каждого рендера (пример: общий цикл 231 мс, но конкретный рендер — лишь 3.1 мс). В крошечном приложении абсолютные числа малы.
- Видно, что «card calculation» ре-рендерится постоянно, хотя кажется, что не должен — повод заглянуть в код.

## Применение useMemo

- `calculate` дорогая и выполняется на **каждом** рендере карточки. Математика «чистая»: при тех же типе и входе — тот же результат (lambda calculus).

```js
const result = useMemo(
  () => calculate(calculationType, calculationInput),
  [calculationType, calculationInput]
);
```

- **Ключевой нюанс (tasting note): передавать в зависимости примитивы, а не объект.**
  - Соблазн положить весь объект `calculation` в зависимости. Но объект может быть **новым в памяти каждый раз** → memo сломается.
  - Важны примитивные значения: `calculationType` (string, union строк), `calculationInput` (number).
  - Всегда спрашивать: я работаю с примитивом (отлично) или с целым объектом (тогда: получаю ли я новый объект, даже если он «выглядит так же»?). `console.log` покажет одинаковое содержимое, но это не значит, что они referentially равны.

## Trade-off кэширования

- Кэширование = размен **скорости рендера на память**: хранение последнего значения занимает больше памяти, чем нехранение.
- Если «сделать» дешевле, чем «проверить и достать из кэша» — кэш вреден. Именно поэтому memoization сложна.

## Эффект

- После `useMemo`: карточка с прежними type/input **не пересчитывается**, даже если ре-рендерилась из-за новых функций `onUpdate`/`onDelete` (их стабилизируют отдельно, см. прошлый урок). Добавление новых карточек не запускает пересчёт уже существующих.
- Полная «блокировка» достигается комбинацией: `useMemo` на вычисление + `useCallback` на функции + `React.memo` на компонент.
- Результат маленького изменения: время цикла упало с ~31 до ~23 мс — неплохо для одной строки.

## Сегвей к React compiler

- Ручная схема = анализ кода + применение эвристик для расстановки аннотаций. Кто отлично следует инструкциям и эвристикам? **Компьютеры.** Логично делать это на build time, а не вручную в runtime (ручное оборачивание само добавляет функции и нагрузку на call stack).

## Главное

- `useMemo` кэширует результат дорогого вычисления при неизменных зависимостях.
- Главный нюанс: в зависимости класть **примитивы** (string, number), а не объекты — объект может быть новым в памяти каждый раз и сломать кэш.
- Кэш — это размен скорости на память; если проверка дороже самого вычисления, memo вредит. Триажить через Profiler («почему ре-рендер»).
- Полная оптимизация = `useMemo` + `useCallback` + `React.memo` вместе; ручная рутина → автоматизируется React compiler.
