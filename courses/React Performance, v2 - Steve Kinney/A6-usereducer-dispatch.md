# useReducer & dispatch — раздел Reducing Renders (архивный курс v1)

> Дополнение из старого курса (archive). Темы нет в v2.

## Отвергнутая альтернатива (two lists)

- Packed/unpacked списки генерируются «на лету» фильтрацией общего списка. Можно было бы хранить **два отдельных списка** и вручную перекладывать элементы между ними, с unit-тестами и отдельными add/update/remove на каждый.
- Лектор **отказался**: complexity cost и дублирование не оправданы ради почти нулевого выигрыша. Но важен принцип: **не тянуться слепо к одному инструменту**, смотреть на flame chart — ре-рендерится ли то, что ожидаешь.

## Проблема, которую решает useReducer

- Отдельные `item` получают **новые** `update`/`remove` функции на каждом рендере → ре-рендерятся.
- Если пробрасывать `setItems` или `dispatch` целиком, они **статичны** (не пересоздаются от items).

## Переход на useReducer

```js
const [items, dispatch] = useReducer(reducer, getInitialItems());
```

- `dispatch` **только запускает actions** — ему не нужно знать текущие items: «toggle этот item». Reducer получает всё состояние и сам разбирается.
- `useState` — абстракция над `useReducer`; «разные вкусы одного и того же». Functional updater `setItems(prev => ...)` дал бы тот же эффект (доступ к текущим items без проброса).

## Эффект

- `dispatch` пробрасывается насквозь → можно **удалить все `useCallback`**, которые писали ранее. Внутри `item` обработчики просто `dispatch(action)`.
- Action creators с теми же именами просто импортируются.
- Результат: отдельные items больше **не** ре-рендерятся:
  - они получают тот же `dispatch` (стабильный);
  - сами объекты в массиве — те же в памяти (immutability: новый **массив** ≠ новые **объекты** внутри, «новая коробка, те же вещи»).
- Осталась только `React.memo` с самого начала; **удаление `useCallback` оказалось производительнее**, чем его использование — «делать меньше = быстрее».

## Бонус: то же через useState

- `useState(getInitialItems)` + `setItems(prev => ...)` с хелпер-функциями (`updateItem(items, id, updates)`, toggle и т.п.) даёт те же гейны без единого `useCallback`.

## Q&A: почему useReducer лучше useMemo/useCallback?

- Не «морально лучше» — просто `dispatch` **не нужно** оборачивать в `useCallback`. `useCallback` нужен был, потому что функции создавались на лету; он говорит «не давай новую ссылку, пока не изменились зависимости». `dispatch` всегда один и тот же с момента вызова хука — устраняет нужду в `useCallback` полностью. «Делать меньше лучше, чем делать больше».

## Q&A: преимущества Redux над useReducer?

- `useReducer` даёт reducer + dispatch. Чего **нет**: middleware, Redux DevTools, встроенной TypeScript-поддержки react-redux.
- Важно: современный **react-redux** (текущая версия) **не использует Context API**, а `useSyncExternalStore`. Store создаётся один раз вне компонентов (статичный объект в памяти) с `getState`/`subscribe`; при неизменном state возвращает **тот же** объект — performance-гейны «из коробки», без ручной работы с двумя контекстами.
- `useReducer` не замена Redux, а «короткая дистанция, на которую идёшь пешком». Нужен небольшой reducer (форма, много меняющихся полей, выводим итоговый state) — Redux избыточен.

## Q&A: Redux + useReducer вместе

- Не «или-или». Разные типы state:
  - **model / business logic** → Context API или Redux (глобальное);
  - **ephemeral state** (валидна ли форма? открыт ли аккордеон?) → `useReducer`, даже если Redux есть в проекте.
- Пример: вместо form-библиотек (которые «выкидываешь через неделю») — один reducer, который собирает значения и выдаёт список ошибок, легко тестируется.

## Главное

- `useReducer` отдаёт стабильный `dispatch`, который не нужно оборачивать в `useCallback` → можно удалить рукописные `useCallback` и получить выигрыш («делать меньше»).
- `dispatch` не знает о state — лишь шлёт actions, reducer всё вычисляет; `useState` — абстракция над `useReducer`.
- Новый массив ≠ новые объекты внутри (immutability) — поэтому memo на items продолжает работать.
- Redux добавляет middleware/devtools/типы и не использует Context (а `useSyncExternalStore`); useReducer — для эфемерного/локального state, не замена Redux. Главный посыл — взвешивать варианты, а не применять один слепо.
