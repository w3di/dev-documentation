# Lanes (Полосы приоритета)

## Идея lanes

- В React Fiber есть концепция **lanes** (полос приоритета): обновления попадают в полосы, и React обрабатывает их от высшего приоритета к низшему — «fast lane» против низкоприоритетной полосы.
- Категорий полос всего ~6 (точнее — 6 категорий, т.к. transition-полос может быть до 16). Разработчику доступны фактически только 2, поэтому на практике можно мыслить двумя.

## Два типа обновлений (практический взгляд)

- **Urgent** (срочные): пользователь напечатал, кликнул кнопку — то, что важно отразить немедленно.
- **Non-urgent** (несрочные): большая перерисовка графика, сортировка списка — долгие операции. «Не urgent» ≠ «не важно»; просто не должно идти в ущерб отклику на действия пользователя.
  - Пример: фильтрация Pokémon по `CHAR`; пользователь удалил `R` → начатый пересчёт уже неактуален.
- Что urgent, а что нет — **решает разработчик**. Если ничего не помечено — всё urgent. «Если всё срочно — ничего не срочно».
- Ключевой принцип: помечают **не** urgent-вещи, а **не-urgent** — тогда urgent проходят свободно. Без opt-in приложение не делает это магически, и **React compiler пока тут не помогает**.

## Справка: 6 полос (со слайда)

| Полоса | Описание |
|---|---|
| **SyncLane** | Немедленные, блокирующие обновления (например, через `flushSync`) |
| **InputContinuousLane** (user actions) | Clicks, keypresses, dragging, scrolling |
| **DefaultLane** | Обычный ход дел (the normal course of business) |
| **TransitionLanes** | То, что явно помещено в полосу низкого приоритета |
| **RetryLanes** | Упавшее, ожидающее повторной попытки |
| **IdleLane** | Работа самого низкого приоритета |

## 6 категорий полос

1. **Sync lane** — только для React; можно вызвать через `flushSync` («не хочу Fiber, перерендери весь DOM немедленно, отключи меня от всего»). На практике почти никогда реально не нужно — совет: считать, что её нет.
2. **Input continuous lane** — действия пользователя: clicks, key presses, drag, scroll. Высокий приоритет (пользователь должен «чувствовать отклик»; ввод, медленно появляющийся в поле, бесит сильнее всего). Управляется React, не разработчиком.
3. **Default lane** — обычные обновления. Тоже управляется React.
4. **Transition lanes** — единственное, чем управляет разработчик. Низкоприоритетные: «нужно сделать, но отзывчивость важнее». Попадают сюда только при явном opt-in (до 16 transition-полос).
5. **Retry lanes** — для того, что упало и получает повторную попытку; низкий приоритет.
6. **Idle lane** — связана с **off-screen / activity APIs** (контент полностью за пределами экрана — не «вне viewport» и не CSS `hidden`). На момент записи это приватные, нестабильные API — пользоваться нельзя.

Под капотом полосы реализованы через **bitwise operators** — сравнение битов гораздо быстрее, чем обход массивов или сравнение свойств объектов. Видеть этот код напрямую не придётся.

## Обработка полос

- React назначает каждое обновление в подходящую полосу, по возможности **группирует** обновления одной полосы и обрабатывает от высшего приоритета к низшему.
- Если при «выныривании» приходит обновление выше приоритетом — React переключается на него (может приводить к неожиданному поведению, если о механизме не знать). По умолчанию должно «просто работать».

## Commit phase

- **Render phase можно прервать** (остановить, приостановить, вклинить другое). **Commit phase прервать нельзя** — это акт изменения реального DOM; начав, надо довести до конца, иначе DOM останется наполовину обновлённым.
- Render phase обновляет **virtual DOM** (current tree + work-in-progress). Когда virtual DOM «устаканился», известно, что нужно сделать с DOM, и commit это применяет.
- Шаги commit:
  1. «Снимок» состояния — чтение максимума информации о DOM (для class-компонентов — `getSnapshotBeforeUpdate`).
  2. Применение изменений к DOM.
  3. Запуск passive effects и cleanups.

## useLayoutEffect и useEffect

- **`useLayoutEffect`** срабатывает **до** отрисовки DOM. Нужен library authors (например, движкам рендеринга — прочитать DOM до отрисовки). Опасность: **блокирует весь commit-процесс** — тяжёлые операции/API-вызовы внутри застопорят всё. Использовать только если это единственное решение.
- **`useEffect`** срабатывает **после** того, как пользователю всё показано — здесь уместны API-вызовы.

## API-вызовы в useEffect и Suspense

- Классический паттерн: `useEffect` с пустым массивом зависимостей вызывает API после первого commit → данные приходят → повторный рендер. Долгое время это был «благословлённый» способ, хотя и не идеальный.
  - Логика была не «получить неполные данные», а «показать хоть что-то, не пустоту» — Suspense тогда не существовало.
- **Suspense** — лучшая альтернатива: при обходе дерева React встречает suspense point, API-вызовы стартуют сразу, показываются suspended-узлы (loading). Если данные вернутся до завершения рендера и React сочтёт это достаточно быстрым — пользователь получит результат сразу, без «вспышки пустоты».
- Бонус: Suspense упрощает работу с асинхронностью и **TypeScript** — вместо «null или значение» везде можно сказать «ничего не делать, пока нет значения». Перформанс-улучшения часто заодно облегчают жизнь разработчику.
- Важно: старый best practice не стал «неправильным» — просто появились лучшие способы. Без opt-in поведение остаётся прежним, ничего не ломается.

## Главное

- Lanes дают приоритизацию; помечать нужно **не-urgent** работу (через transition lanes — единственное, чем управляет разработчик), urgent проходит сама.
- 6 категорий полос: sync, input continuous, default (управляет React), transition (управляет разработчик), retry, idle; реализованы на bitwise-операциях.
- Render phase прерываема и работает с virtual DOM; **commit phase непрерывна** — снимок → изменение DOM → effects.
- `useLayoutEffect` (до отрисовки, блокирует commit, осторожно) vs `useEffect` (после, для API). Современная альтернатива загрузке данных через useEffect — **Suspense**.
