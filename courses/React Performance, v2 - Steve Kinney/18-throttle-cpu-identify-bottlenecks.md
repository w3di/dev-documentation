# Throttle CPU to Identify Bottlenecks — раздел Transitions & Deferred Values

## Демо-приложение (Pokémon)

- Приложение со списком ~1041 Pokémon и поиском.
- Поиск — **fuzzy search** (нечёткий поиск): ищет по имени, описанию, типам и species, по вложенному объекту. По сути дорогая операция по тысяче элементов.

## Диагностика

- При вводе ощущается заметный лаг (CPU throttling включён «для драматизма», но не сильно).
- В обычных **Chrome DevTools** (не React): record → видно, что **CPU максимально загружен** долгими периодами.
- Chrome помечает проблемные участки **красным флажком** («это заняло слишком долго»). Цель — укладываться в **16.6 мс** (60 fps); здесь отдельные события занимали до секунды — это >60 кадров.
- Самый «хаотичный» симптом: **keystroke не успевает отобразиться** — палец уже поднят, а символ ещё не на экране.

## Что хочется

- Нельзя полностью ускорить сам поиск (можно частично оптимизировать). Поэтому цель:
  - показывать ввод пользователя **немедленно** (snappy);
  - возможно, показать **индикатор загрузки** («работаем над этим») — даже это лучше, чем пустота/зависание.
- Это даёт **React Fiber**: начатая работа может быть прервана. Если нажат новый символ — старый поиск уже не нужен, а нажатие должно быть **высокоприоритетным** (показать ввод первым), а фильтрация списка — в фоне.

## Главное

- Воспроизводи реальные условия через **CPU throttling** + обычные Chrome DevTools (видны загрузка CPU и красные флажки «слишком долго»).
- Ориентир — 16.6 мс на кадр; дорогая синхронная работа (fuzzy search по 1000+ объектам) блокирует ввод и ломает отзывчивость.
- Решение не в ускорении самой операции, а в приоритизации: мгновенно показывать ввод, а фильтрацию выполнять в низкоприоритетной полосе (через transitions).
