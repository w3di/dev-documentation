# Memoization with useCallback — раздел Memoization

## Идея memoization

- Если всё, от чего зависит значение/функция, не изменилось — само значение/функция тоже не должно меняться. React даёт «подсказки» через хуки.
- Проблема (из прошлого урока): функции-обработчики определяются заново на каждом рендере, т.к. зависят от `count` и `setCount`, поэтому их нельзя просто вынести за пределы компонента.

## React compiler (отступление)

- Да, **React compiler** делает многое из этого автоматически. Но:
  - Это **миграционный процесс** (как обновления React 17→18→19, занимающие много времени). На момент записи compiler — **release candidate** (используется в проде на Instagram.com).
  - Compiler консервативен: «если я не понимаю, что происходит — не делаю ничего». Поэтому понимание концепции остаётся важным.
  - Часть memoization — не про performance, а про предотвращение дорогих операций или иные цели; некоторые случаи — антипаттерны, которые compiler не тронет.
  - Внедрить сразу может быть нельзя (как любую новую фичу — надо подождать).

## Два хука memoization

- **useMemo** — «то, что ты вычислял для получения значения: если зависимости не изменились, верни старое значение».
- **useCallback** — «эту функцию, которую я использую в других местах: если зависимости не изменились, не создавай новую, держи ту же в памяти».
  - Выгода двойная: не создаём новую функцию + не нагружаем **garbage collection** (старую функцию нужно убирать). В крошечном приложении незаметно, но накапливается.

## Применение useCallback

```js
const onIncrement = useCallback(() => {
  setCount(count + 1);
}, [count, setCount]);
```

- Синтаксис похож на `useEffect`: оборачиваем функцию, передаём массив зависимостей.
- При следующем рендере React проверяет: те же ли `count` и `setCount`? Если да — возвращает ту же функцию.

## Важный нюанс про setCount

- **Сеттеры из `useState` стабильны** — всегда одна и та же функция, кэш не ломают (можно вызывать компонент хоть триллион раз).
  - Под капотом `setCount` — это **dispatch из useReducer** (TypeScript-аннотация это показывает); `useState` — абстракция над `useReducer`, и dispatch сам обёрнут в `useCallback`.
- Поэтому `setCount` в массиве зависимостей технически можно опустить — единственное, что реально может сломать кэш, это `count`. ESLint может быть не согласен; по эвристике «не проверять = быстрее, чем проверять» это оправдано, но выигрыш ничтожен.

## Проблема: зачем кэшировать, если count — единственное, что меняется?

- Если компонент не принимает props и не имеет своего state, он ре-рендерится только при изменении `count`. Тогда оборачивать обработчики в `useCallback` кажется вредным: «делаю работу проверки ровно тогда, когда проверка всё равно сломается».
- **Решение — functional updater API сеттера.** Сеттер принимает не только новое значение, но и функцию от предыдущего значения:

```js
const onIncrement = useCallback(() => setCount((c) => c + 1), []);
const onDecrement = useCallback(() => setCount((c) => c - 1), []);
const onReset = useCallback(() => setCount(0), []);
```

- Теперь `count` **не участвует** в зависимостях — все три функции становятся **referentially stable** (стабильны по ссылке) навсегда, как `setCount`.
- Эффект: если обернуть кнопку в memo («не перерисовывать при тех же props»), кнопки **перестают ре-рендериться** — перерисовывается только сам компонент с новым числом.
- Функции всё равно должны оставаться внутри компонента (нужен `useState` в closure scope), но теперь они referentially одинаковы.

## Извлечение в кастомный хук useCounter

- Если повторяется — вынести в переиспользуемый `useCounter`:

```js
function useCounter(initial = 0) {
  const [count, setCount] = useState(initial);
  const increment = useCallback(() => setCount((c) => c + 1), []);
  const decrement = useCallback(() => setCount((c) => c - 1), []);
  const reset = useCallback(() => setCount(initial), [initial]);
  return { count, increment, decrement, reset };
}
```

- Использование: `const { count, increment, decrement, reset } = useCounter();`
- Не экспортировать `setCount` напрямую — отдавать готовые actions.

## Ловушка: новый объект каждый раз

- Возвращаемый объект `{ count, increment, decrement, reset }` — **новый объект на каждом рендере**, даже если все его члены referentially те же. Передача всего объекта вниз сломает memo у потребителей.
- Если нужен **стабильный сам объект** — обернуть в `useMemo`:

```js
return useMemo(
  () => ({ count, increment, decrement, reset }),
  [count, increment, decrement, reset]
);
```

- Новая проблема: `count` меняется часто → при его изменении весь объект меняется и ре-рендерит всех, кто его получает.
- **Лучшее решение — вернуть два объекта**: отдельно **state** (`count`) и отдельно **actions** (increment/decrement/reset).
  - Actions можно передавать единым стабильным «бандлом» (они никогда не меняются), а `count` держать отдельно.
  - Суть приёма: **разделять то, что меняется, от того, что не меняется** — даёт больше контроля и почти никем не используется, хотя элементарно.

## Главное

- `useMemo` кэширует **значение**, `useCallback` кэширует **функцию** при неизменных зависимостях (экономит создание функций и нагрузку на GC).
- Сеттеры `useState` стабильны (это dispatch из useReducer в useCallback) — кэш не ломают.
- Functional updater `setCount(c => c + 1)` убирает `count` из зависимостей → обработчики становятся referentially stable навсегда, и memo на дочерних компонентах начинает работать.
- При возврате объекта из хука помни: объект новый каждый раз; оборачивай в `useMemo` или (лучше) разделяй изменяемый state и стабильные actions.
- React compiler делает многое автоматически, но он RC, требует миграции и консервативен — понимать концепцию всё равно нужно.
