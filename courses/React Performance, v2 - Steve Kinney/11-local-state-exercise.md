# Local State Exercise (Упражнение: локальный state) — раздел Managing State

## Задание

- Пример `local state` (запуск через `npm run examples`). Намеренно искусственный, цель — проверить, что репозиторий и инструменты работают, и наработать «muscle memory».
- Проблема: изменение чего угодно ре-рендерит почти всё; несвязанные между собой компоненты ре-рендерятся вместе.
- Задача: **опустить state вниз**, устраняя unnecessary renders. Важно реально проделать руками с DevTools, а не просто прочитать.

## Когда state действительно нужен высоко

Вопрос: что если значение input нужно в родителе (например, в `useEffect` для API-вызова) — использовать `useRef`?

- Эвристика прежняя: убираем именно **unnecessary** renders; «как высоко нужно, как низко возможно».
- Прямое назначение `useRef` — handle на DOM-узел (и сохранение ссылки между рендерами). Можно «гнуть» его, чтобы поднять значение высоко, но **complexity cost** этого ради спасения одного компонента часто не оправдан, особенно если замер показывает, что выигрыша нет.
- Принцип: complexity → выше шанс багов. Самое производительное, но не работающее приложение хуже работающего с мелкими неоптимальностями. Открывать «ящик Пандоры» с ref'ами, держащими состояние между рендерами, рискованно.

### Пример `current user`

- `current user` (или `theme`) — классика state, который **обязан** быть высоко: нужен почти всем.
- Две особенности: он почти **никогда не меняется** за время жизни приложения, а **когда меняется — должно перерисоваться почти всё**. Поэтому то, что он наверху и при изменении ре-рендерит всё, — нормально.
- Размещается либо очень высоко в дереве, либо в Context API / state-библиотеке.

## Про state-библиотеки

- **Redux**, **Zustand** и др. внутри используют ровно те же примитивы, что доступны всем: `useMemo`, `useCallback`, `React.memo`, Context API. Поэтому курс делает упор на фундамент, а не на конкретную библиотеку — знания применимы везде.

## Диагностика и замер

- Через Profiler видно, **какой компонент вызвал** обновление; если виновник — высокоуровневый компонент, стоит проверить.
- Любой ре-рендер того, что меняться не должно, — повод посмотреть, но не повод паниковать: пример приходит на **5.4 мс** в крошечном приложении — «починить завтра» не нужно. Опасность в накоплении: одно тянет другое. Инструменты триажа одни и те же для одной мелочи и для кучи.

## Рефактор (опускание state)

- В исходнике весь state хранится в `App`; всё поднимается в `App`, меняет его state и каскадом ре-рендерит всё.
- Решение: перенести state (`count`, `setCount` и обработчики) внутрь компонента `Counter`, которому после этого **не нужны props**.
- Замечание: нормально, если корневой компонент — это просто набор компонентов без props (исключения — `current user` и пр.).
- Результат: при обновлении ре-рендерится только нужное.

## Сегвей: referential equality

- Даже после рефактора кнопки всё ещё ре-рендерятся. Причина — **referential equality** (ссылочное равенство) в JavaScript:
  - две строки `"guitar"` равны; два объекта с одинаковыми полями — **не равны**, т.к. это разные объекты в памяти.
- На каждом рендере заново создаются **новые функции** (обработчики), делающие то же, что и раньше. Они новые объекты → даже `React.memo` («не ре-рендерь при тех же props») не спасает, props технически другие.
- Эти функции нельзя просто вынести наружу, т.к. зависят от `setCount`. Нужен механизм «сохранить предыдущую» (далее — `useCallback`).
- Оговорка по правилам: не создавать новую функцию быстрее, чем создавать — **если** проверка «изменилось ли» не дороже самого создания (для таких мелких функций — вполне может быть дороже). Поэтому: **сначала измерять**, потом применять.

## Главное

- Опускание state вниз — самый простой, эффективный и низкорисковый выигрыш; держи state «как высоко нужно, как низко возможно».
- `useRef` ради поднятия значения высоко обычно не стоит complexity cost; измеряй, прежде чем усложнять.
- Некоторый state (`current user`, `theme`) обязан быть высоко — он редко меняется и при изменении затрагивает всё, так что это приемлемо.
- Referential equality: новые функции на каждом рендере ломают `React.memo`, потому что это новые объекты в памяти — мостик к `useCallback`.
