# Pushing State Down the Tree (Опускание state вниз по дереву) — раздел Managing State

## Главное правило размещения state

- **Держать state так высоко, как нужно, и так низко, как только можно** («as high as you need it, as low as you can get away with»).
- Это первый и самый надёжный «slam dunk» приём — почти никогда не ошибёшься.
- Замечание: даже если такой код кажется тем, что «вы бы никогда не написали», в реальном приложении он почти наверняка есть где-то ниже по дереву — часто потому, что код был хорош при написании, а потом всё вокруг него изменилось.

## Разбор примера (Deep Thoughts)

- Проблема: ввод в input-поле ре-рендерит почти всё приложение (видно по миганию). Причина — `draftThought` (черновик заметки) хранится в корневом `App`.
- В `App` создаётся state `draftThought` + `setDraftThought` и передаётся вниз в `CaptureThought` через props.
- Ключевой принцип потока: **рендер идёт только вниз**, если только колбэк не вызывает что-то вверх (к `App`). State, поднимающий обновления в `App`, каскадом ре-рендерит всё дерево.
- Разделение ответственности: добавление новой заметки в массив `thoughts` **должно** жить в `App` (массив нужен и списку, и отдельным заметкам). А вот хранение и изменение **черновика** в `App` не нужно — его можно опустить вниз.

## Рефактор

1. Вырезать хук `useState` для черновика из `App`.
2. Оставить наверх только возврат к массиву (submit добавляет заметку в `thoughts`).
3. Убрать передачу `onChange` и `draftThought` через props (больше не пробрасываются) — наверх важен только момент submit.
4. Создать локальный `useState` для черновика внутри `CaptureThought`; `onChange` обновляет локальный `draftThought`.
- Результат: после рефактора весь app перестаёт ре-рендериться при вводе. Перед замером — обновить страницу, чтобы избежать false positive.

## Inlining vs отдельный компонент

- Альтернатива опусканию state — **«сплющить» (flatten)** дерево: иногда вопрос не в state, а в том, нужно ли вообще выносить часть в отдельный компонент или можно вставить inline.
- Trade-off: inline может быть чуть производительнее, но если компонент (например, переиспользуемый `Button` с ref, поддержкой ссылки, логикой) используется в 6 местах — важнее maintainability, чем микровыигрыш. Платить эту цену оправдано.

## Когда «мигание» не важно (правило 16.6 мс)

- Браузер рисует кадр каждые **16.6 мс**. Если вся работа укладывается в <16 мс — мигание не имеет значения, глаз не видит.
- Пример замера: рендер занял **1.3 мс** — оптимизировать дальше бессмысленно. Если бы было ~15.7 мс — стоило бы задуматься.
- Не превращаться в человека, который убирает каждый ре-рендер: переиспользуемый `Input` из design system стоит лишнего незаметного мигания. **Сначала измерять**, потом решать.

## Баланс

- Не оптимизировать всё подряд («solve only big problems»), но «смотреть за угол» — мелочи накапливаются годами и в старых кодовых базах превращаются в «all hands on deck» проблему.

## Главное

- Размещай state как можно ниже: рендер идёт вниз, поэтому state, поднятый в корень, ре-рендерит всё дерево.
- Простейший рефактор — вырезать локальный state (черновик) из `App` и перенести в дочерний компонент; наверх оставить только то, что реально нужно нескольким веткам.
- Правило 16.6 мс: если рендер укладывается в кадр (пример: 1.3 мс) — мигание неважно, не оптимизируй.
- Inlining vs отдельный компонент — вопрос баланса performance и maintainability; переиспользуемость часто важнее микровыигрыша.
