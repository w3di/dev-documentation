# React Fiber

## Что это

- **React Fiber** — новый (хотя уже не новый) способ, которым React вычисляет изменения для DOM.
- Формальное определение: **cooperatively scheduled rendering engine** (кооперативно планируемый движок рендеринга).
- Не меняет принцип работы React — делает его «умнее».

## Чем отличается от старого подхода

- Ранний React (классы или функции) начинал с вершины и **проходил всё дерево компонентов разом**. Для маленького приложения — нормально.
- Проблема: процесс **блокировал main thread** и шёл до завершения, что бы ни случилось.
- Раньше для тяжёлых случаев (каждый keystroke → state change → пересортировка DOM) приходилось вручную использовать **debouncing**, **throttling**, **RxJS** для отмены. Эти инструменты остаются актуальны для отдельных случаев, но Fiber даёт элегантные решения меньшим кодом «из коробки».
- Особенность: усложнение внутренностей React здесь **работает на пользователя**, а не усложняет ему жизнь (обычно новые сложные фичи делают простое трудным).

## Что даёт Fiber: приоритет

- Fiber отвечает за **urgent vs «может подождать»** (срочное против несрочного).
  - Для сравнения: **React compiler** отвечает за **necessary vs unnecessary** (нужное против лишнего).
- Раньше единственный способ ускорения — остановить дерево выше или начать ниже. С Fiber React может:
  - **прервать (interrupt)** работу,
  - **приостановить (pause)** и вернуться позже,
  - **выбросить (throw away)** начатое и начать заново, если многое изменилось.
- Механизм: React периодически «проверяется» — «стоит ли мне продолжать то, что я делаю? Есть ли что-то важнее?». Если да — переключается, затем либо возвращается к прерванному, либо начинает заново.
- Кажущийся парадокс: переделывать работу технически **медленнее**, но воспринимается **быстрее** — и это всех устраивает (связь с двумя правилами производительности).

## Как устроено внутри

- Технически это «**a bunch of plain functions, a linked list tree, and a small scheduler hiding in a trench coat**» — обычный JavaScript, ничего экзотического.
- Сам по себе Fiber **не быстрее** старого подхода (если бы тот продолжали оптимизировать). Это не про скорость, а про введение **priority** (приоритета).

### Почему это нетривиально в JavaScript

- В некоторых языках с настоящей concurrency функции можно останавливать на середине.
- В JavaScript функция, начавшись, **выполняется до конца** (run to completion). Завершение — это: `return` со значением, конец функции (`undefined`), `yield` в generator, или брошенная ошибка. Начал функцию — ты «внутри».
- Поэтому вместо одной рекурсивной функции, идущей по дереву, Fiber **разбивает работу на куски**, кладёт их в нечто вроде event queue и периодически «выныривает» проверить, можно ли продолжать.
- Аналогия из обычного JS: разбить тяжёлую задачу через `setTimeout` с нулём — сделать 10 итераций, `setTimeout(0)`, ещё 10. Это даёт другим вещам попасть в event loop и не блокирует main thread. Работа Fiber устроена не точно так, но метафора подходит.

## Дополнительный бонус: уступать кадры

- React — не единственное, что выполняется в приложении (CSS-анимации, промисы и т.д.).
- Браузер стремится рисовать **60 кадров в секунду = 16.6 мс на кадр**. Fiber «выныривает» примерно с этой частотой, чтобы дать выполниться всему остальному (resolving промисов и пр.).
- Вывод: даже если вы ничего из этого не используете и не знаете о Fiber, жизнь стала чуть лучше просто от его существования — он позволяет другим задачам встраиваться в очередь и регулярно проверяется.

## Главное

- React Fiber — cooperatively scheduled rendering engine; обычный JS (функции + linked-list-дерево + планировщик), а не магия.
- Главное нововведение — **priority**, а не скорость: работу можно прервать, приостановить или начать заново ради более срочного.
- Решает проблему single-threaded JS (run-to-completion), разбивая рендер на куски и периодически уступая main thread.
- Fiber → urgent vs non-urgent; React compiler → necessary vs unnecessary. Бонус: уступает кадры (~16.6 мс) другим процессам, улучшая отзывчивость даже без явного использования.
