# React Developer Tools (раздел Managing State)

## Подход к лабораторным

- Начинаем с простых «quick wins» на маленьких приложениях. Примеры выглядят искусственно, но та же проблема в меньшем виде почти наверняка есть где-то ниже по дереву в реальном приложении.
- Самые тяжёлые performance-проблемы — обычно не один «smoking gun», а накопление множества мелочей со временем.

## Запуск репозитория

1. `npm run examples` — выбрать нужный пример (вместо клонирования множества репозиториев). Первый пример — **Deep Thoughts** (приложение для заметок, намеренно неоптимальное).
2. `npm run dev` — запуск через **Vite**.
3. Для смены примера снова `npm run examples`.

## Development vs production mode

- **Важно: в development mode всё медленнее.** React выполняет доп. работу: измеряет рендеры и причины, показывает в DevTools нормальные имена компонентов вместо минифицированных, грузит доп. инфраструктуру.
- Предупреждение: не оценивать производительность (и чужие PR) по development-сборке — мерить только на **production build**, иначе выводы неверны.
- Обратная проблема: некоторые сайты по ошибке деплоят development-сборку React и работают медленнее возможного. Закреплённое (pinned) расширение React DevTools помогает заметить, не сломал ли ты собственный build (на React-странице иконка оранжевая).

## Вкладки расширения

- **Components** — дерево компонентов. Полезно: при наведении видно, какой файл редактировать; есть аналог «inspect element» для компонента — props, hooks, кто его отрендерил (как call stack), путь к файлу. Не строго про performance, но полезно.
- **Profiler** — основной инструмент для производительности.

## Profiler

- **Запись (record)**: выполнить действия → остановить → увидеть, что и как долго рендерилось (например, добавление одной заметки вызывает рендер множества заметок — потому что приложение намеренно плохое).
- Скрытая, но ценная опция — **Highlight updates when components render**: при каждом действии всё перерисованное **мигает**. Видно, сколько раз и что именно ре-рендерится.
  - Сигнал к оптимизации: ре-рендерится то, что меняться не должно (например, кнопка duplicate, в которой ничего не изменилось).
  - Предупреждение: **не** бросаться оптимизировать каждый ре-рендер — можно навредить и испортить отношения в команде. Особенно полезно на этапе разработки новой фичи, пока код «податлив».
  - Виден только при открытых DevTools в development mode.
- **Record why each component rendered** — показывает, какие props изменились (или context), давая инсайт о причине ре-рендера.

## Принцип наблюдателя

- Измерение **само замедляет** работу (включая highlight и «why did this render»): все цифры становятся больше. Аналогия с квантовой физикой — наблюдение меняет результат. Даже в production наблюдение чуть замедляет.
- Для production-инсайтов можно через build-tooling (Vite `resolve.alias`, аналог в Webpack) подменить сборку: production build + `react-dom/profiling` и scheduler tracing. Ближе к production, но всё равно медленнее обычного.

## Намеренное замедление (симуляция реальных условий)

- Разработчики часто на быстрых машинах и Wi-Fi; реальные пользователи — нет. Отчёты пользователей о производительности обычно бесполезны («тормозит»), и нужно воспроизвести проблему.
- **Network throttling** (Chrome DevTools) — замедление сети. Не забыть выключить после теста.
- **CPU throttling** — симуляция слабого устройства вместо дорогого компьютера.
- Эти инструменты нужны, чтобы воспроизводить узкие места без искусственного раздувания кода.

## Главное

- Запуск примеров: `npm run examples` → выбрать → `npm run dev` (Vite).
- Мерить только на production build: development mode всегда медленнее из-за доп. инструментовки.
- Главный инструмент — Profiler с «highlight updates» и «why did this render»; искать ре-рендеры того, что меняться не должно, но не оптимизировать слепо каждый.
- Любое измерение само замедляет (принцип наблюдателя); для реалистичности применяй network/CPU throttling, имитируя слабые устройства и сети.
