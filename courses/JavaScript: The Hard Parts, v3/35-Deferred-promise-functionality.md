# Часть 35. Отложенная функциональность промисов

## Сводка достигнутого

- Новый способ настройки фоновой работы в браузере: он не только запускает фоновую работу, но и в «переднем плане» (foreground) создаёт объект-placeholder для данных.
- Объект автоматически заполняется данными (`"cute puppy"`) в момент завершения фоновой работы — в свойство `result`.
- Через `.then` мы добавили функцию в список функций, автоматически запускаемых при заполнении `result`.
- Запуск функции: она добавляется в call stack, JS сам ставит скобки и сам вставляет данные; новый execution context; заранее подготовленный параметр (`data`) получает строку `"cute puppy"`.

## Цепочка обновления on completion

1. Фоновая работа завершилась.
2. Возврат в JavaScript: найти объект `futureData`, записать в `result` полученную строку.
3. Автоматически запустить функцию `display`, добавленную через `.then` в список функций промиса.
4. Функция выполняется с входными данными.

## Вопрос про область видимости (scope)

- Раньше запись в память рассматривалась в рамках execution context, где эта память используется (локальная память, глобальная память).
- Здесь `futureData` создаётся в глобальной памяти, но браузер тоже имеет к нему доступ — не через callback queue в самом конце, а одновременно из браузера, обновляя `result` on completion.

### Как браузер обновляет объект в JS

- Объект-promise создан той же `fetch`-вызовом, что породил и network request. Эти два последствия тесно связаны.
- network request хранит ссылку (reference) на сохранённый promise-объект в памяти JS. Это позволяет ему обновить свойство `result`.
- Это «деталь реализации» (implementation detail): JS — это runtime внутри браузера, и браузерные API могут держать ссылки на позиции в памяти JS.
- Браузер НЕ получает копию объекта — только ссылку на его позицию в памяти JS. По завершении работы он по этой ссылке обновляет JS-объект.

## Персистентность объекта (heap)

- Даже если promise-объект определён в локальном (временном) execution context, он не исчезает по выходу из функции.
- Любой объект хранится как ссылка на его позицию в **heap** (куче объектов). Даже если потеряем имя в JS, объект остаётся в heap, пока на него есть ссылка.
- Браузер ссылается на promise-объект, поэтому объект сохраняется. Ссылки на JS-данные, сделанные даже самим браузером (не из JS), продлевают существование объекта.
- В JS он и не нужен напрямую: использовать его может только функция, назначенная через `.then`, а её запускает браузер.

## Данные доступны только внутри then-функции

- Сходство со старым callback-стилем сохраняется: данные доступны только внутри функции (`display`), которая запускается по приходу данных.
- Хотя `"cute puppy"` добавляется в обычный JS-объект в синхронной среде, фактически воспользоваться этими данными нельзя, пока что-то не произойдёт в global — должна завершиться синхронная работа в global. (Тема порядка выполнения с очередями — далее.)

## Сводка по промисам (ES6+)

- **Promise** — специальные объекты, встроенные в JS, возвращаемые немедленно при вызове фичи браузера через что-то вроде `fetch`, настроенного возвращать промис.
  - Не все фичи браузера возвращают промис: например, `setTimeout` — нет.
- Промис — placeholder для данных, ожидаемых от фоновой работы; данные хранятся в скрытом свойстве `result`.
- Метод **.then** позволяет прикрепить код/функцию, который запустится по завершении фоновой работы и заполнении `result`.
- Любая функция для запуска на данных из сети должна быть сохранена на promise-объекте через `.then` — он кладёт её в скрытое (по спецификации) свойство **fulfill reactions** (полное имя — *promise fulfill reactions*); по сути это «список функций, которые выполнятся».
- Промис автоматически запускает прикреплённую функцию, передавая ей retrieved result data как вход.

## Что с очередями?

- При добавлении `display` обратно в call stack возникает вопрос: что произошло с очередями?
- Оказывается, в механизме очередей есть больше, чем показано: помимо одной callback queue (task queue) есть и другая (намёк на microtask queue).

## Следующий (самый сложный) пример

```js
function display(data) { console.log(data); }
function printHello() { console.log("hello"); }
function blockFor300ms() { /* блокирует ~300 мс */ }

setTimeout(printHello, 0);
const futureData = fetch("https://tiktok.com/will");
futureData.then(display);
blockFor300ms();
console.log("me first");
```

- Здесь три определения функций (`display`, `printHello`, `blockFor300ms`), вызовы `setTimeout`, two-pronged `fetch` и `blockFor300ms`. На этом примере разбирается порядок выполнения (с участием microtask queue).
- После этого тема async завершается; далее — как прервать (abort) промис, затем переход к OOP.

*(тема продолжается — разбор порядка выполнения с microtask queue и abort в следующих частях)*

## Главное

- Промис создаётся той же `fetch`-вызовом, что и network request; они связаны ссылкой, по которой браузер обновляет `result` объекта в памяти JS (без копирования — только ссылка).
- Объект сохраняется в heap, пока на него есть ссылка (в т.ч. со стороны браузера), даже если определён в локальном контексте.
- Данные из сети доступны только внутри функции, прикреплённой через `.then`; промисы — встроенные объекты-placeholder со скрытыми свойствами `result` и `fulfill reactions`.
- Механизм очередей сложнее одной callback queue — существует ещё одна очередь (microtask queue), разбор которой и порядок выполнения — далее.
