# Часть 31. Callback queue

## Зачем нужны правила

- Взаимодействуя с миром вне JavaScript, мы попадаем в непредсказуемую среду: запрос к сети может занять 10 мс, 100 мс, не ответить вовсе или вернуть другую информацию.
- Чистый JavaScript предсказуем: каждая строка выполняется одна за другой до конца.
- Цель программирования — предсказуемость. Поэтому для возврата результата внешней работы обратно в JavaScript нужны строгие, даже кажущиеся избыточными правила — чтобы всегда можно было предсказать порядок выполнения кода.

## Разбираемый код

```js
function printHello() {
  console.log("hello");
}
function blockForOneSec() {
  // делает что-то «тяжёлое» ~1 секунду внутри потока JS, например большой цикл
}
setTimeout(printHello, 0);
blockForOneSec();
console.log("me first");
```

- `blockForOneSec` должна реально занимать существенное время в одном потоке JS. Подойдёт тяжёлый for-loop или рекурсивная математика (движки сильно оптимизированы, поэтому загрузить поток на секунду непросто).
- JS не позволяет делать одну очень долгую задачу — только множество мелких (как итерации цикла).

## Прохождение по коду

1. Объявляются `printHello` и `blockForOneSec` (тело последней не пишем, но при реальном запуске оно нужно — например, цикл).
2. Вызов `setTimeout` — facade function / обращение к Web Browser API (timer):
   - первый аргумент — определение `printHello` (НЕ вызов, без скобок);
   - второй — `0` миллисекунд.
3. Последствия `setTimeout` — в браузере. Запускается timer на 0 мс; по завершении (on completion) запустить `printHello` (хранится определение).
4. **Ключевой момент**: на 0 мс таймер на 0 мс уже завершён.
5. Казалось бы, `printHello` должна сразу вернуться в call stack — но она этого не делает.

## Введение callback queue

- Появляется ещё одна структура-интерфейс между внешним миром и JS-движком: **callback queue** (она же task queue).
- На 0 мс `printHello`, хотя и готова, **не** попадает в call stack, а отправляется ждать в эту очередь.
- Тем временем JS идёт дальше:

1. На ~1 мс — вызов `blockForOneSec`, добавляется в call stack, новый execution context, поток входит внутрь и выполняет ~1000 мс цикл прямо в JS.
2. Во время выполнения `blockForOneSec` `printHello` НЕ допускается обратно в call stack.
3. На ~1001 мс `blockForOneSec` снимается (popped off) с call stack, возвращаемся в global.
4. `printHello` всё ещё НЕ допускается. На ~1001 мс выполняется `console.log("me first")` → в консоль `me first`.
5. Только на ~1002 мс `printHello` выводится из очереди (dequeued) и добавляется в call stack; новый execution context; выполняется `console.log("hello")` → в консоль `hello`.

## Строгое правило очереди

- Callback queue не выполняется, пока не завершён ВЕСЬ глобальный код — не только пока пуст call stack, но пока отработала вся global-программа.
- Даже миллион `console.log` будут выполнены раньше, чем что-либо из callback queue.
- Это очень строгое, но фундаментальное правило: оно гарантирует, что весь global-код выполнится и ничто не «впрыгнет» в середину — то есть предсказуемость.

## Главное

- callback queue (task queue) — структура между браузером и JS, куда попадают готовые callback-функции из завершившейся фоновой работы.
- Даже таймер на 0 мс не возвращает функцию в call stack сразу: она ждёт в очереди.
- Строгое правило: ничего из callback queue не выполнится, пока не пуст call stack И не завершён весь глобальный код.
- Цель этой строгости — гарантированная предсказуемость порядка выполнения.
