# Часть 48. Ключевое слово class

## Оценка solution 3 (new)

- Плюсы: быстрее писать, фактически стандарт в профессиональном коде.
- Минусы: ~95% разработчиков не понимают, как `new` работает под капотом, и проваливают собеседования. Понимание этой механики помогает объяснять коллегам, как реально работает код в Node, React, Next и т.п.
- Иерархия инженеров (по лектору):
  - junior — решает знакомые задачи знакомыми инструментами;
  - mid-level — решает незнакомые задачи незнакомыми инструментами;
  - senior — даёт возможность другим в команде решать незнакомые задачи незнакомыми инструментами.

## Проблемы подхода new

- Технически можно перезаписать `prototype`: например `userCreator.prototype = 7` — и сломать все объекты (тогда `increment` перестанет существовать). Делать так не нужно.
- JavaScript не является изначально объектно-ориентированным языком: он «латает» прототипный язык, чтобы он выглядел как ООП-язык.
- Если вызвать `userCreator` без `new`:
  - не создаётся автоматический объект;
  - не устанавливается proto-ссылка;
  - нет автоматического возврата.
- При обращении к `this` без `new` `this` указывает на **window**. Тогда `name` и `score` спокойно добавляются как `window.name`, `window.score` — баг без явной ошибки. (Если бы `this` было `undefined`, добавление свойства дало бы явную ошибку — это было бы полезнее.)

## Как сообщить о необходимости new

- Нужно дать коллегам понять, что функцию следует вызывать только с `new`.
- Историческая техника:
  1. блочный комментарий над функцией;
  2. главное — заглавная первая буква имени функции (`UserCreator`).
- Заглавная буква не меняет ничего в JS — это лишь соглашение, подсказка коллегам использовать `new`. Не строгий, не отказоустойчивый подход.

## class — синтаксический сахар

- Стандартным стал подход с ключевым словом **class** — это **syntactic sugar** (синтаксический сахар): не меняет того, что происходит под капотом, но выглядит приятнее и читается легче.
- Со временем классы обзавелись дополнительными полезными возможностями, но изначально `class` лишь перемещает объявления в одно место.
- Без классов: сначала определяли `userCreator`, затем отдельно добавляли функции в `userCreator.prototype`. Это противоречит тому, как работает классический ООП-язык, где методы и конструктор определяются вместе.
- Классы (ES6 и далее) позволяют определить всё в одной структуре, а не добавлять методы в prototype отдельно.

## Структура class

```js
class UserCreator {
  constructor(name, score) {
    this.name = name;
    this.score = score;
  }
  increment() { this.score++; }
  login() { /* ... */ }
}
```

- Под капотом — ровно тот же код, что и раньше; определение функции и присвоение методов в `userCreator.prototype` просто обёрнуты в конструкцию `class`.
- Класс — это тоже **function-object combo** (функция-объект).
- Часть `constructor` — это и есть прежняя функция `userCreator` (её функциональная часть). Принимает `name`, `score`, выполняет `this.name = name`, `this.score = score`.
- Методы `increment` и `login`, которые раньше вручную клались в объектную часть под `prototype`, теперь просто перечисляются внутри тела класса и автоматически добавляются в `userCreator.prototype`.
- Абсолютно ничего не изменилось под капотом — только организация кода.

## Предстоящее расширение

- Далее будет добавлено static public field — метод `describe`. Он выглядит «продвинуто», но фактически просто добавляет ещё один метод на `userCreator`.
- Важно понимать: класс `userCreator` остаётся обычным function-object combo. (тема продолжается)

## Главное

- **class** — синтаксический сахар: под капотом тот же конструктор-функция + методы на `prototype`, но всё описано в одном месте.
- Часть **constructor** соответствует прежней функции `userCreator`; перечисленные методы автоматически попадают в `userCreator.prototype`.
- Класс — это **function-object combo**; механика prototype chain не меняется.
- До классов о необходимости `new` сигнализировали заглавной первой буквой имени — соглашение, не строгая гарантия.
