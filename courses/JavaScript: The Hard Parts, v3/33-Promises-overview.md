# Часть 33. Обзор Promises

## Терминология callback

- Функция, переданная в `setTimeout`, по завершении фоновой работы вызывается обратно (called back) в JavaScript — отсюда название **callback**.
- Этот подход был стандартом взаимодействия с внешним миром (браузером) из JS до ES6 (в ES5 и ранее). `setTimeout` работает так до сих пор: передаём функцию-фасад, она настраивает фоновую работу и почти ничего не делает в JS.

## Проблемы callback-подхода

- Нет нормального способа отслеживать в JS, что фоновая работа идёт — может быть масса фоновых задач, но в самом JS ничего об этом не «видно».
- Данные ответа: многие фоновые задачи получают данные из сети, но эти данные доступны только внутри функции, запускаемой on completion. Больше им «деться» некуда (это by design, но всё же ограничение).
- Передача функции в другую функцию ради запуска много позже неинтуитивна; вложенность приводит к так называемому **callback hell** (ад обратных вызовов).
- Это называют «передачей управления» (passing control): функцию передают, а выполняется она гораздо позже, когда event loop видит, что call stack пуст и весь global-код завершён.

## Плюс callback-подхода

- При понимании механики он очень явный: одна очередь, фоновая работа; все facade functions настраивают фоновую работу, по завершении попадают в очередь и ждут, пока завершится весь global-код.
- Есть полная уверенность в порядке выполнения (хотя и не в точном тайминге).

## Promises (ES6+)

- В ES6 появился новый подход — **Promise** (промис, специальный объект-обещание).
- Лектор называет порождающие их функции **two-pronged facade functions** (двузубые функции-фасады): у них два последствия.
  1. **Один «зубец»**: запускают фоновую работу в браузере (таймер, обращение к сети и т.п.).
  2. **Второй «зубец»**: сразу возвращают в JavaScript объект-placeholder — специальный объект **Promise**.
- Это даёт:
  - A. возможность в JS знать и отслеживать, что фоновая работа запущена;
  - B. способы взаимодействовать с данными, которые вернутся из фоновой работы, в более читабельном виде.
- Promise-объект обычно присваивают сразу:

```js
const futureData = fetch("...");
```

- Замечание: внешне код читабельнее, но под капотом он ещё сильнее скрывает происходящее. Механика по сути та же, что и раньше, но с новыми правилами.

## fetch API

- Promise-подход заменил `XHR` для доступа к сети. Реализуется через встроенную two-pronged facade function — **fetch**.
- `fetch` запускает фоновую работу (обращение к интернету, к TikTok) и одновременно даёт эффект прямо в JavaScript: возвращает специальный объект.
- При вызове `fetch`:
  - первый «зубец» уходит в браузер и делает работу;
  - второй «зубец» немедленно возвращает в JS объект (например, в `futureData`).
- Этот объект — **placeholder** для данных, которые придут от TikTok; когда данные вернутся, мы сможем их использовать.

## Под капотом всё ещё асинхронно

- В JS код остаётся синхронным. Фоновая работа возвращается асинхронно и не по порядку.
- Хотя `fetch`-код выглядит линейным и интуитивным (как будто отображение данных происходит «прямо здесь»), под капотом паттерн очень похож на ранее разобранный callback-механизм.

## Главное

- callback-подход (до ES6): facade function настраивает фоновую работу, callback по завершении ждёт в callback queue; минусы — нет отслеживания работы в JS, данные доступны только внутри callback, callback hell.
- Promises (ES6+) — специальные объекты, возвращаемые two-pronged facade functions: один «зубец» запускает фоновую работу в браузере, другой сразу возвращает объект-placeholder в JS.
- fetch — two-pronged facade function для сети, заменившая XHR.
- Несмотря на более линейный вид, под капотом промисы работают по тому же асинхронному паттерну.
