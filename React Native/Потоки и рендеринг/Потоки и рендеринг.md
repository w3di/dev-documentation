## 1. Многопоточная модель

React Native — многопоточное приложение. В отличие от веб-браузера, где JavaScript и рендеринг делят один Main Thread, в RN они работают **параллельно**.

```
┌──────────────────────────────────────────────────────┐
│                  React Native App                     │
│                                                       │
│  ┌─────────────┐  ┌─────────────┐  ┌──────────────┐ │
│  │  JS Thread  │  │  UI Thread  │  │Shadow Thread │ │
│  │             │  │ (Main)      │  │(Layout)      │ │
│  │ Hermes      │  │ Native UI   │  │ Yoga         │ │
│  │ React       │  │ Gestures    │  │ C++ Tree     │ │
│  │ Business    │  │ Animations  │  │              │ │
│  │ Logic       │  │ (native)    │  │              │ │
│  └─────────────┘  └─────────────┘  └──────────────┘ │
└──────────────────────────────────────────────────────┘
```

В новой архитектуре (v0.76+) Shadow Thread интегрирован иначе — C++ Shadow Tree доступен из любого потока, а Yoga вызывается синхронно в commit phase.

## 2. JS Thread

JS Thread — поток, в котором выполняется **весь JavaScript код** приложения.

### Что выполняется на JS Thread

- **Hermes** (или JSC) — JavaScript-движок
- **React reconciliation** — diffing Virtual DOM, определение изменений
- **Бизнес-логика** — обработка данных, API вызовы, state management
- **Event handlers** — обработка событий, пришедших из Native
- **Timers** — `setTimeout`, `setInterval`, `requestAnimationFrame`

### Что блокирует JS Thread

```jsx
// ПЛОХО: тяжёлое вычисление блокирует JS Thread
function HeavyComponent({ data }) {
  // Это выполняется синхронно — UI замёрзнет
  const sorted = data.sort((a, b) => {
    return complexComparison(a, b); // O(n log n) с тяжёлой функцией
  });

  return <FlatList data={sorted} renderItem={renderItem} />;
}

// ЛУЧШЕ: вынести вычисление
function HeavyComponent({ data }) {
  const [sorted, setSorted] = useState([]);

  useEffect(() => {
    // Выполнить после рендера, не блокируя анимации
    requestAnimationFrame(() => {
      setSorted(data.sort((a, b) => complexComparison(a, b)));
    });
  }, [data]);

  return <FlatList data={sorted} renderItem={renderItem} />;
}
```

### JS Thread и анимации

Если анимация работает на JS Thread (без `useNativeDriver: true`), каждый кадр анимации требует:
1. JS вычисляет новое значение
2. Значение передаётся в Native
3. Native обновляет view

При загруженном JS Thread (API вызов, тяжёлый рендер) анимация **пропускает кадры**.

## 3. UI Thread (Main Thread)

UI Thread — **главный поток приложения**, контролируемый ОС.

### Ответственность

- Отрисовка нативных компонентов (`UIView`, `android.view.View`)
- Захват и обработка touch events на нативном уровне
- Нативные анимации (с `useNativeDriver: true`)
- Рендеринг `Animated` значений, запущенных на native driver
- Scroll inertia, gesture recognition
- System UI (status bar, keyboard, alerts)

### Важно

UI Thread **не зависит от JS Thread** для нативных анимаций. Поэтому `useNativeDriver: true` позволяет плавным анимациям работать даже когда JS Thread занят:

```jsx
// Анимация на UI Thread — плавная даже при тяжёлом JS
Animated.timing(fadeAnim, {
  toValue: 1,
  duration: 300,
  useNativeDriver: true, // ← выполняется на UI Thread
}).start();
```

## 4. Shadow Thread и Yoga

### Shadow Thread (старая архитектура)

В старой архитектуре Shadow Thread — отдельный поток для вычисления layout:

1. Получает описание UI от JS Thread через Bridge
2. Строит Shadow Tree (дерево Yoga-узлов)
3. Вызывает Yoga для расчёта layout
4. Передаёт результат (координаты, размеры) в UI Thread

### Yoga Layout Engine

Yoga — кроссплатформенный C++ layout engine, реализующий спецификацию Flexbox:

```
React Native стили          Yoga вычисляет
─────────────────          ───────────────
flexDirection: 'row'  →    распределение по горизонтали
flex: 1               →    пропорциональный размер
padding: 16           →    внутренние отступы (dp)
margin: 8             →    внешние отступы (dp)
alignItems: 'center'  →    центрирование по cross-axis
justifyContent: 'space-between' → равномерное распределение
```

### Shadow Tree в новой архитектуре

В Fabric Shadow Tree — **иммутабельная C++ структура**, доступная из любого потока:

```
Старая архитектура:
JS Thread → Bridge → Shadow Thread → Yoga → Bridge → UI Thread
(async, через JSON на каждом шаге)

Новая архитектура:
JS Thread → C++ Shadow Tree + Yoga (синхронно) → UI Thread
(JSI, прямые вызовы, иммутабельные snapshots)
```

## 5. Взаимодействие потоков в старой архитектуре

### Цикл обновления UI

```
1. Событие нажатия (UI Thread)
   │
   ▼ Bridge (JSON)
2. JS Thread обрабатывает событие
   │ setState() → React reconciliation → diff
   │
   ▼ Bridge (JSON: createView, updateView, ...)
3. Shadow Thread
   │ Строит/обновляет Shadow Tree
   │ Yoga рассчитывает layout
   │
   ▼ Bridge
4. UI Thread
   Создаёт/обновляет нативные views
```

Каждая стрелка — это **сериализация в JSON** и **ожидание в очереди**. Минимум 3 асинхронных перехода между потоками.

### Batching

Bridge группирует сообщения для уменьшения overhead. Вместо отправки каждого вызова отдельно, `BatchedBridge` накапливает вызовы и отправляет пакетом (обычно раз в 5ms):

```
Без batching:     createView → Bridge → updateView → Bridge → setChildren → Bridge
С BatchedBridge:  [createView, updateView, setChildren] → Bridge (один раз)
```

## 6. Взаимодействие потоков в новой архитектуре

### JSI прямые вызовы

С JSI потоки взаимодействуют **напрямую через C++**, без сериализации:

```
1. Событие нажатия (UI Thread)
   │
   ▼ JSI (прямой C++ вызов)
2. JS Thread обрабатывает событие
   │ setState() → React reconciliation
   │
   ▼ C++ Shadow Tree (синхронно)
3. Yoga layout (в том же вызове)
   │
   ▼ Mount instructions
4. UI Thread
   Обновляет нативные views
```

### Синхронный доступ

Fabric позволяет **синхронно** читать layout информацию:

```jsx
// Старая архитектура: async, результат через callback в следующем кадре
viewRef.current.measure((x, y, width, height, pageX, pageY) => {
  // Данные уже устарели на 1-2 кадра
});

// Новая архитектура: sync через useLayoutEffect
useLayoutEffect(() => {
  const { width, height } = viewRef.current.getBoundingClientRect();
  // Данные актуальны, рендер ещё не произошёл
}, []);
```

## 7. Rendering Pipeline

### Полный цикл: от setState до пикселей

```
setState()
    │
    ▼
┌─────────────────────────────┐
│ 1. RENDER PHASE (JS Thread) │
│    React создаёт новый      │
│    Element Tree (VDOM)      │
│    Diff с предыдущим        │
└──────────────┬──────────────┘
               │
               ▼
┌─────────────────────────────┐
│ 2. COMMIT PHASE             │
│    Создание C++ Shadow Tree │
│    (иммутабельный клон)     │
│    Yoga layout calculation  │
└──────────────┬──────────────┘
               │
               ▼
┌─────────────────────────────┐
│ 3. MOUNT PHASE (UI Thread)  │
│    Diff Shadow Trees        │
│    (старое vs новое)        │
│    Create/Update/Delete     │
│    нативных views           │
└──────────────┬──────────────┘
               │
               ▼
         Пиксели на экране
```

### Concurrent Rendering

С новой архитектурой React может **прерывать** render phase для обработки более приоритетных обновлений:

```jsx
const [isPending, startTransition] = useTransition();

// Высокий приоритет: обновляется немедленно
setInputValue(text);

// Низкий приоритет: может быть прерван
startTransition(() => {
  setSearchResults(filterData(text));
});
```

## 8. Frame Rate и метрики

### Два ключевых показателя

| Метрика | Что измеряет | Целевой показатель |
|---------|-------------|-------------------|
| **JS FPS** | Частота кадров JS Thread | 60 FPS |
| **UI FPS** | Частота кадров UI Thread | 60 FPS |

60 FPS означает ~16.67ms на кадр. Если JS Thread не успевает обработать кадр за 16ms — `JS FPS` падает.

### Типичные сценарии

```
Сценарий                        JS FPS    UI FPS
──────────────────────────────  ──────    ──────
Idle приложение                  60        60
Скролл FlatList (оптимизир.)     60        60
Тяжёлый рендер при скролле       15-30     60 (если native driver)
Анимация без native driver       30-45     60
Анимация с native driver         60        60
JSON парсинг большого ответа     5-15      60
```

### Performance Monitor

Включается через Dev Menu → "Perf Monitor". Показывает в реальном времени:
- JS Thread FPS
- UI Thread FPS
- Views count
- RAM usage

**Критически важно**: всегда измеряйте производительность в **release build**. В debug режиме JS Thread работает значительно медленнее из-за:
- Отключённых оптимизаций Hermes
- Dev tools overhead
- LogBox и error boundaries
- Source maps

## 9. Типичные проблемы и решения

### Проблема 1: JS Thread блокируется при скролле

```jsx
// ПРОБЛЕМА: тяжёлый renderItem блокирует JS Thread
const renderItem = ({ item }) => {
  const processed = heavyTransform(item); // 5ms на каждый item
  return <ComplexComponent data={processed} />;
};

// РЕШЕНИЕ: мемоизация + вынос вычислений
const MemoizedItem = React.memo(({ item }) => {
  return <ComplexComponent data={item} />;
});

const renderItem = useCallback(({ item }) => (
  <MemoizedItem item={item} />
), []);
```

### Проблема 2: Анимация лагает при навигации

```jsx
// ПРОБЛЕМА: навигация запускает тяжёлый рендер нового экрана
// при этом анимация перехода идёт на JS Thread

// РЕШЕНИЕ: native-backed навигатор
import { createNativeStackNavigator } from '@react-navigation/native-stack';
// ↑ Анимация перехода выполняется на UI Thread
```

### Проблема 3: Много setState подряд

```jsx
// ПРОБЛЕМА: каждый setState триггерит отдельный ре-рендер
function handleResponse(data) {
  setLoading(false);   // ре-рендер 1
  setData(data);       // ре-рендер 2
  setError(null);      // ре-рендер 3
}

// В новой архитектуре (v0.76+) React 18 automatic batching
// группирует эти обновления в один ре-рендер автоматически
```

### Проблема 4: console.log в production

```js
// console.log сериализует объекты и отправляет через Bridge/JSI
// В production это бесполезная нагрузка

// Решение: babel-plugin-transform-remove-console
// babel.config.js
module.exports = {
  presets: ['module:@react-native/babel-preset'],
  env: {
    production: {
      plugins: ['transform-remove-console'],
    },
  },
};
```

### Проблема 5: Тяжёлые вычисления

```jsx
// Для вычислений, которые нельзя оптимизировать на JS Thread:
// 1. Вынести в нативный модуль (Turbo Module)
// 2. Использовать Web Worker-подобные решения (react-native-worklets-core)
// 3. Разбить вычисление на чанки с requestAnimationFrame

function processInChunks(items, chunkSize = 100) {
  let index = 0;

  function processChunk() {
    const chunk = items.slice(index, index + chunkSize);
    chunk.forEach(processItem);
    index += chunkSize;

    if (index < items.length) {
      requestAnimationFrame(processChunk);
    }
  }

  requestAnimationFrame(processChunk);
}
```
