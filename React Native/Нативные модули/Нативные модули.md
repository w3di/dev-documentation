## 1. Что такое нативные модули

Нативные модули — это **классы, написанные на нативном языке платформы** (Swift, Objective-C, Kotlin, Java, C++), методы которых можно вызывать из JavaScript.

### Когда нужны нативные модули

- Доступ к платформенным API (камера, Bluetooth, биометрия, NFC)
- Использование нативных SDK (Firebase, платёжные системы, аналитика)
- CPU-intensive задачи (обработка изображений, криптография)
- Интеграция существующего нативного кода
- Доступ к файловой системе, Keychain, Keystore

### Нативные модули vs Нативные компоненты

| Тип | Назначение | Пример |
|-----|-----------|--------|
| **Native Module** | Логика, API, вычисления | Получить GPS-координаты, прочитать файл |
| **Native Component** | UI-элемент | Карта, видеоплеер, кастомный view |

## 2. Legacy Native Modules

> С React Native 0.82 Bridge **полностью удалён**, New Architecture обязательна. Legacy модули работают через **interop layer** (обратная совместимость), но этот слой будет удалён в будущем. Все новые модули должны использовать Turbo Native Modules или Expo Modules API.

### Как работали через Bridge

```
JS Thread                   Bridge                    Native Thread
    │                         │                            │
    │  NativeModules          │                            │
    │    .MyModule            │                            │
    │    .doSomething("arg")  │                            │
    │ ───JSON.stringify()───▶ │                            │
    │                         │  ──JSON.parse()──────────▶ │
    │                         │                 MyModule.   │
    │                         │              doSomething()  │
    │                         │  ◀──JSON.stringify()────── │
    │ ◀──JSON.parse()──────── │                            │
    │  callback/promise       │                            │
```

### Как создавались Legacy-модули

Общая схема:
1. **Android:** класс наследует `ReactContextBaseJavaModule`, методы помечаются `@ReactMethod`, модуль оборачивается в `ReactPackage` и вручную регистрируется в `MainApplication`
2. **iOS:** класс реализует протокол `RCTBridgeModule`, методы экспортируются через макросы `RCT_EXPORT_METHOD`
3. **JS:** доступ через `NativeModules.MyModule` — все методы только async

```jsx
// Использование в JS
import { NativeModules } from 'react-native';
const { DeviceInfo } = NativeModules;

console.log(DeviceInfo.PLATFORM); // константы — синхронно (вычислены при старте)
const level = await DeviceInfo.getBatteryLevel(); // методы — только async
```

### Проблемы legacy модулей

1. **Eager initialization** — все модули загружаются при старте приложения, даже если не используются
2. **JSON сериализация** — каждый вызов и ответ проходят через `JSON.stringify()` → `JSON.parse()`
3. **Только async** — нельзя синхронно получить значение (кроме констант)
4. **Нет type safety** — ошибки типов обнаруживаются только в runtime
5. **Ручной boilerplate** — нужно вручную регистрировать модуль, Package, маппинг типов
6. **Bottleneck на Bridge** — при интенсивной коммуникации Bridge становится узким местом (анимации, скроллинг)

## 3. Turbo Native Modules

Turbo Native Modules — замена legacy модулей, основанная на JSI (JavaScript Interface).

### Ключевые преимущества

1. **JSI** — прямые C++ вызовы без сериализации, JS держит ссылку на C++ host object
2. **Lazy loading** — модуль загружается при первом обращении, не при старте
3. **Type safety** — Codegen генерирует типизированные интерфейсы из TypeScript spec
4. **Sync + Async** — поддержка синхронных вызовов (без Bridge bottleneck)
5. **Автогенерация** — Codegen создаёт платформенный boilerplate

### Архитектура

```
JavaScript
    │
    │ TurboModuleRegistry.getEnforcing('NativeStorage')
    │
    ▼
┌─────────┐
│   JSI   │  C++ прослойка — JS напрямую вызывает C++ методы
└────┬────┘
     │ прямой вызов C++ метода (без JSON, без Bridge)
     ▼
┌──────────────────────────┐
│  Turbo Module (C++/ObjC/ │
│  Java/Kotlin)            │
│  ─ getString()           │  ← JSI создаёт HostObject
│  ─ setString()           │  ← JS вызывает методы напрямую
└──────────────────────────┘
```

### Как работает JSI

```
Legacy Bridge:
  JS → JSON.stringify → Bridge Queue → JSON.parse → Native → JSON.stringify → Bridge Queue → JSON.parse → JS
  Задержка: ~5-15ms на вызов, bottleneck при batch-вызовах

JSI (Turbo Modules):
  JS → C++ HostObject.method() → Native
  Задержка: ~0.01-0.1ms, прямой вызов без очереди

Разница: JSI в 50-100x быстрее за счёт:
  1. Нет JSON сериализации/десериализации
  2. Нет асинхронной очереди сообщений
  3. Прямой вызов C++ функции из JS-движка
```

## 4. Создание Turbo Native Module

### Шаг 1: TypeScript Spec

Имя модуля **обязательно** начинается с `Native`:

```typescript
// specs/NativeDeviceInfo.ts
import type { TurboModule } from 'react-native';
import { TurboModuleRegistry } from 'react-native';

export interface Spec extends TurboModule {
  // Синхронный метод
  getDeviceName(): string;

  // Асинхронный метод
  getBatteryLevel(): Promise<number>;

  // Метод с параметрами
  setPreference(key: string, value: string): void;

  // Метод с callback
  getLocation(callback: (lat: number, lon: number) => void): void;

  // Константы (вычисляются при инициализации модуля)
  getConstants(): {
    platform: string;
    version: string;
  };
}

export default TurboModuleRegistry.getEnforcing<Spec>('NativeDeviceInfo');
```

### Шаг 2: Codegen конфигурация

В `package.json`:

```json
{
  "codegenConfig": {
    "name": "AppSpecs",
    "type": "modules",
    "jsSrcsDir": "specs",
    "android": {
      "javaPackageName": "com.myapp.specs"
    }
  }
}
```

### Шаг 3: Android реализация (Kotlin)

```kotlin
// android/app/src/main/java/com/myapp/NativeDeviceInfoModule.kt
package com.myapp

import android.os.Build
import com.facebook.react.bridge.ReactApplicationContext
import com.facebook.react.bridge.Promise
import com.myapp.specs.NativeDeviceInfoSpec

class NativeDeviceInfoModule(
  reactContext: ReactApplicationContext
) : NativeDeviceInfoSpec(reactContext) {
  // NativeDeviceInfoSpec — сгенерирован Codegen из TypeScript Spec
  // Наследование гарантирует реализацию всех методов

  override fun getName() = NAME

  override fun getDeviceName(): String {
    return "${Build.MANUFACTURER} ${Build.MODEL}"
  }

  override fun getBatteryLevel(promise: Promise) {
    val batteryManager = reactApplicationContext
      .getSystemService(Context.BATTERY_SERVICE) as BatteryManager
    val level = batteryManager.getIntProperty(
      BatteryManager.BATTERY_PROPERTY_CAPACITY
    )
    promise.resolve(level.toDouble())
  }

  override fun setPreference(key: String, value: String) {
    val prefs = reactApplicationContext
      .getSharedPreferences("app_prefs", Context.MODE_PRIVATE)
    prefs.edit().putString(key, value).apply()
  }

  override fun getConstants(): Map<String, Any> {
    return mapOf(
      "platform" to "android",
      "version" to Build.VERSION.RELEASE
    )
  }

  companion object {
    const val NAME = "NativeDeviceInfo"
  }
}
```

### Шаг 4: iOS реализация (Objective-C++)

```objc
// ios/NativeDeviceInfo.h
#import <AppSpecs/AppSpecs.h>

@interface NativeDeviceInfo : NSObject <NativeDeviceInfoSpec>
@end
```

```objc
// ios/NativeDeviceInfo.mm
#import "NativeDeviceInfo.h"
#import <UIKit/UIKit.h>

@implementation NativeDeviceInfo

RCT_EXPORT_MODULE(NativeDeviceInfo)

- (NSString *)getDeviceName {
  return [[UIDevice currentDevice] name];
}

- (void)getBatteryLevel:(RCTPromiseResolveBlock)resolve
                 reject:(RCTPromiseRejectBlock)reject {
  [UIDevice currentDevice].batteryMonitoringEnabled = YES;
  float level = [UIDevice currentDevice].batteryLevel;
  resolve(@(level * 100));
}

- (void)setPreference:(NSString *)key value:(NSString *)value {
  [[NSUserDefaults standardUserDefaults] setObject:value forKey:key];
}

- (NSDictionary *)getConstants {
  return @{
    @"platform": @"ios",
    @"version": [[UIDevice currentDevice] systemVersion]
  };
}

- (std::shared_ptr<facebook::react::TurboModule>)getTurboModule:
    (const facebook::react::ObjCTurboModule::InitParams &)params {
  return std::make_shared<facebook::react::NativeDeviceInfoSpecJSI>(params);
}

@end
```

### Шаг 5: Использование в JS

```jsx
import NativeDeviceInfo from './specs/NativeDeviceInfo';

function DeviceInfoScreen() {
  const [battery, setBattery] = useState(0);
  const deviceName = NativeDeviceInfo.getDeviceName(); // синхронный!
  const { platform, version } = NativeDeviceInfo.getConstants();

  useEffect(() => {
    NativeDeviceInfo.getBatteryLevel().then(setBattery);
  }, []);

  return (
    <View>
      <Text>Device: {deviceName}</Text>
      <Text>Platform: {platform} {version}</Text>
      <Text>Battery: {battery}%</Text>
    </View>
  );
}
```

## 5. Fabric Native Components

Fabric Native Components заменяют legacy Native Components для **рендеринга нативных UI-элементов**.

### Отличие от Turbo Modules

| Аспект | Turbo Module | Fabric Component |
|--------|-------------|-----------------|
| Назначение | Логика, API | UI-компонент |
| Spec | `extends TurboModule` | `codegenNativeComponent` |
| Рендеринг | Нет | Нативный View |
| Props | Методы | React props |

---

## 6. Создание Fabric Native Component

### TypeScript Spec

```typescript
// specs/NativeMapViewNativeComponent.ts
import type { ViewProps } from 'react-native';
import type { Float, Int32 } from 'react-native/Libraries/Types/CodegenTypes';
import codegenNativeComponent from 'react-native/Libraries/Utilities/codegenNativeComponent';

interface NativeProps extends ViewProps {
  latitude: Float;
  longitude: Float;
  zoomLevel?: Int32;
  showsUserLocation?: boolean;
  onRegionChange?: (event: {
    nativeEvent: { latitude: Float; longitude: Float };
  }) => void;
}

export default codegenNativeComponent<NativeProps>('NativeMapView');
```

### Использование

```jsx
import NativeMapView from './specs/NativeMapViewNativeComponent';

<NativeMapView
  style={{ flex: 1 }}
  latitude={55.7558}
  longitude={37.6173}
  zoomLevel={12}
  showsUserLocation={true}
  onRegionChange={(e) => {
    console.log(e.nativeEvent.latitude, e.nativeEvent.longitude);
  }}
/>
```

## 7. Expo Modules API

Expo Modules API — это **фреймворк для создания нативных модулей**, разработанный командой Expo. Работает **в любом React Native проекте** (не только Expo).

### Зачем появился

Turbo Native Modules решили проблему производительности, но остались сложными в написании:
- Нужно писать Objective-C++ (не Swift) для iOS
- Нужно вручную настраивать Codegen, регистрировать пакеты
- Разный boilerplate для Android и iOS
- Нет встроенного маппинга сложных типов

Expo Modules API решает эти проблемы:

### Ключевые преимущества

1. **Swift + Kotlin** — нативные языки без Objective-C++/Java boilerplate
2. **Декларативный DSL** — единообразный API определения модуля для обеих платформ
3. **Автоматическое связывание** — не нужно регистрировать пакеты вручную (autolinking)
4. **Встроенный маппинг типов** — автоматическая конвертация Swift/Kotlin типов ↔ JS
5. **Поддержка JSI** — под капотом использует JSI, как Turbo Modules
6. **View Components** — создание нативных UI-компонентов тем же DSL
7. **Events** — встроенная система событий без дополнительного кода
8. **Работает везде** — в Expo и в bare React Native проектах

### Архитектура Expo Modules

```
JavaScript
    │
    │ requireNativeModule('MyModule')
    │
    ▼
┌──────────────────────┐
│   expo-modules-core   │  ← Единый runtime для обеих платформ
│   (JSI-based)        │
└────────┬─────────────┘
         │
    ┌────┴────┐
    │         │
    ▼         ▼
┌────────┐ ┌────────┐
│ Swift  │ │ Kotlin │
│ Module │ │ Module │
│ (DSL)  │ │ (DSL)  │
└────────┘ └────────┘
```

### DSL — Module Definition

Оба языка используют одинаковую структуру определения:

```
ModuleDefinition {
  Name("...")           → имя модуля для JS
  Constants { ... }     → синхронные константы
  Function("...") {}    → синхронная функция
  AsyncFunction("...") {} → асинхронная функция
  Events("...", "...")   → отправляемые события
  Property("...") {}    → getter/setter свойства
  View(MyNativeView) {} → нативный UI-компонент
  OnCreate {}           → lifecycle: модуль создан
  OnDestroy {}          → lifecycle: модуль уничтожен
  OnAppEntersForeground {} → app lifecycle
  OnAppBecomesActive {}    → app lifecycle
  OnAppEntersBackground {} → app lifecycle
}
```

### Шаг 2: iOS реализация (Swift)

```swift
// ios/MyDeviceModule.swift
import ExpoModulesCore
import UIKit

public class MyDeviceModule: Module {
  public func definition() -> ModuleDefinition {

    // Имя модуля для JS
    Name("MyDevice")

    // Константы — доступны синхронно
    Constants {
      return [
        "platform": "ios",
        "osVersion": UIDevice.current.systemVersion
      ]
    }

    // Синхронная функция
    Function("getDeviceName") {
      return UIDevice.current.name
    }

    // Синхронная функция с параметрами
    Function("add") { (a: Int, b: Int) -> Int in
      return a + b
    }

    // Асинхронная функция
    AsyncFunction("getBatteryLevel") { (promise: Promise) in
      UIDevice.current.isBatteryMonitoringEnabled = true
      let level = UIDevice.current.batteryLevel
      promise.resolve(level * 100)
    }

    // Асинхронная функция (упрощённый синтаксис — автоматический Promise)
    AsyncFunction("fetchUserData") { (userId: String) -> [String: Any] in
      // throw автоматически reject-ит Promise
      let data = try await APIService.fetchUser(userId)
      return ["name": data.name, "email": data.email]
    }

    // Property — getter + setter
    Property("volume") {
      get { AudioManager.shared.volume }
      set { newValue in AudioManager.shared.volume = newValue }
    }

    // Events — отправка событий в JS
    Events("onBatteryChange", "onNetworkChange")

    // Lifecycle hooks
    OnCreate {
      NotificationCenter.default.addObserver(
        self,
        selector: #selector(batteryChanged),
        name: UIDevice.batteryLevelDidChangeNotification,
        object: nil
      )
    }

    OnDestroy {
      NotificationCenter.default.removeObserver(self)
    }

    OnAppEntersBackground {
      // сохранить состояние
    }
  }

  @objc private func batteryChanged() {
    let level = UIDevice.current.batteryLevel * 100
    sendEvent("onBatteryChange", ["level": level])
  }
}
```

### Шаг 3: Android реализация (Kotlin)

```kotlin
// android/src/main/java/expo/modules/mydevice/MyDeviceModule.kt
package expo.modules.mydevice

import android.os.Build
import android.os.BatteryManager
import android.content.Context
import expo.modules.kotlin.modules.Module
import expo.modules.kotlin.modules.ModuleDefinition

class MyDeviceModule : Module() {
  override fun definition() = ModuleDefinition {

    Name("MyDevice")

    Constants {
      mapOf(
        "platform" to "android",
        "osVersion" to Build.VERSION.RELEASE
      )
    }

    Function("getDeviceName") {
      "${Build.MANUFACTURER} ${Build.MODEL}"
    }

    Function("add") { a: Int, b: Int ->
      a + b
    }

    AsyncFunction("getBatteryLevel") {
      val bm = appContext.reactContext
        ?.getSystemService(Context.BATTERY_SERVICE) as? BatteryManager
      val level = bm?.getIntProperty(BatteryManager.BATTERY_PROPERTY_CAPACITY) ?: -1
      level.toDouble()
    }

    AsyncFunction("fetchUserData") { userId: String ->
      val data = APIService.fetchUser(userId)
      mapOf("name" to data.name, "email" to data.email)
    }

    Events("onBatteryChange", "onNetworkChange")

    OnCreate {
      // регистрация listeners
    }

    OnDestroy {
      // cleanup
    }
  }
}
```

### Шаг 4: JS API

```typescript
// src/index.ts
import { requireNativeModule, EventEmitter } from 'expo-modules-core';

const MyDevice = requireNativeModule('MyDevice');

// Типизированный экспорт
export function getDeviceName(): string {
  return MyDevice.getDeviceName();
}

export function add(a: number, b: number): number {
  return MyDevice.add(a, b);
}

export async function getBatteryLevel(): Promise<number> {
  return MyDevice.getBatteryLevel();
}

export async function fetchUserData(userId: string): Promise<{
  name: string;
  email: string;
}> {
  return MyDevice.fetchUserData(userId);
}

// Константы
export const platform: string = MyDevice.platform;
export const osVersion: string = MyDevice.osVersion;

// Events
const emitter = new EventEmitter(MyDevice);

export function addBatteryListener(
  listener: (event: { level: number }) => void
) {
  return emitter.addListener('onBatteryChange', listener);
}
```

### Шаг 5: Использование

```tsx
import {

  getBatteryLevel,
```

## 9. Codegen

Codegen автоматически генерирует типизированный boilerplate из TypeScript/Flow спецификаций.

> **Важно:** Codegen используется в Turbo Modules и Fabric Components. Expo Modules API **не использует Codegen** — у него свой механизм маппинга типов через DSL.

### Что генерируется

```
TypeScript Spec
      │
      ▼ Codegen
      │
      ├── Android (Java)
      │   └── NativeDeviceInfoSpec.java
      │       ├── abstract getDeviceName(): String
      │       ├── abstract getBatteryLevel(Promise): void
      │       └── типизированный маппинг JS ↔ Java
      │
      ├── iOS (Objective-C++)
      │   ├── NativeDeviceInfoSpec.h (protocol)
      │   └── NativeDeviceInfoSpecJSI (C++ JSI binding)
      │
      └── C++ (общие типы)
          └── NativeDeviceInfoSpec-generated.cpp
```

### Запуск Codegen

```bash
# Android — при сборке (автоматически через Gradle)
cd android && ./gradlew generateCodegenArtifactsFromSchema

# iOS — при установке pods (автоматически)
cd ios && bundle exec pod install
```

## 10. Типы данных и маппинг

### JS → Native типы (Turbo Modules / Codegen)

| TypeScript | Java (Android) | ObjC (iOS) | C++ (JSI) |
|-----------|----------------|-------------|-----------|
| `string` | `String` | `NSString *` | `jsi::String` |
| `number` | `double` | `double` | `jsi::Value` |
| `boolean` | `boolean` | `BOOL` | `jsi::Value` |
| `string[]` | `ReadableArray` | `NSArray<NSString *> *` | `jsi::Array` |
| `{ [key: string]: T }` | `ReadableMap` | `NSDictionary *` | `jsi::Object` |
| `Promise<T>` | `Promise` | `RCTPromiseResolveBlock` | callback |
| `(arg: T) => void` | `Callback` | `RCTResponseSenderBlock` | `jsi::Function` |
| `null \| T` | `@Nullable T` | `T _Nullable` | `jsi::Value` (undefined) |

### Codegen-специфичные типы

```typescript
import type {
  Float,      // 32-bit float (vs number = 64-bit double)
  Double,     // 64-bit double (=== number)
  Int32,      // 32-bit integer
} from 'react-native/Libraries/Types/CodegenTypes';
```

### JS → Native типы (Expo Modules API)

Expo Modules автоматически конвертирует типы без Codegen:

| JS | Swift | Kotlin |
|----|-------|--------|
| `number` | `Int`, `Double`, `Float` | `Int`, `Double`, `Float` |
| `boolean` | `Bool` | `Boolean` |
| `string` | `String` | `String` |
| `number[]` | `[Int]`, `[Double]` | `List<Int>`, `List<Double>` |
| `object` | `[String: Any]` | `Map<String, Any>` |
| `null` | `nil` / Optional | `null` / Nullable |
| `Promise` | Автоматически (AsyncFunction) | Автоматически (AsyncFunction) |
| `Uint8Array` | `Data` | `ByteArray` |
| `Date` / ISO string | `Date` | `Date` |
| Enum (string union) | Swift enum | Kotlin enum |

#### Expo Modules: Enum маппинг

```swift
// Swift
enum Priority: String, Enumerable {
  case low
  case medium
  case high

// В DSL:
Function("setPriority") { (priority: Priority) in
  // priority уже Swift enum!
}
```

```kotlin
// Kotlin
enum class Priority(val value: String) : Enumerable {
  LOW("low"),
  MEDIUM("medium"),
  HIGH("high")
}

// В DSL:

  // priority уже Kotlin enum
}
```

```typescript
// JS
setPriority('high'); // строка → enum автоматически
```

```kotlin
  // data.name, data.age, data.email
```

## 11. Обратная совместимость

Для библиотек, которые должны поддерживать **и старую, и новую архитектуру**:

### Подход: Interop Layer

React Native предоставляет interop layer, который позволяет legacy модулям работать в новой архитектуре без изменений. Но для полной поддержки JSI рекомендуется мигрировать.

### Conditional Export

```js
// index.js
const isTurboModuleEnabled =
  global.__turboModuleProxy != null;

module.exports = isTurboModuleEnabled
  ? require('./NativeMyModule').default        // Turbo Module
  : require('./LegacyNativeMyModule').default; // Legacy Module
```

## 12. Сравнение: Legacy vs Turbo vs Expo Modules

### Общая таблица

| Аспект | Legacy Native Module | Turbo Native Module | Expo Modules API |
|--------|---------------------|--------------------|--------------------|
| **Коммуникация** | Bridge (JSON) | JSI (C++) | JSI (C++) |
| **Производительность** | Медленно (сериализация) | Быстро | Быстро |
| **Инициализация** | Eager (все при старте) | Lazy (по требованию) | Lazy (по требованию) |
| **Sync вызовы** | Нет (только async) | Да | Да |
| **Type safety** | Runtime | Compile-time (Codegen) | Compile-time (DSL) |
| **Языки iOS** | Objective-C | Objective-C++ | **Swift** |
| **Языки Android** | Java | Kotlin/Java | **Kotlin** |
| **Boilerplate** | Много (ручная регистрация) | Средне (Codegen помогает) | **Минимум** (DSL) |
| **Codegen** | Нет | Да (обязательно) | Нет (свой механизм) |
| **TypeScript Spec** | Нет | Обязательно | Не нужен |
| **Autolinking** | Ручная регистрация | Полуавтоматическая | **Полная** |
| **View Components** | Отдельный API | Fabric Components | **Тот же DSL** |
| **Events** | Ручной EventEmitter | Ручной | **Встроенный** |
| **Lifecycle hooks** | Ручная подписка | Ручная подписка | **Встроенные** |
| **Enum маппинг** | Нет | Нет | **Автоматический** |
| **Record маппинг** | Нет | ReadableMap | **Типизированные Record** |
| **Статус** | **Мёртв** (interop layer) | Рекомендуемый (RN core) | Рекомендуемый (Expo) |

### Количество кода для одного модуля (примерно)

```
Legacy Native Module:
  ├── Android: Module.java + Package.java + MainApplication регистрация  (~80 строк)
  ├── iOS: Module.m + Module.h                                           (~50 строк)
  └── JS: NativeModules import                                           (~5 строк)
  Итого: ~135 строк + ручная настройка

Turbo Native Module:
  ├── TypeScript Spec                                                     (~20 строк)
  ├── package.json codegen config                                         (~10 строк)
  ├── Android: Module.kt (extends сгенерированный Spec)                  (~40 строк)
  ├── iOS: Module.h + Module.mm (implements сгенерированный protocol)     (~40 строк)
  └── JS: import from spec                                                (~3 строки)
  Итого: ~113 строк + Codegen настройка

Expo Module:
  ├── Android: Module.kt (DSL)                                            (~25 строк)
  ├── iOS: Module.swift (DSL)                                             (~25 строк)
  ├── expo-module.config.json                                             (~5 строк)
  └── JS: requireNativeModule + типизированные экспорты                   (~15 строк)
  Итого: ~70 строк, zero config
```

### Когда что выбирать

```
Legacy Native Module:
  ✗ Bridge удалён в RN 0.82 — работает только через interop layer
  ✗ Interop layer будет удалён в будущих версиях
  ✓ Существующий код пока работает — но миграция обязательна

Turbo Native Module:
  ✓ Библиотека должна работать без Expo зависимостей
  ✓ Нужен максимальный контроль над C++ слоем
  ✓ Контрибьюция в React Native core или core-совместимые библиотеки
  ✓ Проект без Expo (bare React Native)
  ✗ Больше boilerplate, Objective-C++ для iOS

Expo Modules API:
  ✓ Новые модули в Expo-проекте (или bare RN с expo-modules-core)
  ✓ Быстрая разработка — минимум boilerplate
  ✓ Хочется писать на Swift/Kotlin без Obj-C++
  ✓ Нужны View Components, Events, Lifecycle — всё в одном DSL
  ✓ Автоматический маппинг сложных типов (Enum, Record, Date)
  ✓ Библиотека для экосистемы Expo
  ✗ Добавляет зависимость на expo-modules-core (~2MB)
```

### Миграция Legacy → Turbo / Expo

```
Legacy → Turbo:
  1. Написать TypeScript Spec
  2. Настроить Codegen в package.json
  3. Переписать Android (extends сгенерированный Spec)
  4. Переписать iOS (Objective-C → Objective-C++ с JSI)
  5. Обновить JS импорты

Legacy → Expo Modules:
  1. npx create-expo-module --local
  2. Переписать Android логику в Kotlin DSL
  3. Переписать iOS логику в Swift DSL
  4. Удалить старый код и регистрацию
  5. Всё — autolinking подхватит

Turbo → Expo Modules:
  1. Перенести логику из Obj-C++ в Swift DSL
  2. Перенести логику из Kotlin (уже Kotlin) в DSL формат
  3. Удалить TypeScript Spec и Codegen конфиг
  4. Добавить expo-module.config.json
```
