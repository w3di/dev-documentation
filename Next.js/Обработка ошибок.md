# Обработка ошибок — Error Handling в Next.js App Router

> Next.js использует файловые конвенции `error.js`, `global-error.js` и `not-found.js` для создания React Error Boundaries, которые автоматически перехватывают ошибки на уровне сегментов маршрутов и показывают fallback-UI вместо краша всего приложения.

## 1. Обзор обработки ошибок в Next.js

Ошибки в Next.js делятся на две категории:

| Категория | Описание | Подход |
|-----------|----------|--------|
| **Expected errors** | Ожидаемые ошибки (валидация форм, неудачные запросы) | Возвращать как значения, не бросать `throw` |
| **Uncaught exceptions** | Непредвиденные ошибки (баги, ошибки рендера) | Перехватываются `Error Boundaries` |

Next.js автоматически оборачивает сегменты маршрутов в [React Error Boundaries](https://react.dev/reference/react/Component#catching-rendering-errors-with-an-error-boundary). Для этого достаточно создать файл `error.js` / `error.tsx` в нужной папке маршрута.

### Иерархия компонентов сегмента

Внутри каждого сегмента маршрута Next.js выстраивает компоненты в следующем порядке:

```
<Layout>
  <ErrorBoundary fallback={<Error />}>   ← error.js
    <Suspense fallback={<Loading />}>     ← loading.js
      <NotFoundBoundary>                  ← not-found.js
        <Page />                          ← page.js
      </NotFoundBoundary>
    </Suspense>
  </ErrorBoundary>
</Layout>
```

> `error.js` оборачивает `loading.js`, `not-found.js`, `page.js` и вложенные `layout.js`, но **не оборачивает** `layout.js` и `template.js` того же сегмента.

## 2. error.js -- Error Boundary компонент

Файл `error.js` / `error.tsx` экспортирует Client Component, который выступает fallback-UI при непредвиденных ошибках.

### Props

| Prop | Тип | Описание |
|------|-----|----------|
| `error` | `Error & { digest?: string }` | Объект ошибки. В production сообщения от серверных ошибок скрываются |
| `error.message` | `string` | Для клиентских ошибок -- оригинальное сообщение. Для серверных -- generic-сообщение |
| `error.digest` | `string` | Автоматический хеш ошибки для сопоставления с серверными логами |
| `unstable_retry` | `() => void` | Повторный запрос и ре-рендер содержимого error boundary |
| `reset` | `() => void` | Сброс состояния ошибки без повторного запроса данных |

### Базовый пример

```tsx
// app/dashboard/error.tsx
'use client' // Error boundaries обязаны быть Client Components

import { useEffect } from 'react'

export default function Error({
  error,
  unstable_retry,
}: {
  error: Error & { digest?: string }
  unstable_retry: () => void
}) {
  useEffect(() => {
    // Логирование в сервис мониторинга (Sentry, Datadog и т.д.)
    console.error(error)
  }, [error])

  return (
    <div>
      <h2>Что-то пошло не так!</h2>
      <p>Код ошибки: {error.digest}</p>
      <button onClick={() => unstable_retry()}>
        Попробовать снова
      </button>
    </div>
  )
}
```

> В режиме разработки (`next dev`) объект `error` сериализуется с оригинальным сообщением для удобства отладки. В production серверные сообщения скрываются, чтобы не раскрывать внутренние детали.

## 3. global-error.js -- ошибки корневого уровня

`error.js` не перехватывает ошибки в `layout.js` / `template.js` того же сегмента. Для перехвата ошибок в **корневом** `layout.tsx` используется `global-error.js`.

### Ключевые особенности

- Должен содержать собственные теги `<html>` и `<body>`, поскольку **заменяет** корневой layout при активации.
- Должен быть Client Component (`'use client'`).
- Не поддерживает экспорт `metadata` / `generateMetadata` (можно использовать React-компонент `<title>`).
- Начиная с `v15.2.0`, отображается и в режиме разработки.

```tsx
// app/global-error.tsx
'use client'

export default function GlobalError({
  error,
  unstable_retry,
}: {
  error: Error & { digest?: string }
  unstable_retry: () => void
}) {
  return (
    <html>
      <body>
        <h2>Критическая ошибка приложения</h2>
        <p>{error.message}</p>
        <button onClick={() => unstable_retry()}>Перезагрузить</button>
      </body>
    </html>
  )
}
```

## 4. not-found.js -- страницы 404

Файл `not-found.js` показывает UI для ответа `404 Not Found`. Вызывается функцией `notFound()` из `next/navigation`.

### Функция `notFound()`

```tsx
// app/blog/[slug]/page.tsx
import { notFound } from 'next/navigation'
import { getPostBySlug } from '@/lib/posts'

export default async function Page({
  params,
}: {
  params: Promise<{ slug: string }>
}) {
  const { slug } = await params
  const post = getPostBySlug(slug)

  if (!post) {
    notFound() // Прерывает рендер и показывает ближайший not-found.js
  }

  return <article>{post.title}</article>
}
```

### Компонент `not-found.tsx`

```tsx
// app/blog/[slug]/not-found.tsx
export default function NotFound() {
  return (
    <div>
      <h2>404 -- Страница не найдена</h2>
      <p>Запрашиваемый пост не существует.</p>
    </div>
  )
}
```

Если `not-found.js` не определен в текущем сегменте, ошибка всплывает к ближайшему родительскому `not-found.js`. Корневой `app/not-found.tsx` обрабатывает все `404` глобально.

## 5. Обработка ошибок в Server Components

В [Server Components](Server%20и%20Client%20Components.md) ожидаемые ошибки обрабатываются через условные возвраты, а не `try/catch` с `throw`.

### Условный рендер

```tsx
// app/page.tsx
export default async function Page() {
  const res = await fetch('https://api.example.com/data')
  const data = await res.json()

  if (!res.ok) {
    return <p>Ошибка загрузки данных. Попробуйте позже.</p>
  }

  return <div>{data.title}</div>
}
```

### Проброс ошибок в Error Boundary

Если Server Component выбрасывает необработанное исключение, оно всплывает к ближайшему `error.js`:

```tsx
// app/dashboard/page.tsx
async function getData() {
  const res = await fetch('https://api.example.com/data')
  if (!res.ok) {
    throw new Error('Не удалось загрузить данные') // Перехватит error.js
  }
  return res.json()
}

export default async function Page() {
  const data = await getData()
  return <div>{data.title}</div>
}
```

## 6. Обработка ошибок в Client Components

Error Boundaries перехватывают ошибки **во время рендера**. Ошибки в обработчиках событий (`onClick`, `onChange`) ими **не перехватываются**.

### Ошибки в обработчиках событий

Для обработки ошибок в `onClick` / `onChange` используйте `try/catch` с `useState`:

```tsx
'use client'
import { useState } from 'react'

export function DeleteButton() {
  const [error, setError] = useState<string | null>(null)

  const handleClick = async () => {
    try {
      await fetch('/api/delete', { method: 'DELETE' })
    } catch (err) {
      setError('Ошибка при удалении')
    }
  }

  if (error) return <p>{error}</p>
  return <button onClick={handleClick}>Удалить</button>
}
```

### Ошибки внутри `startTransition`

Необработанные ошибки внутри `startTransition` из `useTransition` **всплывают** к ближайшему Error Boundary.

### Компонентный Error Boundary с `unstable_catchError`

Для гранулярного перехвата ошибок (не привязанного к файловым конвенциям) используется `unstable_catchError` из `next/error`. Функция принимает fallback-компонент и возвращает обёртку, которую можно использовать как обычный компонент:

```tsx
'use client'
import { unstable_catchError as catchError, type ErrorInfo } from 'next/error'

function ErrorFallback(
  props: { title: string },
  { error, unstable_retry: retry }: ErrorInfo
) {
  return (
    <div>
      <h2>{props.title}</h2>
      <p>{error.message}</p>
      <button onClick={() => retry()}>Повторить</button>
    </div>
  )
}
export default catchError(ErrorFallback)
// Использование: <ErrorBoundary title="Ошибка">{children}</ErrorBoundary>
```

## 7. Обработка ошибок в Server Actions

В Server Actions (Server Functions) ожидаемые ошибки моделируются как **возвращаемые значения**, а не исключения. Это позволяет использовать `useActionState` для отображения ошибок.

### Server Action -- возвращаем ошибку как значение

```ts
// app/actions.ts
'use server'

export async function createPost(prevState: any, formData: FormData) {
  const res = await fetch('https://api.example.com/posts', {
    method: 'POST',
    body: JSON.stringify({
      title: formData.get('title'),
      content: formData.get('content'),
    }),
  })
  if (!res.ok) return { message: 'Не удалось создать пост' }
  return { message: '' }
}
```

### Форма с `useActionState`

```tsx
'use client'
import { useActionState } from 'react'
import { createPost } from '@/app/actions'

export function PostForm() {
  const [state, formAction, pending] = useActionState(createPost, { message: '' })
  return (
    <form action={formAction}>
      <input type="text" name="title" required />
      <textarea name="content" required />
      {state?.message && <p aria-live="polite">{state.message}</p>}
      <button disabled={pending}>{pending ? 'Создание...' : 'Создать'}</button>
    </form>
  )
}
```

## 8. Обработка ошибок в Route Handlers

В [Route Handlers](Route%20Handlers.md) используется стандартный `try/catch` с возвратом `Response` / `NextResponse`:

```ts
// app/api/posts/route.ts
import { NextResponse } from 'next/server'

export async function GET() {
  try {
    const res = await fetch('https://api.example.com/posts')
    if (!res.ok) return NextResponse.json({ error: 'Ошибка' }, { status: res.status })
    return NextResponse.json(await res.json())
  } catch {
    return NextResponse.json({ error: 'Внутренняя ошибка' }, { status: 500 })
  }
}
```

> Route Handlers не используют Error Boundaries, поскольку они не рендерят UI. Ошибки обрабатываются явно через `try/catch` и соответствующие HTTP-коды.

## 9. Вложенность Error Boundaries

Ошибки **всплывают** к ближайшему родительскому Error Boundary. Это позволяет управлять гранулярностью обработки:

```
app/
├── error.tsx              ← Глобальный fallback для всего приложения
├── layout.tsx
├── dashboard/
│   ├── error.tsx          ← Перехватывает ошибки в dashboard/*
│   ├── layout.tsx
│   ├── page.tsx
│   ├── settings/
│   │   ├── error.tsx      ← Перехватывает только ошибки settings
│   │   └── page.tsx
│   └── analytics/
│       └── page.tsx       ← Ошибки всплывут к dashboard/error.tsx
└── global-error.tsx       ← Перехватывает ошибки корневого layout
```

### Правила всплытия

| Источник ошибки | Перехватчик |
|----------------|-------------|
| `page.tsx` в сегменте | `error.tsx` того же сегмента |
| Вложенный `layout.tsx` | `error.tsx` **родительского** сегмента |
| Корневой `layout.tsx` | `global-error.tsx` |
| `template.tsx` | `error.tsx` **родительского** сегмента |

> Если нужно перехватить ошибку в `layout.tsx` определённого сегмента, поместите `error.tsx` в **родительский** сегмент.

## 10. Типичные паттерны и best practices

### 1. Разделяйте expected и unexpected ошибки

- **Expected**: валидация, 404, ошибки API -- возвращайте как значения.
- **Unexpected**: баги, сетевые сбои -- бросайте исключения, ловите через `error.js`.

### 2. Логируйте ошибки в `useEffect`

```tsx
useEffect(() => {
  reportErrorToService(error) // Sentry, Datadog, LogRocket
}, [error])
```

### 3. Используйте `error.digest` для корреляции

В production серверные сообщения скрыты. Используйте `digest` для поиска ошибки в серверных логах.

### 4. Гранулярные Error Boundaries

Размещайте `error.tsx` на разных уровнях вложенности:
- **Корневой** `app/error.tsx` -- общий fallback.
- **Секционные** `app/dashboard/error.tsx` -- изолированные ошибки модулей.
- **Компонентные** через `unstable_catchError` -- точечная обработка.

### 5. Graceful Degradation

При ошибке рендера можно сохранить последний серверный HTML через кастомный `class`-компонент с `getDerivedStateFromError`, показывая уведомление вместо полного сброса UI.

### 6. Всегда создавайте `global-error.tsx`

Даже если корневой layout простой, `global-error.tsx` перехватит ошибки, которые `error.tsx` не может.

| Версия | Изменения |
|--------|-----------|
| `v16.2.0` | Добавлен prop `unstable_retry` |
| `v15.2.0` | `global-error` отображается в режиме разработки |
| `v13.1.0` | Введён `global-error` |
| `v13.0.0` | Введён `error.js` |
