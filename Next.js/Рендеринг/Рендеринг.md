## 1. Обзор стратегий рендеринга

### Эволюция рендеринга в Next.js

Стратегии рендеринга в Next.js развивались от простых к гибридным:

```
SSG (v9.3)  -->  SSR (getServerSideProps)  -->  ISR (v9.5)
    |                                               |
    v                                               v
Streaming + RSC (v13, App Router)  -->  PPR (v14+, experimental)
    |
    v
Cache Components + `use cache` (v15+)
```

### Ключевые концепции

На сервере Next.js использует React API для оркестрации рендеринга. Работа разбивается на чанки по сегментам маршрута (`layout` и `page`):

- **Server Components** рендерятся в специальный формат — `RSC Payload` (React Server Component Payload)
- **Client Components** и `RSC Payload` используются для пререндеринга HTML
- На клиенте HTML показывается мгновенно, затем `RSC Payload` согласовывает деревья, а JavaScript гидратирует клиентские компоненты

> `RSC Payload` — компактное бинарное представление дерева Server Components. Содержит результат рендера серверных компонентов, плейсхолдеры для клиентских компонентов со ссылками на их JS-файлы, а также пропсы, переданные из серверных компонентов в клиентские.

### Два этапа рендеринга на клиенте

**Первый заход (initial load):**
1. HTML мгновенно показывает неинтерактивный предпросмотр
2. `RSC Payload` согласует деревья серверных и клиентских компонентов
3. JavaScript гидратирует клиентские компоненты

**Последующие навигации:**
- `RSC Payload` префетчится и кэшируется
- Клиентские компоненты рендерятся на клиенте без серверного HTML

## 2. Static Rendering (SSG)

`Static Rendering` — стратегия по умолчанию в Next.js App Router. Страницы рендерятся на этапе сборки (`next build`) или при ревалидации, результат кэшируется и может раздаваться через CDN.

### Когда применяется автоматически

Next.js автоматически выбирает статический рендеринг, если маршрут **не** использует динамические функции (`cookies()`, `headers()`, `searchParams`) и не содержит некэшированных запросов данных.

```tsx
// app/about/page.tsx
// Этот компонент будет статически отрендерен на билде
export default function AboutPage() {
  return (
    <div>
      <h1>О компании</h1>
      <p>Мы создаём продукты для разработчиков.</p>
    </div>
  )
}
```

### Статический рендеринг с данными

```tsx
// app/blog/page.tsx
export default async function BlogPage() {
  // fetch без { cache: 'no-store' } — данные кэшируются на билде
  const res = await fetch('https://api.example.com/posts')
  const posts = await res.json()

  return (
    <ul>
      {posts.map((post: { id: string; title: string }) => (
        <li key={post.id}>{post.title}</li>
      ))}
    </ul>
  )
}
```

### `generateStaticParams` для динамических маршрутов

Функция `generateStaticParams` позволяет статически сгенерировать страницы для динамических сегментов на этапе сборки:

```tsx
// app/blog/[slug]/page.tsx
export async function generateStaticParams() {
  const posts = await fetch('https://api.example.com/posts').then(r => r.json())

  // Возвращаем массив параметров — каждый станет статической страницей
  return posts.map((post: { slug: string }) => ({
    slug: post.slug,
  }))
}

export default async function PostPage({
  params,
}: {
  params: Promise<{ slug: string }>
}) {
  const { slug } = await params
  const post = await fetch(`https://api.example.com/posts/${slug}`).then(r => r.json())

  return <article><h1>{post.title}</h1><p>{post.content}</p></article>
}
```

> **Подводный камень:** если `generateStaticParams` не покрывает все возможные значения параметра, не перечисленные пути по умолчанию будут рендериться динамически при первом запросе. Используйте `dynamicParams = false`, чтобы вернуть 404 для неизвестных путей.

### Проверка стратегии рендеринга

После `next build` в терминале отобразится сводка маршрутов с пометками:

```
Route (app)                    Size     First Load JS
┌ ○ /                          5.2 kB   89 kB
├ ○ /about                     1.2 kB   85 kB
├ ● /blog/[slug]               3.1 kB   87 kB
└ λ /dashboard                 8.4 kB   92 kB

○  (Static)   — предварительно отрендерен как статический HTML
●  (SSG)      — статически сгенерирован с generateStaticParams
λ  (Dynamic)  — рендерится на сервере при каждом запросе
```

## 3. Dynamic Rendering (SSR)

При `Dynamic Rendering` HTML генерируется **на каждый запрос**. Next.js автоматически переключается на динамический рендеринг, когда обнаруживает использование динамических функций или некэшированных данных.

### Динамические функции

Компонент становится динамическим при использовании следующих runtime-API:

| Функция / API | Описание |
|---|---|
| `cookies()` | Чтение cookies текущего запроса |
| `headers()` | Чтение HTTP-заголовков запроса |
| `searchParams` | Параметры строки запроса (`?key=value`) |
| `connection()` | Сигнал о необходимости данных запроса |
| `draftMode()` | Проверка режима черновика |

```tsx
// app/dashboard/page.tsx
import { cookies } from 'next/headers'

export default async function DashboardPage() {
  // Использование cookies() делает этот маршрут динамическим
  const cookieStore = await cookies()
  const theme = cookieStore.get('theme')?.value || 'light'

  const data = await fetch('https://api.example.com/user-data', {
    headers: { Cookie: cookieStore.toString() },
  })
  const userData = await data.json()

  return (
    <div data-theme={theme}>
      <h1>Добро пожаловать, {userData.name}</h1>
    </div>
  )
}
```

### Принудительный динамический рендеринг

Если нужно гарантировать динамический рендеринг независимо от наличия динамических функций:

```tsx
// app/realtime/page.tsx

// Способ 1: экспорт конфигурации
export const dynamic = 'force-dynamic'

// Способ 2: использование connection()
import { connection } from 'next/server'

export default async function RealtimePage() {
  await connection() // Гарантирует рендеринг на каждый запрос

  const data = await fetch('https://api.example.com/live-data')
  const liveData = await data.json()

  return <div>Текущая цена: {liveData.price}</div>
}
```

### Работа с `searchParams`

Проп `searchParams` является `Promise` и делает маршрут динамическим:

```tsx
// app/search/page.tsx
export default async function SearchPage({
  searchParams,
}: {
  searchParams: Promise<{ q?: string; page?: string }>
}) {
  const { q, page } = await searchParams
  const results = await fetch(
    `https://api.example.com/search?q=${q}&page=${page || '1'}`
  ).then(r => r.json())

  return (
    <div>
      <h1>Результаты поиска: {q}</h1>
      {results.map((item: { id: string; title: string }) => (
        <div key={item.id}>{item.title}</div>
      ))}
    </div>
  )
}
```

> **Важно:** в Next.js 15+ `params` и `searchParams` являются `Promise`. Это необходимо для поддержки PPR — значения доступны только после `await`, что позволяет отложить динамическую часть рендеринга.

## 4. Streaming и Suspense

`Streaming` позволяет серверу отправлять части HTML по мере их готовности, не дожидаясь завершения всех операций. Браузер начинает отрисовку, пока сервер ещё генерирует остальной контент.

### Как работает стриминг

При запросе страницы два потока работают параллельно:

1. **HTML-поток**: React рендерит прогрессивные чанки HTML. Статические части (layouts, навигация, фолбэки `Suspense`) отправляются немедленно. Когда асинхронный Server Component разрешается, React стримит его HTML вместе с инлайн-скриптами, которые заменяют фолбэк реальным контентом.

2. **Component Payload**: сериализованное представление дерева компонентов для [[Hydration]]. На первом заходе встроен в HTML-поток. При клиентских навигациях запрашивается отдельно (заголовок `rsc: 1`).

### Статическая оболочка (Static Shell)

Всё, что рендерится до любой асинхронной работы, называется **static shell**: layouts, навигация, фолбэки `<Suspense>`. Оболочка отправляется немедленно, давая пользователю видимый контент, пока динамические части стримятся.

### `loading.js` — стриминг на уровне страницы

Самый простой способ добавить стриминг — создать файл `loading.js` рядом с `page.js`:

```tsx
// app/dashboard/loading.tsx
export default function Loading() {
  return (
    <div className="animate-pulse">
      <div className="h-8 w-48 bg-gray-200 rounded mb-4" />
      <div className="h-4 w-full bg-gray-200 rounded mb-2" />
      <div className="h-4 w-2/3 bg-gray-200 rounded" />
    </div>
  )
}
```

Под капотом Next.js оборачивает `page.js` в `<Suspense>`, используя `loading.js` как фолбэк:

```
layout.js
  └── <Suspense fallback={<Loading />}>
        └── page.js
      </Suspense>
```

### Гранулярный стриминг с `<Suspense>`

`<Suspense>` даёт точный контроль над тем, какие части страницы стримятся независимо:

```tsx
// app/dashboard/page.tsx
import { Suspense } from 'react'
import { Revenue } from './revenue'
import { RecentOrders } from './recent-orders'
import { Recommendations } from './recommendations'

export default function Dashboard() {
  return (
    <div>
      <h1>Dashboard</h1>
      <div className="grid grid-cols-2 gap-4">
        {/* Каждый Suspense — независимая точка стриминга */}
        <Suspense fallback={<p>Загрузка выручки...</p>}>
          <Revenue />
        </Suspense>
        <Suspense fallback={<p>Загрузка заказов...</p>}>
          <RecentOrders />
        </Suspense>
      </div>
      <Suspense fallback={<p>Загрузка рекомендаций...</p>}>
        <Recommendations />
      </Suspense>
    </div>
  )
}
```

Если `Revenue` разрешится за 200ms, `RecentOrders` за 1s, а `Recommendations` за 3s — пользователь увидит каждую секцию по мере готовности, не дожидаясь самой медленной.

### Вложенные границы для прогрессивного раскрытия

```tsx
// app/product/[id]/page.tsx
import { Suspense } from 'react'

export default async function ProductPage({
  params,
}: {
  params: Promise<{ id: string }>
}) {
  const { id } = await params

  return (
    <div>
      <h1>Товар</h1>
      <Suspense fallback={<p>Загрузка информации...</p>}>
        <ProductDetails id={id} />
        <Suspense fallback={<p>Загрузка отзывов...</p>}>
          <Reviews productId={id} />
        </Suspense>
      </Suspense>
    </div>
  )
}
```

Внешняя граница показывает "Загрузка информации..." до разрешения `ProductDetails`. После этого становится видна внутренняя граница с "Загрузка отзывов..." до разрешения `Reviews`.

### Сравнение `loading.js` и `<Suspense>`

| Характеристика | `loading.js` | `<Suspense>` |
|---|---|---|
| **Область** | Вся страница | Любой компонент |
| **Настройка** | Достаточно создать файл | Явная обёртка компонентов |
| **Навигация** | Префетчится как мгновенный фолбэк | Не префетчится по умолчанию |
| **Лучше для** | Страниц, где всё зависит от данных | Гранулярного контроля |

### Ключевой принцип: "Push dynamic access down"

Откладывайте доступ к динамическим данным до компонента, который их реально использует:

```tsx
// app/dashboard/layout.tsx
import { Suspense } from 'react'
import { Nav } from './nav'
import { UserMenu } from './user-menu'
import { cookies } from 'next/headers'

export default function DashboardLayout({
  children,
}: {
  children: React.ReactNode
}) {
  // Начинаем работу, но НЕ вызываем await
  const cookieStore = cookies()

  return (
    <div>
      <Nav>
        <Suspense fallback={<p>Загрузка пользователя...</p>}>
          <UserMenu cookiePromise={cookieStore} />
        </Suspense>
      </Nav>
      {children}
    </div>
  )
}
```

Если бы layout вызвал `await cookies()` наверху — весь layout и его дочерние элементы стали бы динамическими и не могли бы быть частью static shell.

### Обработка ошибок при стриминге

Если компонент выбрасывает ошибку после начала стриминга, ближайший `error.js` перехватывает её и рендерит UI ошибки вместо упавшего компонента. Остальная страница остаётся нетронутой.

> **Важно:** HTTP-статус (`200 OK`) уже отправлен с первым чанком и не может быть изменён на `4xx`/`5xx`. Поэтому `notFound()` нужно вызывать **до** любой `<Suspense>` границы, чтобы получить реальный HTTP 404.

## 5. Client-Side Rendering (CSR)

[[Server и Client Components|Client Components]] рендерятся на клиенте, но в Next.js App Router они также **пререндерятся на сервере** для быстрого начального отображения.

### Объявление Client Component

Директива `'use client'` на первой строке файла объявляет границу между серверным и клиентским графами модулей:

```tsx
// app/ui/counter.tsx
'use client'

import { useState } from 'react'

export default function Counter() {
  const [count, setCount] = useState(0)

  return (
    <div>
      <p>{count} кликов</p>
      <button onClick={() => setCount(count + 1)}>+1</button>
    </div>
  )
}
```

> **Важно:** все импорты и дочерние компоненты файла с `'use client'` попадают в клиентский бандл. Не нужно добавлять директиву в каждый дочерний компонент.

### Когда использовать CSR

Используйте Client Components, когда нужны:
- **Состояние** (`useState`, `useReducer`) и обработчики событий (`onClick`, `onChange`)
- **Жизненный цикл** (`useEffect`, `useLayoutEffect`)
- **Браузерные API** (`localStorage`, `window`, `IntersectionObserver`, `Navigator.geolocation`)
- **Пользовательские хуки**, зависящие от состояния или эффектов

### Паттерн с `useEffect` для клиентских данных

```tsx
// app/ui/live-price.tsx
'use client'

import { useState, useEffect } from 'react'

export default function LivePrice({ symbol }: { symbol: string }) {
  const [price, setPrice] = useState<number | null>(null)

  useEffect(() => {
    const ws = new WebSocket(`wss://stream.example.com/${symbol}`)
    ws.onmessage = (event) => {
      setPrice(JSON.parse(event.data).price)
    }
    return () => ws.close()
  }, [symbol])

  if (price === null) return <span>Загрузка...</span>
  return <span>${price.toFixed(2)}</span>
}
```

### Минимизация клиентского бандла

Помечайте `'use client'` только конкретные интерактивные компоненты, а не целые страницы:

```tsx
// app/layout.tsx — Server Component (по умолчанию)
import Search from './search'  // Client Component
import Logo from './logo'      // Server Component

export default function Layout({ children }: { children: React.ReactNode }) {
  return (
    <>
      <nav>
        <Logo />       {/* Не попадает в клиентский бандл */}
        <Search />     {/* Только этот компонент — клиентский */}
      </nav>
      <main>{children}</main>
    </>
  )
}
```

### Передача данных из Server в Client Components

Пропсы, передаваемые из серверных компонентов в клиентские, должны быть **сериализуемыми** React (нельзя передать функции, `Map`, `Set`, классы):

```tsx
// app/[id]/page.tsx — Server Component
import LikeButton from '@/app/ui/like-button'
import { getPost } from '@/lib/data'

export default async function Page({
  params,
}: {
  params: Promise<{ id: string }>
}) {
  const { id } = await params
  const post = await getPost(id)

  // Передаём сериализуемые данные как пропсы
  return <LikeButton likes={post.likes} />
}
```

### Стриминг данных в Client Component через `use`

Вместо `await` на сервере можно передать `Promise` клиентскому компоненту и прочитать его через хук `use`:

```tsx
// app/dashboard/page.tsx — Server Component
import { Suspense } from 'react'
import { StatsChart } from './stats-chart'

export default function Dashboard() {
  // Не await — передаём промис как есть
  const statsPromise = fetch('https://api.example.com/stats').then(r => r.json())

  return (
    <Suspense fallback={<p>Загрузка графика...</p>}>
      <StatsChart dataPromise={statsPromise} />
    </Suspense>
  )
}
```

```tsx
// app/dashboard/stats-chart.tsx — Client Component
'use client'

import { use } from 'react'

type Stats = { revenue: number; orders: number }

export function StatsChart({ dataPromise }: { dataPromise: Promise<Stats> }) {
  const stats = use(dataPromise)

  return <div>Выручка: {stats.revenue}, Заказы: {stats.orders}</div>
}
```

### Интерливинг: Server Components внутри Client Components

Паттерн `children` позволяет вложить серверные компоненты в клиентские:

```tsx
// app/ui/modal.tsx — Client Component
'use client'

import { useState } from 'react'

export default function Modal({ children }: { children: React.ReactNode }) {
  const [isOpen, setIsOpen] = useState(false)
  if (!isOpen) return <button onClick={() => setIsOpen(true)}>Открыть</button>

  return <div className="modal">{children}</div>
}
```

```tsx
// app/page.tsx — Server Component
import Modal from './ui/modal'
import Cart from './ui/cart' // Server Component

export default function Page() {
  return (
    <Modal>
      <Cart /> {/* Рендерится на сервере, результат передаётся через RSC Payload */}
    </Modal>
  )
}
```

## 6. Incremental Static Regeneration (ISR)

`ISR` позволяет обновлять статические страницы **после** деплоя, без полной пересборки. Страница рендерится статически, но периодически перегенерируется в фоне.

### Time-based Revalidation

```tsx
// app/products/page.tsx
export const revalidate = 3600 // Ревалидация каждые 60 минут

export default async function ProductsPage() {
  const products = await fetch('https://api.example.com/products').then(r => r.json())

  return (
    <ul>
      {products.map((p: { id: string; name: string; price: number }) => (
        <li key={p.id}>{p.name} — ${p.price}</li>
      ))}
    </ul>
  )
}
```

Как это работает:

1. На билде страница рендерится статически
2. В течение 3600 секунд все запросы получают кэшированную версию
3. После истечения таймера следующий запрос получает **ещё** кэшированную версию (stale)
4. Next.js запускает регенерацию в фоне
5. После успешной регенерации кэш обновляется — последующие запросы получают свежую версию
6. Если регенерация не удалась — предыдущая версия продолжает отдаваться

### On-demand Revalidation

Для немедленного обновления используйте `revalidatePath` или `revalidateTag`:

```tsx
// app/actions.ts
'use server'

import { revalidatePath, revalidateTag } from 'next/cache'

export async function publishPost() {
  await db.post.create({ /* ... */ })

  // Способ 1: ревалидация по пути
  revalidatePath('/blog')

  // Способ 2: ревалидация по тегу
  revalidateTag('posts')
}
```

```tsx
// app/blog/page.tsx
export default async function BlogPage() {
  const res = await fetch('https://api.example.com/posts', {
    next: { tags: ['posts'] }, // Привязка тега для on-demand ревалидации
  })
  const posts = await res.json()

  return <ul>{posts.map((p: { id: string; title: string }) => <li key={p.id}>{p.title}</li>)}</ul>
}
```

### Route Handler для вебхуков

```tsx
// app/api/revalidate/route.ts
import { revalidateTag } from 'next/cache'
import { NextRequest } from 'next/server'

export async function POST(request: NextRequest) {
  const secret = request.headers.get('x-revalidate-secret')
  if (secret !== process.env.REVALIDATION_SECRET) {
    return new Response('Unauthorized', { status: 401 })
  }

  const { tag } = await request.json()
  revalidateTag(tag)

  return Response.json({ revalidated: true, now: Date.now() })
}
```

### ISR с `use cache` (Next.js 15+)

В новой модели Cache Components вместо `revalidate` используются `'use cache'` и `cacheLife`:

```tsx
// app/products/page.tsx
import { cacheLife, cacheTag } from 'next/cache'

export default async function ProductsPage() {
  'use cache'
  cacheLife('hours') // Профиль кэширования
  cacheTag('products') // Тег для on-demand ревалидации

  const products = await fetch('https://api.example.com/products').then(r => r.json())

  return (
    <ul>
      {products.map((p: { id: string; name: string }) => (
        <li key={p.id}>{p.name}</li>
      ))}
    </ul>
  )
}
```

> **Подводный камень:** `revalidate = 0` — это **не** "кэшировать навсегда". Это означает "ревалидировать на каждый запрос", т.е. фактически динамический рендеринг. Для бесконечного кэша используйте `revalidate = false` (значение по умолчанию для статики).

## 7. Partial Pre-rendering (PPR)

[[Partial Pre-rendering (PPR)]] — гибридная стратегия, которая комбинирует статическую оболочку с динамическими "дырами" на **одной странице**. Статическая часть отдаётся мгновенно с Edge, а динамические компоненты стримятся по мере готовности.

### Зачем нужен PPR

Традиционно Next.js выбирал стратегию рендеринга **для всего маршрута**: либо статика, либо динамика. PPR снимает это ограничение — теперь одна страница может быть **частично статической и частично динамической**.

### Как работает

1. На билде рендерится максимально возможная часть страницы — **static shell**
2. Динамические части (компоненты, использующие runtime-API) изолируются границами `<Suspense>`
3. При запросе пользователь мгновенно получает оболочку с фолбэками
4. Динамические части стримятся параллельно, заменяя фолбэки по готовности

```tsx
// app/page.tsx
import { Suspense } from 'react'
import { cookies } from 'next/headers'

// Статическая часть — попадёт в static shell
function Hero() {
  return (
    <section>
      <h1>Добро пожаловать в магазин</h1>
      <p>Лучшие товары по лучшим ценам</p>
    </section>
  )
}

// Динамическая часть — стримится при запросе
async function UserGreeting() {
  const cookieStore = await cookies()
  const name = cookieStore.get('username')?.value || 'Гость'
  return <p>Привет, {name}!</p>
}

// Динамическая часть — стримится при запросе
async function PersonalRecommendations() {
  const cookieStore = await cookies()
  const userId = cookieStore.get('userId')?.value
  const recs = await fetch(`https://api.example.com/recommendations/${userId}`).then(r => r.json())

  return (
    <ul>
      {recs.map((item: { id: string; name: string }) => (
        <li key={item.id}>{item.name}</li>
      ))}
    </ul>
  )
}

export default function HomePage() {
  return (
    <>
      {/* Статика — мгновенно */}
      <Hero />

      {/* Динамика — стримится */}
      <Suspense fallback={<p>Загрузка...</p>}>
        <UserGreeting />
      </Suspense>

      <Suspense fallback={<p>Подбираем рекомендации...</p>}>
        <PersonalRecommendations />
      </Suspense>
    </>
  )
}
```

### Включение PPR

PPR включается с помощью конфигурации `cacheComponents` (Next.js 15+):

```ts
// next.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
}

export default nextConfig
```

С включённым `cacheComponents` PPR становится **поведением по умолчанию**: всё, что не обёрнуто в `'use cache'` или не является детерминированной операцией, должно быть обёрнуто в `<Suspense>`.

### Что делает компонент динамическим в PPR

| Сигнал | Пример |
|---|---|
| `cookies()` | `const c = await cookies()` |
| `headers()` | `const h = await headers()` |
| `searchParams` | `const { q } = await searchParams` |
| `connection()` | `await connection()` |
| Некэшированный `fetch` | `fetch(url, { cache: 'no-store' })` |
| `Math.random()`, `Date.now()` | Недетерминированные операции |

> **Подводный камень:** если динамический компонент не обёрнут в `<Suspense>`, Next.js выбросит ошибку: `Uncached data was accessed outside of <Suspense>`. Это защитный механизм, предотвращающий "заражение" всей страницы динамичностью.

### Отказ от static shell

Если весь контент должен рендериться динамически, используйте `<Suspense>` с пустым фолбэком вокруг `<body>` в Root Layout:

```tsx
// app/layout.tsx
import { Suspense } from 'react'

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html>
      <Suspense fallback={null}>
        <body>{children}</body>
      </Suspense>
    </html>
  )
}
```

## 8. Hydration

`Hydration` (гидратация) — процесс, при котором React "присоединяет" обработчики событий и состояние к статическому HTML, отрендеренному на сервере, делая страницу интерактивной.

### Как работает гидратация

1. Сервер рендерит HTML (включая Client Components) и отправляет его клиенту
2. Браузер отображает HTML — пользователь видит страницу, но она неинтерактивна
3. React загружает JS-бандлы клиентских компонентов
4. React "проходит" по DOM, сравнивает его с виртуальным деревом и присоединяет обработчики событий
5. Страница становится полностью интерактивной

```
Сервер                           Клиент
  |                                |
  |-- HTML (SSR) ----------------> | Пользователь видит контент
  |                                | (неинтерактивный)
  |-- JS bundles --------------->  |
  |                                | React гидратирует
  |                                | Страница интерактивна
```

### Selective Hydration

React поддерживает **выборочную гидратацию** с `<Suspense>`: каждая граница `Suspense` — отдельная единица гидратации. React гидратирует компоненты независимо по мере их стриминга и **приоритизирует** то, с чем пользователь взаимодействует.

Без `<Suspense>` React гидратирует всю страницу за один блокирующий проход. С границами `Suspense` гидратация разбивается на маленькие задачи, которые уступают управление браузеру, сохраняя отзывчивость main thread.

```tsx
// Каждая Suspense-граница — отдельная единица гидратации
<Suspense fallback={<HeaderSkeleton />}>
  <Header />    {/* Гидратируется первым — маленький компонент */}
</Suspense>

<Suspense fallback={<ContentSkeleton />}>
  <Content />   {/* Гидратируется вторым */}
</Suspense>

<Suspense fallback={<SidebarSkeleton />}>
  <Sidebar />   {/* Гидратируется третьим */}
</Suspense>
```

Если пользователь кликнет на `Sidebar` до его гидратации, React повысит приоритет гидратации `Sidebar` и обработает событие.

### Ошибки гидратации (Hydration Mismatch)

Hydration mismatch возникает, когда HTML, отрендеренный на сервере, **не совпадает** с тем, что React ожидает на клиенте.

**Типичные причины:**

1. **Браузерные API при рендере:**

```tsx
// ОШИБКА: window не существует на сервере
'use client'
export default function Theme() {
  // Это вызовет hydration mismatch
  const isDark = window.matchMedia('(prefers-color-scheme: dark)').matches
  return <div className={isDark ? 'dark' : 'light'}>...</div>
}
```

**Решение — отложить до `useEffect`:**

```tsx
'use client'
import { useState, useEffect } from 'react'

export default function Theme() {
  const [isDark, setIsDark] = useState(false)

  useEffect(() => {
    setIsDark(window.matchMedia('(prefers-color-scheme: dark)').matches)
  }, [])

  return <div className={isDark ? 'dark' : 'light'}>...</div>
}
```

2. **Текущая дата/время:**

```tsx
// ОШИБКА: время на сервере и клиенте разное
'use client'
export default function Clock() {
  return <p>{new Date().toLocaleTimeString()}</p> // Hydration mismatch!
}
```

**Решение:**

```tsx
'use client'
import { useState, useEffect } from 'react'

export default function Clock() {
  const [time, setTime] = useState<string>('')

  useEffect(() => {
    setTime(new Date().toLocaleTimeString())
    const interval = setInterval(() => {
      setTime(new Date().toLocaleTimeString())
    }, 1000)
    return () => clearInterval(interval)
  }, [])

  return <p>{time || 'Загрузка...'}</p>
}
```

3. **Невалидный HTML (вложенность):**

```tsx
// ОШИБКА: <p> не может содержать <div>
return <p><div>Контент</div></p> // Hydration mismatch!
```

4. **Расширения браузера**, модифицирующие DOM (решение — `suppressHydrationWarning`):

```tsx
<time suppressHydrationWarning>{formattedDate}</time>
```

> **Важно:** `suppressHydrationWarning` подавляет предупреждение, но **не исправляет** проблему. Используйте его только для заведомо различающихся значений (даты, расширения), а не для маскировки багов.

### Влияние на Web Vitals

| Метрика | Как гидратация влияет |
|---|---|
| **TTFB** | Не влияет — HTML отправляется до гидратации |
| **FCP** | Не влияет — контент отображается из серверного HTML |
| **LCP** | Не влияет напрямую, но если LCP-элемент внутри `Suspense` — он задержится |
| **INP** | Selective hydration с `Suspense` улучшает отзывчивость |
| **CLS** | Скелетоны-фолбэки должны совпадать по размеру с финальным контентом |

## 9. Сводная таблица стратегий

| Стратегия | Когда рендерится | Где рендерится | Данные | Лучше для | Компромиссы |
|---|---|---|---|---|---|
| **SSG** | На билде | Сервер | Статические, известны на билде | Блоги, документация, лендинги | Данные устаревают до следующего билда |
| **SSR** | На каждый запрос | Сервер | Динамические, зависят от запроса | Персонализация, дашборды, поиск | Высокая нагрузка на сервер, медленнее TTFB |
| **ISR** | На билде + фоновая ревалидация | Сервер | Обновляемые по времени или событию | Каталоги, новостные ленты | Данные могут быть stale в окне ревалидации |
| **CSR** | В браузере | Клиент | Клиентские API, реалтайм | Интерактивные виджеты, чаты | Нет SEO для CSR-контента, нужен JS |
| **Streaming** | Прогрессивно на запрос | Сервер -> клиент | Смешанные (быстрые + медленные) | Дашборды, сложные страницы | Сложность управления `Suspense` |
| **PPR** | Статическая оболочка на билде, динамика на запрос | Сервер (Edge + Origin) | Статика + динамика | Страницы с персонализацией + статикой | Требует осознанного дизайна `Suspense` границ |

### Дерево принятия решений

```
Страница полностью статична?
├── Да --> SSG
└── Нет
    ├── Данные обновляются редко?
    │   ├── Да --> ISR (time-based / on-demand)
    │   └── Нет
    │       ├── Есть и статические, и динамические части?
    │       │   ├── Да --> PPR (или Streaming + Suspense)
    │       │   └── Нет (всё динамическое)
    │       │       └── SSR (Dynamic Rendering)
    │       └── Нужна интерактивность без серверного рендеринга?
    │           └── CSR (Client Component + useEffect)
    └── Нужен реалтайм в браузере?
        └── CSR (WebSocket, SSE) + Server Component для начальных данных
```
