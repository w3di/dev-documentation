# Partial Pre-rendering (PPR) — гибридный рендеринг

> **PPR** объединяет статическое и динамическое на одной странице: мгновенная статическая
> оболочка (shell) с Edge CDN, а динамические части стримятся по мере готовности
> через `<Suspense>` boundaries. Одна HTTP-response, один маршрут, два режима рендеринга.

## 1. Зачем нужен PPR

До PPR выбор был бинарным: **вся страница** статическая или **вся** динамическая. Но в реальности:
- Страница блога — статична, кроме кнопки «лайк» и счётчика просмотров.
- Дашборд — каркас статичен, виджеты с метриками динамичны.
- Лендинг — контент статичен, персонализированный блок — динамичен.

PPR позволяет не выбирать — статические и динамические части **сосуществуют** в одном маршруте.

---

## 2. Как это работает

### На этапе сборки (build time)

1. Next.js рендерит **максимально возможную** статическую часть страницы.
2. Компоненты внутри `<Suspense>`, использующие runtime API, откладываются — вместо них в HTML вставляется `fallback`.
3. Результат — **статическая оболочка** (shell) с «дырами» для динамики.

### На этапе запроса (request time)

1. Статическая оболочка отдаётся мгновенно (из Edge CDN).
2. Параллельно запускается рендер динамических частей на сервере.
3. Готовые части **стримятся** через тот же HTTP-ответ, заменяя fallback-плейсхолдеры.

```
Статическая оболочка (мгновенно с CDN)
┌─────────────────────────────────┐
│  Header (статика)               │
│  ┌───────────────────────────┐  │
│  │  Suspense fallback...     │◄─── динамика стримится по готовности
│  └───────────────────────────┘  │
│  Sidebar (статика)              │
│  Content (статика)              │
│  ┌───────────────────────────┐  │
│  │  Suspense fallback...     │◄─── ещё одна динамическая зона
│  └───────────────────────────┘  │
│  Footer (статика)               │
└─────────────────────────────────┘
```

## 3. Что делает компонент динамическим

Компонент становится динамическим при использовании **runtime API**:

| API | Описание |
|-----|----------|
| `cookies()` | Чтение cookies запроса |
| `headers()` | Чтение заголовков запроса |
| `connection()` | Ожидание установки соединения |
| `draftMode()` | Проверка режима черновика |
| `searchParams` (проп страницы) | Query-параметры URL |
| `unstable_noStore()` | Явный отказ от кэширования |
| `fetch({ cache: 'no-store' })` | Некэшируемый запрос |

**Ключевое правило**: динамичность определяется **фактом доступа** к runtime API, а не местом определения компонента. Пропс можно передать через статичный слой — динамика «срабатывает» только при чтении значения.

## 4. Роль Suspense

`<Suspense>` в PPR выполняет двойную функцию:
1. **Барьер динамичности** — удерживает dynamic API внутри, не «заражая» остальную страницу.
2. **Точка стриминга** — определяет, где показывать fallback и куда подставить готовый контент.

```tsx
import { Suspense } from 'react'
import { StaticHeader } from './header'
import { DynamicUserPanel } from './user-panel'

export default function Page() {
  return (
    <>
      <StaticHeader /> {/* пререндерится на билде */}
      <Suspense fallback={<UserPanelSkeleton />}>
        <DynamicUserPanel /> {/* стримится в рантайме */}
      </Suspense>
    </>
  )
}
```

**Важно**: Suspense сам по себе **не делает** компонент динамическим. Динамичность определяет использование runtime API внутри.

---

## 5. Стриминг в PPR

- Статический HTML + динамические чанки отправляются **в одном HTTP-ответе**.
- Браузер начинает отрисовку статики немедленно.
- По мере готовности динамические части заменяют fallback-плейсхолдеры.
- Динамические зоны стримятся **параллельно** — одна медленная зона не блокирует другие.

---

## 6. Отличия от SSR и SSG

| Характеристика | SSG | SSR | PPR |
|----------------|-----|-----|-----|
| Когда рендерится | Build time | Request time | Оба |
| TTFB | Мгновенный (CDN) | Ждёт сервер | Мгновенный (shell с CDN) |
| Персонализация | ❌ | ✅ | ✅ (в dynamic holes) |
| JS бандл | Минимальный | Полный | Минимальный (shell) |
| Стриминг | ❌ | ✅ | ✅ (только для dynamic) |
| Кэшируемость | Полная | Ограниченная | Shell — полная, dynamic — настраиваемая |

## 7. Включение PPR

PPR — **экспериментальная** функция. Включается в два шага:

### Шаг 1: Конфигурация

```js
// next.config.js
module.exports = {
  experimental: {
    ppr: 'incremental', // поэтапное внедрение
  },
}
```

### Шаг 2: Opt-in на уровне маршрута

```tsx
// app/dashboard/layout.tsx
export const experimental_ppr = true

export default function DashboardLayout({ children }) {
  return <section>{children}</section>
}
```

Маршруты без явного `experimental_ppr = true` **остаются без PPR**.

---

## 8. Наследование и отключение

- Флаг `experimental_ppr` **наследуется** дочерними сегментами (layout + page).
- Для отключения у потомка: `export const experimental_ppr = false`.

```
app/
├── layout.tsx                    ← PPR выключен (по умолчанию)
├── dashboard/
│   ├── layout.tsx                ← experimental_ppr = true
│   ├── page.tsx                  ← наследует PPR
│   └── settings/
│       └── page.tsx              ← наследует PPR
└── blog/
    └── page.tsx                  ← без PPR
```

## 9. Практические паттерны

### Изоляция динамики

Оборачивайте каждый динамический участок в свой `<Suspense>`:

```tsx
<Suspense fallback={<CartSkeleton />}>
  <Cart /> {/* cookies(), персонализация */}
</Suspense>
```

### Содержательные fallback

Используйте скелетоны, а не спиннеры — они сохраняют layout и улучшают CLS:

```tsx
<Suspense fallback={<div className="h-48 animate-pulse bg-gray-200 rounded" />}>
  <DynamicWidget />
</Suspense>
```

### Передача динамических пропов

```tsx
// page.tsx — статичный
export default function Page({ searchParams }) {
  return (
    <Suspense fallback={<ResultsSkeleton />}>
      <SearchResults query={searchParams.q} /> {/* динамика срабатывает здесь */}
    </Suspense>
  )
}
```

## 10. Роль Middleware

[[Middleware]] усиливает PPR: можно rewrite на разные статические оболочки по:
- Локали / геолокации
- Feature flags / A/B тесты
- Статусу аутентификации

Разные оболочки кэшируются отдельно, динамические зоны остаются одинаковыми.

---

## 11. Кэширование и ревалидация

- **Статическая оболочка**: кэшируется на Edge CDN, ревалидируется через ISR (`revalidate`) или on-demand.
- **Динамические части**: могут использовать Data Cache для снижения задержек.
- **Совместимость**: PPR работает с `revalidatePath`, `revalidateTag` и `use cache`.

---

## 12. Ограничения и статус

- **Экспериментальная** фича — API может измениться.
- Требуется **дисциплина** в выделении Suspense boundaries.
- Максимальный эффект при **Edge-доставке** статики.
- Не рекомендуется для production до стабилизации (следите за релиз-нотами).
