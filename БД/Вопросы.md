### Реляционная модель данных

1. **Что такое отношение в реляционной модели?**
    Это именованная таблица — множество кортежей (строк), где каждая строка содержит значения атрибутов (столбцов). Кортежи уникальны, порядок строк не имеет значения.

2. **Чем отношение отличается от таблицы в СУБД?**
    - **Отношение** — теоретическая концепция: множество кортежей без дубликатов и порядка.
    - **Таблица** — физическое представление отношения, допускает порядок строк и повторения.

3. **Что такое кортеж?**
    Строка (запись) в таблице — упорядоченный набор значений для всех атрибутов.

4. **Что такое атрибут?**
    Именованное свойство сущности, столбец в таблице, определяющий характер данных (например, имя, возраст, цена).

5. **Почему порядок строк в отношении не имеет значения?**
    Потому что отношение — множество кортежей, а в множестве порядок элементов не определён.

6. **Почему порядок атрибутов логически неважен?**
    Каждый атрибут идентифицируется именем, а не позицией, поэтому к данным можно обращаться по имени.

7. **Почему в отношении не допускаются дубликаты кортежей?**
    Отношение — множество, а множества не содержат одинаковых элементов. Это обеспечивает уникальность данных и корректность ссылок через ключи.

8. **Что такое домен атрибута?**
    Множество допустимых значений атрибута (тип данных, диапазон, ограничения), обеспечивающее целостность данных.

9. **Что означает атомарность значений и как она связана с 1NF?**
    Каждое поле содержит одно неделимое значение. Это требование Первой Нормальной Формы (1NF), которая исключает повторяющиеся группы и обеспечивает базовую структурированность таблицы.

10. **Можно ли считать таблицу без ключей отношением?**
    Можно, если таблица представляет множество кортежей с атрибутами. Но отсутствие ключей нарушает требование уникальности, поэтому формально это неполное отношение.

### Ключи и целостность

11. **Что такое candidate key?**
    Candidate key — минимальный набор атрибутов, однозначно идентифицирующий каждый кортеж в отношении. В таблице может быть несколько кандидатных ключей, из которых один выбирается в качестве primary key. Минимальность означает, что удаление любого атрибута из набора приведёт к потере уникальности.

12. **Что такое primary key?**
    Primary key — кандидатный ключ, выбранный в качестве основного идентификатора строк таблицы. Он гарантирует уникальность каждой строки и не допускает значений NULL. В таблице может быть только один primary key, хотя физически он реализуется как уникальный индекс.

13. **Что такое super key?**
    Super key — любой набор атрибутов, однозначно идентифицирующий кортеж в отношении. В отличие от candidate key, super key может содержать избыточные атрибуты. Каждый candidate key является super key, но не наоборот — super key может включать дополнительные столбцы сверх необходимого минимума.

14. **Чем natural key отличается от surrogate key?**
    Natural key — ключ, составленный из реальных атрибутов предметной области (например, номер паспорта или ИНН). Surrogate key — искусственный идентификатор, не имеющий бизнес-смысла (например, автоинкрементный id или UUID). Natural key может измениться при изменении бизнес-правил, тогда как surrogate key стабилен и компактен, что упрощает связи между таблицами.

15. **Почему primary key является логическим требованием?**
    Primary key обеспечивает фундаментальное свойство реляционной модели — уникальную идентификацию каждого кортежа. Без него невозможно однозначно адресовать строки, устанавливать внешние ключи и поддерживать ссылочную целостность. Это требование модели данных, а не особенность конкретной СУБД.

16. **Что такое entity integrity?**
    Entity integrity — правило целостности, требующее, чтобы primary key не содержал NULL ни в одном из своих атрибутов. Это гарантирует, что каждая сущность (строка) в таблице однозначно идентифицируема. Нарушение этого правила делает невозможным различение строк и корректную работу ссылок.

17. **Что такое referential integrity?**
    Referential integrity — правило, гарантирующее, что каждое значение foreign key ссылается на существующую строку в связанной таблице или равно NULL. Это предотвращает появление «висячих» ссылок. В PostgreSQL реализуется через ограничение FOREIGN KEY с действиями ON DELETE и ON UPDATE (CASCADE, SET NULL, RESTRICT и др.).

18. **Что такое domain integrity?**
    Domain integrity — правило, обеспечивающее допустимость значений в столбце в рамках заданного домена. Реализуется через типы данных, ограничения CHECK, NOT NULL и ENUM. Например, столбец «возраст» с типом INTEGER и ограничением CHECK (age > 0 AND age < 150) обеспечивает domain integrity.

19. **В чём разница между логической и физической целостностью данных?**
    Логическая целостность определяется на уровне модели данных — это правила ключей, ссылочной целостности, доменов и бизнес-ограничений. Физическая целостность обеспечивается на уровне хранения — контрольные суммы, журналирование (WAL), резервное копирование. Логическая целостность отвечает на вопрос «данные корректны?», физическая — «данные не повреждены?».

20. **Может ли foreign key быть NULL и что это означает логически?**
    Да, foreign key может быть NULL, если столбец не имеет ограничения NOT NULL. Логически это означает, что связь между сущностями не установлена — например, сотрудник ещё не назначен в отдел. NULL в foreign key не нарушает referential integrity, так как NULL не является ссылкой на несуществующую строку.

### NULL и логика

21. **Что такое NULL в реляционной модели?**
    NULL — специальный маркер, обозначающий отсутствие значения. Он указывает на то, что значение неизвестно, неприменимо или ещё не задано. NULL не является нулём, пустой строкой или значением false — это принципиально отдельная концепция, требующая особой обработки в запросах.

22. **Почему NULL не является значением?**
    NULL — это маркер отсутствия значения, а не конкретное значение из домена атрибута. Именно поэтому NULL != NULL (результат — UNKNOWN, а не TRUE). Любая арифметическая или строковая операция с NULL также возвращает NULL, а для проверки используется оператор IS NULL, а не сравнение через =.

23. **Что такое трёхзначная логика?**
    Трёхзначная логика (three-valued logic) — система, в которой логические выражения могут принимать три значения: TRUE, FALSE и UNKNOWN. Она возникает в SQL из-за наличия NULL: сравнение любого значения с NULL даёт UNKNOWN. Операторы AND и OR работают по расширенным таблицам истинности: например, TRUE AND UNKNOWN = UNKNOWN, а TRUE OR UNKNOWN = TRUE.

24. **Почему сравнение с NULL не даёт TRUE или FALSE?**
    Потому что NULL обозначает неизвестное значение. Сравнивать неизвестное с чем-либо логически некорректно — результат также неизвестен (UNKNOWN). Поэтому выражения вида `x = NULL` и даже `NULL = NULL` возвращают UNKNOWN, и строки, для которых условие WHERE оценивается как UNKNOWN, исключаются из результата.

25. **Какие логические проблемы вносит NULL в модель данных?**
    NULL усложняет предикаты — условия WHERE и JOIN могут неожиданно исключать строки из-за UNKNOWN. Агрегатные функции (COUNT, SUM, AVG) игнорируют NULL, что может искажать результаты. UNIQUE-ограничение в PostgreSQL допускает несколько NULL (они считаются различными), что отличается от поведения других СУБД. Всё это требует явной обработки через IS NULL, COALESCE и NULLIF.

### Реляционная алгебра

26. **Что такое реляционная алгебра?**
    Реляционная алгебра — формальная система операций над отношениями, предложенная Коддом. Каждая операция принимает одно или несколько отношений и возвращает новое отношение. Она является теоретическим фундаментом SQL и определяет минимальный набор операций для работы с данными: выборка, проекция, объединение, разность, декартово произведение и переименование.

27. **Что такое selection?**
    Selection (выборка, сигма) — унарная операция реляционной алгебры, которая выбирает из отношения кортежи, удовлетворяющие заданному предикату. В SQL аналогом является конструкция WHERE. Selection не изменяет схему отношения — результат содержит те же атрибуты, но подмножество строк.

28. **Что такое projection?**
    Projection (проекция, пи) — унарная операция, выбирающая из отношения подмножество атрибутов (столбцов). В SQL аналогом является перечисление столбцов в SELECT. Проекция удаляет дубликаты из результата (в теории), так как результат должен быть отношением — множеством уникальных кортежей.

29. **Что такое Cartesian product?**
    Cartesian product (декартово произведение) — бинарная операция, объединяющая каждый кортеж одного отношения с каждым кортежем другого. Если первое отношение содержит N строк, а второе M строк, результат содержит N * M строк. В SQL реализуется через CROSS JOIN или перечисление таблиц без условия соединения.

30. **Что такое join с точки зрения реляционной алгебры?**
    Join — операция, комбинирующая кортежи из двух отношений на основе условия (предиката). Она эквивалентна последовательности декартова произведения и selection. Natural join автоматически соединяет по одноимённым атрибутам и устраняет дубликаты столбцов. В SQL реализуется через конструкции JOIN ... ON.

31. **Чем inner join отличается от outer join концептуально?**
    Inner join возвращает только кортежи, для которых выполняется условие соединения в обоих отношениях. Outer join дополнительно сохраняет кортежи из одного или обоих отношений, не нашедшие пары, заполняя отсутствующие атрибуты значениями NULL. LEFT OUTER JOIN сохраняет все строки левого отношения, RIGHT — правого, FULL — обоих.

32. **Почему join является производной операцией?**
    Join можно выразить через базовые операции реляционной алгебры: декартово произведение (Cartesian product) с последующей selection по условию соединения. Он не входит в минимальный набор пяти фундаментальных операций (selection, projection, union, difference, Cartesian product), но используется как удобная и часто применяемая комбинация.

33. **Можно ли выразить все запросы через реляционную алгебру?**
    Реляционная алгебра является реляционно полной — через неё можно выразить любой запрос, который можно сформулировать в реляционном исчислении. Однако она не является Тьюринг-полной: рекурсивные запросы, вычисления с циклами и агрегация не выражаются чистой реляционной алгеброй. Для этого SQL включает расширения: GROUP BY, рекурсивные CTE, оконные функции.

### Нормальные формы

34. **Зачем нужны нормальные формы?**
    Нормальные формы устраняют избыточность данных и предотвращают аномалии вставки, обновления и удаления. Без нормализации одни и те же данные дублируются в разных строках, что приводит к несогласованности при изменении. Нормализация структурирует данные так, чтобы каждый факт хранился ровно в одном месте.

35. **Что нарушается при несоблюдении 1NF?**
    При нарушении 1NF в ячейках таблицы содержатся неатомарные значения — списки, множества или вложенные структуры. Это делает невозможным корректную фильтрацию, сортировку и соединение по отдельным элементам. Также нарушается фундаментальное свойство реляционной модели, где каждое пересечение строки и столбца содержит ровно одно значение из домена.

36. **Что такое функциональная зависимость?**
    Функциональная зависимость A -> B означает, что значение набора атрибутов A однозначно определяет значение набора атрибутов B. Например, номер паспорта функционально определяет ФИО владельца. Функциональные зависимости — основа для определения нормальных форм и выявления избыточности в схеме данных.

37. **Что такое 2NF?**
    Таблица находится в 2NF, если она удовлетворяет 1NF и каждый неключевой атрибут полностью зависит от всего candidate key, а не от его части. 2NF актуальна для таблиц с составным ключом: если атрибут зависит только от части ключа, его нужно вынести в отдельную таблицу. Для таблиц с простым (одноатрибутным) ключом 2NF выполняется автоматически.

38. **Что такое 3NF?**
    Таблица находится в 3NF, если она удовлетворяет 2NF и ни один неключевой атрибут не зависит транзитивно от candidate key. Транзитивная зависимость: A -> B -> C, где A — ключ, B — неключевой атрибут, C — зависит от B. Решение — вынести B и C в отдельную таблицу с ключом B.

39. **В чём отличие 3NF от BCNF?**
    В 3NF допускается, чтобы детерминант функциональной зависимости не был кандидатным ключом, если зависимый атрибут входит в какой-либо candidate key. BCNF (форма Бойса-Кодда) строже: каждый детерминант любой нетривиальной функциональной зависимости обязан быть суперключом. BCNF устраняет аномалии, которые 3NF может оставить в таблицах с перекрывающимися составными кандидатными ключами.

40. **Какие проблемы решает нормализация?**
    Нормализация устраняет три типа аномалий: аномалию вставки (невозможно добавить данные без избыточной информации), аномалию обновления (изменение одного факта требует обновления множества строк), аномалию удаления (удаление строки теряет сопутствующие данные). Она также уменьшает объём хранимых данных за счёт устранения дублирования.

41. **Когда денормализация оправдана?**
    Денормализация оправдана, когда производительность чтения критичнее стоимости записи и места хранения. Типичные случаи: аналитические запросы с тяжёлыми JOIN, кэширование агрегированных данных, материализованные представления. Денормализация должна быть осознанным решением с чётким пониманием, какие аномалии она вносит и как они будут контролироваться на уровне приложения.

### PostgreSQL и реляционная теория

42. **Является ли PostgreSQL строго реляционной СУБД?**
    PostgreSQL — объектно-реляционная СУБД. Она реализует основные принципы реляционной модели (таблицы, ключи, ссылочная целостность, SQL), но расширяет их объектными возможностями: наследование таблиц, пользовательские типы данных, массивы и JSONB. Строго реляционная СУБД не допускала бы таких расширений.

43. **В чём PostgreSQL отходит от классической реляционной модели?**
    PostgreSQL допускает дубликаты строк (без PRIMARY KEY), поддерживает неатомарные типы данных (массивы, JSONB, hstore), позволяет наследование таблиц и имеет систему пользовательских типов. Также порядок строк без ORDER BY не гарантирован, но физически зависит от реализации хранения, что отличается от чисто математического отношения.

44. **Почему PostgreSQL допускает дубликаты строк физически?**
    Потому что PostgreSQL хранит строки в heap-таблицах без встроенного механизма дедупликации. Уникальность обеспечивается только через явные ограничения (PRIMARY KEY, UNIQUE). Каждая строка имеет скрытый системный идентификатор ctid (физическую позицию), что позволяет различать даже полностью идентичные строки на уровне хранения.

45. **Как NULL в PostgreSQL соотносится с реляционной теорией?**
    PostgreSQL реализует трёхзначную логику SQL-стандарта: сравнение с NULL даёт UNKNOWN, IS NULL/IS NOT NULL используется для проверки. В контексте UNIQUE-ограничений PostgreSQL считает значения NULL различными, допуская несколько NULL в уникальном столбце. Это соответствует стандарту SQL, но расходится с некоторыми трактовками реляционной теории, где NULL вообще нежелателен.

46. **Является ли JSONB нарушением реляционной модели?**
    Формально JSONB нарушает требование атомарности значений (1NF), так как одна ячейка содержит сложную вложенную структуру. Однако PostgreSQL позволяет индексировать и запрашивать содержимое JSONB через операторы (->>, @>) и GIN-индексы. На практике JSONB полезен для полуструктурированных данных, которые сложно нормализовать, и является осознанным компромиссом между строгостью модели и гибкостью.

### Транзакции и ACID

47. **Что такое транзакция?**
    Транзакция — логическая единица работы с базой данных, объединяющая одну или несколько операций в неделимое целое. Она начинается с BEGIN и завершается COMMIT (подтверждение) или ROLLBACK (откат). Все операции внутри транзакции либо выполняются полностью, либо полностью отменяются, обеспечивая согласованное состояние данных.

48. **Что означает атомарность транзакции?**
    Атомарность (Atomicity) гарантирует, что транзакция выполняется как единая неделимая операция: либо все изменения фиксируются, либо ни одно. При сбое на любом этапе все уже выполненные изменения откатываются. В PostgreSQL атомарность реализуется через WAL (Write-Ahead Log) и механизм MVCC.

49. **Что означает согласованность (consistency) в ACID?**
    Согласованность гарантирует, что транзакция переводит базу данных из одного корректного состояния в другое, не нарушая заданных инвариантов. К инвариантам относятся ограничения целостности (CHECK, FOREIGN KEY, UNIQUE, NOT NULL), триггеры и бизнес-правила. Если транзакция нарушает хотя бы одно ограничение, она откатывается целиком.

50. **Что означает изоляция?**
    Изоляция (Isolation) определяет степень видимости изменений одной транзакции для других параллельно выполняющихся транзакций. Она предотвращает аномалии конкурентного доступа (dirty read, non-repeatable read, phantom read). Уровень изоляции задаёт компромисс между корректностью и производительностью: чем строже изоляция, тем меньше параллелизм.

51. **Что означает долговечность (durability)?**
    Долговечность гарантирует, что после успешного COMMIT данные сохраняются даже при сбое питания, краше процесса или аппаратной ошибке. В PostgreSQL это обеспечивается через WAL: изменения сначала записываются в журнал на диск, а затем применяются к файлам данных. Параметр synchronous_commit контролирует момент подтверждения записи WAL.

52. **Как ACID связан с инвариантами данных?**
    ACID обеспечивает сохранение инвариантов данных при конкурентном доступе и сбоях. Атомарность не допускает частичного выполнения, нарушающего инварианты. Согласованность проверяет инварианты при завершении транзакции. Изоляция предотвращает чтение промежуточных состояний, а долговечность гарантирует, что подтверждённые инварианты не будут утеряны.

### MVCC и изоляция

53. **Что такое MVCC?**
    MVCC (Multi-Version Concurrency Control) — механизм управления конкурентным доступом, при котором каждая транзакция работает со своим снимком (snapshot) данных. Вместо блокировки строк при чтении СУБД хранит несколько версий каждой строки. Каждая версия помечена идентификаторами транзакций создания (xmin) и удаления (xmax), что позволяет определить видимость строки для конкретной транзакции.

54. **Зачем PostgreSQL использует MVCC?**
    MVCC позволяет читателям не блокировать писателей и наоборот, что значительно повышает параллелизм. Без MVCC каждая операция чтения требовала бы блокировки строк, что снижало бы пропускную способность. MVCC обеспечивает согласованные снимки данных без использования разделяемых блокировок на чтение.

55. **Как MVCC влияет на чтение данных?**
    При MVCC каждая транзакция видит согласованный снимок данных на определённый момент времени. Читающая транзакция не видит незафиксированных изменений других транзакций и не блокируется записями. Это обеспечивает неблокирующее чтение, но требует механизма очистки устаревших версий строк (VACUUM).

56. **Почему в PostgreSQL чтение не блокирует запись?**
    Потому что читающая транзакция обращается к видимой для неё версии строки (на основе xmin/xmax), а пишущая создаёт новую версию. Они работают с разными физическими копиями данных и не конкурируют за одни и те же ресурсы. Блокировки возникают только при конкурентной записи в одну и ту же строку.

57. **Какие аномалии возможны при конкурентном доступе?**
    Основные аномалии: dirty read (чтение незафиксированных данных), non-repeatable read (повторное чтение возвращает другие данные), phantom read (появление новых строк при повторном запросе), serialization anomaly (результат отличается от любого последовательного выполнения). PostgreSQL исключает dirty read на всех уровнях изоляции. Уровень Read Committed допускает non-repeatable read и phantom read.

58. **Чем Read Committed отличается от Repeatable Read концептуально?**
    Read Committed берёт новый снимок данных перед каждым оператором внутри транзакции — каждый SELECT видит последние зафиксированные данные. Repeatable Read фиксирует снимок в начале транзакции (при первом операторе) и использует его до конца. Поэтому в Repeatable Read повторный SELECT всегда возвращает одинаковые данные, а в Read Committed — может вернуть новые зафиксированные изменения.

59. **Почему Serializable в PostgreSQL считается полноценным?**
    PostgreSQL реализует Serializable через SSI (Serializable Snapshot Isolation) — механизм, обнаруживающий конфликты сериализации на основе отслеживания зависимостей между транзакциями. В отличие от простой блокировочной модели, SSI не блокирует чтение и обеспечивает высокий параллелизм. При обнаружении конфликта транзакция откатывается с ошибкой serialization_failure, гарантируя, что итоговый результат эквивалентен последовательному выполнению.

### Хранение и физическая модель

60. **Как логическое отношение представлено физически в PostgreSQL?**
    Логическое отношение хранится как heap-таблица — неупорядоченная коллекция страниц размером 8 КБ каждая. Каждая страница содержит заголовок, массив указателей на строки (item pointers) и сами кортежи. Таблице соответствуют один или несколько файлов на диске в каталоге данных, а также отдельные файлы для TOAST (больших значений), карт видимости и карт свободного пространства.

61. **Что такое кортеж на уровне хранения?**
    На уровне хранения кортеж (tuple) — это структура из заголовка (HeapTupleHeader) и данных. Заголовок содержит xmin, xmax (идентификаторы транзакций создания и удаления), ctid (физическую позицию), информацию о NULL-маске и флаги состояния. Данные записываются последовательно в соответствии с порядком столбцов, с учётом выравнивания.

62. **Почему UPDATE не является обновлением строки физически?**
    В PostgreSQL UPDATE не изменяет существующую строку in-place. Вместо этого он помечает старую версию строки как удалённую (устанавливает xmax) и создаёт новую версию с обновлёнными данными в свободном пространстве страницы. Это следствие MVCC: старая версия может быть нужна другим транзакциям, работающим со своим снимком данных.

63. **Что такое версионность строк?**
    Версионность строк — следствие MVCC, при котором одна логическая строка может иметь несколько физических версий (tuples) одновременно. Каждая версия содержит метаданные (xmin, xmax), определяющие, для каких транзакций она видима. Актуальной является версия, у которой xmin зафиксирована и xmax не установлен (или не зафиксирован).

64. **Зачем нужен VACUUM?**
    VACUUM удаляет «мёртвые» версии строк (dead tuples) — строки, которые более не видимы ни одной активной транзакции. Без VACUUM таблицы бесконтрольно разрастаются (table bloat), индексы содержат ссылки на неактуальные строки, и производительность деградирует. VACUUM также обновляет карту видимости и статистику для планировщика. Autovacuum выполняет эту работу автоматически по настроенным порогам.

65. **Почему MVCC приводит к «мёртвым» версиям строк?**
    При каждом UPDATE или DELETE PostgreSQL не удаляет физическую строку, а помечает её как неактуальную (устанавливает xmax). Старая версия остаётся доступной для транзакций, которые были запущены до изменения. После того как все такие транзакции завершатся, старая версия становится «мёртвой» — она занимает место, но больше никем не используется.

### Индексы (концептуально)

66. **Зачем нужны индексы с точки зрения модели данных?**
    Индексы — механизм физической оптимизации, ускоряющий поиск строк по значениям атрибутов без полного сканирования таблицы. Они реализуют эффективный доступ к данным, не изменяя логическую модель: результаты запросов с индексом и без него идентичны. Индексы критичны для JOIN, WHERE и ORDER BY на больших объёмах данных.

67. **Почему индекс — это не часть реляционной модели?**
    Реляционная модель описывает логическую структуру данных и операции над ними, абстрагируясь от способа хранения и доступа. Индексы относятся к физическому уровню — это структуры хранения, созданные для ускорения операций. Можно удалить все индексы, и данные останутся корректными, а запросы будут возвращать те же результаты, только медленнее.

68. **Какие логические свойства должен сохранять индекс?**
    Индекс должен быть согласован с данными таблицы: при любом INSERT, UPDATE или DELETE индекс обновляется синхронно. Он должен корректно обрабатывать NULL (в B-tree NULL хранится в индексе и участвует в поиске). Уникальный индекс должен обеспечивать уникальность значений на уровне транзакционной изоляции.

69. **Почему наличие индекса не гарантирует его использование?**
    Планировщик PostgreSQL выбирает план выполнения на основе оценки стоимости (cost). Если таблица мала, sequential scan может быть дешевле, чем обращение к индексу. Низкая селективность условия (большая доля строк удовлетворяет предикату), устаревшая статистика или несовместимый тип операции также приводят к игнорированию индекса.

70. **Что такое селективность?**
    Селективность — доля строк таблицы, удовлетворяющих условию предиката, выраженная числом от 0 до 1. Высокая селективность (близко к 0) означает, что условие отбирает мало строк — индекс эффективен. Низкая селективность (близко к 1) означает, что условие отбирает большинство строк — sequential scan может быть дешевле. Планировщик оценивает селективность на основе статистики (pg_statistic).

### Планирование и выполнение

71. **Что такое план выполнения запроса?**
    План выполнения — дерево операций, которое PostgreSQL строит для обработки SQL-запроса. Каждый узел дерева представляет операцию (Seq Scan, Index Scan, Hash Join, Sort и др.). План можно посмотреть через EXPLAIN и EXPLAIN ANALYZE — первый показывает оценочную стоимость, второй выполняет запрос и показывает реальное время и количество строк.

72. **Что значит cost-based optimization?**
    Cost-based optimization — подход, при котором планировщик генерирует несколько возможных планов выполнения и выбирает тот, у которого наименьшая оценочная стоимость (cost). Стоимость рассчитывается на основе статистики таблиц (количество строк, распределение значений, размер страниц) и конфигурационных параметров (random_page_cost, cpu_tuple_cost и др.). Это отличает его от rule-based подхода, где правила фиксированы.

73. **Почему оптимальный с точки зрения модели план может быть плохим физически?**
    Логически эквивалентные планы могут кардинально различаться по физической стоимости из-за объёма данных, расположения на диске, наличия индексов и объёма оперативной памяти. Например, nested loop join оптимален для малых таблиц, но катастрофически медлен для больших, где hash join будет эффективнее. Модель данных не учитывает эти физические аспекты.

74. **Как статистика влияет на выбор плана?**
    Планировщик использует статистику из pg_statistic (собираемую ANALYZE) для оценки количества строк, селективности предикатов и распределения значений. Устаревшая статистика приводит к неверным оценкам кардинальности, из-за чего планировщик выбирает неоптимальный план — например, sequential scan вместо index scan или nested loop вместо hash join. Autovacuum регулярно запускает ANALYZE для обновления статистики.

75. **Почему один и тот же запрос может выполняться по-разному?**
    План зависит от текущей статистики, объёма данных, значений параметров и конфигурации сервера. После массовой вставки данных или изменения seq_page_cost планировщик может выбрать другую стратегию. Параметризованные запросы (prepared statements) могут использовать generic plan или custom plan в зависимости от значений параметров. Также обновление статистики через ANALYZE может изменить выбор плана.

### Репликация и согласованность

76. **Что такое WAL?**
    WAL (Write-Ahead Log) — журнал предварительной записи, в который PostgreSQL записывает все изменения данных перед их применением к файлам таблиц. Это обеспечивает durability: при сбое система восстанавливает согласованное состояние, воспроизводя записи из WAL. WAL также используется для репликации — реплика получает и применяет WAL-записи мастера.

77. **Зачем PostgreSQL ведёт журнал изменений?**
    Журнал (WAL) обеспечивает три ключевые возможности: crash recovery (восстановление после сбоя без потери зафиксированных данных), point-in-time recovery (восстановление на произвольный момент времени) и репликацию (передача изменений на реплики). Без WAL пришлось бы синхронно записывать каждое изменение в файлы данных, что было бы крайне медленно из-за случайного ввода-вывода.

78. **В чём разница между физической и логической репликацией?**
    Физическая репликация передаёт WAL-записи побайтово — реплика является точной копией мастера на уровне блоков данных. Логическая репликация передаёт изменения на уровне строк (INSERT, UPDATE, DELETE) в декодированном виде. Физическая реплика доступна только для чтения и не может иметь собственных таблиц. Логическая репликация позволяет реплицировать отдельные таблицы, преобразовывать данные и иметь на реплике собственные объекты.

79. **Что означает согласованность данных между репликами?**
    Согласованность между репликами определяет, насколько данные на реплике соответствуют данным мастера в данный момент. Синхронная репликация гарантирует, что транзакция на мастере подтверждается только после записи WAL на реплику — данные всегда согласованы. Асинхронная репликация допускает задержку (replication lag), при которой реплика может отставать от мастера.

80. **Какие компромиссы между согласованностью и доступностью есть в PostgreSQL?**
    Синхронная репликация обеспечивает строгую согласованность, но снижает доступность: при недоступности реплики мастер приостанавливает подтверждение транзакций. Асинхронная репликация сохраняет доступность мастера, но допускает потерю данных при failover. PostgreSQL предлагает компромисс через synchronous_commit: можно выбирать между remote_apply (строгая согласованность), on (запись WAL на реплику) и local (только локальный WAL).

### Расширяемость и модель

81. **Что значит, что PostgreSQL — extensible database?**
    PostgreSQL спроектирован для расширения: можно создавать пользовательские типы данных, операторы, функции, агрегаты, методы доступа к индексам и даже языки программирования для серверных функций. Расширения (extensions) устанавливаются через CREATE EXTENSION и становятся полноценной частью СУБД. Примеры: PostGIS (геоданные), pg_trgm (нечёткий поиск), hstore (key-value), pgcrypto (шифрование).

82. **Чем пользовательские типы отличаются от встроенных логически?**
    С логической точки зрения пользовательские типы эквивалентны встроенным: они определяют домен допустимых значений, поддерживают операторы и индексирование. Различие — в реализации: встроенные типы оптимизированы на уровне исходного кода PostgreSQL, а пользовательские типы определяются через SQL/C-функции. Планировщик может хуже оценивать стоимость операций с пользовательскими типами из-за ограниченной статистики.

83. **Как расширения влияют на реляционную модель?**
    Расширения не изменяют фундаментальную реляционную модель — таблицы, ключи и ссылочная целостность работают одинаково. Но расширения добавляют новые типы данных и операции, которые могут выходить за рамки классической реляционной теории. Например, PostGIS добавляет пространственные типы и индексы, а pg_trgm — операторы нечёткого сравнения строк, недоступные в стандартной реляционной алгебре.

84. **Где проходит граница между моделью данных и реализацией?**
    Модель данных определяет, что хранится (сущности, атрибуты, связи) и какие операции возможны (реляционная алгебра, SQL). Реализация определяет, как это хранится и выполняется (страницы, B-tree, MVCC, WAL). Граница проходит на уровне SQL: запрос описывает, какой результат нужен (модель), а планировщик и исполнитель определяют, как его получить (реализация).

### Контрольные вопросы на понимание

85. **Можно ли построить корректную систему без строгих инвариантов данных?**
    Технически можно, но такая система будет ненадёжной. Без инвариантов (ограничений целостности, ключей, типизации) ответственность за корректность данных перекладывается на код приложения, который сложнее верифицировать и легче нарушить. Со временем данные деградируют: появляются дубликаты, «висячие» ссылки и противоречия, стоимость исправления которых растёт экспоненциально.

86. **Почему данные важнее кода?**
    Код можно переписать, а повреждённые или утраченные данные — нет. Данные представляют накопленные факты бизнеса и часто невосстановимы. Кроме того, данные обычно переживают несколько версий приложения и даже смену технологий. Поэтому инвестиции в корректную модель данных, ограничения целостности и резервное копирование приоритетнее архитектурных изысканий в коде.

87. **Можно ли полностью реализовать реляционную модель поверх key-value хранилища?**
    Да, реляционную модель можно реализовать поверх любого хранилища, способного сохранять и извлекать данные — включая key-value. Потребуется реализовать сериализацию кортежей, индексирование, обработку SQL, планировщик запросов и управление транзакциями. Фактически так работают некоторые NewSQL-системы (CockroachDB, TiDB), использующие key-value хранилище (RocksDB) как нижний уровень.

88. **Почему ошибки в модели данных самые дорогие?**
    Модель данных — фундамент, на котором строятся запросы, бизнес-логика и API. Исправление модели на поздних этапах требует миграции данных, переписывания запросов и изменения интерфейсов, что затрагивает всю систему. В отличие от бага в коде, который локален, ошибка в модели (неверная нормализация, пропущенное ограничение, неправильные связи) имеет каскадный эффект на все зависимые компоненты.

89. **Что важнее: производительность или корректность модели?**
    Корректность модели важнее, потому что некорректные данные обесценивают любую производительность. Быстрый запрос, возвращающий неверный результат, бесполезен. Сначала обеспечивается корректность через нормализацию, ключи и ограничения, а затем, при необходимости, оптимизируется производительность через индексы, денормализацию и кэширование. Преждевременная оптимизация в ущерб модели создаёт технический долг.

90. **В чём основная ценность реляционной модели сегодня?**
    Реляционная модель предоставляет формальный и проверенный временем способ описания данных и операций над ними. Она обеспечивает декларативный доступ через SQL (описываем что, а не как), строгие гарантии целостности через ключи и ограничения, и математическую основу для оптимизации запросов. Несмотря на появление NoSQL-решений, реляционная модель остаётся стандартом для систем, где критичны согласованность, сложные запросы и долгосрочная надёжность данных.
