## Что такое нормализация

**Нормализация** -- это процесс организации данных в реляционной базе данных, направленный на уменьшение избыточности и обеспечение целостности данных. Нормализация выполняется путём декомпозиции таблиц (отношений) в соответствии с набором правил, называемых **нормальными формами**.

### Цели нормализации

1. **Устранение избыточности данных** -- одна и та же информация не должна храниться в нескольких местах.
2. **Предотвращение аномалий вставки (INSERT anomaly)** -- невозможность добавить данные без наличия других, логически не связанных данных.
3. **Предотвращение аномалий обновления (UPDATE anomaly)** -- при обновлении данных в одном месте они могут остаться неизменными в другом, что приведёт к противоречию.
4. **Предотвращение аномалий удаления (DELETE anomaly)** -- удаление строки может привести к непреднамеренной потере других данных.

### Пример аномалий

Рассмотрим ненормализованную таблицу:

```sql
CREATE TABLE orders_denorm (
    order_id     INT,
    product_name VARCHAR(100),
    customer_name VARCHAR(100),
    customer_email VARCHAR(100),
    customer_city  VARCHAR(100)
);

INSERT INTO orders_denorm VALUES
(1, 'Ноутбук',   'Иванов', 'ivanov@mail.ru', 'Москва'),
(2, 'Телефон',   'Иванов', 'ivanov@mail.ru', 'Москва'),
(3, 'Планшет',   'Петров', 'petrov@mail.ru', 'Санкт-Петербург');
```

**Аномалия обновления**: если Иванов сменил email, нужно обновить все строки с его заказами. Если обновить только одну -- данные станут противоречивыми.

**Аномалия вставки**: нельзя добавить нового клиента без создания заказа.

**Аномалия удаления**: если удалить единственный заказ Петрова, мы потеряем и данные о самом клиенте.

## Функциональная зависимость

**Функциональная зависимость (FD)** -- это ограничение, при котором значение одного набора атрибутов однозначно определяет значение другого набора атрибутов.

Запись: `A -> B` означает «A функционально определяет B», то есть для каждого значения A существует ровно одно значение B.

Примеры:
- `order_id -> order_date` -- номер заказа однозначно определяет дату заказа.
- `customer_id -> customer_name, customer_email` -- идентификатор клиента определяет его имя и email.
- `{student_id, course_id} -> grade` -- комбинация студент + курс определяет оценку.

### Виды функциональных зависимостей

| Вид | Описание |
|-----|----------|
| **Полная FD** | B зависит от всего составного ключа A, но не от его подмножества |
| **Частичная FD** | B зависит только от части составного ключа |
| **Транзитивная FD** | A -> B и B -> C, следовательно A -> C (через промежуточный атрибут) |
| **Многозначная FD** | A ->> B -- для каждого значения A существует набор значений B, не зависящий от других атрибутов |

## Нормальные формы

Каждая следующая нормальная форма является более строгой, чем предыдущая. Таблица в N-й нормальной форме автоматически находится во всех предыдущих формах.

```
UNF -> 1NF -> 2NF -> 3NF -> BCNF -> 4NF -> 5NF
```

---

### Первая нормальная форма (1NF)

Таблица находится в **1NF**, если:
1. Все значения атрибутов **атомарны** (неделимы) -- в каждой ячейке хранится одно значение, а не список или вложенная структура.
2. Нет **повторяющихся групп** столбцов (например, `phone1`, `phone2`, `phone3`).
3. Каждая строка **уникально идентифицируема** (существует первичный ключ).

#### Пример нарушения 1NF

```sql
-- Нарушение: столбец phones содержит несколько значений (не атомарен)
CREATE TABLE customers_bad (
    customer_id   INT PRIMARY KEY,
    name          VARCHAR(100),
    phones        VARCHAR(200)   -- '8-900-111-22-33, 8-900-444-55-66'
);

INSERT INTO customers_bad VALUES
(1, 'Иванов', '8-900-111-22-33, 8-900-444-55-66'),
(2, 'Петров', '8-900-777-88-99');
```

Проблемы:
- Нельзя эффективно искать по конкретному номеру телефона.
- Сложно добавлять или удалять отдельный номер.
- Нет стандартного способа гарантировать уникальность номеров.

#### Приведение к 1NF

```sql
-- Вариант 1: вынести телефоны в отдельную таблицу
CREATE TABLE customers (
    customer_id   INT PRIMARY KEY,
    name          VARCHAR(100)
);

CREATE TABLE customer_phones (
    phone_id      SERIAL PRIMARY KEY,
    customer_id   INT NOT NULL REFERENCES customers(customer_id),
    phone         VARCHAR(20) NOT NULL
);

INSERT INTO customers VALUES (1, 'Иванов'), (2, 'Петров');

INSERT INTO customer_phones (customer_id, phone) VALUES
(1, '8-900-111-22-33'),
(1, '8-900-444-55-66'),
(2, '8-900-777-88-99');
```

Теперь каждое значение атомарно, каждая строка уникальна, повторяющихся групп нет.

#### Ещё один пример нарушения -- повторяющиеся группы столбцов

```sql
-- Нарушение: повторяющиеся группы (subject1, grade1, subject2, grade2...)
CREATE TABLE student_grades_bad (
    student_id  INT PRIMARY KEY,
    subject1    VARCHAR(50),
    grade1      INT,
    subject2    VARCHAR(50),
    grade2      INT,
    subject3    VARCHAR(50),
    grade3      INT
);
```

#### Исправление

```sql
CREATE TABLE students (
    student_id  INT PRIMARY KEY,
    name        VARCHAR(100)
);

CREATE TABLE grades (
    grade_id    SERIAL PRIMARY KEY,
    student_id  INT NOT NULL REFERENCES students(student_id),
    subject     VARCHAR(50) NOT NULL,
    grade       INT NOT NULL
);
```

### Вторая нормальная форма (2NF)

Таблица находится в **2NF**, если:
1. Она находится в **1NF**.
2. Каждый неключевой атрибут **полностью функционально зависит** от всего первичного ключа (нет частичных зависимостей).

Проблема частичной зависимости возникает, когда первичный ключ **составной**, и некоторый атрибут зависит только от части этого ключа.

> Если первичный ключ простой (один столбец), таблица в 1NF автоматически находится в 2NF.

#### Пример нарушения 2NF

```sql
-- Первичный ключ: (student_id, course_id)
-- course_name зависит только от course_id -- частичная зависимость
CREATE TABLE enrollments_bad (
    student_id   INT,
    course_id    INT,
    course_name  VARCHAR(100),  -- зависит только от course_id
    grade        INT,           -- зависит от (student_id, course_id)
    PRIMARY KEY (student_id, course_id)
);

INSERT INTO enrollments_bad VALUES
(1, 101, 'Математика', 5),
(2, 101, 'Математика', 4),
(1, 102, 'Физика',     3),
(3, 101, 'Математика', 5);
```

Зависимости:
- `{student_id, course_id} -> grade` -- полная зависимость (OK)
- `course_id -> course_name` -- частичная зависимость (нарушение 2NF)

Проблема: `course_name` дублируется для каждого студента на одном курсе.

#### Приведение к 2NF

Выносим частично зависимые атрибуты в отдельную таблицу:

```sql
CREATE TABLE courses (
    course_id    INT PRIMARY KEY,
    course_name  VARCHAR(100) NOT NULL
);

CREATE TABLE enrollments (
    student_id   INT,
    course_id    INT REFERENCES courses(course_id),
    grade        INT,
    PRIMARY KEY (student_id, course_id)
);

INSERT INTO courses VALUES
(101, 'Математика'),
(102, 'Физика');

INSERT INTO enrollments VALUES
(1, 101, 5),
(2, 101, 4),
(1, 102, 3),
(3, 101, 5);
```

Теперь `course_name` хранится в одном месте, и нет частичных зависимостей.

### Третья нормальная форма (3NF)

Таблица находится в **3NF**, если:
1. Она находится в **2NF**.
2. Нет **транзитивных зависимостей** -- неключевой атрибут не зависит от другого неключевого атрибута.

Формально: для каждой нетривиальной функциональной зависимости `X -> A`, где A -- неключевой атрибут, X должен быть суперключом.

#### Пример нарушения 3NF

```sql
-- PK: employee_id
-- department_id -> department_name (транзитивная зависимость)
-- employee_id -> department_id -> department_name
CREATE TABLE employees_bad (
    employee_id      INT PRIMARY KEY,
    employee_name    VARCHAR(100),
    department_id    INT,
    department_name  VARCHAR(100)  -- зависит от department_id, а не от employee_id напрямую
);

INSERT INTO employees_bad VALUES
(1, 'Иванов',  10, 'Разработка'),
(2, 'Петров',  10, 'Разработка'),
(3, 'Сидоров', 20, 'Маркетинг'),
(4, 'Козлов',  10, 'Разработка');
```

Зависимости:
- `employee_id -> department_id` (прямая)
- `department_id -> department_name` (прямая)
- `employee_id -> department_name` (транзитивная, через `department_id`)

Проблема: `department_name` дублируется и может стать противоречивым при обновлении.

#### Приведение к 3NF

```sql
CREATE TABLE departments (
    department_id    INT PRIMARY KEY,
    department_name  VARCHAR(100) NOT NULL
);

CREATE TABLE employees (
    employee_id      INT PRIMARY KEY,
    employee_name    VARCHAR(100) NOT NULL,
    department_id    INT REFERENCES departments(department_id)
);

INSERT INTO departments VALUES
(10, 'Разработка'),
(20, 'Маркетинг');

INSERT INTO employees VALUES
(1, 'Иванов',  10),
(2, 'Петров',  10),
(3, 'Сидоров', 20),
(4, 'Козлов',  10);

-- Для получения полной информации используем JOIN:
SELECT e.employee_id, e.employee_name, d.department_name
FROM employees e
JOIN departments d ON e.department_id = d.department_id;
```

### Нормальная форма Бойса-Кодда (BCNF)

**BCNF** (Boyce-Codd Normal Form) -- усиленная версия 3NF. Таблица находится в BCNF, если:

Для каждой нетривиальной функциональной зависимости `X -> A`, **X является суперключом**.

#### Отличие от 3NF

В 3NF допускается ситуация, когда A является частью ключа-кандидата (так называемый «prime attribute»). BCNF запрещает любую зависимость, где детерминант не является суперключом -- даже если зависимый атрибут входит в ключ.

Таблица в BCNF всегда в 3NF, но не наоборот. Разница проявляется, когда в таблице несколько перекрывающихся ключей-кандидатов.

#### Когда BCNF строже 3NF

Рассмотрим таблицу расписания, где:
- Один преподаватель ведёт ровно один предмет.
- Один предмет могут вести несколько преподавателей.
- Студент на одном предмете закреплён за одним преподавателем.

```sql
CREATE TABLE schedule_bad (
    student_id   INT,
    subject      VARCHAR(50),
    teacher      VARCHAR(50),
    PRIMARY KEY (student_id, subject)
);

INSERT INTO schedule_bad VALUES
(1, 'Математика', 'Козлов'),
(2, 'Математика', 'Новиков'),
(1, 'Физика',     'Сидоров'),
(3, 'Математика', 'Козлов');
```

Ключи-кандидаты: `{student_id, subject}` и `{student_id, teacher}`.

Функциональная зависимость `teacher -> subject` (каждый преподаватель ведёт один предмет), но `teacher` **не является суперключом**. Таблица в 3NF (subject -- prime attribute), но **не в BCNF**.

#### Приведение к BCNF

```sql
-- Связь преподавателя с предметом
CREATE TABLE teacher_subject (
    teacher    VARCHAR(50) PRIMARY KEY,
    subject    VARCHAR(50) NOT NULL
);

-- Назначение студента преподавателю
CREATE TABLE student_teacher (
    student_id  INT,
    teacher     VARCHAR(50) REFERENCES teacher_subject(teacher),
    PRIMARY KEY (student_id, teacher)
);

INSERT INTO teacher_subject VALUES
('Козлов',  'Математика'),
('Новиков', 'Математика'),
('Сидоров', 'Физика');

INSERT INTO student_teacher VALUES
(1, 'Козлов'),
(2, 'Новиков'),
(1, 'Сидоров'),
(3, 'Козлов');
```

Теперь в каждой таблице все детерминанты являются суперключами.

### Четвёртая нормальная форма (4NF)

Таблица находится в **4NF**, если:
1. Она находится в **BCNF**.
2. Нет нетривиальных **многозначных зависимостей** (MVD), не являющихся следствием функциональных зависимостей.

**Многозначная зависимость** `A ->> B` означает: для каждого значения A набор связанных значений B **не зависит** от остальных атрибутов таблицы.

#### Пример нарушения 4NF

Преподаватель может вести несколько курсов и владеть несколькими языками программирования. Эти два факта **независимы**.

```sql
-- Нарушение 4NF: две независимые многозначные зависимости
-- teacher ->> course
-- teacher ->> language
CREATE TABLE teacher_skills_bad (
    teacher   VARCHAR(50),
    course    VARCHAR(50),
    language  VARCHAR(50),
    PRIMARY KEY (teacher, course, language)
);

INSERT INTO teacher_skills_bad VALUES
('Козлов', 'Алгоритмы',      'Python'),
('Козлов', 'Алгоритмы',      'Java'),
('Козлов', 'Базы данных',    'Python'),
('Козлов', 'Базы данных',    'Java');
```

Проблема: для каждой комбинации нужно хранить полное декартово произведение курсов и языков. При добавлении нового языка нужно добавить строку для каждого курса.

#### Приведение к 4NF

Разделяем независимые многозначные зависимости:

```sql
CREATE TABLE teacher_courses (
    teacher   VARCHAR(50),
    course    VARCHAR(50),
    PRIMARY KEY (teacher, course)
);

CREATE TABLE teacher_languages (
    teacher   VARCHAR(50),
    language  VARCHAR(50),
    PRIMARY KEY (teacher, language)
);

INSERT INTO teacher_courses VALUES
('Козлов', 'Алгоритмы'),
('Козлов', 'Базы данных');

INSERT INTO teacher_languages VALUES
('Козлов', 'Python'),
('Козлов', 'Java');
```

Теперь добавление нового языка -- одна строка, без дублирования по курсам.

### Пятая нормальная форма (5NF)

Таблица находится в **5NF** (она же **проекционно-соединительная нормальная форма**, PJNF), если:
1. Она находится в **4NF**.
2. Каждая **зависимость соединения** (join dependency) является следствием ключей-кандидатов.

**Зависимость соединения** существует, когда таблицу можно без потерь разложить на несколько проекций, а затем восстановить соединением.

#### Когда возникает проблема

5NF актуальна, когда три или более сущности связаны таким образом, что парные связи не полностью описывают тройственную связь.

```sql
-- Поставщик может поставлять товар, товар продаётся в магазине,
-- но конкретный поставщик поставляет конкретный товар
-- только в определённые магазины.
CREATE TABLE supply_bad (
    supplier  VARCHAR(50),
    product   VARCHAR(50),
    shop      VARCHAR(50),
    PRIMARY KEY (supplier, product, shop)
);

INSERT INTO supply_bad VALUES
('Поставщик_А', 'Молоко', 'Магазин_1'),
('Поставщик_А', 'Хлеб',  'Магазин_1'),
('Поставщик_А', 'Молоко', 'Магазин_2'),
('Поставщик_Б', 'Молоко', 'Магазин_1');
```

Если данные таковы, что тройственная связь **не сводится** к парным (то есть из того, что А поставляет молоко и А поставляет в Магазин_1, **не следует**, что А поставляет молоко в Магазин_1), то таблица уже в 5NF и дальнейшее разложение приведёт к потере данных.

Если же тройственная связь **сводится** к парным (то есть при любых данных соединение трёх проекций всегда восстанавливает исходную таблицу), то для 5NF нужно выполнить декомпозицию:

```sql
CREATE TABLE supplier_product (
    supplier  VARCHAR(50),
    product   VARCHAR(50),
    PRIMARY KEY (supplier, product)
);

CREATE TABLE supplier_shop (
    supplier  VARCHAR(50),
    shop      VARCHAR(50),
    PRIMARY KEY (supplier, shop)
);

CREATE TABLE product_shop (
    product   VARCHAR(50),
    shop      VARCHAR(50),
    PRIMARY KEY (product, shop)
);
```

На практике 5NF встречается крайне редко. В большинстве реальных проектов достаточно привести данные к 3NF или BCNF.

## Денормализация

**Денормализация** -- намеренное внесение избыточности в структуру базы данных для повышения производительности операций чтения.

### Зачем нужна

Нормализованная схема может требовать большого количества JOIN-ов при чтении, что замедляет запросы. Денормализация устраняет необходимость в некоторых соединениях за счёт дублирования данных.

### Типичные приёмы денормализации

#### 1. Дублирование данных из связанных таблиц

```sql
-- Нормализованная структура: нужен JOIN для получения имени клиента
SELECT o.order_id, c.name, o.total
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id;

-- Денормализованная: имя клиента хранится прямо в заказе
CREATE TABLE orders_denorm (
    order_id      SERIAL PRIMARY KEY,
    customer_id   INT REFERENCES customers(customer_id),
    customer_name VARCHAR(100),  -- дублированное поле
    total         NUMERIC(10, 2)
);
```

#### 2. Предвычисленные (агрегатные) поля

```sql
-- Вместо COUNT(*) при каждом запросе хранить количество заказов в таблице клиентов
ALTER TABLE customers ADD COLUMN order_count INT DEFAULT 0;

-- Обновлять при создании заказа (через триггер или в коде приложения)
CREATE OR REPLACE FUNCTION update_order_count()
RETURNS TRIGGER AS $$
BEGIN
    UPDATE customers
    SET order_count = order_count + 1
    WHERE customer_id = NEW.customer_id;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_update_order_count
    AFTER INSERT ON orders
    FOR EACH ROW
    EXECUTE FUNCTION update_order_count();
```

#### 3. Материализованные представления

```sql
-- Создание материализованного представления для тяжёлого аналитического запроса
CREATE MATERIALIZED VIEW mv_monthly_sales AS
SELECT
    date_trunc('month', order_date) AS month,
    product_id,
    SUM(quantity) AS total_quantity,
    SUM(quantity * price) AS total_revenue
FROM order_items oi
JOIN orders o ON oi.order_id = o.order_id
GROUP BY date_trunc('month', order_date), product_id;

-- Создание индекса на материализованном представлении
CREATE INDEX idx_mv_monthly_sales_month ON mv_monthly_sales(month);

-- Обновление данных (вручную или по расписанию)
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_monthly_sales;
```

#### 4. Хранение вычисляемых значений

```sql
-- Хранение полного адреса вместо JOIN с таблицами city, region, country
ALTER TABLE addresses ADD COLUMN full_address TEXT;

UPDATE addresses
SET full_address = street || ', ' || city || ', ' || region || ', ' || country;
```

### Когда денормализация оправдана

| Ситуация | Пояснение |
|----------|-----------|
| Преобладание чтения над записью | Если данные читаются в 10-100 раз чаще, чем записываются |
| Тяжёлые JOIN-ы | Когда регулярные запросы требуют соединения 5+ таблиц |
| Аналитические хранилища (OLAP) | Схемы «звезда» и «снежинка» изначально денормализованы |
| Кэширование агрегатов | Вместо пересчёта суммы на каждый запрос |
| Высоконагруженные системы | Когда экономия даже миллисекунд на запрос критична |

### Риски денормализации

- **Аномалии данных** -- дублированные данные могут рассинхронизироваться.
- **Сложность поддержки** -- нужны триггеры или логика в приложении для синхронизации.
- **Увеличение объёма хранения** -- дублирование занимает дополнительное место.

## Практические рекомендации

### Для OLTP-систем (транзакционная обработка)

OLTP-системы (интернет-магазины, CRM, банковские системы) характеризуются частыми операциями вставки, обновления и удаления. Рекомендуется **3NF или BCNF**:

```sql
-- Типичная нормализованная OLTP-схема
CREATE TABLE customers (
    customer_id SERIAL PRIMARY KEY,
    email       VARCHAR(255) UNIQUE NOT NULL,
    name        VARCHAR(100) NOT NULL
);

CREATE TABLE products (
    product_id  SERIAL PRIMARY KEY,
    name        VARCHAR(200) NOT NULL,
    price       NUMERIC(10, 2) NOT NULL
);

CREATE TABLE orders (
    order_id     SERIAL PRIMARY KEY,
    customer_id  INT NOT NULL REFERENCES customers(customer_id),
    order_date   TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE order_items (
    order_item_id  SERIAL PRIMARY KEY,
    order_id       INT NOT NULL REFERENCES orders(order_id),
    product_id     INT NOT NULL REFERENCES products(product_id),
    quantity       INT NOT NULL CHECK (quantity > 0),
    unit_price     NUMERIC(10, 2) NOT NULL  -- цена на момент заказа
);
```

### Для OLAP-систем (аналитическая обработка)

В аналитических хранилищах (Data Warehouse) преобладает чтение. Используется **денормализация** -- схемы «звезда» (Star Schema) и «снежинка» (Snowflake Schema):

```sql
-- Схема "звезда" для аналитического хранилища

-- Таблица фактов (центральная)
CREATE TABLE fact_sales (
    sale_id       BIGSERIAL PRIMARY KEY,
    date_key      INT NOT NULL,
    product_key   INT NOT NULL,
    customer_key  INT NOT NULL,
    store_key     INT NOT NULL,
    quantity      INT NOT NULL,
    amount        NUMERIC(12, 2) NOT NULL
);

-- Таблицы измерений (денормализованные)
CREATE TABLE dim_date (
    date_key      INT PRIMARY KEY,
    full_date     DATE NOT NULL,
    day_of_week   VARCHAR(10),
    month_name    VARCHAR(10),
    quarter       INT,
    year          INT
);

CREATE TABLE dim_product (
    product_key    INT PRIMARY KEY,
    product_name   VARCHAR(200),
    category_name  VARCHAR(100),    -- денормализовано (могло бы быть отдельной таблицей)
    brand_name     VARCHAR(100)     -- денормализовано
);

CREATE TABLE dim_customer (
    customer_key   INT PRIMARY KEY,
    customer_name  VARCHAR(100),
    city           VARCHAR(100),    -- денормализовано
    region         VARCHAR(100),    -- денормализовано
    country        VARCHAR(100)     -- денормализовано
);
```

### Баланс между нормализацией и производительностью

Общий подход:

1. **Начинайте с нормализации** -- проектируйте схему в 3NF/BCNF.
2. **Профилируйте запросы** -- определите узкие места с помощью `EXPLAIN ANALYZE`.
3. **Денормализуйте точечно** -- только те части, которые действительно тормозят.
4. **Используйте альтернативы** -- прежде чем денормализовать, рассмотрите:
   - Создание индексов
   - Материализованные представления
   - Кэширование на уровне приложения

```sql
-- Прежде чем денормализовать, проверьте план запроса:
EXPLAIN ANALYZE
SELECT o.order_id, c.name, SUM(oi.quantity * oi.unit_price) AS total
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
JOIN order_items oi ON o.order_id = oi.order_id
GROUP BY o.order_id, c.name;

-- Возможно, достаточно добавить индексы:
CREATE INDEX idx_orders_customer_id ON orders(customer_id);
CREATE INDEX idx_order_items_order_id ON order_items(order_id);
```

### Сводная таблица нормальных форм

| Нормальная форма | Требование | Устраняет |
|-----------------|------------|-----------|
| **1NF** | Атомарные значения, нет повторяющихся групп | Неатомарные данные |
| **2NF** | 1NF + нет частичных зависимостей | Частичные зависимости от составного ключа |
| **3NF** | 2NF + нет транзитивных зависимостей | Зависимости между неключевыми атрибутами |
| **BCNF** | Каждый детерминант -- суперключ | Зависимости, где детерминант -- не суперключ |
| **4NF** | BCNF + нет многозначных зависимостей | Независимые многозначные факты в одной таблице |
| **5NF** | 4NF + нет зависимостей соединения | Потери при декомпозиции тройственных связей |
