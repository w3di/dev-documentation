## Транзакции и блокировки

Транзакция -- это последовательность операций с базой данных, которые выполняются как единое целое. Транзакции позволяют множеству пользователей работать с одними и теми же данными безопасно.

---

## Что такое транзакция

Транзакции позволяют объединять несколько SQL-инструкций в одну группу, гарантируя, что:
- либо все инструкции выполнятся успешно
- либо ни одна из них не будет выполнена

Это обеспечивает целостность данных при одновременном доступе к базе данных.

Зачем нужны транзакции:
- Серверы баз данных не работают безотказно 100% времени
- Пользователи не всегда позволяют программам завершить выполнение
- Приложения могут завершаться с фатальными ошибками
- Несколько пользователей могут одновременно изменять одни и те же данные

---

## ACID свойства

Каждая транзакция в реляционной СУБД должна удовлетворять четырём свойствам ACID.

### Atomicity (Атомарность)

Транзакция выполняется как единая неделимая операция. Либо все операции внутри транзакции завершаются успешно, либо ни одна из них не применяется.

Если на середине транзакции произойдёт сбой, все уже выполненные операции будут отменены (откат), и база данных вернётся в состояние до начала транзакции.

```sql
BEGIN;
UPDATE accounts SET balance = balance - 1000 WHERE user_id = 1;
-- Сбой питания здесь -- оба UPDATE будут отменены
UPDATE accounts SET balance = balance + 1000 WHERE user_id = 2;
COMMIT;
```

### Consistency (Согласованность)

Транзакция переводит базу данных из одного согласованного состояния в другое. Все ограничения целостности (constraints), триггеры и правила должны быть соблюдены после завершения транзакции.

Если транзакция нарушает какое-либо ограничение, она целиком откатывается.

Примеры ограничений:
- `NOT NULL`, `UNIQUE`, `CHECK`, `FOREIGN KEY`
- Сумма денег в системе не должна меняться при переводе между счетами

### Isolation (Изолированность)

Параллельно выполняющиеся транзакции не должны влиять друг на друга. Каждая транзакция работает так, как будто она единственная в системе.

Степень изоляции настраивается уровнями изоляции (подробнее ниже). Более высокий уровень изоляции обеспечивает лучшую защиту, но снижает параллелизм.

### Durability (Долговечность)

После успешного выполнения `COMMIT` изменения гарантированно сохранены, даже если сразу после этого произойдёт сбой системы (отключение питания, крах ОС).

PostgreSQL реализует это через механизм WAL (Write-Ahead Log) -- все изменения сначала записываются в журнал, а затем применяются к данным.

## Команды управления транзакциями

### BEGIN / START TRANSACTION

Начинает новую транзакцию:

```sql
BEGIN;
-- или
START TRANSACTION;
```

### COMMIT

Подтверждает все изменения, сделанные в транзакции, и делает их постоянными. Освобождает все ресурсы (блокировки), использовавшиеся во время транзакции.

```sql
BEGIN;
UPDATE accounts SET balance = balance - 1000 WHERE user_id = 1;
UPDATE accounts SET balance = balance + 1000 WHERE user_id = 2;
COMMIT;
```

### ROLLBACK

Отменяет все изменения, сделанные в текущей транзакции. Возвращает данные в состояние до начала транзакции. Освобождает все ресурсы.

```sql
BEGIN;
DELETE FROM Users WHERE id = 1;
-- Передумали
ROLLBACK;
-- Удаление отменено, данные на месте
```

### SAVEPOINT

Точка сохранения позволяет откатиться к конкретной точке в транзакции, а не к её началу. Каждой точке сохранения присваивается уникальное имя.

Создание точки сохранения:

```sql
SAVEPOINT my_savepoint;
```

Откат к точке сохранения:

```sql
ROLLBACK TO SAVEPOINT my_savepoint;
```

### RELEASE SAVEPOINT

Удаляет точку сохранения, не откатывая к ней. После освобождения точка сохранения больше недоступна для отката.

```sql
RELEASE SAVEPOINT my_savepoint;
```

### Пример использования точек сохранения

```sql
BEGIN;

SAVEPOINT before_updating_user_1;
UPDATE accounts SET balance = balance + 100 WHERE user_id = 1;

-- Откат только этой операции
ROLLBACK TO SAVEPOINT before_updating_user_1;

UPDATE accounts SET balance = balance + 200 WHERE user_id = 2;

COMMIT;
```

В результате баланс первого пользователя останется без изменений (откат к точке сохранения), а баланс второго пользователя увеличится на 200.

Важные моменты:
- При создании точки сохранения ничего не сохраняется. Чтобы изменения стали постоянными, необходимо выполнить `COMMIT`
- При выполнении `ROLLBACK` без указания точки сохранения все установленные точки сохранения будут проигнорированы, и будет произведён откат всей транзакции

### Внешние факторы завершения транзакции

Помимо команд `COMMIT` и `ROLLBACK`, транзакция может завершиться в результате внешних факторов: если сервер выключается, транзакция будет автоматически отменена при перезапуске.

## Уровни изоляции

Уровень изоляции определяет, какие аномалии допустимы при параллельном выполнении транзакций. Чем выше уровень, тем строже изоляция, но ниже производительность.

Установка уровня изоляции:

```sql
-- Для текущей транзакции
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- ...
COMMIT;

-- Для всей сессии
SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

### Read Uncommitted (Чтение незафиксированных данных)

Самый низкий уровень изоляции. Транзакция может видеть незафиксированные изменения других транзакций.

В PostgreSQL этот уровень реализован как Read Committed -- PostgreSQL не допускает грязное чтение даже на этом уровне.

### Read Committed (Чтение зафиксированных данных)

Уровень по умолчанию в PostgreSQL. Транзакция видит только зафиксированные изменения других транзакций.

Каждый оператор `SELECT` в транзакции видит снимок данных на момент начала этого оператора (не транзакции).

```sql
-- Транзакция A
BEGIN;
SELECT balance FROM accounts WHERE user_id = 1; -- 1000

-- Транзакция B (параллельно)
BEGIN;
UPDATE accounts SET balance = 500 WHERE user_id = 1;
COMMIT;

-- Транзакция A (продолжение)
SELECT balance FROM accounts WHERE user_id = 1; -- 500 (видит зафиксированные изменения)
COMMIT;
```

Допускает: non-repeatable read, phantom read.

### Repeatable Read (Повторяемое чтение)

Транзакция видит снимок данных на момент начала транзакции. Повторное чтение тех же данных гарантированно вернёт те же результаты.

```sql
-- Транзакция A
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE user_id = 1; -- 1000

-- Транзакция B (параллельно)
BEGIN;
UPDATE accounts SET balance = 500 WHERE user_id = 1;
COMMIT;

-- Транзакция A (продолжение)
SELECT balance FROM accounts WHERE user_id = 1; -- 1000 (видит старый снимок)
COMMIT;
```

В PostgreSQL этот уровень также защищает от phantom read (в отличие от стандарта SQL).

Если две транзакции пытаются изменить одну и ту же строку, вторая получит ошибку сериализации:

```
ERROR: could not serialize access due to concurrent update
```

### Serializable (Сериализуемый)

Самый строгий уровень изоляции. Гарантирует, что результат параллельного выполнения транзакций эквивалентен какому-либо последовательному выполнению тех же транзакций.

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
-- Операции
COMMIT;
```

PostgreSQL использует механизм SSI (Serializable Snapshot Isolation) для обнаружения конфликтов. При обнаружении аномалии транзакция откатывается с ошибкой.

Используйте, когда абсолютная корректность важнее производительности (финансовые операции, бронирование).

## Аномалии параллельного доступа

### Dirty Read (Грязное чтение)

Транзакция читает данные, которые были изменены другой транзакцией, но ещё не зафиксированы. Если та транзакция откатится, прочитанные данные окажутся некорректными.

В PostgreSQL грязное чтение невозможно на любом уровне изоляции.

### Non-Repeatable Read (Неповторяемое чтение)

Транзакция читает одну и ту же строку дважды и получает разные значения, потому что другая транзакция изменила и зафиксировала эту строку между двумя чтениями.

```
Транзакция A: SELECT balance FROM accounts WHERE id = 1;  --> 1000
Транзакция B: UPDATE accounts SET balance = 500 WHERE id = 1; COMMIT;
Транзакция A: SELECT balance FROM accounts WHERE id = 1;  --> 500 (другое значение!)
```

Защита: уровень Repeatable Read и выше.

### Phantom Read (Фантомное чтение)

Транзакция выполняет один и тот же запрос дважды и получает разный набор строк, потому что другая транзакция добавила или удалила строки, удовлетворяющие условию запроса.

```
Транзакция A: SELECT COUNT(*) FROM orders WHERE status = 'new';  --> 5
Транзакция B: INSERT INTO orders (status) VALUES ('new'); COMMIT;
Транзакция A: SELECT COUNT(*) FROM orders WHERE status = 'new';  --> 6 (появился фантом!)
```

Защита: уровень Repeatable Read и выше (в PostgreSQL).

### Serialization Anomaly (Аномалия сериализации)

Результат параллельного выполнения транзакций не соответствует ни одному возможному последовательному порядку их выполнения.

```
Транзакция A: читает сумму всех балансов = 1000, записывает в отчёт
Транзакция B: добавляет 500 к одному счёту, читает сумму = 1500
```

Ни один последовательный порядок (A->B или B->A) не даёт такой результат.

Защита: только уровень Serializable.

### Таблица аномалий по уровням изоляции

```
Уровень              | Dirty Read | Non-Repeatable Read | Phantom Read | Serialization Anomaly
---------------------|------------|---------------------|--------------|----------------------
Read Uncommitted*    | Нет        | Да                  | Да           | Да
Read Committed       | Нет        | Да                  | Да           | Да
Repeatable Read      | Нет        | Нет                 | Нет**        | Да
Serializable         | Нет        | Нет                 | Нет          | Нет
```

\* В PostgreSQL работает как Read Committed.
\** В PostgreSQL Repeatable Read защищает от фантомов (строже, чем требует стандарт SQL).

## Блокировки

Блокировка -- это метод ограничения доступа к данным для обеспечения корректной обработки транзакций.

Серверы баз данных используют блокировки, чтобы управлять одновременным доступом к данным: пока одна транзакция работает с данными, другие транзакции не могут их изменять.

Когда данные в базе блокируются, другие пользователи, которые хотят изменить или прочитать эти же данные, должны подождать, пока блокировка не будет снята.

### PostgreSQL и MVCC

PostgreSQL использует многоверсионное управление конкурентностью (MVCC -- Multi-Version Concurrency Control). MVCC позволяет нескольким транзакциям работать с данными одновременно, создавая для каждой транзакции свою версию данных.

Благодаря MVCC:
- Чтение никогда не блокирует запись
- Запись никогда не блокирует чтение
- Блокировки возникают только при конкурентной записи одних и тех же строк

---

## Гранулярность блокировок

Сервер может применять блокировку на разных уровнях детализации.

### Блокировка таблиц

Не позволяет нескольким пользователям одновременно изменять данные в одной таблице. Самый грубый уровень -- блокирует больше, чем нужно, но требует минимальных накладных расходов.

### Блокировка страниц

Не позволяет нескольким пользователям изменять данные в одной и той же странице (сегмент памяти, обычно 8 Кбайт в PostgreSQL) таблицы одновременно.

### Блокировка строк

Не позволяет нескольким пользователям одновременно изменять одну и ту же строку в таблице. Самый тонкий уровень -- PostgreSQL использует его по умолчанию.

Компромисс:
- Блокировка таблицы: минимум накладных расходов, максимум ожидания
- Блокировка строк: максимум накладных расходов, минимум ожидания

---

## Типы блокировок

### Блокировки таблиц (Table-Level Locks)

PostgreSQL поддерживает несколько режимов блокировки таблиц с разной степенью ограничения:

`ACCESS SHARE` -- самая слабая блокировка. Устанавливается оператором `SELECT`. Конфликтует только с `ACCESS EXCLUSIVE`.

```sql
SELECT * FROM Users; -- ACCESS SHARE
```

`ROW SHARE` -- устанавливается командой `SELECT ... FOR UPDATE/FOR SHARE`.

```sql
SELECT * FROM Users WHERE id = 1 FOR UPDATE; -- ROW SHARE
```

`ROW EXCLUSIVE` -- устанавливается командами `INSERT`, `UPDATE`, `DELETE`.

```sql
UPDATE Users SET name = 'Test' WHERE id = 1; -- ROW EXCLUSIVE
```

`SHARE` -- устанавливается командой `CREATE INDEX` (без CONCURRENTLY). Блокирует изменения в таблице, но разрешает чтение.

`SHARE ROW EXCLUSIVE` -- устанавливается при создании триггеров и некоторых ALTER TABLE.

`EXCLUSIVE` -- блокирует чтение и запись (кроме ACCESS SHARE).

`ACCESS EXCLUSIVE` -- самая сильная блокировка. Устанавливается командами `DROP TABLE`, `ALTER TABLE`, `VACUUM FULL`, `LOCK TABLE`. Блокирует любой доступ.

### Блокировки строк (Row-Level Locks)

`FOR UPDATE` -- полная блокировка строки. Другие транзакции не могут изменять, удалять или блокировать эту строку.

```sql
BEGIN;
SELECT * FROM accounts WHERE user_id = 1 FOR UPDATE;
-- Строка заблокирована до COMMIT/ROLLBACK
UPDATE accounts SET balance = balance - 100 WHERE user_id = 1;
COMMIT;
```

`FOR NO KEY UPDATE` -- блокировка строки без блокировки ссылающихся ключей. Слабее, чем FOR UPDATE.

`FOR SHARE` -- разделяемая блокировка. Запрещает изменение и удаление строки, но позволяет другим транзакциям также установить FOR SHARE.

```sql
SELECT * FROM accounts WHERE user_id = 1 FOR SHARE;
-- Другие могут читать и ставить FOR SHARE, но не могут UPDATE/DELETE
```

`FOR KEY SHARE` -- самая слабая строковая блокировка. Запрещает только удаление строки и изменение ключевых столбцов.

### Совместимость блокировок

Общий принцип:
- Shared (разделяемые) блокировки совместимы друг с другом (несколько транзакций могут читать одновременно)
- Exclusive (эксклюзивные) блокировки несовместимы ни с какими другими (только одна транзакция может писать)

## Deadlock (Взаимная блокировка)

Deadlock -- это ситуация, когда две или более транзакции блокируют ресурсы друг друга и ни одна из них не может продолжить выполнение.

### Пример

```
Транзакция A: UPDATE accounts SET balance = 100 WHERE id = 1;  -- блокирует строку 1
Транзакция B: UPDATE accounts SET balance = 200 WHERE id = 2;  -- блокирует строку 2
Транзакция A: UPDATE accounts SET balance = 300 WHERE id = 2;  -- ждёт строку 2 (блокирована B)
Транзакция B: UPDATE accounts SET balance = 400 WHERE id = 1;  -- ждёт строку 1 (блокирована A)
-- Deadlock! Обе ждут друг друга
```

### Обнаружение

PostgreSQL автоматически обнаруживает deadlock (проверка выполняется периодически, по умолчанию раз в секунду -- параметр `deadlock_timeout`). При обнаружении одна из транзакций принудительно откатывается:

```
ERROR: deadlock detected
DETAIL: Process 1234 waits for ShareLock on transaction 5678; blocked by process 9012.
```

### Как избежать deadlock

Единый порядок блокировки: все транзакции должны блокировать ресурсы в одном и том же порядке.

```sql
-- Всегда блокируйте сначала меньший ID
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = LEAST(1, 2);
UPDATE accounts SET balance = balance + 100 WHERE id = GREATEST(1, 2);
COMMIT;
```

Короткие транзакции: чем быстрее транзакция завершается, тем меньше шанс deadlock.

Избегайте блокировки в цикле: не держите блокировку при выполнении внешних вызовов или длительных вычислений.

Используйте `NOWAIT` или `SKIP LOCKED`:

```sql
-- Не ждать, а сразу получить ошибку
SELECT * FROM orders WHERE id = 1 FOR UPDATE NOWAIT;

-- Пропустить заблокированные строки
SELECT * FROM orders WHERE status = 'new' FOR UPDATE SKIP LOCKED LIMIT 1;
```

`SKIP LOCKED` особенно полезен для реализации очередей задач.

## Рекомендации

Транзакции:
- Делайте транзакции как можно короче
- Не выполняйте внешние вызовы (HTTP-запросы, отправка email) внутри транзакции
- Всегда обрабатывайте ошибки -- не оставляйте транзакции открытыми
- Используйте SAVEPOINT для сложных транзакций с частичным откатом

Уровни изоляции:
- Используйте Read Committed (по умолчанию) для большинства задач
- Repeatable Read -- для отчётов, где важна согласованность данных
- Serializable -- для критически важных финансовых операций
- Будьте готовы к повторным попыткам при ошибках сериализации

Блокировки:
- Используйте `SELECT ... FOR UPDATE` при чтении данных, которые будете изменять
- Применяйте `FOR UPDATE SKIP LOCKED` для очередей задач
- Мониторьте блокировки через `pg_stat_activity` и `pg_locks`

```sql
-- Просмотр текущих блокировок
SELECT pid, locktype, relation::regclass, mode, granted
FROM pg_locks
WHERE NOT granted;

-- Просмотр ожидающих запросов
SELECT pid, query, wait_event_type, wait_event, state
FROM pg_stat_activity
WHERE wait_event IS NOT NULL;
```
