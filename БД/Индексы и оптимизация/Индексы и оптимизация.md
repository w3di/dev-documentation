## Индексы и оптимизация

Когда вы добавляете в таблицу новую строку, СУБД размещает эти данные не оптимально. Она просто помещает данные в следующее доступное место в файле.

Это приводит к тому, что для выполнения запроса серверу базы данных приходится проверять каждую строку таблицы, чтобы найти соответствия. Это подходит для маленьких таблиц, но становится чрезмерно времязатратным по мере роста объёма данных.

---

## Что такое индексы

Индексы функционируют как предметные указатели в книге, позволяя быстро находить информацию без прочтения всего текста.

Они представляют собой специальные таблицы, строки которых расположены в строго определённом порядке. Но вместо того, чтобы содержать все данные о некоторой записи, индекс содержит только столбец (или столбцы), используемый для поиска строк в таблице данных, вместе с информацией, описывающей, где физически расположена эта строка.

Роль индексов состоит в том, чтобы облегчить поиск подмножества строк и столбцов таблицы без необходимости сканировать каждую строку в таблице.

## Создание и удаление индексов

### Создание индекса

Для ускорения запросов, которые работают со значением столбца `email` в таблице `Users`, можно добавить индекс:

```sql
CREATE INDEX idx_email
    ON Users (email);
```

Эта инструкция создаёт индекс c именем `idx_email` для столбца `Users.email`.

При наличии индекса оптимизатор запросов может выбрать использование индекса, если сочтёт это полезным. Если в таблице имеется более одного индекса, оптимизатор должен решить, применение какого именно индекса наиболее выгодно для конкретной инструкции SQL.

### Просмотр существующих индексов

Для просмотра всех индексов для конкретной таблицы в PostgreSQL:

```sql
SELECT indexname, indexdef
FROM pg_indexes
WHERE tablename = 'users';
```

Результат:

```
indexname     indexdef
users_pkey    CREATE UNIQUE INDEX users_pkey ON public.users USING btree (id)
idx_email     CREATE INDEX idx_email ON public.users USING btree (email)
```

PostgreSQL автоматически создаёт индекс для столбца первичного ключа. Это особый тип индекса, используемый с ограничением первичного ключа, которое гарантирует, что каждое значение уникально и не может быть `NULL`.

### Удаление индекса

Если индекс больше не нужен, его можно удалить:

```sql
DROP INDEX idx_email;
```

Безопасное удаление (без ошибки, если индекс не существует):

```sql
DROP INDEX IF EXISTS idx_email;
```

Удаление без блокировки таблицы (для продакшен-окружений):

```sql
DROP INDEX CONCURRENTLY idx_email;
```

## Типы индексов в PostgreSQL

### B-tree (по умолчанию)

Тип индекса, используемый по умолчанию. Подходит для большинства случаев.

Поддерживаемые операции: `<`, `<=`, `=`, `>=`, `>`, `BETWEEN`, `IN`, `IS NULL`, `IS NOT NULL`.

```sql
CREATE INDEX idx_age ON Users (age);
-- Эквивалентно:
CREATE INDEX idx_age ON Users USING btree (age);
```

Когда использовать:
- Операции сравнения и сортировки
- Поиск по диапазону значений
- Сортировка (`ORDER BY`)

Данные хранятся в виде сбалансированного дерева. Поиск по B-tree имеет логарифмическую сложность O(log n).

### Hash

Индекс на основе хеш-таблицы. Поддерживает только операцию `=`.

```sql
CREATE INDEX idx_email_hash ON Users USING hash (email);
```

Когда использовать:
- Только для операций точного равенства (`=`)
- Не подходит для диапазонов и сортировки

Преимущества перед B-tree для равенства: компактнее и быстрее при проверке точного совпадения.

### GIN (Generalized Inverted Index)

Обобщённый инвертированный индекс. Предназначен для составных значений, где каждый элемент индексируется отдельно.

```sql
-- Для массивов
CREATE INDEX idx_tags ON Articles USING gin (tags);

-- Для JSONB
CREATE INDEX idx_data ON Events USING gin (metadata);

-- Для полнотекстового поиска
CREATE INDEX idx_search ON Articles USING gin (to_tsvector('russian', content));
```

Когда использовать:
- Массивы (`@>`, `&&`, `<@`)
- JSONB (`@>`, `?`, `?|`, `?&`)
- Полнотекстовый поиск (`@@`)

### GiST (Generalized Search Tree)

Обобщённое поисковое дерево. Поддерживает пользовательские типы данных и сложные запросы.

```sql
-- Для геометрических данных
CREATE INDEX idx_location ON Places USING gist (coordinates);

-- Для полнотекстового поиска
CREATE INDEX idx_search ON Articles USING gist (to_tsvector('russian', content));

-- Для диапазонов
CREATE INDEX idx_period ON Reservations USING gist (date_range);
```

Когда использовать:
- Геометрические данные и пространственные запросы (PostGIS)
- Полнотекстовый поиск (менее точный, но быстрее на вставку, чем GIN)
- Диапазонные типы (`tsrange`, `int4range`)
- Операции "ближайший сосед" (`<->`)

### BRIN (Block Range Index)

Компактный индекс, хранящий сводную информацию о диапазонах значений для блоков страниц.

```sql
CREATE INDEX idx_created ON Logs USING brin (created_at);
```

Когда использовать:
- Очень большие таблицы (сотни миллионов строк)
- Данные с естественной корреляцией (например, временные метки, автоинкрементные ID)
- Когда данные физически упорядочены по индексируемому столбцу

Преимущества:
- Занимает значительно меньше места, чем B-tree (в сотни раз)
- Быстрое создание
- Минимальное влияние на вставку

Недостатки:
- Менее точный, чем B-tree -- может давать ложные срабатывания
- Эффективен только при физической корреляции данных

### SP-GiST (Space-Partitioned Generalized Search Tree)

Индекс с пространственным разбиением. Использует несбалансированные структуры данных: деревья квадрантов, k-d деревья, префиксные деревья.

```sql
-- Для IP-адресов
CREATE INDEX idx_ip ON AccessLogs USING spgist (ip_address inet_ops);

-- Для текстового поиска по префиксу
CREATE INDEX idx_phone ON Users USING spgist (phone text_ops);

-- Для геометрических точек
CREATE INDEX idx_point ON Locations USING spgist (point);
```

Когда использовать:
- Данные с неравномерным распределением
- IP-адреса и подсети
- Телефонные номера (поиск по префиксу)
- Геометрические данные, когда важен поиск по квадрантам

Отличие от GiST: SP-GiST эффективнее для данных, которые можно разбить на непересекающиеся области. GiST лучше для пересекающихся структур.

## Уникальные индексы

При проектировании баз данных важно определить, для каких столбцов допускаются повторения значений, а для каких -- нет.

Уникальный индекс выполняет две функции:
- Обеспечивает все преимущества стандартного индекса
- Предотвращает дублирование значений в индексируемом столбце

Создание уникального индекса:

```sql
CREATE UNIQUE INDEX idx_email
    ON Users (email);
```

При попытке добавить дублирующееся значение вы получите ошибку:

```
ERROR: duplicate key value violates unique constraint "idx_email"
DETAIL: Key (email)=(duplicate@gmail.com) already exists.
```

Важно: Создание уникальных индексов для столбцов первичного ключа излишне, так как СУБД автоматически обеспечивает уникальность значений первичного ключа.

---

## Многостолбцовые индексы

Существует возможность создавать индексы, включающие несколько столбцов:

```sql
CREATE INDEX idx_full_name
    ON Student (last_name, first_name);
```

Такой индекс полезен для запросов, где необходимы:
- И имя, и фамилия
- Только фамилия (первый столбец в индексе)

Однако для запросов, задающих только имя, он не принесёт пользы.

Это аналогично поиску номера телефона по телефонному справочнику: если известны и имя, и фамилия, поиск упрощается благодаря упорядоченности справочника по фамилии, а затем по имени. Если же известно только имя, придётся перебирать все записи.

При создании индексов с несколькими столбцами важно продумать порядок столбцов в индексе для максимальной эффективности:
- Первым ставьте столбец с большей селективностью (больше уникальных значений)
- Столбец, который чаще используется в WHERE, ставьте первым

## Частичные индексы (Partial Indexes)

Частичный индекс покрывает только подмножество строк таблицы, определённое условием `WHERE`. Это экономит дисковое пространство и ускоряет вставку, так как индексируются не все строки.

```sql
CREATE INDEX idx_active_users ON Users (email) WHERE is_active = true;
```

Такой индекс будет использоваться только для запросов с соответствующим условием:

```sql
-- Индекс используется
SELECT * FROM Users WHERE email = 'user@example.com' AND is_active = true;

-- Индекс НЕ используется
SELECT * FROM Users WHERE email = 'user@example.com' AND is_active = false;
```

Типичные сценарии применения:

```sql
-- Индекс только для необработанных заказов
CREATE INDEX idx_pending_orders ON Orders (created_at)
    WHERE status = 'pending';

-- Индекс только для ненулевых значений
CREATE INDEX idx_discount ON Products (discount)
    WHERE discount IS NOT NULL;

-- Индекс для "мягко удалённых" записей
CREATE INDEX idx_not_deleted ON Users (email)
    WHERE deleted_at IS NULL;
```

Преимущества:
- Меньше размер индекса на диске
- Быстрее операции вставки и обновления
- Точнее соответствует паттернам запросов

---

## Функциональные индексы (Expression Indexes)

Функциональные индексы создаются на основе результата выражения или функции, а не на значении столбца напрямую. Это позволяет ускорить запросы, использующие вычисляемые значения.

```sql
-- Индекс для регистронезависимого поиска по email
CREATE INDEX idx_lower_email ON Users (LOWER(email));
```

Теперь запрос с `LOWER()` будет использовать индекс:

```sql
-- Индекс используется
SELECT * FROM Users WHERE LOWER(email) = 'user@example.com';

-- Индекс НЕ используется (нет LOWER)
SELECT * FROM Users WHERE email = 'user@example.com';
```

Другие примеры:

```sql
-- Индекс по году из даты
CREATE INDEX idx_order_year ON Orders (EXTRACT(YEAR FROM order_date));

-- Использование
SELECT * FROM Orders WHERE EXTRACT(YEAR FROM order_date) = 2025;
```

```sql
-- Индекс по вычисляемому полю из JSONB
CREATE INDEX idx_json_name ON Users ((metadata->>'name'));

-- Использование
SELECT * FROM Users WHERE metadata->>'name' = 'John';
```

Важно: выражение в запросе WHERE должно точно совпадать с выражением, использованным при создании индекса.

## Покрывающие индексы (Covering / INCLUDE)

Покрывающий индекс включает дополнительные столбцы, которые не участвуют в поиске, но нужны в результате запроса. Это позволяет выполнить запрос целиком из индекса, не обращаясь к таблице (Index Only Scan).

```sql
CREATE INDEX idx_email_include ON Users (email) INCLUDE (name, created_at);
```

Теперь запрос, запрашивающий только `email`, `name` и `created_at`, может быть выполнен без обращения к таблице:

```sql
-- Index Only Scan (все данные есть в индексе)
SELECT name, created_at FROM Users WHERE email = 'user@example.com';
```

Отличие от многостолбцового индекса:

```sql
-- Многостолбцовый: все столбцы участвуют в дереве поиска
CREATE INDEX idx_multi ON Users (email, name, created_at);

-- Покрывающий: только email в дереве, остальные хранятся "рядом"
CREATE INDEX idx_cover ON Users (email) INCLUDE (name, created_at);
```

Преимущества покрывающего индекса:
- Столбцы из INCLUDE не увеличивают глубину дерева
- Меньше размер индекса по сравнению с многостолбцовым
- Позволяет избежать чтения таблицы (heap)

Ограничения:
- Столбцы из INCLUDE нельзя использовать для поиска или сортировки
- Доступно с PostgreSQL 11+

## EXPLAIN и EXPLAIN ANALYZE

Для определения, какой метод выберет оптимизатор запросов, используется команда `EXPLAIN`:

```sql
EXPLAIN
  SELECT id, first_name, last_name
  FROM Student
  WHERE first_name LIKE 'A%'
  AND last_name LIKE 'L%';
```

Результат:

```
QUERY PLAN
Index Scan using idx_full_name on student (cost=0.42..8.44 rows=1 width=68)
Index Cond: ((last_name >= 'L'::text) AND (last_name < 'M'::text))
Filter: ((first_name ~~ 'A%'::text) AND (last_name ~~ 'L%'::text))
```

Для получения реальной статистики выполнения (запрос действительно выполняется):

```sql
EXPLAIN ANALYZE
  SELECT id, first_name, last_name
  FROM Student
  WHERE first_name LIKE 'A%'
  AND last_name LIKE 'L%';
```

Результат:

```
QUERY PLAN
Index Scan using idx_full_name on student (cost=0.42..8.44 rows=1 width=68) (actual time=0.025..0.027 rows=1 loops=1)
Index Cond: ((last_name >= 'L'::text) AND (last_name < 'M'::text))
Filter: ((first_name ~~ 'A%'::text) AND (last_name ~~ 'L%'::text))
Planning Time: 0.156 ms
Execution Time: 0.048 ms
```

Дополнительные полезные варианты:

```sql
-- Подробный вывод с буферами и форматированием
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
  SELECT * FROM Users WHERE email = 'user@example.com';

-- JSON-формат (удобен для программного анализа)
EXPLAIN (ANALYZE, FORMAT JSON)
  SELECT * FROM Users WHERE email = 'user@example.com';
```

Важно: `EXPLAIN ANALYZE` реально выполняет запрос. Для запросов `UPDATE`, `DELETE`, `INSERT` оборачивайте в транзакцию с откатом:

```sql
BEGIN;
EXPLAIN ANALYZE UPDATE Users SET name = 'Test' WHERE id = 1;
ROLLBACK;
```

## Типы сканирования

Анализируя результаты `EXPLAIN`, можно увидеть, какой метод доступа выбрал оптимизатор.

### Seq Scan (Sequential Scan)

Последовательное сканирование -- полный перебор всех строк таблицы.

```
Seq Scan on users (cost=0.00..35.50 rows=1000 width=72)
```

Когда используется:
- Таблица маленькая
- Запрос возвращает значительную долю строк (> 5-10%)
- Нет подходящего индекса

### Index Scan

Поиск по индексу с последующим чтением строк из таблицы (heap).

```
Index Scan using idx_email on users (cost=0.28..8.29 rows=1 width=72)
  Index Cond: (email = 'user@example.com'::text)
```

Как работает:
1. Находит нужные записи в индексе
2. По указателю обращается к таблице за полными данными строки

### Index Only Scan

Все необходимые данные извлекаются из индекса, обращение к таблице не требуется.

```
Index Only Scan using idx_cover on users (cost=0.28..4.29 rows=1 width=36)
  Index Cond: (email = 'user@example.com'::text)
```

Условия:
- Все запрашиваемые столбцы входят в индекс (или в INCLUDE)
- Visibility Map должна быть актуальной (после VACUUM)

Это самый быстрый тип сканирования по индексу.

### Bitmap Scan

Двухэтапный метод: сначала строится битовая карта подходящих строк, затем таблица читается блоками.

```
Bitmap Heap Scan on users (cost=4.20..15.30 rows=50 width=72)
  Recheck Cond: (age > 25)
  -> Bitmap Index Scan on idx_age (cost=0.00..4.19 rows=50 width=0)
        Index Cond: (age > 25)
```

Когда используется:
- Запрос возвращает умеренное количество строк (слишком много для Index Scan, слишком мало для Seq Scan)
- Комбинация нескольких индексов (BitmapAnd, BitmapOr)

Преимущество: читает страницы таблицы последовательно, а не в случайном порядке.

## Оптимизация запросов

### Чтение плана выполнения

Каждый узел плана выполнения содержит следующие параметры:

```
Index Scan using idx_email on users (cost=0.28..8.29 rows=1 width=72) (actual time=0.015..0.017 rows=1 loops=1)
```

Оценочные (до выполнения):
- `cost=0.28..8.29` -- стоимость запуска и общая стоимость (в условных единицах). Первое число -- стоимость получения первой строки, второе -- всех строк
- `rows=1` -- предполагаемое количество строк
- `width=72` -- средний размер строки в байтах

Фактические (после ANALYZE):
- `actual time=0.015..0.017` -- время в миллисекундах (первая строка..все строки)
- `rows=1` -- реальное количество строк
- `loops=1` -- сколько раз выполнялся этот узел

Если оценочные `rows` сильно расходятся с фактическими -- это сигнал о неактуальной статистике.

### Селективность и статистика (pg_stats)

PostgreSQL использует статистику о распределении данных для построения оптимального плана. Статистика собирается командой `ANALYZE`:

```sql
-- Обновить статистику по таблице
ANALYZE Users;

-- Обновить по конкретному столбцу
ANALYZE Users (email);
```

Просмотр статистики:

```sql
SELECT
    attname AS column,
    n_distinct,
    most_common_vals,
    most_common_freqs,
    correlation
FROM pg_stats
WHERE tablename = 'users' AND attname = 'status';
```

Ключевые поля:
- `n_distinct` -- число уникальных значений (отрицательное значение = доля от общего числа строк)
- `most_common_vals` -- самые частые значения
- `most_common_freqs` -- частоты самых частых значений
- `correlation` -- корреляция физического и логического порядка (важно для BRIN)

Увеличение точности статистики для конкретного столбца:

```sql
ALTER TABLE Users ALTER COLUMN email SET STATISTICS 1000;
ANALYZE Users;
```

Значение по умолчанию -- 100. Для столбцов с неравномерным распределением можно увеличить до 1000-10000.

### Рекомендации по оптимизации

Используйте EXPLAIN ANALYZE для диагностики:
- Сравнивайте оценочные и фактические строки
- Обращайте внимание на Seq Scan на больших таблицах
- Ищите узлы с высоким `actual time`

Обновляйте статистику:
- `ANALYZE` после массовой загрузки данных
- Автовакуум обычно справляется, но для критичных таблиц обновляйте вручную

Избегайте функций на индексированных столбцах:

```sql
-- Плохо: индекс по email НЕ используется
SELECT * FROM Users WHERE LOWER(email) = 'user@example.com';

-- Хорошо: создайте функциональный индекс
CREATE INDEX idx_lower_email ON Users (LOWER(email));
SELECT * FROM Users WHERE LOWER(email) = 'user@example.com';
```

Избегайте неявного приведения типов:

```sql
-- Плохо: id -- integer, но передаётся строка
SELECT * FROM Users WHERE id = '42';

-- Хорошо
SELECT * FROM Users WHERE id = 42;
```

Используйте LIMIT для больших выборок:

```sql
SELECT * FROM Logs ORDER BY created_at DESC LIMIT 100;
```

Денормализация для тяжёлых JOIN:
- Если JOIN выполняется часто и на больших таблицах, рассмотрите материализованные представления

## Когда индексы НЕ помогают

Почему бы просто не индексировать всё подряд?

### Замедление операций записи

Каждый раз, когда строка добавляется или удаляется, все индексы должны быть изменены. При обновлении строки любые индексы для затронутых столбцов также должны быть изменены. Чем больше индексов, тем больше работы для СУБД.

### Дополнительное место на диске

Каждый индекс представляет собой отдельную структуру данных. Индексы занимают дополнительное место на диске, которое может быть сопоставимо с размером самой таблицы.

### Индексы игнорируются оптимизатором, когда:

- Таблица слишком маленькая -- Seq Scan быстрее, чем обращение к индексу
- Запрос возвращает большую долю строк (> 5-10% таблицы) -- последовательное чтение эффективнее
- Используется функция над столбцом без функционального индекса:
  ```sql
  -- Индекс по email НЕ используется
  WHERE UPPER(email) = 'TEST@MAIL.COM'
  ```
- Используется `LIKE` с подстановкой в начале:
  ```sql
  -- Индекс НЕ используется
  WHERE name LIKE '%john%'
  ```
- Столбец имеет низкую селективность (мало уникальных значений, например, `gender` с 2 вариантами)
- Статистика устарела -- оптимизатор принимает неверные решения

### Требуют управления

Индексы необходимо периодически обслуживать:
- `REINDEX` для перестроения раздутых индексов
- Удаление неиспользуемых индексов (проверка через `pg_stat_user_indexes`)

```sql
-- Поиск неиспользуемых индексов
SELECT indexrelname, idx_scan, idx_tup_read
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;
```

## Рекомендации по использованию индексов

Создавайте индексы только тогда, когда это действительно необходимо:
- Для столбцов, часто используемых в условиях `WHERE`
- Для столбцов, используемых в `JOIN`
- Для столбцов, используемых в `ORDER BY`

Временные индексы:
- Можно создать индекс перед выполнением процедуры (например, месячного отчёта)
- Удалить после её завершения

Найдите баланс:
- Иметь достаточно индексов для эффективной работы
- Но не столько, чтобы это сказывалось на производительности

Если не уверены:
- Начните с минимального числа индексов
- Добавляйте по мере необходимости
- Используйте `EXPLAIN ANALYZE` для проверки

Создание индексов без блокировки:

```sql
-- Не блокирует таблицу во время создания (важно для продакшена)
CREATE INDEX CONCURRENTLY idx_email ON Users (email);
```

## Примеры использования

### Индекс для поиска по email

```sql
CREATE INDEX idx_email ON Users (email);

SELECT * FROM Users WHERE email = 'user@example.com';
```

### Уникальный индекс для предотвращения дублей

```sql
CREATE UNIQUE INDEX idx_username ON Users (username);

INSERT INTO Users (username, email) VALUES ('john_doe', 'john@example.com');
```

### Составной индекс для сложных запросов

```sql
CREATE INDEX idx_status_date ON Orders (status, order_date);

SELECT * FROM Orders
WHERE status = 'pending'
ORDER BY order_date DESC;
```

### Частичный индекс (только для определённых строк)

```sql
CREATE INDEX idx_active_users ON Users (email) WHERE is_active = true;

SELECT * FROM Users WHERE email LIKE '%@gmail.com' AND is_active = true;
```

### Функциональный индекс

```sql
CREATE INDEX idx_lower_email ON Users (LOWER(email));

SELECT * FROM Users WHERE LOWER(email) = 'user@example.com';
```

### Покрывающий индекс

```sql
CREATE INDEX idx_order_cover ON Orders (user_id) INCLUDE (status, total_amount);

SELECT status, total_amount FROM Orders WHERE user_id = 42;
```
